| 표시 | 공부할 깊이 |
| --- | --- |

| 선택 심화 | 목적과 연결 관계를 먼저 이해합니다. 내부 구현과 세부 규격 암기는 미룹니다. |

**실행용 자바 코드는 자바 21 정식 기능을 기준으로 합니다.** 각 `java` 블록은 독립적인 `Main.java` 전체 코드입니다. 서로 다른 블록의 `Main` 클래스를 한 파일에 합치지 않습니다.

예제의 `main`에 있는 `throws Exception`이나 `throws Throwable`은 관찰하려는 동작에 집중하기 위한 학습용 선언입니다. 실제 프로그램에서는 실패·취소·복구 정책에 맞게 예외를 처리합니다.

자바 21 이후 기능은 버전을 표시한 **보충 설명 또는 `text` 흐름도**로 분리합니다. 자바 25의 범위 지정 값, 자바 25 문서에서 미리보기인 구조적 동시성, 자바 22의 외부 함수·메모리 기능을 자바 21의 정식 문법처럼 섞지 않습니다.[^scoped][^structured][^foreign]

</blockquote>

## 13부. 스레드·동시성·자바 메모리 모델

### 101. 스레드의 생성과 생명주기

**스레드는 프로그램 안에서 코드를 실행하는 흐름입니다.** 같은 프로세스의 스레드는 객체를 공유할 수 있지만, 각자의 호출 흐름은 구분됩니다.[^thread][^vm-structure]

| 구분 | 의미 | 직관 |
| --- | --- | --- |
| 프로세스 | 실행 중인 프로그램의 운영체제상 단위 | 작업장 |
| 스레드 | 프로세스 안의 실행 흐름 | 작업자 |
| 동시성 | 여러 작업이 겹치는 기간 동안 진행되는 성질 | 번갈아 진행할 수도 있습니다. |
| 병렬성 | 여러 작업이 실제로 같은 시점에 실행되는 성질 | 여러 실행 자원을 함께 사용합니다. |

**작업을 정의하는 것과 새 스레드를 시작하는 것은 다릅니다.** `Runnable`은 반환값 없는 작업을 표현합니다. `Thread.start()`는 새 실행 흐름을 시작하고, `run()` 직접 호출은 일반 메서드 호출입니다.

```java
public class Main {
    public static void main(String[] 인수) throws InterruptedException {
        Thread 호출자 = Thread.currentThread();
        Thread 작업 = new Thread(() ->
            System.out.println(Thread.currentThread() == 호출자));

        System.out.println(작업.getState());
        작업.run();
        System.out.println(작업.getState());
        작업.start();
        작업.join();
        System.out.println(작업.getState());
    }
}
```

출력:

```text
NEW
true
NEW
false
TERMINATED
```

첫 번째 `run()`은 호출자 스레드에서 실행됩니다. 이후 `start()`로 실행한 작업은 별도 스레드이므로 참조 비교가 `false`입니다. 마지막 상태는 `join()`으로 종료를 확인한 뒤 읽습니다.

**자바의 스레드 상태는 여섯 가지입니다.** 운영체제의 상태 이름과 일대일로 대응한다고 가정하지 않습니다.[^thread-state]

| 상태 | 의미 | 대표 상황 |
| --- | --- | --- |
| `NEW` | 시작 전 | 생성 후 `start()` 전 |
| `RUNNABLE` | 가상 머신 관점의 실행 가능 상태 | 실제 실행 중이거나 실행 자원을 기다림 |
| `BLOCKED` | 모니터 잠금 획득 대기 | 다른 스레드가 가진 `synchronized` 잠금 기다림 |
| `WAITING` | 시간 제한 없는 대기 | `wait()`, 시간 없는 `join()`, `park()` |
| `TIMED_WAITING` | 시간 제한 있는 대기 | `sleep()`, 시간 있는 `wait()`·`join()` |
| `TERMINATED` | 실행 종료 | `run()` 종료 또는 처리되지 않은 예외로 종료 |

`ReentrantLock` 획득을 기다리는 상태를 무조건 `BLOCKED`라고 단정하지 않습니다. 자바의 `BLOCKED`는 **모니터 잠금**과 관련된 상태입니다.

| 메서드·속성 | 정확한 의미 |
| --- | --- |
| `start()` | 같은 스레드 객체에서는 한 번만 시작할 수 있습니다. 종료 후 재시작도 불가능합니다. |
| `join()` | 호출한 스레드가 대상 스레드의 종료를 기다립니다. |
| 시간 있는 `join()` | 시간이 지났다고 대상 작업이 끝났다는 뜻은 아닙니다. |
| `sleep()` | 현재 실행 중인 스레드가 일정 시간 대기합니다. 보유한 모니터를 놓지 않습니다. |
| `yield()` | 실행 기회를 양보하겠다는 힌트입니다. 순서를 보장하지 않습니다. |
| 우선순위 | 플랫폼·스케줄러에 영향을 받습니다. 높은 값의 선실행을 보장하지 않습니다. |
| 데몬 | 데몬 스레드만 남으면 가상 머신의 정상 종료를 붙잡지 않습니다. |

플랫폼 스레드의 데몬 설정은 시작 전에 합니다. 가상 스레드는 데몬 스레드입니다. **중요 작업을 데몬으로 만들었다고 완료가 보장되지는 않습니다.**

### 102. 인터럽트와 협력적 취소

**인터럽트는 스레드에게 중단을 요청하는 신호입니다.** 모든 코드를 즉시 강제 종료하는 명령이 아닙니다.[^thread]

| 기능 | 대상 | 인터럽트 상태를 지우는가? |
| --- | --- | --- |
| `작업.interrupt()` | 지정한 작업 | 중단 요청을 보냅니다. 대기 방식에 따라 반응이 달라집니다. |
| `작업.isInterrupted()` | 지정한 작업 | 지우지 않고 조회합니다. |
| `Thread.interrupted()` | 현재 스레드 | 조회하면서 지웁니다. |

```java
public class Main {
    public static void main(String[] 인수) {
        Thread.currentThread().interrupt();
        System.out.println(Thread.currentThread().isInterrupted());
        System.out.println(Thread.interrupted());
        System.out.println(Thread.currentThread().isInterrupted());
    }
}
```

출력:

```text
true
true
false
```

`sleep`, `wait`, `join` 등은 인터럽트를 감지하면 `InterruptedException`을 던지면서 인터럽트 상태를 지웁니다. 예외를 상위로 전달할 수 없고 바깥 코드가 취소를 알아야 한다면 상태를 복구합니다.

```java
public class Main {
    public static void main(String[] 인수) {
        Thread.currentThread().interrupt();
        try {
            Thread.sleep(1);
        } catch (InterruptedException 예외) {
            System.out.println(Thread.currentThread().isInterrupted());
            Thread.currentThread().interrupt();
        }
        System.out.println(Thread.currentThread().isInterrupted());
        Thread.interrupted(); // 이 예제의 종료 전에 상태를 정리합니다.
    }
}
```

출력:

```text
false
true
```

**취소 처리는 “요청 → 감지 → 자원 정리 → 종료”입니다.** 계산 반복문은 인터럽트 상태를 확인하고 반환할 수 있습니다. 대기 메서드는 인터럽트 예외를 전달하거나 적절한 종료 처리로 연결합니다.

모니터 진입 대기는 `interrupt()`로 곧바로 중단되지 않습니다. 모든 입출력도 같은 취소 규칙을 갖지는 않습니다. 강제 종료 계열의 구형 `stop`·`suspend`·`resume`에 의존하지 않습니다.

**시험 포인트:** `interrupt()`를 호출했다는 사실과 실제로 작업이 종료됐다는 사실은 다릅니다. 빈 `catch`로 취소 신호를 삼키는 코드도 주의합니다.

### 103. 자바 메모리 모델

**자바 메모리 모델은 여러 스레드의 읽기·쓰기에 어떤 관찰 결과가 허용되는지 정하는 규칙입니다.** 힙·스택을 나누는 메모리 영역 그림과는 다른 개념입니다.[^memory-model]

| 개념 | 질문 | 대표 문제 |
| --- | --- | --- |
| 가시성 | 다른 스레드가 변경한 값을 볼 수 있는가? | 종료 요청을 계속 보지 못함 |
| 원자성 | 연산 도중에 다른 접근이 끼어들 수 없는가? | 증가 결과를 서로 덮어씀 |
| 순서성 | 어떤 작업이 다른 작업보다 먼저 일어난 것으로 보장되는가? | 준비 표시를 봤지만 데이터 관찰이 보장되지 않음 |

`개수++`는 개념적으로 **읽기 → 더하기 → 쓰기**입니다. 숫자 하나에 대한 코드 한 줄이라고 해서 전체가 원자적이지는 않습니다.

| 진행 | 첫 번째 스레드 | 두 번째 스레드 |
| --- | --- | --- |
| 1 | 0을 읽음 |  |
| 2 |  | 0을 읽음 |
| 3 | 1을 씀 |  |
| 4 |  | 1을 씀 |

두 번 증가시켰지만 1이 남을 수 있습니다. 이 표는 **가능한 실행 하나**이며, 항상 1이 나온다는 주장이 아닙니다.

**선행 발생 관계**는 단순한 시계상 선후가 아니라, 스레드 사이에서 순서와 가시성을 추론할 수 있게 하는 보장입니다.

| 연결 | 보장되는 방향 |
| --- | --- |
| 같은 스레드의 프로그램 순서 | 앞의 작업 → 뒤의 작업 |
| 동일한 모니터 | 잠금 해제 → 이후 그 모니터의 잠금 획득 |
| 동일한 `volatile` 필드 | 쓰기 → 이후 읽기 |
| 스레드 시작 | `start()` 전의 작업 → 시작된 스레드의 작업 |
| 스레드 종료 확인 | 종료한 스레드의 작업 → 종료를 확인한 `join()` 뒤의 작업 |
| 작업 제출·결과 획득 | 제출 전 작업 → 작업 실행 → `Future.get()` 뒤의 작업 |

마지막 행은 동시성 라이브러리의 메모리 일관성 계약입니다. 여러 관계는 이어서 추론할 수 있습니다.[^concurrent][^future]

```java
public class Main {
    private static int 결과;

    public static void main(String[] 인수) throws InterruptedException {
        Thread 작업 = new Thread(() -> 결과 = 42);
        작업.start();
        작업.join();
        System.out.println(결과);
    }
}
```

출력:

```text
42
```

이 예제의 마지막 읽기는 `join()`으로 종료를 확인한 뒤입니다. 따라서 `결과`가 `volatile`이 아니어도 42가 보장됩니다. 반대로 `sleep(1000)`만 넣으면 이 보장을 대체하지 못합니다.

**안전한 공개**는 객체가 적절히 초기화된 상태로 다른 스레드에 전달되도록 하는 것입니다. 클래스 초기화, 동일 잠금, `volatile` 참조, 적절한 동시성 자료구조 등의 계약을 활용합니다.

**보충:** 생성 중인 `this`를 외부에 노출하지 않고 올바르게 생성한 객체의 `final` 필드에는 초기화 안전성 보장이 있습니다. 다만 그 객체의 일반 가변 필드나 생성 후 변경까지 모두 보호되는 것은 아닙니다.

### 104. synchronized와 모니터

**`synchronized`는 같은 객체의 모니터를 이용해 임계 구역을 한 번에 한 스레드만 실행하도록 합니다.** 잠금 해제와 이후 획득은 가시성 보장도 제공합니다.[^memory-model][^classes]

| 형태 | 잠그는 대상 |
| --- | --- |
| 인스턴스 `synchronized` 메서드 | 그 메서드를 호출한 객체, 즉 `this` |
| 정적 `synchronized` 메서드 | 그 메서드를 정의한 클래스의 `Class` 객체 |
| `synchronized (잠금)` | 괄호 안 참조가 가리키는 객체 |

```java
public class Main {
    static class 계수기 {
        private int 값;
        synchronized void 증가() { 값++; }
        synchronized int 읽기() { return 값; }
    }

    public static void main(String[] 인수) throws InterruptedException {
        계수기 공유 = new 계수기();
        Runnable 작업 = () -> {
            for (int 순서 = 0; 순서 < 1000; 순서++) {
                공유.증가();
            }
        };
        Thread 첫째 = new Thread(작업);
        Thread 둘째 = new Thread(작업);
        첫째.start();
        둘째.start();
        첫째.join();
        둘째.join();
        System.out.println(공유.읽기());
    }
}
```

출력:

```text
2000
```

두 작업은 **같은 `공유` 객체**의 모니터를 사용합니다. 증가 중간에 다른 증가가 끼어들어 결과를 잃지 않습니다.

| 특성 | 의미 |
| --- | --- |
| 재진입 가능 | 잠금을 가진 스레드는 같은 잠금을 다시 획득할 수 있습니다. |
| 자동 해제 | 정상 반환이나 예외로 구역을 빠져나갈 때 해제됩니다. |
| 객체 기준 | 같은 클래스의 서로 다른 객체는 서로 다른 잠금을 가집니다. |
| 접근 규칙 필요 | 다른 코드가 잠금 없이 필드에 접근하면 자동으로 막아주지 않습니다. |

**시험 포인트:** 인스턴스 잠금과 클래스 잠금은 서로 다릅니다. “두 메서드에 모두 `synchronized`가 있다”가 아니라 **같은 잠금을 쓰는가**를 확인합니다.

잠금은 `private final Object`처럼 정체성이 바뀌지 않는 전용 객체로 관리할 수 있습니다. 외부 코드와 우연히 공유되는 문자열 리터럴이나 래퍼 캐시 객체는 잠금으로 사용하지 않는 편이 좋습니다.

### 105. 대기·통지·스레드 정지

**`wait()`는 조건이 충족되기를 기다리는 동안 해당 객체의 모니터를 놓습니다.** 반환하기 전에는 그 모니터를 다시 획득합니다.[^object]

| 기능 | 잠금 소유 필요 | 해당 모니터 해제 | 핵심 |
| --- | --- | --- | --- |
| `wait()` | 필요 | 해제 후 다시 획득 | 조건이 바뀌기를 기다림 |
| `notify()` | 필요 | 즉시 해제하지 않음 | 같은 객체에서 대기하는 한 스레드를 깨울 대상으로 선택 |
| `notifyAll()` | 필요 | 즉시 해제하지 않음 | 같은 객체에서 대기하는 모든 스레드에 알림 |
| `sleep()` | 불필요 | 해제하지 않음 | 현재 스레드를 시간 동안 대기시킴 |

`wait()`는 **호출한 객체의 잠금만** 놓습니다. 동시에 보유한 다른 객체의 잠금까지 전부 놓는 것은 아닙니다.

```java
public class Main {
    private static final Object 잠금 = new Object();
    private static boolean 준비;
    private static int 값;

    public static void main(String[] 인수) throws InterruptedException {
        Thread 생산 = new Thread(() -> {
            synchronized (잠금) {
                값 = 7;
                준비 = true;
                잠금.notifyAll();
            }
        });

        synchronized (잠금) {
            생산.start();
            while (!준비) {
                잠금.wait();
            }
            System.out.println(값);
        }
        생산.join();
    }
}
```

출력:

```text
7
```

**조건 검사에는 `if`가 아니라 `while`을 사용합니다.** 허위 깨움이 가능하고, 알림 뒤 잠금을 다시 획득하기 전에 다른 스레드가 조건을 바꿀 수도 있기 때문입니다.

`notifyAll()`은 대기 스레드 전부가 동시에 임계 구역에 들어간다는 뜻이 아닙니다. 깨어난 스레드들도 잠금을 차례로 획득해야 합니다.

**선택 심화 — `park()`와 `unpark()`**

`LockSupport`는 스레드별 허가를 이용한 낮은 수준의 대기 도구입니다. 허가는 최대 하나만 유지되며 `unpark()`를 여러 번 호출해도 무제한 누적되지 않습니다. 먼저 `unpark()`가 실행되고 나중에 `park()`가 실행되는 경우에도 허가를 사용할 수 있습니다.[^locksupport]

`park()`도 허위 반환이 가능하므로 조건을 다시 검사합니다. 인터럽트 시 `InterruptedException`을 던지는 `wait()`와 달리 반환할 수 있으며, 인터럽트 상태를 자동으로 지우지 않습니다.

### 106. volatile의 정확한 의미

**`volatile`은 해당 필드의 읽기·쓰기와 관련된 가시성·순서를 보장합니다.** 잠금을 걸어 복합 연산 전체를 묶는 기능은 아닙니다.[^memory-model]

| 사용 | 적합성 | 이유 |
| --- | --- | --- |
| 하나의 종료·준비 표시 | 적합할 수 있음 | 변경 관찰과 앞선 쓰기 전달에 사용 |
| 여러 스레드의 `개수++` | 이것만으로 부족 | 읽기·계산·쓰기의 결합은 원자적이지 않음 |
| 두 필드의 동시 변경 | 이것만으로 부족 | 둘 사이의 불변조건을 묶지 않음 |
| 참조 변수에 적용 | 참조 읽기·쓰기에 적용 | 참조 대상의 모든 내부 변경을 보호하지 않음 |

```java
public class Main {
    private static int 데이터;
    private static volatile boolean 준비;

    public static void main(String[] 인수) throws InterruptedException {
        Thread 작성 = new Thread(() -> {
            데이터 = 9;
            준비 = true;
        });
        작성.start();
        while (!준비) {
            Thread.onSpinWait();
        }
        System.out.println(데이터);
        작성.join();
    }
}
```

출력:

```text
9
```

`준비`가 `true`임을 관찰하면 그 쓰기보다 앞선 `데이터 = 9`도 연결해 추론할 수 있습니다. 단, 다른 스레드가 이후 `데이터`를 별도 규칙 없이 계속 바꾸는 사례까지 확장하지 않습니다.

이 코드는 짧은 학습용 회전 대기입니다. `onSpinWait()`는 성능 힌트이지 동기화 장치가 아닙니다. 일반적인 긴 대기에는 대기열·래치 등으로 불필요한 계산 자원 소비를 줄입니다.

**보충:** 이중 검사 잠금으로 지연 생성 객체를 공개할 때 공유 참조의 `volatile` 여부가 중요합니다. 기초 단계에서는 안전한 클래스 초기화나 적절한 잠금 방식부터 이해합니다.

**자바의 세밀한 규칙:** `volatile`이 아닌 `long`·`double`의 읽기·쓰기는 명세상 비원자적으로 구현될 수 있습니다. `volatile` 읽기·쓰기는 원자적입니다. 이것도 `증가++` 전체의 원자성 보장과는 별개입니다.

### 107. 명시적 잠금과 조건 변수

**`ReentrantLock`은 잠금 획득·해제를 메서드로 제어하는 도구입니다.** 대기 취소, 제한 시간, 여러 조건 대기열이 필요한 상황에 사용합니다.[^lock]

```java
import java.util.concurrent.locks.ReentrantLock;

public class Main {
    public static void main(String[] 인수) {
        ReentrantLock 잠금 = new ReentrantLock();
        잠금.lock();
        try {
            잠금.lock();
            try {
                System.out.println(잠금.getHoldCount());
            } finally {
                잠금.unlock();
            }
        } finally {
            잠금.unlock();
        }
        System.out.println(잠금.isLocked());
    }
}
```

출력:

```text
2
false
```

같은 스레드가 두 번 획득했으므로 두 번 해제합니다. **성공적으로 획득한 뒤에만 `finally`에서 해제**하도록 구조를 잡습니다.

| 기능 | 목적 |
| --- | --- |
| `lock()` | 잠금 획득까지 기다립니다. |
| `lockInterruptibly()` | 획득을 기다리다가 인터럽트로 중단할 수 있습니다. |
| `tryLock()` | 즉시 획득을 시도하고 성공 여부를 반환합니다. |
| 시간 있는 `tryLock()` | 정해진 시간까지 획득을 시도합니다. |
| `newCondition()` | 그 잠금과 연결된 조건 대기열을 만듭니다. |
| `await()` | 조건을 기다리며 잠금을 놓고, 반환 전에 다시 획득합니다. |
| `signal()`·`signalAll()` | 해당 조건에서 기다리는 스레드에 알립니다. |

`Condition.await()`도 조건을 `while`로 다시 검사합니다. 한 잠금 아래에 “비어 있지 않음”과 “가득 차지 않음”처럼 여러 조건을 둘 수 있습니다.[^condition]

**공정 잠금**은 오래 기다린 스레드를 우대하는 정책입니다. 운영체제의 실행까지 완벽하게 선착순으로 만드는 것은 아닙니다. 시간 인수가 없는 `tryLock()`은 공정성 설정을 따르지 않을 수 있습니다.

**선택 심화 — 읽기 잠금과 낙관적 읽기**

| 도구 | 목적 | 주의 |
| --- | --- | --- |
| `ReentrantReadWriteLock` | 읽기끼리는 함께 허용하고 쓰기는 배타적으로 처리 | 읽기 잠금을 잡은 채 쓰기 잠금으로 전환하는 방식은 주의 |
| `StampedLock` | 읽기·쓰기와 검증 가능한 낙관적 읽기 | 재진입 잠금이 아님 |
| 낙관적 읽기 | 잠금 없이 값을 읽고 변경 여부를 검증 | 검증 실패 시 읽기 잠금 등으로 다시 읽어야 함 |

낙관적 읽기 도중의 값은 일관되지 않을 수 있습니다. 검증 전에 읽은 값으로 외부 부수효과를 일으키는 식으로 사용하지 않습니다.[^stamped]

### 108. 원자 변수와 비교 후 교환

**원자 변수는 증가·조건부 갱신 같은 연산을 원자적으로 제공합니다.** `AtomicInteger` 하나가 여러 변수의 업무 규칙을 전부 보호하는 것은 아닙니다.[^atomic]

```java
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] 인수) {
        AtomicInteger 값 = new AtomicInteger(3);
        System.out.println(값.getAndIncrement());
        System.out.println(값.incrementAndGet());
        System.out.println(값.compareAndSet(5, 9));
        System.out.println(값.compareAndSet(5, 12));
        System.out.println(값.get());
    }
}
```

출력:

```text
3
5
true
false
9
```

| 연산 | 반환 기준 |
| --- | --- |
| `getAndIncrement()` | 증가하기 전 값 |
| `incrementAndGet()` | 증가한 뒤 값 |
| `getAndSet(새값)` | 변경 전 값 |
| `compareAndSet(예상, 새값)` | 현재 값이 예상과 같으면 바꾸고 성공 여부 반환 |
| `updateAndGet(함수)` | 함수를 적용해 갱신한 값 |

비교 후 교환은 “내가 읽은 값이 아직 그대로인가?”를 검사하고 갱신을 묶습니다. 충돌하면 재시도하는 알고리즘을 구성할 수 있습니다. 갱신 함수는 재시도로 여러 번 평가될 수 있으므로 외부 부수효과를 넣지 않습니다.

**선택 심화**

| 개념 | 기억할 내용 |
| --- | --- |
| `AtomicReference` | 참조에 대한 조건부 갱신을 제공합니다. 비교는 내용 동등성이 아닌 참조 동일성입니다. |
| 값의 복귀 문제 | 값이 처음 값 → 다른 값 → 처음 값으로 돌아오면 값만 비교해 변경 이력을 놓칠 수 있습니다. |
| `AtomicStampedReference` | 참조와 표지를 함께 비교해 이러한 변경 이력을 구분하는 데 사용합니다. |
| `LongAdder` | 경쟁이 많은 누적 통계를 분산해 갱신합니다. |
| `sum()` | 동시에 갱신 중일 때 한 순간의 원자적 스냅샷은 아닙니다. |
| 원자 필드 갱신기 | 특정 필드를 원자적으로 갱신하는 도구입니다. 해당 필드의 접근 규칙을 일관되게 지켜야 합니다. |
| `VarHandle` | 필드·배열 요소 등의 접근과 원자 연산, 메모리 순서 모드를 제어합니다. |

`LongAdder`는 통계 누적에 유용하지만, 다음 고유 번호를 발급하는 원자적 증가의 대체품은 아닙니다. `VarHandle`의 일반·불투명·획득·해제·휘발성 접근은 서로 같은 강도의 보장이 아닙니다.[^longadder][^varhandle]

### 109. 스레드 지역 저장소

**`ThreadLocal`은 같은 키를 사용해도 스레드마다 별도의 값을 갖게 합니다.** 공유 변수 하나를 여러 스레드가 함께 갱신하는 것과 다릅니다.[^threadlocal]

```java
public class Main {
    private static final ThreadLocal<Integer> 지역값 =
        ThreadLocal.withInitial(() -> 0);

    public static void main(String[] 인수) throws InterruptedException {
        지역값.set(100);
        Thread 작업 = new Thread(() -> {
            try {
                System.out.println(지역값.get());
                지역값.set(200);
                System.out.println(지역값.get());
            } finally {
                지역값.remove();
            }
        });
        작업.start();
        작업.join();
        System.out.println(지역값.get());
        지역값.remove();
        System.out.println(지역값.get());
        지역값.remove();
    }
}
```

출력:

```text
0
200
100
0
```

작업 스레드에서 설정한 200은 주 스레드의 100을 바꾸지 않습니다. `remove()` 후 다시 `get()`하면 초기값 공급자가 다시 사용될 수 있습니다.

| 구분 | 핵심 |
| --- | --- |
| 일반 정적 필드 | 같은 클래스의 스레드들이 같은 필드에 접근합니다. |
| `ThreadLocal` 값 | 현재 스레드에 연결된 값을 읽고 씁니다. |
| `InheritableThreadLocal` | 자식 스레드 생성 시 부모의 값을 이어받는 기능입니다. |
| 스레드 풀 | 작업이 끝나도 스레드는 살아서 다음 작업에 재사용될 수 있습니다. |

**주의:** 스레드 풀에서는 요청이 끝날 때 `finally`에서 제거하는 습관이 중요합니다. 이전 요청의 값이 다음 요청에 남거나 오래 살아 있는 스레드가 불필요한 객체를 붙들 수 있습니다.

`InheritableThreadLocal`은 **작업 제출 시마다 요청 문맥을 자동 복사하는 장치가 아닙니다.** 또한 각 저장소에 같은 가변 객체 참조를 넣으면 참조 대상은 여전히 공유됩니다. “저장 칸이 별도”와 “객체도 별도”를 구분합니다.

### 110. 작업 실행기와 스레드 풀

**작업 실행기는 해야 할 일과 그 일을 실행할 스레드의 관리를 분리합니다.** 스레드 풀은 작업자를 재사용하여 반복적인 생성 비용을 줄일 수 있지만, 대기 작업과 자원의 한도를 설계해야 합니다.[^executor][^pool]

| 구성 | 역할 | 반환값·예외 |
| --- | --- | --- |
| `Runnable` | 실행할 작업 | 반환값이 없고 검사 예외를 선언하지 않음 |
| `Callable` | 결과를 만드는 작업 | 결과 반환·검사 예외 선언 가능 |
| `Executor` | 작업 실행의 기본 계약 | `execute` 제공 |
| `ExecutorService` | 제출·완료·종료 관리 | `submit` 등 제공 |
| `Future` | 아직 끝나지 않았을 수 있는 결과 | 완료 대기·결과 조회·취소 |

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Main {
    public static void main(String[] 인수) throws Exception {
        try (ExecutorService 실행기 = Executors.newFixedThreadPool(2)) {
            Future<Integer> 첫째 = 실행기.submit(() -> 10 + 20);
            Future<Integer> 둘째 = 실행기.submit(() -> 20 + 40);
            System.out.println(첫째.get());
            System.out.println(둘째.get());
            System.out.println(첫째.isDone());
        }
    }
}
```

출력:

```text
30
60
true
```

어느 작업이 먼저 완료되는지는 고정하지 않았습니다. 다만 주 스레드가 첫째 결과, 둘째 결과 순으로 출력하므로 **출력 순서는 고정**됩니다.

**`Future`의 결과·실패·취소 구분**

| 기능 | 의미 |
| --- | --- |
| `get()` | 필요하면 기다린 뒤 결과를 받습니다. 작업 실패는 `ExecutionException`으로 전달됩니다. |
| 시간 있는 `get()` | 기다리는 시간을 제한합니다. 시간 초과만으로 작업을 취소하지는 않습니다. |
| `isDone()` | 성공·실패·취소를 포함한 완료 여부입니다. 성공 여부만 뜻하지 않습니다. |
| `cancel(true)` | 가능한 경우 실행 중 작업에 인터럽트를 요청하며 취소합니다. 강제 종료를 보장하지 않습니다. |
| 취소 뒤 `get()` | 취소된 결과에서는 `CancellationException`이 발생합니다. |

`submit()`으로 실행한 작업의 예외는 보통 반환된 결과 객체에 담깁니다. 결과를 확인하지 않으면 실패를 놓칠 수 있습니다.[^future]

**실행기 종료**

| 기능 | 신규 작업 | 기존 작업 | 호출 자체가 종료를 기다리는가? |
| --- | --- | --- | --- |
| `shutdown()` | 거부 | 제출된 작업은 처리 | 아니요 |
| `shutdownNow()` | 거부 | 진행 중 작업 중단을 시도하고 대기 작업을 반환 | 완료 보장은 없음 |
| `awaitTermination()` | 종료 요청과 함께 사용 | 종료 완료를 관찰 | 정해진 시간까지 기다림 |
| 자바 21의 `close()` | 종료 절차 수행 | 종료를 기다리는 계약 | 예 |

위 예제의 자동 자원 해제는 자바 21에서 사용할 수 있습니다. 작업이 종료 요청에 협력하지 않고 계속 실행하면 닫기도 오래 걸릴 수 있습니다.

**보충 — 풀과 작업 대기열**

| 구성 | 특성 | 위험 |
| --- | --- | --- |
| 고정 크기 풀 | 일정 수의 작업자를 재사용 | 기본 팩터리의 사실상 무제한 대기열이 메모리를 소모할 수 있음 |
| 단일 스레드 실행기 | 한 작업씩 순차 실행 | 앞의 긴 작업이 뒤 작업을 지연 |
| 캐시형 풀 | 유휴 작업자를 재사용하고 필요하면 생성 | 작업자가 과도하게 늘 수 있음 |
| 예약 실행기 | 지연·주기 작업 | 주기 방식과 실패 후 동작 확인 필요 |
| 직접 설정한 풀 | 작업자 수·대기열·거절 정책 제어 | 설정들이 함께 작동하는 방식 이해 필요 |

일반적인 `ThreadPoolExecutor`는 **핵심 작업자 수보다 적으면 생성 → 아니면 대기열 추가 시도 → 대기열이 못 받으면 최대 작업자 수까지 생성 시도 → 그래도 못 받으면 거절**하는 흐름입니다. 종료 상태 등의 추가 조건도 적용됩니다.

무제한 대기열을 쓰면 대기열이 차지 않아 최대 작업자 수가 기대대로 늘지 않을 수 있습니다. 거절 정책에는 예외 발생·호출자 실행·폐기 등이 있으며, 조용한 폐기는 업무 결과 누락으로 이어질 수 있습니다.

**선택 심화:** 고정 주기는 예정 시각 간격을 기준으로 하고, 고정 지연은 앞 작업의 종료부터 다음 시작까지의 간격을 기준으로 합니다. 완료 서비스는 제출 순서가 아니라 **완료 순서로 결과를 꺼내는 데** 사용합니다.

### 111. 비동기 결과의 조합

**`CompletableFuture`는 완료될 결과와 그 뒤의 계산을 연결하는 도구입니다.** 이름에 비동기라는 의미가 있다고 모든 연결이 항상 다른 스레드에서 실행되는 것은 아닙니다.[^completable]

| 기능 | 작업 관계 | 결과 |
| --- | --- | --- |
| `thenApply` | 앞 결과로 일반 값을 계산 | 변환된 결과 |
| `thenCompose` | 앞 결과로 다음 비동기 결과를 생성 | 중첩 결과를 평탄화 |
| `thenCombine` | 두 결과를 모아 계산 | 결합 결과 |
| `thenAccept` | 결과를 소비 | 결과값 없는 완료 |
| `thenRun` | 완료 뒤 실행 | 앞 결과를 인수로 받지 않음 |
| `exceptionally` | 실패에 대한 대체 결과 | 복구된 값 |
| `handle` | 성공·실패를 모두 변환 | 새 결과 |
| `whenComplete` | 성공·실패를 관찰 | 원래 결과를 전달하는 것이 주목적 |

```java
import java.util.concurrent.CompletableFuture;

public class Main {
    public static void main(String[] 인수) {
        CompletableFuture<Integer> 처음 =
            CompletableFuture.completedFuture(10);
        CompletableFuture<Integer> 결과 = 처음
            .thenApply(값 -> 값 + 1)
            .thenCompose(값 -> CompletableFuture.completedFuture(값 * 2))
            .thenCombine(CompletableFuture.completedFuture(3), Integer::sum);

        System.out.println(처음.join());
        System.out.println(결과.join());
        System.out.println(CompletableFuture.<Integer>failedFuture(
            new IllegalStateException("실패"))
            .exceptionally(예외 -> 7).join());
    }
}
```

출력:

```text
10
25
7
```

이 예제는 결과 조합만 보여줍니다. `completedFuture()`는 이미 완료된 결과를 만들며 **새 스레드를 만드는 메서드가 아닙니다.**

| 비교 | 차이 |
| --- | --- |
| `Future.get()` | 인터럽트·실행 실패를 검사 예외로 다루는 경로 |
| `CompletableFuture.join()` | 실행 실패가 보통 비검사 `CompletionException`으로 전달되는 경로 |
| 접미사 없는 연결 메서드 | 완료를 수행하는 스레드 등에서 실행될 수 있음 |
| `...Async` 메서드 | 지정 실행기 또는 기본 비동기 실행 시설 사용 |
| `allOf` | 모든 완료를 모음. 결과 자체는 각 원소의 값 목록이 아닌 `Void` |
| `anyOf` | 먼저 완료된 결과를 사용. 먼저 실패한 경우도 포함 |

기본 비동기 실행은 보통 공용 분할 정복 풀을 사용하지만 기본 풀의 병렬성 등 문서상 예외가 있습니다. 실행 스레드가 중요하면 실행기를 명시합니다.

**시간 초과와 취소는 별도로 설계합니다.** 시간 초과로 결과 객체가 예외 완료되어도 이미 실행 중인 외부 요청이 자동으로 중단된다고 단정하지 않습니다. 이 클래스의 `cancel(true)`는 일반적인 스레드 중단 장치로 작동하지 않으며, 인수로 실행 중 계산의 인터럽트를 보장하지 않습니다.

### 112. 분할 정복 실행 프레임워크

**분할 정복 실행은 큰 계산을 작은 작업으로 나누고 결과를 합치는 방식입니다.** `ForkJoinPool`은 작업자가 다른 작업자의 남은 일을 가져오는 작업 훔치기 방식을 사용합니다.[^forkjoin]

| 구성 | 역할 |
| --- | --- |
| `RecursiveTask` | 결과를 반환하는 재귀 작업 |
| `RecursiveAction` | 결과값 없는 재귀 작업 |
| `fork()` | 하위 작업의 실행을 예약 |
| `join()` | 해당 하위 작업의 결과를 기다림 |
| `compute()` | 작업의 계산 로직 |

```java
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveTask;

public class Main {
    static class 합계 extends RecursiveTask<Integer> {
        private final int 시작;
        private final int 끝;
        합계(int 시작, int 끝) {
            this.시작 = 시작;
            this.끝 = 끝;
        }
        @Override protected Integer compute() {
            if (끝 - 시작 <= 1) {
                int 합 = 0;
                for (int 값 = 시작; 값 <= 끝; 값++) 합 += 값;
                return 합;
            }
            int 중간 = 시작 + (끝 - 시작) / 2;
            합계 왼쪽 = new 합계(시작, 중간);
            합계 오른쪽 = new 합계(중간 + 1, 끝);
            왼쪽.fork();
            return 오른쪽.compute() + 왼쪽.join();
        }
    }

    public static void main(String[] 인수) {
        try (ForkJoinPool 풀 = new ForkJoinPool(2)) {
            System.out.println(풀.invoke(new 합계(1, 6)));
        }
    }
}
```

출력:

```text
21
```

직접 계산하는 작은 구간을 두어 분할을 끝냅니다. 이 예제의 크기는 원리 설명용이며 이렇게 작은 합계를 병렬화해야 빠르다는 뜻은 아닙니다.

**시험 포인트:** 분할 비용·결과 결합 비용이 더 크면 느려집니다. 긴 입출력 대기를 계산용 공용 풀에 무분별하게 섞는 것도 주의합니다. 관리되는 대기 기능이 있지만 모든 임의의 대기가 자동으로 보상되지는 않습니다.

### 113. 동기화 도구와 동시성 컬렉션

**잠금은 주로 접근을 제한하고, 동기화 도구는 작업 사이의 진행 조건을 맞춥니다.** 같은 “기다림”이어도 기다리는 조건이 다릅니다.[^concurrent][^latch]

| 도구 | 기다리는 조건 | 특징 |
| --- | --- | --- |
| `CountDownLatch` | 횟수가 0이 됨 | 한 번 열리면 원래 횟수로 되돌리지 않음 |
| `CyclicBarrier` | 정해진 수의 참여자가 도착 | 단계별로 재사용 가능 |
| `Semaphore` | 사용할 수 있는 허가가 있음 | 동시 자원 사용 수 제한 |
| `Phaser` | 등록 참여자들의 단계 진행 | 참여자 등록·해제 가능 |
| `Exchanger` | 짝이 와서 값을 교환 | 두 참여자가 데이터를 교환 |
| `BlockingQueue` | 넣을 자리나 꺼낼 원소가 생김 | 생산자·소비자 연결 |

```java
import java.util.Arrays;
import java.util.concurrent.CountDownLatch;

public class Main {
    public static void main(String[] 인수) throws InterruptedException {
        int[] 결과 = new int[2];
        CountDownLatch 완료 = new CountDownLatch(2);
        Thread 첫째 = new Thread(() -> {
            try { 결과[0] = 10; }
            finally { 완료.countDown(); }
        });
        Thread 둘째 = new Thread(() -> {
            try { 결과[1] = 20; }
            finally { 완료.countDown(); }
        });
        첫째.start();
        둘째.start();
        완료.await();
        System.out.println(Arrays.toString(결과));
        첫째.join();
        둘째.join();
    }
}
```

출력:

```text
[10, 20]
```

각 작업은 서로 다른 배열 요소를 씁니다. 성공적으로 끝난 `await()`는 `countDown()` 이전의 쓰기를 관찰할 수 있게 합니다. 래치 자체가 작업의 성공·실패 결과를 저장하는 것은 아니므로 실무에서는 실패 전달도 별도로 설계합니다.

**대표 동시성 컬렉션**

| 도구 | 핵심 | 주의 |
| --- | --- | --- |
| `ConcurrentHashMap` | 동시 조회·갱신과 원자적 키 연산 | `null` 키·값 금지. 값 객체의 내부까지 보호하지 않음 |
| `CopyOnWriteArrayList` | 변경 시 새 배열을 만들어 읽기와 분리 | 변경 비용이 큼. 반복자는 생성 시점의 스냅샷 |
| `BlockingQueue` | 공간·원소 대기를 포함한 삽입·제거 | 구현체마다 용량 제한 여부가 다름 |
| `ConcurrentLinkedQueue` | 동시 접근 가능한 연결 큐 | `poll()`은 비어 있으면 `null`을 반환하며 기다리지 않음 |

다음은 키 하나의 누적을 하나의 갱신 연산으로 표현합니다.

```java
import java.util.concurrent.ConcurrentHashMap;

public class Main {
    public static void main(String[] 인수) {
        ConcurrentHashMap<String, Integer> 횟수 = new ConcurrentHashMap<>();
        횟수.merge("자바", 1, Integer::sum);
        횟수.merge("자바", 1, Integer::sum);
        System.out.println(횟수.get("자바"));
        System.out.println(횟수.putIfAbsent("자바", 10));
        System.out.println(횟수.get("자바"));
    }
}
```

출력:

```text
2
2
2
```

**`containsKey()`로 확인한 뒤 `put()`을 따로 하는 두 호출**은 각각 안전해도 하나의 원자적 업무가 아닙니다. `putIfAbsent`, `compute`, `merge` 등 적합한 결합 연산을 검토합니다.[^concurrent-map]

**보충:** 세마포어는 잠금 소유권과 같은 개념이 아닙니다. 보통 허가를 성공적으로 획득한 경로에서만 해제합니다. 획득하지 않고 `release()`를 추가 호출하면 허가 수가 잘못 늘 수 있습니다.

### 114. 동시성 실패와 설계 원칙

**경쟁 조건은 실행 순서에 따라 올바르지 않은 결과가 생기는 상황입니다.** 그중 동기화되지 않은 충돌하는 메모리 접근을 자바 메모리 모델에서 데이터 경쟁으로 구분합니다.[^memory-model]

| 문제 | 의미 | 직관 |
| --- | --- | --- |
| 데이터 경쟁 | 선행 발생 관계 없는 충돌 접근 | 같은 필드를 규칙 없이 읽고 씀 |
| 경쟁 조건 | 타이밍에 따라 업무 판단·결과가 달라짐 | 재고 확인과 차감을 따로 수행 |
| 교착 상태 | 서로가 가진 자원을 기다려 진행하지 못함 | 서로 다른 열쇠를 하나씩 쥐고 나머지를 기다림 |
| 활성 교착 | 계속 행동하지만 유용한 진전이 없음 | 서로 양보하는 동작만 반복 |
| 기아 | 특정 작업이 계속 자원을 얻지 못함 | 항상 다른 작업에 밀림 |

**교착 상태의 고전적 네 조건**

| 조건 | 내용 |
| --- | --- |
| 상호 배제 | 자원을 동시에 공유할 수 없음 |
| 점유와 대기 | 가진 자원을 유지한 채 다른 자원을 기다림 |
| 비선점 | 다른 작업의 자원을 임의로 빼앗을 수 없음 |
| 순환 대기 | 서로 기다리는 관계가 고리를 이룸 |

```text
첫째 작업: 왼쪽 잠금을 보유 → 오른쪽 잠금을 기다림
둘째 작업: 오른쪽 잠금을 보유 → 왼쪽 잠금을 기다림

예방 방향: 모든 작업이 왼쪽 → 오른쪽의 같은 순서로 획득
```

두 잠금이 필요한 상황에서 일관된 전체 순서를 두면 순환 대기를 피하는 데 도움이 됩니다. 제한 시간·잠금 범위 축소·메시지 전달 방식도 함께 검토합니다.

**공유 데이터 설계의 우선순위**

| 방향 | 설명 |
| --- | --- |
| 공유 줄이기 | 작업마다 별도 자료를 계산하고 마지막에 합칩니다. |
| 불변 값 공유 | 안전하게 공개한 뒤 바꾸지 않는 값을 이용합니다. |
| 하나의 규칙으로 보호 | 관련된 상태와 불변조건을 동일 잠금 등으로 묶습니다. |
| 기존 도구 활용 | 직접 대기열을 만들기 전에 표준 동시성 도구를 검토합니다. |
| 취소·실패 포함 | 정상 완료만 아니라 실패와 종료 시나리오도 설계합니다. |

<mark>스레드 안전한 부품을 여러 번 호출한다고 업무 전체가 자동으로 원자적이 되는 것은 아닙니다.</mark>

재현할 때는 `sleep()`으로 운에 맡기기보다 시작·진행·완료 지점을 래치나 장벽 등으로 통제합니다. 반복 실행에서 문제가 없었다는 사실만으로 모든 실행의 안전성을 증명할 수는 없습니다.

### 115. 반응형 흐름과 역압력 — 선택 심화

**역압력은 받는 쪽의 처리 가능량을 보내는 쪽에 전달하는 흐름 제어입니다.** `Flow`는 이러한 협력을 위한 인터페이스 묶음입니다.[^flow]

| 구성 | 역할 |
| --- | --- |
| `Publisher` | 데이터를 제공하고 구독을 받음 |
| `Subscriber` | 구독과 데이터·완료·실패 알림을 받음 |
| `Subscription` | 요청량과 취소를 전달하는 연결 |
| `Processor` | 구독자이면서 발행자인 중간 처리 단계 |

```text
구독자: 구독을 시작합니다.
발행자: 구독 제어 객체를 전달합니다.
구독자: 지금은 원소 두 개를 받을 수 있습니다.
발행자: 요청량 범위에서 원소를 전달합니다.
구독자: 처리가 끝났으니 하나를 더 요청합니다.
```

`request(양수)`로 수요를 알리고 `cancel()`로 중단을 요청합니다. 완료·실패 신호는 원소 요청량과 같은 방식으로 소비되는 데이터 원소가 아닙니다. 인터페이스를 썼다는 이유만으로 별도 스레드가 자동 생성되는 것도 아닙니다.

| 비교 | 일반 `Stream` | `Flow` 기반 구독 |
| --- | --- | --- |
| 초점 | 데이터의 일괄 처리 파이프라인 | 발행·구독과 요청량 제어 |
| 처리 시작 | 최종 연산 | 구독과 수요 전달 |
| 작업 배치 | 순차 또는 병렬 연산 | 구현에 따라 동기·비동기 전달 |
| 종료 | 최종 결과·소비 | 완료·실패·취소 신호 |

기초 단계에서는 **생산 속도가 소비 속도보다 빠를 때 무제한 적재만 하지 않고 흐름을 조절한다**는 목적을 기억합니다.

## 14부. 현대 자바의 동시성

### 116. 가상 스레드

**가상 스레드는 자바 실행 환경이 관리하는 가벼운 스레드입니다.** 많은 작업이 입출력 때문에 기다리는 프로그램의 처리량을 높이는 데 목적이 있으며, 계산 한 건 자체를 빠르게 만드는 기능은 아닙니다. 자바 21에서 정식 기능입니다.[^virtual]

| 구분 | 플랫폼 스레드 | 가상 스레드 |
| --- | --- | --- |
| 실행 관리 | 운영체제 스레드와 밀접한 대응 | 자바 실행 환경이 운반 스레드에 배치 |
| 주된 관심 | 제한된 실행 작업자 | 많은 독립적인 대기 작업 |
| 대기 비용 | 작업자가 점유될 수 있음 | 지원되는 대기에서는 운반 스레드를 다른 작업에 사용 가능 |
| 계산 자원 | 실제 처리 장치 수의 제약 | 실제 처리 장치 수의 제약은 그대로 |
| 작업 실행 방식 | 풀에서 재사용하기도 함 | 보통 작업마다 새 가상 스레드를 사용 |

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Main {
    public static void main(String[] 인수) throws Exception {
        Thread 작업 = Thread.ofVirtual().unstarted(() ->
            System.out.println(Thread.currentThread().isVirtual()));
        System.out.println(작업.isDaemon());
        작업.start();
        작업.join();

        try (ExecutorService 실행기 = Executors.newVirtualThreadPerTaskExecutor()) {
            Future<Integer> 결과 = 실행기.submit(() -> 40 + 2);
            System.out.println(결과.get());
        }
    }
}
```

출력:

```text
true
true
42
```

**운반 스레드**는 가상 스레드의 코드를 실제로 실행하는 플랫폼 스레드입니다. 대기 중 운반 스레드에서 떨어졌다가 다시 배치될 수 있습니다. `Thread.currentThread()`는 실행 중인 가상 스레드를 나타내며 운반 스레드를 반환하는 것이 아닙니다.

**주의할 세 가지**

| 오해 | 올바른 판단 |
| --- | --- |
| 많을수록 계산이 빨라진다 | 계산 중심 작업은 처리 장치와 알고리즘의 제약을 받습니다. |
| 스레드가 가벼우니 외부 연결도 무제한이다 | 데이터베이스 연결·요청 수·메모리는 별도로 제한해야 합니다. |
| 가상 스레드 풀을 작게 만들어 재사용한다 | 작업별 생성이 기본 방향이며, 부족한 외부 자원은 세마포어 등으로 제한합니다. |

**버전 보충 — 고정 현상**

자바 21에서는 모니터를 보유하는 등의 상황에서 가상 스레드가 운반 스레드에서 떨어지지 못하는 고정 현상이 성능 문제가 될 수 있습니다. 자바 24의 모니터 구현 개선은 `synchronized` 관련 고정 문제를 개선합니다. 그렇다고 모든 네이티브 호출·모든 대기가 무조건 자유롭게 분리되는 것은 아닙니다.[^pinning]

### 117. 범위 지정 값 — 자바 25 보충

**범위 지정 값은 정해진 호출 범위에서 읽을 문맥 데이터를 전달하는 기능입니다.** `ScopedValue`는 자바 25에서 정식 기능이며, 이 절은 개념 위주로 다룹니다.[^scoped]

```text
바깥 범위: 요청 이름을 “첫 요청”으로 연결
    하위 메서드: “첫 요청”을 읽음
    안쪽 범위: 요청 이름을 “임시 요청”으로 다시 연결
        더 안쪽 메서드: “임시 요청”을 읽음
    안쪽 범위 종료
    하위 메서드: 다시 “첫 요청”을 읽음
바깥 범위 종료: 처음에 연결되지 않았다면 연결 없는 상태로 복귀
```

| 비교 | `ThreadLocal` | `ScopedValue` |
| --- | --- | --- |
| 주된 방식 | 현재 스레드의 값을 설정·변경·제거 | 호출 범위에 값을 연결 |
| 수명 | 명시적 제거를 놓치기 쉬움 | 범위가 끝나면 이전 연결 상태로 복귀 |
| 하위 호출의 변경 | 같은 저장소에 새 값 설정 가능 | 중첩 범위에서 별도 연결 가능 |
| 주된 목적 | 스레드에 귀속되는 상태 | 호출 흐름으로 전달할 문맥 |

**읽기용 연결과 객체 불변성은 다릅니다.** 연결된 대상이 가변 목록이라면 그 목록의 내용까지 저절로 불변이 되지는 않습니다. 여러 스레드가 쓰는 값은 불변이거나 적절히 동기화되어야 합니다.

구조적 작업 범위에서 하위 작업으로 연결 정보를 이어줄 수 있습니다. 아무 스레드나 생성하면 모든 문맥이 자동으로 전파된다고 일반화하지 않습니다.

### 118. 구조적 동시성 — 미리보기 보충

**구조적 동시성은 하나의 업무에서 갈라진 하위 작업들의 수명·완료·실패를 하나의 범위 안에서 관리하는 방식입니다.** 이 절은 자바 25 문서의 `StructuredTaskScope`를 기준으로 하며, 해당 버전에서는 미리보기 기능입니다.[^structured]

```text
상위 업무 시작
    작업 범위 열기
        고객 정보 조회 시작
        거래 정보 조회 시작
        정해진 정책에 따라 하위 결과 대기
        성공한 결과 결합 또는 실패 처리
    작업 범위 닫기: 필요한 취소와 하위 작업 종료 대기
상위 업무 종료
```

| 일반적인 개별 결과 관리 | 구조적 작업 범위 |
| --- | --- |
| 각각 제출한 작업의 수명을 수동으로 추적 | 상위 범위에 하위 작업을 묶음 |
| 한 작업 실패 뒤 나머지 취소를 따로 설계 | 범위의 정책과 실패 처리를 연결 |
| 상위 요청이 끝나도 하위 작업이 남기 쉬움 | 범위 밖으로 실행 수명이 새지 않도록 관리 |
| 완료 대기·기한·정리를 여러 곳에서 처리 | 하나의 업무 단위로 정리 |

**취소 요청과 실제 종료는 여전히 다릅니다.** 하위 작업이 인터럽트에 협력하지 않으면 범위 닫기도 기다릴 수 있습니다. 구조를 썼다고 모든 외부 요청의 취소가 즉시 강제되는 것은 아닙니다.

기초 수준에서는 목적과 `Future` 개별 관리와의 차이를 기억합니다. 미리보기 기능은 버전마다 선언 형태와 메서드가 바뀔 수 있으므로, 실행 코드는 사용 버전의 문서와 활성화 옵션을 함께 확인합니다.

<details markdown="1">
<summary>14부 한 줄로</summary>

가상 스레드는 많은 작업의 실행 비용, 범위 지정 값은 문맥 전달, 구조적 동시성은 하위 작업들의 수명을 다룹니다. 서로 연관되지만 같은 기능은 아닙니다.

</details>

## 15부. 가상 머신·메모리·가비지 컬렉션

### 119. 가상 머신 명세와 실제 구현

**자바 가상 머신은 클래스 파일을 읽고 정해진 실행 규칙에 따라 프로그램을 실행하는 추상적인 기계입니다.** 실제 구현체는 메모리 배치·컴파일·수집 알고리즘을 달리 선택할 수 있습니다.[^vm-structure]

```text
자바 소스 파일
    → 소스 컴파일
클래스 파일과 바이트코드
    → 로딩·링킹·초기화
가상 머신 실행
    → 인터프리터 실행 또는 실행 중 기계어 컴파일 등
운영체제와 실제 처리 장치
```

| 구분 | 뜻 |
| --- | --- |
| 자바 언어 명세 | 문법·타입·표현식·클래스·스레드의 언어 규칙 |
| 가상 머신 명세 | 클래스 파일·명령어·실행 영역·로딩 등의 규칙 |
| 표준 라이브러리 문서 | 클래스와 메서드가 제공하는 동작 계약 |
| 구현체 | 명세를 실제 환경에서 구현한 프로그램 |
| 구현 최적화 | 외부에서 관찰되는 규칙을 지키며 실행을 개선하는 방법 |

**플랫폼 독립성의 대상은 적절한 버전의 가상 머신에서 실행되는 클래스 파일입니다.** 가상 머신 실행 프로그램 자체는 운영체제와 처리 장치에 맞게 제공됩니다. 네이티브 라이브러리·운영체제별 경로·외부 프로그램까지 아무 조건 없이 독립적인 것은 아닙니다.

**시험 포인트:** “가상 머신이 실행한다”와 “모든 코드를 처음부터 끝까지 한 줄씩 해석만 한다”는 같은 말이 아닙니다. 실행 중 컴파일은 대표적인 구현 최적화이며, 모든 가상 머신이 특정 방식의 컴파일러를 반드시 가져야 한다는 명세는 아닙니다.

### 120. 클래스 파일의 구조

**클래스 파일은 실행에 필요한 타입·상수·멤버·코드 정보를 담은 이진 형식입니다.** 자바 소스의 문장을 그대로 보관한 텍스트 파일이 아닙니다.[^class-file]

| 구성 | 내용 | 기억할 점 |
| --- | --- | --- |
| 식별값 | `0xCAFEBABE` | 클래스 파일 형식을 식별 |
| 버전 | 주 버전·부 버전 | 실행 환경이 지원하는 형식인지 확인 |
| 상수 풀 | 리터럴·이름·타입·멤버 참조 등 | 정수 상수만 있는 곳이 아님 |
| 접근 플래그 | 공개·추상·최종·인터페이스 등 | 타입의 성격 표현 |
| 상위 타입·인터페이스 | 상속·구현 관계 | 타입 계층 연결 |
| 필드·메서드 | 이름·자료형·속성 | 시그니처와 실행 정보 |
| 부가 속성 | 코드·예외 처리·애너테이션·줄 정보 등 | 속성마다 역할이 다름 |

**버전의 예:** 자바 8은 주 버전 52, 자바 17은 61, 자바 21은 65입니다. 숫자 자체보다 **실행 환경보다 새로운 형식으로 컴파일하면 로딩에 실패할 수 있다**는 관계를 먼저 이해합니다.

```text
javac --release 21 -encoding UTF-8 Main.java
javap -c -p Main
javap -v Main
```

위 명령은 각각 컴파일, 바이트코드 확인, 상세 클래스 정보를 확인하는 실습 명령입니다. `--release`는 단순 파일 형식만 아니라 대상 버전의 언어·사용 가능한 표준 기능 범위를 함께 고려하게 합니다.[^javac]

**검증과 안전성:** 클래스 파일 검증은 잘못된 스택 사용·자료형·명령 흐름 등을 검사합니다. 검증에 통과했다고 업무 로직의 정답이나 교착 상태 부재까지 증명되는 것은 아닙니다.

**선택 심화:** `Code` 속성의 예외 처리 테이블은 어느 코드 범위의 예외를 어디서 처리하는지 나타냅니다. 스택 맵은 특정 지점의 지역 변수·스택 자료형을 검증하는 데 사용합니다. 미리보기 기능에 의존하는 클래스 파일에는 일반 파일과 다른 버전 규칙도 적용됩니다.

### 121. 바이트코드와 호출 명령

**자바 가상 머신의 명령어는 피연산자 스택을 중심으로 값을 계산합니다.** 메서드의 매개변수·지역 변수는 지역 변수 배열의 칸을 사용합니다.[^instructions]

```java
public class Main {
    static int 더하기(int 왼쪽, int 오른쪽) {
        return 왼쪽 + 오른쪽;
    }
    public static void main(String[] 인수) {
        System.out.println(더하기(2, 3));
    }
}
```

출력:

```text
5
```

정적 `더하기` 메서드의 핵심 명령 흐름은 다음과 같습니다.

```text
iload_0  : 첫 번째 정수 인수를 스택에 올림
iload_1  : 두 번째 정수 인수를 스택에 올림
iadd     : 두 정수를 꺼내 더하고 결과를 올림
ireturn  : 정수 결과를 반환
```

| 호출 명령 | 주된 역할 |
| --- | --- |
| `invokestatic` | 정적 메서드 호출 |
| `invokevirtual` | 일반적인 클래스 인스턴스 메서드 호출 |
| `invokeinterface` | 인터페이스 메서드 호출 |
| `invokespecial` | 생성자·상위 구현 등 특수한 호출 |
| `invokedynamic` | 연결 규칙으로 결정되는 동적 호출 지점 |

위 표는 대표 용도를 이해하는 수준입니다. 소스의 모든 `private` 호출 등이 반드시 한 종류의 명령어만 사용한다고 버전·문맥을 무시해 단정하지 않습니다.

**보충:** 인스턴스 메서드는 보통 지역 변수 첫 칸에 `this`가 들어갑니다. 명세상 `long`·`double`은 지역 변수 배열에서 두 칸을 사용합니다. 슬롯의 개수와 실제 처리 장치의 레지스터 배치는 서로 다른 층위입니다.

`new`와 생성자 호출은 구분되는 동작입니다. 람다·문자열 연결에는 컴파일러가 동적 호출 지점을 활용할 수 있으나, 구체적인 생성 코드는 대상 버전과 컴파일러에 따라 달라질 수 있습니다.

### 122. 로딩·링킹·초기화

**클래스를 읽는 것, 연결하는 것, 정적 초기화 코드를 실행하는 것은 서로 다른 단계입니다.** 객체 하나를 초기화하는 생성자 실행과 클래스 초기화도 구분합니다.[^loading][^execution]

| 단계 | 하는 일 |
| --- | --- |
| 로딩 | 타입의 이진 표현을 읽고 해당 타입을 만듦 |
| 검증 | 형식과 실행 규칙에 맞는지 검사 |
| 준비 | 정적 필드 저장 공간과 기본값 등 실행 준비 |
| 해석 | 심벌 참조를 실제 타입·멤버와 연결 |
| 초기화 | 정적 필드의 명시적 초기화와 정적 초기화 블록 실행 |

**링킹은 검증·준비·해석을 포함합니다.** 해석은 구현에 따라 필요한 시점에 지연될 수 있으므로, 모든 참조의 해석이 언제나 초기화 전에 한꺼번에 끝난다고 외우지 않습니다.

```java
public class Main {
    static class 부모 {
        static { System.out.println("부모 초기화"); }
        static int 값 = 10;
    }
    static class 자식 extends 부모 {
        static final int 상수 = 7;
        static { System.out.println("자식 초기화"); }
    }
    public static void main(String[] 인수) {
        System.out.println(자식.상수);
        System.out.println(자식.값);
        new 자식();
        new 자식();
    }
}
```

출력:

```text
7
부모 초기화
10
자식 초기화
```

첫째, 컴파일타임 상수 읽기는 그 선언 클래스의 초기화를 일으키지 않습니다. 둘째, 상속된 정적 필드는 실제 선언한 부모를 초기화합니다. 셋째, `new 자식()`은 자식 초기화를 일으키지만 같은 타입을 또 생성한다고 정적 초기화가 반복되지는 않습니다.

**기본값과 명시적 초기화의 순서**

```java
public class Main {
    static int 첫째 = 읽기();
    static int 둘째 = 5;
    static int 읽기() { return 둘째; }

    public static void main(String[] 인수) {
        System.out.println(첫째);
        System.out.println(둘째);
    }
}
```

출력:

```text
0
5
```

`첫째`의 초기값을 계산할 때 `둘째`의 명시적 대입이 아직 실행되지 않았습니다. 그때는 기본값 0을 읽습니다. 이 예제의 읽기는 메서드 안에 있으므로 단순한 금지된 전방 참조와 혼동하지 않습니다.

| 상황 | 초기화 판단 |
| --- | --- |
| `new`로 인스턴스 생성 | 해당 클래스 초기화 필요 |
| 일반 정적 필드 읽기·쓰기 | 실제 선언 클래스 초기화 필요 |
| 정적 메서드 호출 | 실제 선언 클래스 초기화 필요 |
| 컴파일타임 상수 읽기 | 그 읽기만으로 초기화하지 않음 |
| `자료형.class` | 클래스 리터럴만으로 초기화하지 않음 |
| 해당 타입의 참조 배열 생성 | 원소 타입의 초기화를 요구하지 않음 |

**보충:** 클래스 초기화에는 동기화 규칙이 있어 여러 스레드가 같은 타입을 임의로 여러 번 초기화하지 않습니다. 상위 클래스와 일부 상위 인터페이스의 초기화 규칙도 있으므로 “부모 인터페이스는 항상 전부 먼저 초기화된다”는 문장은 부정확합니다.

정적 초기화가 실패하면 최초에는 원인에 따라 `ExceptionInInitializerError` 등이 나타나고, 이후 사용에서는 초기화 실패 때문에 `NoClassDefFoundError`가 날 수 있습니다. 이 오류를 언제나 “파일이 없다”로만 해석하지 않습니다.

### 123. 클래스 로더

**클래스 로더는 클래스의 이진 표현을 찾아 타입을 정의하는 역할을 합니다.** 실행 시 타입 정체성에는 이름뿐 아니라 **정의한 클래스 로더**도 포함됩니다.[^loading][^classloader]

| 로더 | 대표 역할 |
| --- | --- |
| 부트스트랩 로더 | 핵심 플랫폼 클래스 로딩 |
| 플랫폼 로더 | 플랫폼의 추가 클래스 로딩 |
| 애플리케이션 로더 | 일반적인 애플리케이션 클래스 로딩 |
| 사용자 정의 로더 | 플러그인·격리·특수한 로딩 정책 |

**부모에게 먼저 위임하는 방식**은 기본적인 로딩 모델입니다. 하지만 모든 사용자 정의 로더가 어떤 경우에도 같은 정책을 반드시 사용한다고 단정하지 않습니다.

```java
public class Main {
    public static void main(String[] 인수) throws ClassNotFoundException {
        Class<?> 첫째 = String.class;
        Class<?> 둘째 = Class.forName("java.lang.String");
        System.out.println(첫째 == 둘째);
        System.out.println(String.class.getClassLoader() == null);
        System.out.println(Main.class.getClassLoader() != null);
    }
}
```

출력:

```text
true
true
true
```

위 출력은 일반적인 자바 21 명령행 실행 환경 기준입니다. 부트스트랩 로더는 `getClassLoader()`에서 `null`로 표현됩니다. `null`이라고 해당 클래스가 로딩되지 않았다는 뜻은 아닙니다.

| 오해 | 구분 |
| --- | --- |
| 전체 이름이 같으면 언제나 같은 타입 | 정의 로더가 다르면 다른 타입일 수 있음 |
| 서로 다른 로더로 요청하면 항상 다른 타입 | 부모 위임으로 같은 로더가 정의한 클래스를 받을 수도 있음 |
| 정적 필드는 이름이 같은 모든 클래스에서 하나 | 다른 정의 로더로 별도 정의된 타입은 정적 상태도 분리 가능 |
| 클래스 경로는 소스 가져오기와 같다 | 클래스 경로는 탐색 경로이고 `import`는 소스의 이름 해석 |

**선택 심화:** 문맥 클래스 로더는 서비스 제공자 등 동적으로 찾는 타입에 사용될 수 있습니다. 클래스 로더가 오래 살아 있거나 다른 곳에서 참조되면 연결된 클래스와 자료가 함께 남을 수 있습니다.

### 124. 실행 중 메모리 영역

**힙과 메서드 영역은 명세상 공유 영역이고, 호출 스택과 실행 위치 정보는 스레드별 영역입니다.** 지역 변수의 값이 참조이면 그 지역 변수와 참조 대상 객체의 위치를 구분해야 합니다.[^vm-structure]

| 영역 | 주요 내용 | 공유 여부 |
| --- | --- | --- |
| 힙 | 클래스 인스턴스와 배열의 논리적 할당 영역 | 스레드들이 공유 가능 |
| 메서드 영역 | 타입별 구조·실행 중 상수 풀·필드와 메서드 정보 | 공유 |
| 가상 머신 스택 | 호출별 프레임 | 스레드별 |
| 프레임 | 지역 변수·피연산자 스택·실행 중 연결 정보 | 해당 호출의 실행 흐름 |
| 실행 위치 정보 | 현재 명령 위치 | 스레드별 |
| 네이티브 메서드 스택 | 네이티브 호출 등을 지원하는 스택 | 구현에 따라 제공 |

```text
호출 프레임의 지역 변수
    학생 참조 ─────────→ 힙의 학생 객체
    점수 80                 이름 참조 ──→ 문자열 객체
                            점수 필드 80
```

**“기본형은 스택, 참조형은 힙”은 잘못된 단순화입니다.** 기본형도 객체의 필드나 배열 요소이면 그 객체·배열에 포함됩니다. 참조값도 지역 변수·필드·배열 요소 등 여러 곳에 저장됩니다.

| 혼동하기 쉬운 용어 | 관계 |
| --- | --- |
| 메서드 영역 | 가상 머신 명세상의 논리적 영역 |
| 메타스페이스 | 대표 구현체에서 클래스 메타데이터를 관리하는 네이티브 메모리 구조 |
| 코드 캐시 | 실행 중 컴파일된 기계어 등을 저장하는 구현 영역 |
| 직접 메모리 | 직접 버퍼 등에서 사용하는 자바 힙 바깥의 메모리 |
| 문자열 풀 | 동일 내용 문자열의 대표 참조를 관리하는 구조 |
| 실행 중 상수 풀 | 타입별 상수·심벌 참조 등의 실행 정보 |

**보충:** 메서드 영역을 메타스페이스 하나와 완전히 같은 말로 외우지 않습니다. 현대 대표 구현체에서는 클래스의 `Class` 객체·문자열 객체 등은 자바 힙에 존재하며, 관련 메타데이터는 다른 영역에 있을 수 있습니다. 정적 멤버와 관련된 모든 것이 하나의 물리적 칸에 모인다는 뜻도 아닙니다.[^vm-performance]

가상 스레드의 스택 저장 같은 구현 세부사항은 명세상의 “각 실행 흐름에 호출 상태가 있다”는 설명과 별도로 봅니다. 물리적인 배치와 할당 제거 여부는 구현 최적화에 따라 달라질 수 있습니다.

### 125. 객체 배치와 메모리 할당 — 보충

**객체의 실제 크기는 필드 값의 크기만 단순히 더한 것과 다를 수 있습니다.** 헤더·정렬·패딩·참조 표현과 구현 설정이 영향을 줍니다.[^vm-performance][^object-headers]

| 구성·기법 | 의미 |
| --- | --- |
| 객체 헤더 | 타입과 잠금·해시 등 관리에 필요한 정보 |
| 인스턴스 데이터 | 객체의 필드 값 |
| 정렬 | 정해진 경계에 맞춰 배치 |
| 패딩 | 정렬 때문에 생기는 채움 공간 |
| 압축 참조 | 조건이 맞을 때 더 작은 표현으로 객체 참조 저장 |
| 간결한 객체 헤더 | 관리 정보 배치를 줄이는 구현 개선 |
| 스레드별 할당 버퍼 | 힙의 일부를 스레드가 빠르게 할당하도록 사용 |

스레드별 할당 버퍼가 있다고 그 안의 객체가 별도의 “스레드 전용 힙”으로 영원히 고립되는 것은 아닙니다. **할당의 빠른 경로**와 **객체가 다른 스레드에 공유될 수 있는지**는 별도 질문입니다.

**시험 포인트:** “정수 필드 두 개니까 객체는 정확히 8바이트”처럼 단정하지 않습니다. 또한 참조값을 사용한다고 프로그램이 객체의 실제 주소를 마음대로 계산하는 포인터 연산을 제공하는 것은 아닙니다.

헤더 크기와 특정 최적화의 기본 활성화 여부는 버전·배포판·실행 옵션에 따라 확인합니다. 이 글에서는 특정 바이트 수를 자바 언어의 불변 규칙처럼 암기하지 않습니다.

### 126. 가비지 컬렉션의 원리

**가비지 컬렉션은 더 이상 필요한 실행 경로에서 도달할 수 없는 객체의 메모리를 자동으로 회수하는 관리 방식입니다.** 참조 하나를 지우는 것과 즉시 메모리를 회수하는 것은 다릅니다.[^references][^gc-intro]

**도달 가능성을 보는 순서**

```text
실행이 사용하는 시작 참조들
    → 그 참조가 가리키는 객체
    → 그 객체에서 다시 가리키는 객체들

따라갈 수 있는 연결 안의 객체: 살아 있는 것으로 취급
어떤 살아 있는 시작 경로에서도 갈 수 없는 객체: 회수 후보
```

대표적인 시작 경로에는 살아 있는 스레드의 사용 중 참조, 로딩된 클래스와 관련된 살아 있는 정적 참조, 네이티브 연결 등이 포함될 수 있습니다. 정확한 시작점 처리와 시점은 구현과 최적화의 영향을 받습니다.

```java
public class Main {
    static class 연결 {
        연결 다음;
    }
    public static void main(String[] 인수) {
        연결 첫째 = new 연결();
        연결 둘째 = new 연결();
        첫째.다음 = 둘째;
        둘째.다음 = 첫째;
        첫째 = null;
        둘째 = null;
        System.out.println("순환 연결만 남음");
    }
}
```

출력:

```text
순환 연결만 남음
```

두 객체가 서로를 참조해도 외부의 살아 있는 경로에서 도달할 수 없다면 회수 대상이 될 수 있습니다. **자바의 회수 원리를 단순한 참조 횟수 세기로만 설명하면 순환 참조를 잘못 판단하게 됩니다.** 이 출력은 실제 회수가 일어났다는 관찰 결과가 아닙니다.

| 기본 방식 | 동작 | 장단점의 방향 |
| --- | --- | --- |
| 표시·제거 | 살아 있는 대상을 표시하고 나머지를 제거 | 빈 공간이 흩어질 수 있음 |
| 복사 | 살아 있는 객체를 다른 영역에 복사 | 공간을 정리하기 쉽지만 이동·여유 영역 필요 |
| 표시·압축 | 살아 있는 대상을 한쪽으로 정리 | 단편화를 줄이지만 이동 비용 존재 |
| 세대별 관리 | 수명 특성을 이용해 대상을 나누어 관리 | 짧게 사는 객체가 많은 특성을 활용 |

**세대 가설**은 많은 객체가 짧게 살고, 오래 살아남은 객체는 더 오래 남는 경향이 있다는 관찰입니다. 모든 객체에 적용되는 수명 보장이 아닙니다.

전통적 세대 구조의 새 객체 영역·생존 영역·오래된 객체 영역은 대표적인 설명 방식입니다. 모든 수집기가 힙을 같은 고정 구역으로 나누지는 않습니다. 살아남은 객체를 오래된 세대로 옮기는 것을 승격이라고 부릅니다.[^gc-generations]

**보충:** 쓰기·읽기 장벽은 객체 참조의 변경이나 접근을 추적하는 실행 장치입니다. 일부 수집은 애플리케이션을 잠시 멈추고, 일부는 애플리케이션과 함께 진행합니다. 이때의 장벽을 잠금의 조건 대기 도구와 혼동하지 않습니다.

### 127. 가비지 컬렉터의 종류 — 보충

**수집기는 처리량·응답 지연·메모리 사용·구현 비용 사이에서 다른 균형을 선택합니다.** 한 수집기가 모든 작업에서 언제나 우수하다고 정하지 않습니다.[^collectors]

| 수집기 | 중심 특징 | 기초 기억 |
| --- | --- | --- |
| `Serial` | 주요 수집을 단일 작업자로 수행 | 단순한 구조 |
| `Parallel` | 여러 작업자로 수집하여 처리량을 중시 | 수집의 병렬화 |
| `G1` | 힙을 영역 단위로 관리하고 정지 목표를 고려 | 영역·혼합 수집·지연 목표 |
| `ZGC` | 많은 작업을 애플리케이션과 동시 수행하며 짧은 정지를 지향 | 저지연 목적 |
| `Shenandoah` | 객체 이동을 포함한 동시 작업으로 정지 시간을 줄이는 방향 | 배포판의 지원 확인 |
| `Epsilon` | 할당은 하지만 메모리 회수는 하지 않음 | 특수한 측정·시험 목적 |

마지막 두 수집기의 목적은 각 프로젝트 설명을 함께 확인합니다. 지원 여부는 배포판과 실행 환경에 따라 다릅니다.[^shenandoah][^epsilon]

| 비교 | 의미 |
| --- | --- |
| 병렬 수집 | 수집 작업자 여러 개가 함께 작업 |
| 동시 수집 | 수집 작업과 애플리케이션 작업이 겹쳐 진행 |
| 처리량 목표 | 전체 시간 중 애플리케이션 작업에 쓰는 비중을 중시 |
| 정지 시간 목표 | 개별 중단을 짧게 하는 데 관심 |

**동시 수집이라고 정지가 전혀 없다는 뜻은 아닙니다.** 또한 `G1`의 정지 시간 목표는 모든 환경에서 지켜지는 절대적인 실시간 기한이 아닙니다.

**버전 주의:** 수집기 기본값·세대형 지원·옵션은 달라집니다. 예를 들어 자바 21 계열과 이후 버전의 `ZGC` 세대형 선택 방식을 하나로 섞지 않습니다. 구형 수집기가 최신 실행 환경에도 그대로 존재한다고 가정하지 않습니다.

기초 문제에서는 **목적과 차이**를 먼저 구분합니다. 실제 선택은 사용 중인 배포판, 객체 수명, 할당량, 응답 목표, 측정 결과를 함께 봅니다.

### 128. 참조 종류와 객체 정리

**참조의 종류는 객체를 얼마나 강하게 살려두는지와 회수 알림을 어떻게 받는지에 영향을 줍니다.** 일반 참조와 참조 객체의 `get()` 결과를 구분합니다.[^references]

| 참조 | 대표 형태 | 특징 |
| --- | --- | --- |
| 강한 참조 | 일반 변수·필드의 객체 참조 | 살아 있는 경로가 있으면 대상을 유지 |
| 소프트 참조 | `SoftReference` | 메모리 상황에 따라 회수될 수 있음 |
| 약한 참조 | `WeakReference` | 강하게 유지할 필요 없는 연결에 사용 |
| 팬텀 참조 | `PhantomReference` | 대상 객체를 꺼내기보다 회수 이후 정리 관찰에 사용 |

**참조 큐**는 수집기에 의해 처리된 참조 객체를 받아 후속 정리를 연결하는 데 사용합니다. 큐에 들어오는 것은 대상 객체 자체가 아니라 해당 참조 객체입니다.

```java
import java.lang.ref.PhantomReference;
import java.lang.ref.Reference;
import java.lang.ref.ReferenceQueue;
import java.lang.ref.WeakReference;

public class Main {
    public static void main(String[] 인수) {
        Object 대상 = new Object();
        WeakReference<Object> 약한참조 = new WeakReference<>(대상);
        PhantomReference<Object> 팬텀참조 =
            new PhantomReference<>(대상, new ReferenceQueue<>());

        System.out.println(약한참조.get() == 대상);
        System.out.println(팬텀참조.get() == null);
        약한참조.clear();
        System.out.println(약한참조.get() == null);
        Reference.reachabilityFence(대상);
    }
}
```

출력:

```text
true
true
true
```

여기서는 `System.gc()`의 실행 시점에 기대지 않습니다. 강한 참조를 유지하고, 약한 참조를 명시적으로 비우는 동작을 비교했습니다. 팬텀 참조의 `get()`은 항상 `null`입니다.[^phantom]

`reachabilityFence`는 해당 지점까지 대상이 강하게 도달 가능한 상태로 유지되게 하는 보충 기능입니다. 마지막 사용을 앞당겨 판단할 수 있는 최적화와 관련되며, 기본적인 자원 해제의 대체품은 아닙니다.

| 정리 방식 | 의미 | 주의 |
| --- | --- | --- |
| `close()`·자동 자원 해제 | 코드가 자원 수명 끝을 명시 | 파일·연결 등의 우선적인 관리 방식 |
| `Cleaner` | 대상의 도달 불가능 상태와 정리 동작을 연결 | 실행 시점에 의존하지 말고 보조적으로 사용 |
| `finalize()` | 구형 객체 종료 처리 | 자바 21에서 제거 예정 비권장 기능 |
| `System.gc()` | 메모리 회수 노력 요청 | 즉시·반드시·특정 객체 회수 보장 아님 |

`Cleaner`의 정리 동작이 원래 대상을 강하게 캡처하면 대상을 계속 살려두는 문제가 생길 수 있습니다. 정리 상태를 분리합니다.[^cleaner][^object][^system]

<mark>자동 메모리 회수는 파일·소켓·데이터베이스 연결을 필요한 순간에 닫아주는 보장이 아닙니다.</mark>

### 129. 실행 중 컴파일과 최적화 — 보충

**실행 중 컴파일은 실행 정보를 이용해 자주 쓰는 코드를 기계어로 바꾸는 방식입니다.** 소스를 클래스 파일로 만드는 컴파일과 구분합니다.[^vm-performance]

| 개념 | 의미 |
| --- | --- |
| 인터프리터 | 바이트코드 의미에 따라 실행 |
| 실행 중 컴파일 | 실행 중 대상 코드를 기계어로 변환 |
| 계층적 컴파일 | 준비 비용과 최적화 정도가 다른 실행 단계를 활용 |
| 프로파일링 | 자주 실행되는 경로·타입 등 정보를 수집 |
| 인라이닝 | 작은 호출의 본문을 호출 위치에 결합하여 최적화 |
| 탈출 분석 | 객체가 메서드·스레드 밖으로 전달되는지 분석 |
| 스칼라 치환 | 객체를 구성 값들로 대체하여 실제 할당을 제거할 수 있음 |
| 잠금 제거 | 다른 스레드와 공유되지 않는 등 안전한 조건에서 불필요한 잠금 제거 |
| 실행 중 교체 | 이미 진행 중인 반복문 등을 최적화된 코드로 전환 |
| 최적화 취소 | 최적화 가정이 깨지면 적절한 실행 상태로 복귀 |

**중요한 구분:** 탈출하지 않는 객체가 반드시 스택에 그대로 할당된다고 설명하지 않습니다. 실제 객체의 할당 자체가 제거되고 값만 남는 최적화도 있습니다.

```text
소스 관점: 작은 객체를 만들고 두 필드를 더함
최적화 가능성: 객체 전체를 만들지 않고 필요한 값만 계산

보장: 자바 프로그램이 관찰할 수 있는 올바른 의미는 유지
비보장: 소스의 new 개수만큼 반드시 실제 힙 할당이 발생
```

준비 실행을 거치기 전과 후의 시간은 달라질 수 있습니다. 결과를 사용하지 않는 단순 반복 측정은 계산 자체가 제거되는 등 함정이 있습니다. 성능 검증은 다음 편의 측정 도구에서 이어 다룹니다.

**선택 심화:** 내장 최적화는 특정 연산을 실행 환경이 특별한 구현으로 대체하는 것입니다. 특정 메서드가 항상 같은 기계어로 바뀐다는 식으로 버전과 처리 장치를 무시하지 않습니다.

### 130. 메모리·실행 장애의 분류

**메모리 문제는 힙 부족 하나로 설명되지 않습니다.** 오류 종류·메시지·시점·참조 경로를 함께 확인합니다.[^vm-structure][^troubleshoot]

| 증상·오류 | 대표 원인 후보 | 먼저 구분할 점 |
| --- | --- | --- |
| 힙 관련 `OutOfMemoryError` | 객체가 너무 많거나 계속 참조됨 | 최대 힙과 살아 있는 객체량 |
| 메타데이터 관련 부족 | 동적 클래스·클래스 로더가 누적됨 | 클래스와 정의 로더의 수명 |
| 직접 버퍼 관련 부족 | 힙 밖 메모리 사용·제한 | 힙 수치만으로 판단하지 않음 |
| 네이티브 스레드 생성 실패 | 스레드 수·운영체제 한도·네이티브 메모리 | 작업자 수와 자원 제한 |
| `StackOverflowError` | 지나치게 깊은 호출·재귀 | 호출 깊이·종료 조건 |
| 실행 중단·강제 종료 | 운영체제나 컨테이너의 메모리 제한 | 자바 예외가 남지 않을 수도 있음 |
| 반복적인 긴 수집 | 할당 압박·살아 있는 객체량·설정 | 수집 로그와 지연 측정 |

**메모리 누수**는 더 이상 필요하지 않지만 참조가 남아 회수할 수 없는 상황에서도 발생합니다. 자동 수집 기능의 존재만으로 누수가 없어지는 것은 아닙니다.

| 누수 경로 예 | 이유 | 검토 방향 |
| --- | --- | --- |
| 무제한 정적 목록·캐시 | 살아 있는 클래스가 자료를 계속 유지 | 크기·만료·제거 정책 |
| 등록 후 해제하지 않은 청취자 | 등록 기관이 객체를 계속 참조 | 수명에 맞춰 등록 해제 |
| 스레드 지역 값 | 오래 사는 작업자에 자료가 남음 | 작업 경계에서 제거 |
| 플러그인 클래스 로더 | 다른 참조가 로더를 붙잡음 | 작업자·등록 자료·문맥 연결 해제 |
| 큐에 쌓이는 작업 | 처리보다 제출이 빠름 | 대기열 제한·흐름 제어 |

**스레드 덤프**는 실행·대기·잠금 상태를, **힙 덤프**는 객체와 참조 경로를 보는 자료입니다. 수집 로그는 회수 횟수·시간·메모리 변화를 보는 데 사용합니다.

덤프에는 애플리케이션의 실제 값이 포함될 수 있습니다. 공유 전 민감한 내용을 확인합니다. 무작정 메모리를 늘리거나 가비지 컬렉션을 요청하기 전에 **무엇이 무엇을 붙들고 있는가**를 찾습니다.

## 16부. 리플렉션·모듈·코드 생성·외부 함수

### 131. 리플렉션과 실행 시 타입 정보

**리플렉션은 실행 중에 타입의 필드·메서드·생성자 등을 조사하고, 허용된 범위에서 동적으로 접근하는 기능입니다.** 타입 이름을 소스에 모두 고정하기 어려운 도구나 프레임워크에 사용됩니다.[^class][^accessible]

| 구성 | 나타내는 것 |
| --- | --- |
| `Class` | 실행 시 타입 정보 |
| `Field` | 필드 정보·읽기·쓰기 |
| `Method` | 메서드 정보·호출 |
| `Constructor` | 생성자 정보·객체 생성 |
| 애너테이션 조회 | 실행 시 보존된 메타정보 |
| 제네릭 타입 조회 | 선언에 남아 있는 타입 인수·경계 정보 등 |

```java
import java.lang.reflect.Method;

public class Main {
    static class 부모 {
        public void 상속함수() { }
    }
    static class 자식 extends 부모 {
        private int 점수 = 80;
        public int 두배(int 값) { return 값 * 2; }
    }
    public static void main(String[] 인수) throws Exception {
        Class<?> 타입 = 자식.class;
        System.out.println(타입.getMethod("상속함수").getDeclaringClass() == 부모.class);
        System.out.println(타입.getDeclaredField("점수").getType() == int.class);
        Method 메서드 = 타입.getMethod("두배", int.class);
        System.out.println(메서드.invoke(new 자식(), 6));
    }
}
```

출력:

```text
true
true
12
```

| 조회 방식 | 공개 멤버 | 비공개 멤버 | 상속 멤버 |
| --- | --- | --- | --- |
| `getMethods()`·`getFields()` | 조회 | 직접 포함하지 않음 | 공개 멤버 포함 |
| `getDeclaredMethods()`·`getDeclaredFields()` | 조회 | 조회 | 해당 타입에 직접 선언한 것만 |
| `getConstructors()` | 공개 생성자 | 제외 | 생성자는 상속되지 않음 |
| `getDeclaredConstructors()` | 해당 타입의 생성자 | 포함 | 생성자는 상속되지 않음 |

**조회와 접근 허가는 다릅니다.** 비공개 필드의 존재를 알아냈다고 언제나 읽고 쓸 수 있는 것은 아닙니다. `setAccessible(true)`도 모든 모듈의 캡슐화를 무조건 해제하지 못합니다. `trySetAccessible()`은 허용 여부에 따라 실패할 수 있습니다.

**실행 시 애너테이션**

```java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

public class Main {
    @Retention(RetentionPolicy.RUNTIME)
    @interface 표시 { String value(); }

    @표시("학습")
    static class 자료 { }

    public static void main(String[] 인수) {
        System.out.println(자료.class.isAnnotationPresent(표시.class));
        System.out.println(자료.class.getAnnotation(표시.class).value());
    }
}
```

출력:

```text
true
학습
```

`SOURCE`는 소스 단계, `CLASS`는 클래스 파일까지 보존하는 정책이며, 일반 리플렉션으로 읽으려면 `RUNTIME` 보존이 필요합니다. 보존 정책을 생략하면 기본은 `CLASS`입니다.[^annotations]

**잘 놓치는 점:** 제네릭 타입 소거가 있어도 필드·메서드의 선언 시그니처에 제네릭 정보가 남을 수 있습니다. 반대로 임의의 목록 객체를 보고 실행 중 원소 타입 인수를 항상 복원할 수 있는 것은 아닙니다.

`final` 필드를 바꾸는 것은 정상적인 설계 수단이 아닙니다. 자바 21에서도 정적 `final`, 레코드의 `final` 등에는 리플렉션 쓰기 제한이 있으며, 후속 버전의 경고·허용 정책도 따로 확인해야 합니다.

**보충:** 리플렉션 호출 대상이 던진 예외는 `InvocationTargetException`에 감싸질 수 있습니다. 메서드 배열의 반환 순서가 소스 선언 순서라고 가정하지 않습니다.

### 132. 동적 프록시

**동적 프록시는 인터페이스의 호출을 중간 처리기로 보내 부가 동작을 수행하는 대리 객체입니다.** 로깅·접근 검사·실행 시간 측정 등에서 호출의 앞뒤를 감쌀 수 있습니다.[^proxy]

```java
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Proxy;

public class Main {
    interface 계산 { int 두배(int 값); }

    public static void main(String[] 인수) {
        계산 원본 = 값 -> 값 * 2;
        계산 대리 = (계산) Proxy.newProxyInstance(
            계산.class.getClassLoader(),
            new Class<?>[] { 계산.class },
            (대리객체, 메서드, 매개값) -> {
                if (메서드.getDeclaringClass() == Object.class) {
                    return switch (메서드.getName()) {
                        case "equals" -> 대리객체 == 매개값[0];
                        case "hashCode" -> System.identityHashCode(대리객체);
                        case "toString" -> "학습용 계산 프록시";
                        default -> throw new UnsupportedOperationException();
                    };
                }
                System.out.println("호출 전");
                try {
                    return 메서드.invoke(원본, 매개값);
                } catch (InvocationTargetException 예외) {
                    throw 예외.getCause();
                } finally {
                    System.out.println("호출 후");
                }
            });
        System.out.println(대리.두배(6));
        System.out.println(Proxy.isProxyClass(대리.getClass()));
    }
}
```

출력:

```text
호출 전
호출 후
12
true
```

호출 흐름은 **사용자 코드 → 대리 객체 → 호출 처리기 → 원본 객체**입니다. 위 예제는 객체 기본 메서드에 대해서는 대리 객체의 정체성을 기준으로 별도 처리했습니다.

| 구분 | 표준 동적 프록시 | 상속 기반 프록시 |
| --- | --- | --- |
| 중심 | 인터페이스 구현 | 클래스의 하위 타입 |
| 표준 도구 | `Proxy`·`InvocationHandler` | 보통 외부 라이브러리 사용 |
| 적용 범위 | 프록시 인터페이스의 호출 | 상속·재정의가 가능한 호출 |
| 대표 제약 | 임의의 클래스를 그대로 상속하는 도구가 아님 | `final` 클래스·메서드 등 제약 |

**주의:** 처리기 안에서 원본이 아닌 대리 객체에 같은 메서드를 다시 호출하면 재귀 호출로 빠질 수 있습니다. 원본 객체 내부에서 자신을 직접 호출하는 동작이 항상 외부 프록시를 다시 거친다고 가정하지도 않습니다.

프록시는 모든 보안 문제를 자동 해결하는 장치가 아니라 호출 경로를 중간 처리하는 방법입니다.

### 133. 메서드 핸들과 바이트코드 조작 — 선택 심화

**메서드 핸들은 타입이 정해진 실행 가능한 동작에 대한 참조입니다.** 메서드뿐 아니라 생성·필드 접근 등을 조합하는 낮은 수준의 실행 도구와 연결됩니다.[^methodhandle]

```java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

public class Main {
    public static int 두배(int 값) { return 값 * 2; }

    public static void main(String[] 인수) throws Throwable {
        MethodHandle 손잡이 = MethodHandles.lookup().findStatic(
            Main.class, "두배", MethodType.methodType(int.class, int.class));
        int 결과 = (int) 손잡이.invokeExact(7);
        System.out.println(결과);
    }
}
```

출력:

```text
14
```

| 구성 | 의미 |
| --- | --- |
| `MethodType` | 반환형과 매개변수형 |
| `MethodHandles.Lookup` | 어떤 접근 권한으로 대상을 찾는지 |
| `MethodHandle` | 호출할 동작에 대한 타입 있는 참조 |
| `invokeExact` | 호출 지점의 타입이 정확하게 맞아야 하는 호출 |
| `invoke` | 허용되는 타입 변환을 적용할 수 있는 호출 |
| 호출 지점 | 동적으로 연결되는 동작의 위치 |

핸들의 타입과 호출 지점이 맞지 않으면 `WrongMethodTypeException` 등이 발생할 수 있습니다. `invokeExact`의 반환값을 아무 타입으로 받아도 알아서 변환해 준다고 생각하지 않습니다.

**변수 핸들**은 필드·배열 요소 등의 메모리 접근과 원자 연산을 다룹니다.[^varhandle]

```java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;

public class Main {
    private int 점수;

    public static void main(String[] 인수) throws Exception {
        VarHandle 손잡이 = MethodHandles.lookup()
            .findVarHandle(Main.class, "점수", int.class);
        Main 대상 = new Main();
        System.out.println(손잡이.compareAndSet(대상, 0, 7));
        System.out.println((int) 손잡이.getVolatile(대상));
    }
}
```

출력:

```text
true
7
```

이렇게 원자 연산을 사용할 수 있어도 다른 코드가 같은 필드를 임의의 방식으로 읽고 쓰면 전체 설계를 다시 검토해야 합니다. 단순 원자 변수면 충분한 상황에서 더 낮은 수준의 기능을 먼저 사용할 필요는 없습니다.

**코드 생성·변환의 지도**

| 기능 | 시점·목적 |
| --- | --- |
| 자바 24의 클래스 파일 처리 기능 | 클래스 파일 읽기·생성·변환 |
| `Instrumentation` | 에이전트를 통한 클래스 바이트 변환·계측 등 |
| 자바 에이전트 | 시작 시 또는 지원되는 연결 방식으로 계측 기능 참여 |
| 가상 머신 도구 인터페이스 | 네이티브 도구가 실행 상태를 관찰·제어하는 전문 기능 |

클래스 파일 처리 기능은 자바 24 정식 기능입니다. 이미 로딩된 클래스를 바꾸는 계측에는 변경 가능한 구조의 제약이 있으므로, 아무 필드·메서드나 무제한으로 추가할 수 있다고 보지 않습니다.[^classfile-api][^instrument]

### 134. 컴파일러와 애너테이션 처리 — 보충

**프로그램은 표준 도구 인터페이스를 통해 자바 컴파일러를 사용할 수 있습니다.** 다만 실행 이미지에 컴파일러가 포함되어 있는지 확인해야 합니다.[^toolprovider]

```java
import javax.tools.ToolProvider;

public class Main {
    public static void main(String[] 인수) {
        System.out.println(ToolProvider.getSystemJavaCompiler() != null);
    }
}
```

출력:

```text
true
```

이 출력은 **자바 21 개발 도구가 포함된 이 글의 검사 환경** 기준입니다. 컴파일러를 포함하지 않은 사용자 정의 실행 이미지에서는 `null`일 수 있습니다. 이 코드는 존재 확인이며 소스 컴파일 작업 자체를 수행하지는 않습니다.

| 구성 | 목적 |
| --- | --- |
| `JavaCompiler` | 컴파일 작업 생성·실행 |
| 진단 수집기 | 경고·오류·위치 정보 수집 |
| 파일 관리자 | 소스·클래스·자원 접근 |
| 언어 모델 | 타입·멤버·매개변수 등의 선언 정보 표현 |
| 애너테이션 처리기 | 컴파일 과정에서 선언을 읽고 추가 소스·자원 등을 생성 |

**애너테이션은 표시이고, 처리기는 그 표시를 해석하는 코드입니다.** 표시를 붙이기만 했다고 모든 표시가 자동으로 특별한 실행 동작을 만들지는 않습니다.[^processing]

```text
원본 소스 읽기
    → 애너테이션 처리 단계
    → 필요한 소스·자원 생성
    → 생성된 소스에 대한 추가 처리 라운드 가능
    → 일반적인 타입 검사와 클래스 파일 생성 과정
```

| 비교 | 애너테이션 처리 | 리플렉션 |
| --- | --- | --- |
| 대표 시점 | 컴파일 중 | 프로그램 실행 중 |
| 관찰 대상 | 선언·언어 모델 | 로딩된 타입 정보 |
| 대표 결과 | 생성 소스·자원·진단 | 동적 조사·호출·접근 |
| 보존 정책 | 소스 단계 정보도 활용 가능 | 일반적으로 실행 시 보존이 필요 |

**버전 주의:** 자바 23 이후의 컴파일러에서는 자동 탐색만 기대하지 말고 `-processor`, 처리기 경로, `-proc:full` 등 문서에 따른 명시적인 설정을 확인합니다. 명령의 의미와 보안 정책을 읽고 필요한 처리기만 활성화합니다.[^javac]

임의로 받은 소스를 서버에서 컴파일·실행하면 별도의 보안·자원 격리 문제가 생깁니다. 컴파일 기능이 있다고 신뢰할 수 없는 코드를 안전하게 실행하는 환경이 저절로 생기는 것은 아닙니다.

### 135. 모듈 시스템과 서비스 로딩

**모듈은 패키지들의 집합에 의존성과 공개 범위를 선언하는 단위입니다.** 패키지 이름만 나누는 것보다 강한 경계를 만들 수 있습니다.[^modules]

| 단위 | 의미 |
| --- | --- |
| 클래스 | 상태·동작을 정의하는 타입 |
| 패키지 | 타입의 이름 공간과 접근 단위 |
| 모듈 | 패키지 집합의 의존성·공개·서비스 선언 |
| 자바 아카이브 | 클래스·자원을 묶는 배포 파일 형식 |

일반적으로 `module-info.java`에 모듈을 선언합니다. 다음은 별도 프로젝트의 **설정 예시**이며, `Main.java` 안에 붙이는 코드가 아닙니다.

```text
module 학습.업무 {
    requires java.sql;
    exports 학습.업무.공개;
    opens 학습.업무.자료;
}
```

| 선언 | 의미 |
| --- | --- |
| `requires` | 의존 모듈을 읽을 수 있게 함 |
| `requires transitive` | 나를 읽는 모듈에도 해당 의존성의 읽기 관계를 전달 |
| `requires static` | 컴파일 시 필요하지만 실행 시 의존성을 선택적으로 둘 수 있음 |
| `exports` | 패키지의 공개 타입을 다른 모듈에서 사용할 수 있게 함 |
| `opens` | 실행 시 깊은 리플렉션 접근을 허용하는 경계 |
| `exports ... to ...` | 지정한 모듈에만 공개 |
| `opens ... to ...` | 지정한 모듈에만 리플렉션 개방 |
| `uses` | 특정 서비스 타입을 사용 |
| `provides ... with ...` | 특정 서비스의 구현 제공 |

**`exports`와 `opens`를 구분합니다.** 공개된 패키지라고 모든 비공개 필드를 깊은 리플렉션으로 읽을 수 있는 것은 아닙니다. 반대로 `opens`만 썼다고 그 패키지의 타입을 다른 모듈 소스에서 일반적인 방식으로 가져다 쓸 수 있는 것도 아닙니다.

**`public` 하나만으로 충분하지 않을 수 있습니다.** 모듈 사이의 읽기 관계와 해당 패키지의 공개 여부까지 함께 맞아야 합니다.

```java
public class Main {
    public static void main(String[] 인수) {
        System.out.println(String.class.getModule().getName());
        System.out.println(String.class.getModule().isNamed());
        System.out.println(Main.class.getModule().isNamed());
    }
}
```

출력:

```text
java.base
true
false
```

이 예제는 `module-info.java` 없이 일반 클래스 경로에서 실행했습니다. 따라서 `Main`은 이름 없는 모듈에 속합니다. 이름 있는 모듈 프로젝트로 옮기면 마지막 결과는 달라집니다.

| 구분 | 특징 |
| --- | --- |
| 명시적 모듈 | 모듈 선언을 가짐 |
| 자동 모듈 | 선언 없는 일반 아카이브를 모듈 경로에 놓아 모듈로 취급 |
| 이름 없는 모듈 | 일반 클래스 경로의 코드를 위한 모듈 |
| 클래스 경로 | 전통적인 클래스·자원 탐색 경로 |
| 모듈 경로 | 모듈을 찾는 경로 |

**서비스 로딩**은 사용자가 구체 구현 클래스를 모두 고정하지 않고 서비스 타입을 기준으로 제공자를 찾는 기능입니다.[^service]

```text
서비스 계약: 보고서를 만드는 기능
제공자 하나: 간단한 보고서 구현
제공자 둘: 상세한 보고서 구현
소비자: 서비스 타입으로 제공자를 찾아 사용
```

모듈에서는 `uses`와 `provides`를 사용합니다. 전통적인 클래스 경로에서는 `META-INF/services/서비스의전체이름` 형태의 제공자 설정 파일을 사용할 수 있습니다. 서비스 제공자 탐색·생성은 지연될 수 있으므로 설정 오류가 순회 중 나타날 수 있습니다.

**보충:** `requires static`이라고 필요한 타입을 실제로 사용하는 모든 실행까지 자동으로 안전해지는 것은 아닙니다. 선택 의존성이 없을 때 그 기능을 사용하지 않도록 설계해야 합니다.

**버전 보충:** 자바 25의 모듈 가져오기는 소스에서 타입 이름을 편리하게 사용하는 기능입니다. 모듈의 접근 권한을 무시하거나 패키지를 자동으로 공개하는 기능으로 이해하지 않습니다.[^module-import]

### 136. 네이티브 코드와 외부 메모리 — 선택 심화

**네이티브 연동은 자바 바깥의 기계어 코드나 메모리와 연결하는 기능입니다.** 자바의 일반 객체 접근보다 수명·경계·운영체제 의존성을 더 주의해야 합니다.[^foreign][^jni]

| 방식 | 역할 |
| --- | --- |
| 네이티브 인터페이스 | 자바와 외부 언어 코드 사이의 기존 연결 규약 |
| `native` 메서드 | 본문 구현을 자바 바깥에서 연결하는 메서드 선언 |
| 직접 버퍼 | 자바 힙 바깥의 메모리 등을 사용하는 버퍼 |
| 외부 함수·메모리 기능 | 외부 함수 호출과 명시적 메모리 구역 관리 |

**먼저 자바 21에서 직접 메모리 버퍼를 확인합니다.** 이것은 자바 22의 외부 함수·메모리 예제를 대신 실행한 것이 아니라, 힙 밖 메모리와 자바 객체의 구분을 보여주는 기존 표준 기능입니다.[^bytebuffer]

```java
import java.nio.ByteBuffer;

public class Main {
    public static void main(String[] 인수) {
        ByteBuffer 버퍼 = ByteBuffer.allocateDirect(Integer.BYTES);
        버퍼.putInt(0, 42);
        System.out.println(버퍼.isDirect());
        System.out.println(버퍼.getInt(0));
    }
}
```

출력:

```text
true
42
```

버퍼를 조작하는 자바 객체와 실제 데이터 저장 메모리는 구분됩니다. 직접 버퍼도 한도가 있고, 모든 상황에서 일반 힙 버퍼보다 빠르다는 보장은 없습니다.

**외부 함수·메모리 기능은 자바 22 정식 기능입니다.** 아래는 구현 코드가 아닌 구성요소 지도입니다.[^foreign]

| 구성 | 역할 |
| --- | --- |
| `MemorySegment` | 범위와 수명을 가진 메모리 구역 |
| `MemoryLayout` | 메모리 안에서 값이 배치되는 구조 |
| `ValueLayout` | 정수 등 개별 값의 배치 |
| `Arena` | 여러 메모리 할당의 수명을 묶는 영역 |
| `Linker` | 외부 함수 호출·자바 콜백 연결 |
| 함수 서술자 | 외부 함수의 반환·인수 메모리 형식 |

```text
수명 영역을 연다.
    → 정해진 크기의 메모리 구역을 할당한다.
    → 형식과 범위를 맞춰 읽고 쓴다.
    → 필요한 외부 함수와 연결한다.
수명 영역을 닫는다.
    → 그 수명에 종속된 구역을 더 이상 사용하지 않는다.
```

| 수명 방식 | 기억할 점 |
| --- | --- |
| 한 스레드에 한정된 영역 | 접근 가능한 스레드와 닫기 시점을 제한 |
| 공유 가능한 영역 | 여러 스레드 접근 가능. 데이터 경쟁은 별도 관리 |
| 자동 관리 영역 | 도달 가능성에 따라 수명 관리 |
| 전역 영역 | 프로그램의 긴 수명과 연결 |

**안전성의 한계:** 자바 측의 범위·수명 검사가 있어도 외부 함수에 잘못된 주소·배치·서명을 넘기면 프로그램이 손상되거나 비정상 종료할 수 있습니다. 네이티브 코드의 모든 오류를 가상 머신이 대신 막는다고 생각하지 않습니다.

기초 수준에서는 **외부 연동의 목적 → 메모리의 크기와 배치 → 소유권과 수명 → 스레드 접근 → 실행 환경의 네이티브 접근 허용** 순서만 잡습니다. 실제 실행 옵션과 허용 정책은 사용 버전에서 확인합니다.

<a id="pitfalls"></a>

## 잘 놓치는 핵심

### 1. 코드 한 줄과 원자적 연산은 다릅니다

`값++`는 읽기·계산·쓰기가 결합된 연산입니다. `volatile`만 붙여도 한 번의 원자적 증가가 되지는 않습니다. 또한 원자 변수 두 개를 각각 갱신해도 둘 사이의 관계가 자동으로 함께 보호되지는 않습니다.[^memory-model][^atomic]

### 2. 먼저 시작·먼저 종료·먼저 출력은 다릅니다

먼저 `start()`한 작업이 먼저 종료할 필요는 없습니다. 결과를 주 스레드에서 첫째·둘째 순서로 꺼내 출력하면 실제 완료 순서와 다른 순서로 출력할 수도 있습니다. 문제에서 묻는 것이 실행 순서인지 출력 순서인지 구분합니다.[^thread][^future]

### 3. 잠금은 표시가 아니라 같은 대상에 대한 규칙입니다

같은 필드를 보호하려는데 작업마다 다른 객체를 잠그면 상호 배제가 성립하지 않습니다. 인스턴스 잠금과 정적 메서드의 클래스 잠금도 다른 대상입니다.[^memory-model]

### 4. 기다린 시간과 동기화는 다릅니다

“충분히 오래 잤다”는 이유로 다른 스레드의 완료·가시성이 보장되지 않습니다. `join`, 래치, 잠금, 결과 획득 등 명시된 연결을 찾습니다. 시간 있는 대기가 끝났다는 사실과 대상의 종료 확인도 구분합니다.[^thread][^latch]

### 5. 알림과 잠금 양도는 다릅니다

`notify()`를 호출한 스레드는 모니터를 즉시 놓지 않습니다. 깨어난 쪽은 모니터를 다시 얻어야 진행할 수 있으며 조건을 재검사해야 합니다.[^object]

### 6. 결과의 완료와 업무의 성공은 다릅니다

`Future.isDone()`은 예외와 취소도 포함합니다. 시간 초과도 외부 작업의 취소와 동일하지 않습니다. 결과 객체의 상태와 실제 실행·외부 자원의 상태를 함께 봅니다.[^future][^completable]

### 7. 스레드 안전한 컬렉션과 안전한 값 객체는 다릅니다

동시성 맵에 일반 가변 목록을 넣었다고 목록 내부까지 스레드 안전해지지 않습니다. 키 하나의 원자적 연산과 여러 키를 아우르는 업무 전체의 원자성도 구분합니다.[^concurrent-map]

### 8. 스레드별 저장과 요청별 수명은 다릅니다

풀의 작업자는 여러 요청을 처리합니다. 이전 요청의 스레드 지역 값을 지우지 않으면 새 요청이 그 값을 읽을 수 있습니다. 범위 지정 값도 가변 객체 자체의 안전성을 대신 보장하지는 않습니다.[^threadlocal][^scoped]

### 9. 로딩·초기화·객체 생성은 다릅니다

클래스 리터럴이나 배열 원소 타입의 사용만으로 정적 초기화가 반드시 실행되지 않습니다. 정적 초기화는 해당 런타임 타입에 대해 한 번이며, 객체 생성자는 객체를 만들 때마다 실행됩니다.[^execution]

### 10. 참조를 지우는 것과 회수 시점은 다릅니다

다른 강한 참조가 남아 있으면 대상을 유지합니다. 전부 없어져도 언제 회수되는지는 별도입니다. 순환 연결만으로는 외부 도달 경로가 생기지 않습니다.[^references]

### 11. 기본형·참조형과 힙·스택은 같은 분류가 아닙니다

자료형은 값의 종류이고, 메모리 영역은 실행 상태를 관리하는 구조입니다. 객체의 정수 필드는 기본형이지만 그 객체의 데이터이고, 지역 참조 변수는 호출 상태에 포함됩니다.[^vm-structure]

### 12. 볼 수 있는 정보와 사용할 수 있는 권한은 다릅니다

리플렉션으로 비공개 멤버를 조회하는 것과 실제로 접근하는 것은 다릅니다. 모듈의 `exports`는 일반 사용 경계이고, `opens`는 깊은 리플렉션 경계와 관련됩니다.[^accessible][^modules]

### 핵심 암기표

| 질문 | 한 문장 답 |
| --- | --- |
| `run()`을 직접 호출하면? | 현재 호출 흐름에서 일반 메서드처럼 실행됩니다. |
| 같은 스레드 객체를 두 번 시작할 수 있는가? | 종료 후에도 다시 `start()`할 수 없습니다. |
| `join()`은 누가 기다리는가? | 호출한 스레드가 대상의 종료를 기다립니다. |
| 인터럽트는 강제 종료인가? | 작업이 감지하고 협력해야 하는 중단 요청입니다. |
| `Thread.interrupted()`의 함정은? | 현재 스레드의 상태를 확인하면서 지웁니다. |
| `sleep()`은 모니터를 놓는가? | 보유한 모니터를 놓지 않습니다. |
| `wait()`에서 왜 반복 조건을 쓰는가? | 허위 깨움과 조건 변화에 대비해 다시 검사합니다. |
| `volatile`은 증가를 원자적으로 만드는가? | 읽기·쓰기 보장과 복합 증가의 원자성은 다릅니다. |
| `final` 참조는 객체를 불변으로 만드는가? | 재대입 제한과 내부 변경은 다릅니다. |
| 공정 잠금이면 실행 순서가 절대 보장되는가? | 잠금 정책과 운영체제의 실행 순서는 다릅니다. |
| 원자적 증가의 결과가 필요하면? | 반환 전후를 구분해 원자 변수의 결합 연산을 사용합니다. |
| `ThreadLocal`의 주요 관리 지점은? | 재사용되는 스레드의 작업 종료 경계입니다. |
| `isDone()`이 참이면 성공인가? | 실패·취소도 완료에 포함됩니다. |
| `shutdown()`은 기다리는가? | 종료를 요청하며 완료 대기는 별도로 합니다. |
| 가상 스레드는 무엇을 개선하는가? | 많은 대기 작업의 실행 확장성을 개선합니다. |
| 클래스 초기화와 생성자는 같은가? | 타입의 준비와 객체의 초기화는 다릅니다. |
| 같은 이름은 같은 클래스인가? | 정의한 클래스 로더까지 확인합니다. |
| 객체가 서로 참조하면 못 지우는가? | 외부의 살아 있는 도달 경로가 없으면 회수 후보입니다. |
| `System.gc()`는 회수를 보장하는가? | 요청일 뿐 특정 시점과 객체 회수를 보장하지 않습니다. |
| `getDeclaredMethods()`는 상속 멤버를 모두 주는가? | 해당 타입에 직접 선언된 메서드를 대상으로 합니다. |
| `exports`와 `opens`가 같은가? | 일반 접근 공개와 리플렉션 개방은 구분됩니다. |
| 애너테이션 처리와 리플렉션의 차이는? | 대표적으로 컴파일 중 처리와 실행 중 조사입니다. |

각 답의 조건과 예외는 본문의 해당 절을 기준으로 합니다. 특히 `join()`은 종료를 실제로 확인했는지, 메모리 배치는 명세와 구현 중 어느 설명인지까지 함께 읽습니다.

### 면접에서 이유까지 설명하는 답변

**질문: 자동 메모리 회수가 있는데 왜 누수가 생기나요?**

“프로그램이 더 이상 쓰지 않아도 정적 목록이나 청취자 등록처럼 살아 있는 참조가 남으면 도달 가능한 객체입니다. 수집기는 업무상 필요 없는 것까지 판단하는 것이 아니라 도달 가능성에 따라 회수하므로, 무엇이 객체를 붙들고 있는지 확인해야 합니다.”[^references][^troubleshoot]

**질문: 동기화된 메서드를 썼는데 왜 결과가 틀릴 수 있나요?**

“서로 다른 객체를 잠갔거나, 관련된 여러 메서드 호출을 하나의 업무로 묶지 않았을 수 있습니다. 같은 잠금으로 보호하는 상태가 무엇인지와 확인·변경 전체가 하나의 임계 구역인지 확인합니다.”[^memory-model]

**질문: 가상 스레드를 쓰면 풀과 자원 제한이 필요 없나요?**

“가상 스레드 자체는 작업마다 생성하는 방향이지만 데이터베이스 연결 같은 외부 자원은 여전히 제한됩니다. 스레드의 비용을 줄이는 것과 외부 시스템에 보낼 작업 수를 제한하는 문제는 나눠 설계해야 합니다.”[^virtual]

## 예시로 한 바퀴

### 작업 제출·실패·공유 집계·문맥 정리 연결

정수 입력 네 개를 처리합니다. 양수 입력은 열 배로 계산하고, 음수 입력은 실패로 처리합니다. 성공 수와 점수 합은 같은 집계 객체의 잠금으로 함께 변경합니다.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Main {
    private static final ThreadLocal<String> 요청이름 = new ThreadLocal<>();

    record 결과(String 이름, int 점수) { }
    record 요약(int 성공수, int 점수합) { }

    static class 집계 {
        private int 성공수;
        private int 점수합;

        synchronized void 기록(int 점수) {
            성공수++;
            점수합 += 점수;
        }
        synchronized 요약 읽기() {
            return new 요약(성공수, 점수합);
        }
    }

    public static void main(String[] 인수) throws InterruptedException {
        int[] 입력 = { 2, 3, -1, 4 };
        집계 공유집계 = new 집계();
        List<Future<결과>> 결과들 = new ArrayList<>();

        try (ExecutorService 실행기 = Executors.newFixedThreadPool(2)) {
            for (int 순서 = 0; 순서 < 입력.length; 순서++) {
                int 값 = 입력[순서];
                String 이름 = "작업" + (순서 + 1);
                결과들.add(실행기.submit(() -> {
                    요청이름.set(이름);
                    try {
                        if (값 < 0) {
                            throw new IllegalArgumentException("음수 입력");
                        }
                        int 점수 = 값 * 10;
                        공유집계.기록(점수);
                        return new 결과(요청이름.get(), 점수);
                    } finally {
                        요청이름.remove();
                    }
                }));
            }

            for (Future<결과> 미래결과 : 결과들) {
                try {
                    결과 처리 = 미래결과.get();
                    System.out.println(처리.이름() + ": " + 처리.점수());
                } catch (ExecutionException 예외) {
                    System.out.println("실패: " + 예외.getCause().getMessage());
                }
            }
        }

        요약 최종 = 공유집계.읽기();
        System.out.println("성공 수: " + 최종.성공수());
        System.out.println("점수 합: " + 최종.점수합());
    }
}
```

출력:

```text
작업1: 20
작업2: 30
실패: 음수 입력
작업4: 40
성공 수: 3
점수 합: 90
```

### 실행을 여섯 단계로 해석

| 단계 | 코드에서 일어난 일 | 연결 개념 |
| --- | --- | --- |
| 첫째 | 작업을 네 번 제출 | 실행기와 작업의 분리 |
| 둘째 | 각 작업에 필요한 값·이름을 캡처 | 실질적 `final` 지역 변수 |
| 셋째 | 작업자에 요청 이름 설정 | 스레드 지역 저장소 |
| 넷째 | 성공 수·점수 합을 같은 잠금 안에서 변경 | 관련 상태의 임계 구역 |
| 다섯째 | 성공·실패 모두 요청 이름 제거 | `finally`와 문맥 수명 |
| 여섯째 | 결과를 제출 순서로 읽고 최종 요약 조회 | 완료 대기·실패 전파·일관된 읽기 |

**출력이 고정되는 이유:** 네 작업의 실제 완료 순서는 달라도 출력은 주 스레드에서 결과 목록의 순서대로 합니다. 공유 집계의 변경은 동일 객체의 잠금으로 보호하고, 최종 출력 전에는 결과 획득과 실행기 종료를 거칩니다.

**기초 확인:** 람다가 캡처한 `공유집계` 참조를 재대입하지 않는다고 그 내부 필드까지 불변인 것은 아닙니다. 그래서 내부 집계에는 별도의 동기화가 필요합니다.

**실무 확장:** 이 예제는 오류 종류별 재시도, 외부 요청의 제한 시간, 대규모 작업의 대기열 제한을 구현한 운영용 실행기가 아닙니다. 앞의 네 입력을 대상으로 개념을 연결합니다. 작업이 외부 부수효과를 만든 뒤 실패하는 경우에는 집계·재시도의 의미도 별도로 설계합니다.

② getMethods()는 비공개 메서드만 반환한다.

③ 멤버를 조회할 수 있으면 모듈 제한과 무관하게 항상 수정할 수 있다.

④ 실행 시 보존 정책이 없는 모든 애너테이션도 일반 리플렉션으로 항상 조회된다.

## 코드 확인 범위

본문·통합 예제·객관식 문제에 포함된 **독립 실행용 자바 코드 37개**를 `javac --release 21`로 컴파일했습니다. 37개를 각각 실행해 본문과 해설의 출력 결과 37개와 대조했습니다.

검사 환경은 자바 21 개발 도구가 설치된 일반 클래스 경로 실행 환경입니다. 클래스 로더·모듈·컴파일러 조회 예제는 본문에 명시한 이 환경을 전제로 합니다.

구조적 동시성·범위 지정 값·외부 함수·메모리 등 자바 21 이후 기능의 개념 설명과 `text` 설정 예시는 위 컴파일 검사 수에 포함하지 않습니다. 메모리 회수 시점, 성능 수치, 모든 가능한 스레드 스케줄을 검증한 것도 아닙니다.

다음 편은 기존 목차의 **137~150번**입니다. 컴파일과 실행 도구, 의존성 관리, 테스트, 성능 측정과 장애 진단을 정리한 뒤, 설계 원칙과 서버 개발·외부 라이브러리의 관계를 구분합니다.
