이상 현상(Anomaly)은 하나의 Table에 서로 다른 사실이 과도하게 섞여 저장될 때 삽입·수정·삭제 과정에서 데이터 문제가 발생하는 현상입니다.

이 글에서는 정의만 외우지 않고 실제 Table을 어떻게 보고 판단하는지까지 연결합니다.

<blockquote class="prompt-info">
<p>한 줄: 삽입 이상, 수정 이상, 삭제 이상은 정규화가 필요한 대표적인 신호입니다.</p>
</blockquote>

<details>
<summary>한 줄로</summary>

Anomaly = 삽입 이상 + 수정 이상 + 삭제 이상

</details>

| Table | 핵심 Column | 역할 |
| --- | --- | --- |
| DEPARTMENT | DEPT_ID, DEPT_NAME, REGION | 부서 |

정규화 설명에서는 이해를 위해 별도의 작은 예시 Table도 함께 사용합니다.


## 예시 Table

다음처럼 주문, 고객, 상품 정보가 하나의 Table에 모두 들어 있다고 해봅시다.

```text
주문상세_통합

ORDER_ID | ORDER_DATE | CUSTOMER_ID | CUSTOMER_NAME | PRODUCT_ID | PRODUCT_NAME | PRICE | QTY
O1       | 9/1        | C1          | 김고객        | P1         | 키보드       | 50000 | 1
O1       | 9/1        | C1          | 김고객        | P2         | 마우스       | 30000 | 2
O2       | 9/2        | C2          | 이고객        | P1         | 키보드       | 50000 | 1
```

이 구조에서는 같은 고객 이름과 상품 이름이 여러 번 반복됩니다.

## 삽입 이상

새 상품을 등록하고 싶은데 아직 주문이 하나도 없다고 해봅시다.

통합 Table이 주문 정보를 반드시 요구한다면 상품만 독립적으로 넣기 어렵습니다.

```text
새 상품 P3 등록
→ ORDER_ID가 없음
→ 주문 Row 없이는 상품 정보 저장 곤란
```

이것이 삽입 이상입니다.

## 수정 이상

상품 P1의 이름이 `키보드`에서 `기계식 키보드`로 바뀌었다고 해봅시다.

P1이 여러 주문 Row에 반복되어 있다면 모든 Row를 수정해야 합니다.

하나라도 빠뜨리면

```text
P1 → 키보드
P1 → 기계식 키보드
```

처럼 같은 상품 ID에 서로 다른 이름이 존재하게 됩니다.

이것이 수정 이상입니다.

## 삭제 이상

O2 주문이 P1의 마지막 주문이라고 가정해봅시다.

O2 Row를 삭제했더니 P1 상품 정보 자체도 함께 사라질 수 있습니다.

```text
주문 삭제
→ 상품 정보까지 손실
```

원하지 않는 정보까지 같이 사라지는 것이 삭제 이상입니다.

## 왜 생기는가

서로 다른 주제의 사실을 한 Table에 저장하기 때문입니다.

```text
주문 사실
고객 사실
상품 사실
```

이 세 사실은 서로 다른 Key에 종속됩니다.

```text
ORDER_ID → ORDER_DATE, CUSTOMER_ID
CUSTOMER_ID → CUSTOMER_NAME
PRODUCT_ID → PRODUCT_NAME, PRICE
```

하나의 Relation에 섞이면 중복과 이상이 발생합니다.

## 정규화로 해결

통합 Table을 다음처럼 나눌 수 있습니다.

```text
ORDERS
→ ORDER_ID, ORDER_DATE, CUSTOMER_ID

CUSTOMER
→ CUSTOMER_ID, CUSTOMER_NAME

PRODUCT
→ PRODUCT_ID, PRODUCT_NAME, PRICE

ORDER_ITEM
→ ORDER_ID, PRODUCT_ID, QTY
```

각 사실을 자신을 결정하는 Key와 함께 저장합니다.

## 이상 현상과 중복

중복 자체가 항상 나쁜 것은 아니지만, 같은 사실이 여러 Row에 반복되면 수정 비용과 불일치 위험이 커집니다.

정규화는 이런 **의미 중복**을 줄이는 것이 핵심입니다.

## 시험 포인트

세 이상 현상은 다음처럼 구분합니다.

```text
삽입 이상
→ 넣고 싶은 정보만 독립적으로 넣기 어려움

수정 이상
→ 같은 사실을 여러 곳에서 수정해야 함

삭제 이상
→ 한 사실을 지웠는데 다른 필요한 사실도 함께 사라짐
```

## 다른 개념과 비교

### 비교 1. 삽입 이상

```text
삽입 이상
→ 독립 정보 삽입 곤란
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 2. 수정 이상

```text
수정 이상
→ 여러 중복 Row 수정
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 3. 삭제 이상

```text
삭제 이상
→ 원하지 않는 정보 손실
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

## 자주 하는 실수

### 실수 1. Table 이름만 보고 Entity와 Relation을 같은 수준으로 생각한다.

이 실수를 피하려면 다음 순서를 지킵니다.

```text
업무 규칙
→ Key
→ 함수 종속
→ 이상 현상
→ 필요한 분해
```

## 시험·면접

### 핵심 암기

```text
Anomaly = 삽입 이상 + 수정 이상 + 삭제 이상
```

### 시험 접근 순서

```text
1. Entity 또는 Relation 확인
2. Candidate Key 확인
3. 함수 종속 확인
4. 이상 현상 확인
5. 정규형 조건 확인
6. 필요한 분해 확인
```

### 시험 함정

현재 예시 데이터에서 값이 우연히 유일하다고 해서 함수 종속이나 Key가 자동으로 성립하는 것은 아닙니다.

Schema와 업무 규칙을 기준으로 판단해야 합니다.

### 면접에서 짧게 답한다면

이상 현상(Anomaly)은 하나의 Table에 서로 다른 사실이 과도하게 섞여 저장될 때 삽입·수정·삭제 과정에서 데이터 문제가 발생하는 현상입니다.

정규화와 모델링에서는 Key와 함수 종속을 기준으로 중복과 이상 현상을 줄이는 방향으로 구조를 설계합니다.

## 예시로 한 바퀴

`이상 현상 · Anomaly` 문제를 만나면 작은 Relation부터 그립니다.

```text
Key
→ 결정되는 Attribute
→ 반복되는 사실
→ 발생 가능한 이상 현상
```

그다음 어떤 Attribute가 어떤 Key에 종속되는지 화살표로 표시합니다.

마지막으로 분해가 필요하다면 **같은 사실을 한 곳에서만 관리할 수 있도록** Relation을 나눕니다.
