Functional Dependency(함수 종속)는 어떤 Attribute 값이 정해졌을 때 다른 Attribute 값이 하나로 결정되는 관계입니다.

이 글에서는 정의만 외우지 않고 실제 Table을 어떻게 보고 판단하는지까지 연결합니다.

<blockquote class="prompt-info">
<p>한 줄: X가 정해지면 Y가 하나로 결정될 때 X가 Y를 함수적으로 결정한다고 합니다.</p>
</blockquote>

<details>
<summary>한 줄로</summary>

X → Y = X 값이 같으면 Y 값도 같아야 함

</details>

## 기본 개념

다음 관계를 생각합니다.

```text
EMP_ID → EMP_NAME
```

직원 번호가 하나 정해지면 직원 이름도 하나로 결정됩니다.

따라서 `EMP_NAME`은 `EMP_ID`에 함수적으로 종속됩니다.

## 결정자와 종속자

표현은 다음처럼 읽습니다.

```text
X → Y
```

```text
X
→ 결정자

Y
→ 종속자
```

X 값이 같다면 Y도 같아야 합니다.

## 실습 EMPLOYEE

다음과 같은 함수 종속을 생각할 수 있습니다.

```text
EMP_ID → EMP_NAME
EMP_ID → DEPT_ID
EMP_ID → SALARY
```

EMP_ID가 직원 Row를 식별하는 Key이므로 다른 직원 속성을 결정합니다.

## 완전 함수 종속

복합 Key 전체에 의존하고 일부 Key만으로는 결정되지 않는 관계입니다.

예를 들어 주문 상세를 봅니다.

```text
(ORDER_ID, PRODUCT_ID) → QTY
```

수량은 주문 번호만으로도, 상품 번호만으로도 결정되지 않고 두 값을 함께 알아야 결정됩니다.

이런 관계가 완전 함수 종속입니다.

## 부분 함수 종속

복합 Key의 일부만으로 일반 Attribute가 결정되는 관계입니다.

예를 들어 다음 통합 Table을 생각합니다.

```text
(ORDER_ID, PRODUCT_ID) → PRODUCT_NAME
```

실제로는 `PRODUCT_ID → PRODUCT_NAME`입니다.

즉 복합 Key 전체가 아니라 일부인 PRODUCT_ID만으로 결정됩니다.

이것이 부분 함수 종속입니다.

## 이행 함수 종속

다음 구조를 봅니다.

```text
EMP_ID → DEPT_ID
DEPT_ID → DEPT_NAME
```

그러면 간접적으로

```text
EMP_ID → DEPT_NAME
```

이 됩니다.

Primary Key에서 일반 Attribute를 거쳐 다른 일반 Attribute가 결정되는 이런 구조가 3NF에서 중요한 이행 함수 종속입니다.

## Trivial Dependency

Y가 X의 부분집합이면 자명한 함수 종속으로 봅니다.

```text
(A, B) → A
```

왼쪽에 이미 A가 포함되어 있으므로 당연한 관계입니다.

BCNF나 함수 종속 이론에서는 자명한 종속인지도 구분합니다.

## Candidate Key 찾기

Candidate Key는 Relation의 모든 Attribute를 결정할 수 있는 최소 Attribute 집합입니다.

예를 들어

```text
A → B
B → C
```

라면 A로 B와 C까지 결정할 수 있습니다.

A가 모든 Attribute를 결정하고 더 줄일 수 없다면 Candidate Key가 될 수 있습니다.

## 정규화와 함수 종속

정규화는 함수 종속을 이용해 중복과 이상 현상을 분석합니다.

```text
부분 함수 종속
→ 2NF에서 제거

이행 함수 종속
→ 3NF에서 제거

모든 결정자가 Super Key
→ BCNF
```

## 다른 개념과 비교

### 비교 1. 완전 종속

```text
완전 종속
→ 복합 Key 전체 필요
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 2. 부분 종속

```text
부분 종속
→ Key 일부만 필요
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 3. 이행 종속

```text
이행 종속
→ 일반 Attribute를 거쳐 결정
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

## 자주 하는 실수

### 실수 1. Table 이름만 보고 Entity와 Relation을 같은 수준으로 생각한다.

이 실수를 피하려면 다음 순서를 지킵니다.

```text

```

→ 함수 종속
→ 이상 현상

## 시험·면접

### 핵심 암기

```text
X → Y = X 값이 같으면 Y 값도 같아야 함
```

### 시험 접근 순서

```text
1. Entity 또는 Relation 확인
2. Candidate Key 확인
3. 함수 종속 확인
4. 이상 현상 확인
5. 정규형 조건 확인
6. 필요한 분해 확인
```

### 시험 함정

현재 예시 데이터에서 값이 우연히 유일하다고 해서 함수 종속이나 Key가 자동으로 성립하는 것은 아닙니다.

Schema와 업무 규칙을 기준으로 판단해야 합니다.

### 면접에서 짧게 답한다면

Functional Dependency(함수 종속)는 어떤 Attribute 값이 정해졌을 때 다른 Attribute 값이 하나로 결정되는 관계입니다.

정규화와 모델링에서는 Key와 함수 종속을 기준으로 중복과 이상 현상을 줄이는 방향으로 구조를 설계합니다.

## 예시로 한 바퀴

`Functional Dependency · 함수 종속` 문제를 만나면 작은 Relation부터 그립니다.

```text
Key
→ 결정되는 Attribute
→ 반복되는 사실
→ 발생 가능한 이상 현상
```

그다음 어떤 Attribute가 어떤 Key에 종속되는지 화살표로 표시합니다.

마지막으로 분해가 필요하다면 **같은 사실을 한 곳에서만 관리할 수 있도록** Relation을 나눕니다.
