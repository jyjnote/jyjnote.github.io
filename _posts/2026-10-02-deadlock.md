`Deadlock`은 <mark>둘 이상의 Transaction이 서로 상대방이 가진 자원을 기다리면서 더 이상 진행하지 못하는 상태</mark>입니다.

Lock을 사용하는 동시성 제어에서는 대표적으로 발생할 수 있는 문제입니다.

<blockquote class="prompt-info">
<p>한 줄: Deadlock은 서로가 가진 Lock을 기다리며 모든 Transaction이 멈춘 상태입니다.</p>
</blockquote>

<details markdown="1">
<summary>한 줄로</summary>

Transaction 1은 Transaction 2를 기다리고, Transaction 2는 Transaction 1을 기다리면 Deadlock이 발생할 수 있습니다.

</details>

## 대표 상황

두 Transaction이 각각 다른 데이터를 먼저 잠근 뒤 상대방이 가진 데이터를 요청한다고 가정합니다.

```text
Transaction 1
→ A Lock 보유
→ B Lock 요청
```

```text
Transaction 2
→ B Lock 보유
→ A Lock 요청
```

이제 두 Transaction은 서로 상대방의 Lock 해제를 기다립니다.

```text
T1
→ B 기다림

T2
→ A 기다림
```

둘 다 진행할 수 없습니다.

```text
서로 기다림
→ Deadlock
```

## 실행 흐름으로 보기

### 1. Transaction 1이 A를 잠근다

```text
T1
→ A Lock 획득
```

### 2. Transaction 2가 B를 잠근다

```text
T2
→ B Lock 획득
```

### 3. Transaction 1이 B를 요청한다

하지만 B는 T2가 사용 중입니다.

```text
T1
→ B Lock 요청
→ 대기
```

### 4. Transaction 2가 A를 요청한다

하지만 A는 T1이 사용 중입니다.

```text
T2
→ A Lock 요청
→ 대기
```

### 결과

```text
T1
→ T2 기다림

T2
→ T1 기다림

→ Deadlock
```

## SQL 예시

다음 두 Transaction이 동시에 실행된다고 가정합니다.

### Transaction 1

```sql
BEGIN TRANSACTION;

UPDATE ACCOUNT
SET BALANCE = BALANCE - 1000
WHERE ACCOUNT_ID = 'A';

UPDATE ACCOUNT
SET BALANCE = BALANCE + 1000
WHERE ACCOUNT_ID = 'B';
```

### Transaction 2

```sql
BEGIN TRANSACTION;

UPDATE ACCOUNT
SET BALANCE = BALANCE - 500
WHERE ACCOUNT_ID = 'B';

UPDATE ACCOUNT
SET BALANCE = BALANCE + 500
WHERE ACCOUNT_ID = 'A';
```

만약 첫 번째 UPDATE 이후 각각 Lock을 유지한 상태라면 다음처럼 될 수 있습니다.

```text
T1
→ A Lock 보유
→ B Lock 필요
```

```text
T2
→ B Lock 보유
→ A Lock 필요
```

서로 상대방이 가진 Lock을 기다리며 진행하지 못합니다.

## Deadlock 발생 조건

교착상태는 일반적으로 다음 네 조건이 동시에 성립할 때 발생할 수 있습니다.

| 조건 | 의미 |
| --- | --- |
| 상호 배제 | 하나의 자원을 동시에 여러 Transaction이 사용할 수 없음 |
| 점유와 대기 | 자원을 가진 상태에서 다른 자원을 기다림 |
| 비선점 | 다른 Transaction의 자원을 강제로 빼앗을 수 없음 |
| 순환 대기 | 여러 Transaction이 원형으로 서로를 기다림 |

이 네 조건은 운영체제의 Deadlock 조건과 동일한 개념으로 자주 설명됩니다.

## 상호 배제

하나의 자원을 동시에 여러 Transaction이 사용할 수 없는 상태입니다.

```text
배타 Lock
→ 한 Transaction만 사용 가능
```

## 점유와 대기

Transaction이 이미 하나의 자원을 가진 상태에서 다른 자원을 기다립니다.

```text
T1
→ A 보유
→ B 대기
```

## 비선점

다른 Transaction이 가진 자원을 강제로 빼앗지 못합니다.

```text
T1이 A 보유
→ T2가 강제로 A 회수 불가
```

## 순환 대기

Transaction 사이에 기다림의 고리가 생깁니다.

```text
T1
→ T2 기다림

T2
→ T1 기다림
```

세 개 이상도 가능합니다.

```text
T1 → T2
T2 → T3
T3 → T1
```

## Wait-for Graph

Deadlock을 탐지할 때 `Wait-for Graph`를 사용할 수 있습니다.

Transaction을 Node로 두고 기다리는 관계를 화살표로 표현합니다.

```text
T1 → T2
```

의 의미는

```text
T1이
→ T2가 가진 자원을 기다림
```

입니다.

### Deadlock이 없는 경우

```text
T1 → T2
T2 → T3
```

순환 구조가 없습니다.

### Deadlock이 있는 경우

```text
T1 → T2
T2 → T1
```

Cycle이 존재합니다.

```text
Cycle 존재
→ Deadlock 가능
```

<blockquote class="prompt-warning">
<p>Wait-for Graph 문제에서는 Transaction 사이에 Cycle이 존재하는지 확인하는 것이 핵심입니다.</p>
</blockquote>

## Deadlock 예방

Deadlock 발생 조건 중 하나라도 깨뜨리면 Deadlock을 예방할 수 있습니다.

```text
상호 배제
점유와 대기
비선점
순환 대기
```

중 하나를 제거하는 방식입니다.

### 자원 획득 순서 통일

모든 Transaction이 같은 순서로 Lock을 획득하도록 하면 순환 대기를 줄일 수 있습니다.

예를 들어 항상

```text
A
→ B
→ C
```

순서로 Lock을 얻도록 합니다.

Transaction마다 서로 다른 순서로 자원을 잡는 것을 피하는 것입니다.

## Deadlock 회피

Transaction이 자원을 요청할 때 현재 상태를 보고 Deadlock 위험이 있는 요청을 피하는 방식입니다.

```text
자원 요청
↓
안전 상태인지 판단
↓
허용 또는 대기
```

데이터베이스에서는 구현 방식에 따라 Timestamp 기반 기법 등을 사용할 수 있습니다.

## Deadlock 탐지

Deadlock이 발생할 수 있도록 허용한 뒤 주기적으로 탐지하는 방식도 있습니다.

대표적으로 Wait-for Graph의 Cycle을 확인할 수 있습니다.

```text
Wait-for Graph
↓
Cycle 검사
↓
Cycle 발견
→ Deadlock 탐지
```

## Deadlock 회복

Deadlock이 발견되면 Transaction 중 하나를 중단시켜 고리를 끊어야 합니다.

```text
T1 ↔ T2
```

중 하나를 선택해

```text
ROLLBACK
```

시키면 해당 Transaction이 가진 Lock이 해제됩니다.

```text
Transaction 하나 중단
↓
Lock 해제
↓
다른 Transaction 진행
```

## Victim

Deadlock을 해결하기 위해 중단 대상으로 선택된 Transaction을 `Victim`이라고 합니다.

Victim을 선택할 때는 시스템에 따라 다음과 같은 요소를 고려할 수 있습니다.

```text
이미 수행한 작업량
남은 작업량
보유한 Lock 수
ROLLBACK 비용
우선순위
```

목표는 전체 복구 비용을 줄이는 것입니다.

## Timeout

일정 시간 이상 Lock을 기다리면 Transaction을 중단하는 방식도 있습니다.

```text
Lock 대기
↓
일정 시간 초과
↓
Transaction 중단
```

구현은 단순하지만 실제 Deadlock이 아닌 단순 지연도 중단될 수 있습니다.

## Deadlock과 일반 대기 차이

모든 Lock 대기가 Deadlock은 아닙니다.

### 일반 대기

```text
T1
→ A 사용 중

T2
→ A 기다림

T1 종료
→ A 해제

T2 진행
```

기다리면 결국 진행할 수 있습니다.

### Deadlock

```text
T1
→ T2 기다림

T2
→ T1 기다림
```

서로가 상대방의 진행을 기다리므로 외부 개입 없이는 계속 멈출 수 있습니다.

| 구분 | 일반 대기 | Deadlock |
| --- | --- | --- |
| 기다림 | 한쪽 방향 | 순환 구조 |
| 자동 진행 | 가능 | 어려움 |
| 해결 | Lock 해제 대기 | 탐지·중단 필요 |

## Deadlock과 2PL

2PL은 Transaction의 직렬 가능성을 보장하는 데 사용되지만 Deadlock을 완전히 막지는 못합니다.

```text
2PL
→ Lock 획득 규칙 제공
→ 직렬 가능성 보장 가능
```

하지만 여러 Transaction이 서로 다른 자원을 가지고 추가 Lock을 기다리면 Deadlock은 발생할 수 있습니다.

```text
2PL 사용
≠
Deadlock 없음
```

## 잘 놓치는 핵심

### 1. 모든 Lock 대기가 Deadlock은 아니다

Cycle이 없는 단순 대기는 정상적으로 풀릴 수 있습니다.

### 2. Deadlock의 핵심은 순환 대기

```text
T1 → T2
T2 → T1
```

처럼 기다림이 원형 구조를 만드는지가 중요합니다.

### 3. 2PL도 Deadlock이 발생할 수 있다

2PL은 직렬 가능성을 위한 규칙이지 Deadlock 제거 규칙이 아닙니다.

### 4. 해결하려면 고리를 끊어야 한다

Transaction 중 하나를 ROLLBACK하면 Lock이 해제되어 다른 Transaction이 진행할 수 있습니다.

## 시험·면접

### 핵심 암기

```text
Deadlock
→ 서로 상대방 Lock 기다림
```

```text
발생 조건
→ 상호 배제
→ 점유와 대기
→ 비선점
→ 순환 대기
```

```text
Wait-for Graph
→ Cycle 확인
```

```text
회복
→ Transaction 하나 ROLLBACK
```

### 시험 함정

Lock을 기다린다고 무조건 Deadlock은 아닙니다.

시험에서는 `Cycle`, `순환 대기`, `서로 상대방 자원 대기`가 있는지 확인해야 합니다.

### 면접 짧은 답변

Deadlock은 둘 이상의 Transaction이 서로 상대방이 가진 Lock을 기다리면서 더 이상 진행하지 못하는 상태입니다. 상호 배제, 점유와 대기, 비선점, 순환 대기의 네 조건이 동시에 성립할 때 발생할 수 있으며, Wait-for Graph에서 Cycle을 찾아 탐지할 수 있습니다. 발생 후에는 Transaction 중 하나를 Victim으로 선택해 ROLLBACK하여 Lock을 해제하는 방식으로 회복할 수 있습니다.

## 객관식 문제

### 문제 1 · 개념

Deadlock에 대한 설명으로 가장 적절한 것은?

① Transaction이 정상적으로 COMMIT된 상태  
② 서로 상대방이 가진 자원을 기다리며 진행하지 못하는 상태  
③ Table을 정규화한 상태  
④ Index가 없는 상태

<details markdown="1">
<summary>정답</summary>

②

Deadlock은 Transaction들이 서로 상대방의 자원을 기다리면서 진행하지 못하는 상태입니다.

</details>

### 문제 2 · 발생 조건

다음 중 Deadlock의 대표적인 발생 조건이 아닌 것은?

① 상호 배제  
② 점유와 대기  
③ 비선점  
④ 자동 COMMIT

<details markdown="1">
<summary>정답</summary>

④

자동 COMMIT은 Deadlock의 네 가지 대표 발생 조건에 포함되지 않습니다.

</details>

### 문제 3 · Wait-for Graph

Wait-for Graph에서 Deadlock을 판단하는 핵심은?

① Node의 개수  
② Cycle 존재 여부  
③ Table의 Column 수  
④ Transaction 이름

<details markdown="1">
<summary>정답</summary>

②

Transaction 사이의 기다림 관계에 Cycle이 존재하는지 확인하는 것이 핵심입니다.

</details>

### 문제 4 · 회복

Deadlock이 발생했을 때 대표적인 회복 방법은?

① 모든 Table DROP  
② Transaction 중 하나를 ROLLBACK  
③ 모든 Lock을 영구 유지  
④ 모든 Index 삭제

<details markdown="1">
<summary>정답</summary>

②

Transaction 하나를 중단하고 ROLLBACK하면 해당 Transaction의 Lock이 해제되어 순환 대기를 끊을 수 있습니다.

</details>

### 문제 5 · 2PL 관계

2PL과 Deadlock의 관계로 옳은 것은?

① 2PL을 사용하면 Deadlock이 절대 발생하지 않는다.  
② 2PL은 Deadlock을 발생시키지 않는다.  
③ 2PL은 직렬 가능성을 보장할 수 있지만 Deadlock은 발생할 수 있다.  
④ 2PL은 Lock을 사용하지 않는다.

<details markdown="1">
<summary>정답</summary>

③

2PL은 직렬 가능성을 보장하는 대표적인 방식이지만 Deadlock을 완전히 방지하지는 못합니다.

</details>

## Deadlock 전체 요약

```text
T1
→ A 보유
→ B 기다림
```

```text
T2
→ B 보유
→ A 기다림
```

```text
서로 기다림
→ Deadlock
```

| 핵심 | 내용 |
| --- | --- |
| 발생 조건 | 상호 배제, 점유와 대기, 비선점, 순환 대기 |
| 탐지 | Wait-for Graph의 Cycle 확인 |
| 예방 | 자원 획득 순서 통일 등 |
| 회복 | Victim 선택 후 ROLLBACK |
| 주의 | 2PL에서도 발생 가능 |

</blockquote>
