Deadlock(교착상태)은 둘 이상의 Transaction이 서로 상대가 보유한 자원을 기다리면서 영원히 진행하지 못하는 상태입니다.

이 글에서는 용어를 외우는 데서 끝내지 않고 Transaction의 시간 순서와 실제 결과를 연결해서 봅니다.

## 대표 예시

두 Transaction이 반대 순서로 Lock을 잡습니다.

```text
T1
→ A Lock 획득
→ B Lock 요청
→ 대기

T2
→ B Lock 획득
→ A Lock 요청
→ 대기
```

서로 상대가 가진 Lock을 기다리므로 진행할 수 없습니다.

## 시간 순서

| 순서 | T1 | T2 |
| --- | --- | --- |
| 1 | A Lock | |
| 2 | | B Lock |
| 3 | B 요청 → 대기 | |
| 4 | | A 요청 → 대기 |
| 결과 | 대기 | 대기 |

이것이 전형적인 Deadlock입니다.

## Deadlock과 단순 대기

모든 Lock 대기가 Deadlock은 아닙니다.

```text
T1이 A 사용
T2가 A 대기
T1이 COMMIT
T2 진행
```

이 경우는 정상적인 Lock 대기입니다.

Deadlock은 **순환 대기**가 핵심입니다.

## Wait-for Graph

Transaction 간 대기 관계를 그래프로 표현할 수 있습니다.

```text
T1 → T2
T2 → T1
```

Cycle이 있으면 Deadlock 가능성을 판단할 수 있습니다.

## Deadlock 조건

운영체제에서 배우는 Coffman 조건과 연결해서 다음 네 조건을 설명하기도 합니다.

```text
Mutual Exclusion
Hold and Wait
No Preemption
Circular Wait
```

데이터베이스 Deadlock에서도 순환 대기가 중요한 핵심입니다.

## 예방

대표적인 예방 방법은 Lock 획득 순서를 통일하는 것입니다.

```text
항상 A
→ B
→ C 순서로 Lock
```

반대 순서 요청을 줄이면 순환 대기 가능성이 낮아집니다.

## 탐지와 Victim

DBMS는 Deadlock을 탐지한 뒤 Transaction 하나를 Victim으로 선택해 ROLLBACK할 수 있습니다.

```text
Deadlock 발견
→ T2 ROLLBACK
→ Lock 해제
→ T1 진행
```

애플리케이션은 Deadlock 오류 후 재시도 로직이 필요할 수 있습니다.

## Timeout

일부 시스템에서는 일정 시간 이상 Lock을 얻지 못하면 Timeout으로 중단하기도 합니다.

Timeout은 Deadlock만 정확히 판별하는 방식과는 다르며 단순 장시간 대기도 중단될 수 있습니다.

## 2PL과 Deadlock

2PL은 Serializability에 도움을 주지만 Deadlock을 제거하지는 않습니다.

```text
2PL
→ Lock 규칙 보장

Deadlock
→ 여전히 가능
```

이 두 개념을 혼동하면 안 됩니다.

이 실수를 피하려면 다음 순서로 봅니다.

