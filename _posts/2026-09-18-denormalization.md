반정규화(Denormalization)는 정규화된 구조에서 조회 성능이나 운영 편의를 위해 의도적으로 중복이나 결합 정보를 추가하는 설계 기법입니다.

이 글에서는 정의만 외우지 않고 실제 Table을 어떻게 보고 판단하는지까지 연결합니다.

<blockquote class="prompt-info">
<p>한 줄: 반정규화는 정규화를 되돌리는 것이 아니라 성능과 운영 목적을 위해 중복을 통제해서 허용하는 선택입니다.</p>
</blockquote>

## 왜 반정규화하는가

정규화가 높아질수록 데이터 중복은 줄지만 조회 시 JOIN이 많아질 수 있습니다.

```text
정규화
→ 무결성·일관성

반정규화
→ 조회 성능·단순화
```

읽기 부하가 매우 큰 시스템에서는 일부 정보를 중복 저장하는 선택을 할 수 있습니다.

## 예시

정규화된 구조는 다음과 같습니다.

```text
ORDERS
ORDER_ID | CUSTOMER_ID

CUSTOMER
CUSTOMER_ID | CUSTOMER_NAME
```

주문 목록에서 항상 고객 이름이 필요하면 매번 JOIN해야 합니다.

반정규화로 ORDERS에 `CUSTOMER_NAME`을 추가하는 선택을 생각할 수 있습니다.

하지만 고객 이름 변경 시 중복 값을 모두 동기화해야 합니다.

## 중복 Column 추가

자주 조회하는 값을 다른 Table에 복사해 둘 수 있습니다.

```text
ORDERS
→ CUSTOMER_ID
→ CUSTOMER_NAME 추가
```

조회는 단순해지지만 수정 이상 위험이 다시 생깁니다.

## 집계값 저장

매번 계산 비용이 큰 집계값을 미리 저장할 수 있습니다.

예를 들어

```text
ORDER_TOTAL
```

을 ORDERS에 저장할 수 있습니다.

하지만 ORDER_ITEM 변경 시 ORDER_TOTAL도 함께 갱신해야 합니다.

## Table 병합

항상 같이 조회되고 1:1 관계인 Table을 물리적으로 합치는 방식도 고려할 수 있습니다.

하지만 Column 수 증가와 NULL 증가, 변경 영향도 함께 봐야 합니다.

## 반정규화의 위험

중복 데이터가 생기면 다음 위험이 있습니다.

- 수정 불일치
- 추가 저장 공간
- 갱신 로직 복잡
- Transaction 범위 증가
- 데이터 무결성 관리 비용 증가

성능 개선만 보고 적용하면 안 됩니다.

## 언제 고려하는가

다음 상황에서 검토할 수 있습니다.

```text
JOIN 비용이 실제 병목
읽기가 쓰기보다 압도적으로 많음
집계 계산이 반복적으로 비쌈
캐시나 Materialized View만으로 해결하기 어려움
```

먼저 실행 계획과 실제 성능 측정이 필요합니다.

## Index와 먼저 비교

조회가 느리다고 바로 반정규화하지 않습니다.

먼저 다음을 확인합니다.

```text
Index
Query 구조
통계 정보
불필요한 Column 조회
JOIN 조건
캐시
```

이후에도 병목이 남을 때 반정규화를 고려합니다.

## 정규화와 반정규화 비교

| 구분 | 정규화 | 반정규화 |
| --- | --- | --- |
| 목표 | 중복 감소·무결성 | 조회 성능·단순화 |
| 데이터 중복 | 적음 | 증가 가능 |
| JOIN | 증가 가능 | 감소 가능 |
| 수정 비용 | 상대적으로 낮음 | 동기화 비용 증가 |
| 적용 | 기본 설계 | 측정 후 선택 |

정규화가 기본이고 반정규화는 필요에 따른 최적화입니다.

## 실무 원칙

반정규화는 다음 순서가 좋습니다.

```text
1. 정상적으로 정규화
2. 실제 성능 측정
3. 병목 확인
4. 다른 최적화 검토
5. 필요한 부분만 반정규화
6. 동기화 방법 설계
```

의도와 유지 방법이 명확해야 합니다.

## 다른 개념과 비교

### 비교 1. 정규화

```text
정규화
→ 중복·이상 감소
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 2. 반정규화

```text
반정규화
→ 성능을 위해 중복 허용
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 3. Index

```text
Index
→ 구조 중복 없이 성능 개선 가능
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

## 시험·면접

### 핵심 암기

```text
반정규화 = 성능·단순화를 위해 의도적으로 중복 허용
```

### 시험 접근 순서

```text
1. Entity 또는 Relation 확인
2. Candidate Key 확인
3. 함수 종속 확인
4. 이상 현상 확인
5. 정규형 조건 확인
6. 필요한 분해 확인
```

### 시험 함정

현재 예시 데이터에서 값이 우연히 유일하다고 해서 함수 종속이나 Key가 자동으로 성립하는 것은 아닙니다.

Schema와 업무 규칙을 기준으로 판단해야 합니다.

### 면접에서 짧게 답한다면

반정규화(Denormalization)는 정규화된 구조에서 조회 성능이나 운영 편의를 위해 의도적으로 중복이나 결합 정보를 추가하는 설계 기법입니다.

정규화와 모델링에서는 Key와 함수 종속을 기준으로 중복과 이상 현상을 줄이는 방향으로 구조를 설계합니다.

## 예시로 한 바퀴

`반정규화` 문제를 만나면 작은 Relation부터 그립니다.

```text
Key
→ 결정되는 Attribute
→ 반복되는 사실
→ 발생 가능한 이상 현상
```

그다음 어떤 Attribute가 어떤 Key에 종속되는지 화살표로 표시합니다.

마지막으로 분해가 필요하다면 **같은 사실을 한 곳에서만 관리할 수 있도록** Relation을 나눕니다.
