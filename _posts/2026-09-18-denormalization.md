`반정규화`는 <mark>정규화된 데이터 모델에서 조회 성능이나 처리 효율을 높이기 위해 의도적으로 중복을 허용하거나 Table을 합치는 기법</mark>입니다.

정규화의 반대처럼 보이지만, 무조건 구조를 되돌리는 것이 아니라 **성능상 필요한 부분에 제한적으로 적용**합니다.

<blockquote class="prompt-info">
<p>한 줄: 반정규화는 성능 향상을 위해 의도적으로 중복을 허용하는 설계 기법입니다.</p>
</blockquote>

<details markdown="1">
<summary>한 줄로</summary>

정규화로 인한 JOIN 비용이나 반복 계산이 너무 크다면 일부 중복을 허용해 조회 성능을 높일 수 있습니다.

</details>

## 왜 반정규화를 하는가

정규화를 하면 데이터 중복은 줄어들지만 Table이 여러 개로 분리됩니다.

```text
정규화
→ Table 분리
→ 중복 감소
→ 무결성 관리 쉬움
```

하지만 조회할 때 여러 Table을 계속 JOIN해야 한다면 처리 비용이 커질 수 있습니다.

```text
Table 분리 증가
↓
JOIN 증가
↓
조회 비용 증가 가능
```

이때 성능상 필요하다면 일부 구조를 다시 합치거나 필요한 값을 중복 저장할 수 있습니다.

```text
성능 문제 확인
↓
일부 중복 허용
↓
반정규화
```

## 대표 예시

정규화된 다음 두 Table이 있다고 가정합니다.

### CUSTOMER

| CUSTOMER_ID | NAME | REGION |
| --- | --- | --- |
| C001 | 고객1 | 서울 |
| C002 | 고객2 | 부산 |

### ORDERS

| ORDER_ID | CUSTOMER_ID | ORDER_DATE |
| --- | --- | --- |
| O001 | C001 | 2026-09-01 |
| O002 | C002 | 2026-09-02 |

주문 목록을 조회할 때마다 고객 이름까지 필요하면 다음과 같이 JOIN해야 합니다.

```sql
SELECT
    O.ORDER_ID,
    C.NAME,
    O.ORDER_DATE
FROM ORDERS O
JOIN CUSTOMER C
    ON O.CUSTOMER_ID = C.CUSTOMER_ID;
```

조회가 매우 빈번하고 JOIN 비용이 문제가 된다면 ORDERS에 고객 이름을 중복 저장하는 방식을 고려할 수 있습니다.

### 반정규화 후

| ORDER_ID | CUSTOMER_ID | CUSTOMER_NAME | ORDER_DATE |
| --- | --- | --- | --- |
| O001 | C001 | 고객1 | 2026-09-01 |
| O002 | C002 | 고객2 | 2026-09-02 |

이제 일부 조회에서는 CUSTOMER와 JOIN하지 않고도 고객 이름을 바로 가져올 수 있습니다.

```text
JOIN 감소
→ 조회 단순화
→ 성능 향상 가능
```

하지만 고객 이름이 변경되면 여러 곳을 함께 수정해야 할 수 있습니다.

## 반정규화의 장점

### 1. JOIN 감소

여러 Table을 결합하는 횟수를 줄일 수 있습니다.

```text
JOIN 감소
→ 조회 비용 감소 가능
```

### 2. 반복 계산 감소

자주 사용하는 집계 결과를 미리 저장할 수 있습니다.

예를 들어 주문 합계를 매번 계산하지 않고 고객별 누적 구매금액을 별도 Column에 저장할 수 있습니다.

### 3. 조회 Query 단순화

복잡한 JOIN과 집계가 줄어들어 조회 Query가 단순해질 수 있습니다.

## 반정규화의 단점

### 1. 데이터 중복 증가

같은 정보가 여러 곳에 저장될 수 있습니다.

```text
CUSTOMER.NAME
+
ORDERS.CUSTOMER_NAME
```

### 2. 수정 이상 가능

한 곳만 수정하면 값이 서로 달라질 수 있습니다.

```text
CUSTOMER.NAME
→ 고객A

ORDERS.CUSTOMER_NAME
→ 고객1
```

같은 고객인데 서로 다른 이름이 저장될 수 있습니다.

### 3. 저장 공간 증가

중복 데이터를 저장하므로 필요한 저장 공간이 증가할 수 있습니다.

### 4. 무결성 관리가 어려워짐

중복된 값을 여러 곳에서 일관되게 유지해야 합니다.

<blockquote class="prompt-warning">
<p>반정규화는 조회 성능을 높일 수 있지만 중복과 데이터 불일치 위험도 함께 증가합니다.</p>
</blockquote>

## 대표적인 반정규화 방법

반정규화는 단순히 Table을 합치는 것만 의미하지 않습니다.

대표적으로 다음과 같은 방식이 있습니다.

```text
Table 통합
Column 중복
파생값 저장
집계값 저장
```

## Table 통합

자주 JOIN하는 두 Table을 하나로 합치는 방식입니다.

### 정규화 구조

```text
고객 Table
+
고객등급 Table
```

### 반정규화 구조

```text
고객 Table
→ 고객정보 + 등급정보
```

JOIN은 줄어들지만 등급 정보의 중복이 증가할 수 있습니다.

## Column 중복

다른 Table에서 자주 조회하는 값을 현재 Table에도 저장합니다.

### 기존

```text
ORDERS.CUSTOMER_ID
→ CUSTOMER.NAME 조회 필요
```

### 반정규화

```text
ORDERS
→ CUSTOMER_ID
→ CUSTOMER_NAME도 함께 저장
```

조회는 빨라질 수 있지만 이름 변경 시 여러 Row를 수정해야 할 수 있습니다.

## 파생값 저장

원래 다른 값으로 계산할 수 있는 결과를 미리 저장하는 방식입니다.

예를 들어 다음 값이 있다고 가정합니다.

| 수량 | 단가 |
| ---: | ---: |
| 3 | 10000 |

원래 주문금액은 계산할 수 있습니다.

```text
3 × 10000
→ 30000
```

반정규화에서는 계산 결과인 `30000`을 별도 Column에 저장할 수도 있습니다.

```text
반복 계산 감소
→ 조회 속도 향상 가능
```

대신 수량이나 단가가 바뀌면 주문금액도 함께 수정해야 합니다.

## 집계값 저장

매번 합계를 계산하지 않고 결과를 미리 저장할 수도 있습니다.

예를 들어 고객별 주문금액 합계를 매번 계산하는 대신

```text
고객별 누적 구매금액
```

을 별도 Column이나 요약 Table에 저장할 수 있습니다.

이는 대량 조회에서 유리할 수 있지만 원본 데이터가 변경될 때 집계값도 함께 갱신해야 합니다.

## 정규화와 반정규화 비교

| 구분 | 정규화 | 반정규화 |
| --- | --- | --- |
| 핵심 목적 | 중복 감소 | 성능 향상 |
| Table 수 | 증가 가능 | 감소 가능 |
| JOIN | 증가 가능 | 감소 가능 |
| 데이터 중복 | 적음 | 증가 가능 |
| 무결성 관리 | 상대적으로 쉬움 | 더 어려워질 수 있음 |
| 조회 성능 | JOIN 비용 발생 가능 | 향상 가능 |

```text
정규화
→ 무결성 중심
```

```text
반정규화
→ 성능 중심
```

둘 중 하나가 항상 더 좋은 것이 아니라 시스템 요구사항에 따라 선택합니다.

## 언제 고려하는가

반정규화는 먼저 실제 성능 문제가 있는지 확인한 뒤 적용하는 것이 좋습니다.

```text
정규화된 구조 사용
↓
성능 측정
↓
병목 확인
↓
반정규화 필요성 판단
```

다음과 같은 상황에서 고려할 수 있습니다.

```text
JOIN이 지나치게 많음
자주 사용하는 집계 계산이 무거움
조회 비중이 매우 높음
응답 시간이 중요한 서비스
```

## 무조건 하면 안 되는 이유

반정규화는 성능을 높일 수 있지만 데이터 중복과 무결성 문제를 만들 수 있습니다.

따라서 다음처럼 접근해야 합니다.

```text
성능 문제 없음
→ 반정규화 필요 없음

성능 병목 확인
→ 필요한 부분만 반정규화
```

<blockquote class="prompt-danger">
<p>반정규화는 정규화를 무시하는 기법이 아니라 성능상 필요성이 확인된 부분에 의도적으로 적용하는 최적화 기법입니다.</p>
</blockquote>

## 잘 놓치는 핵심

### 1. 반정규화의 목적은 성능이다

중복을 만드는 것 자체가 목적이 아닙니다.

### 2. 정규화 후 필요할 때 적용한다

먼저 정규화된 구조를 설계한 뒤 성능 문제를 확인하는 것이 기본입니다.

### 3. 조회는 빨라질 수 있지만 수정은 어려워질 수 있다

중복된 값을 여러 곳에서 관리해야 하기 때문입니다.

### 4. 무결성 관리 비용이 증가한다

반정규화된 값이 원본과 항상 일치하도록 관리해야 합니다.

## 시험·면접

### 핵심 암기

```text
반정규화
→ 성능 향상 목적
```

```text
장점
→ JOIN 감소
→ 조회 속도 향상 가능
```

```text
단점
→ 데이터 중복
→ 무결성 관리 어려움
→ 수정 이상 가능
```

### 시험 함정

반정규화는 정규화가 잘못되었기 때문에 수행하는 것이 아닙니다.

정규화된 구조에서 실제 성능 문제를 해결하기 위해 의도적으로 일부 중복을 허용하는 것입니다.

### 면접 짧은 답변

반정규화는 정규화된 데이터 모델에서 조회 성능이나 처리 효율을 높이기 위해 의도적으로 중복을 허용하거나 Table을 통합하는 기법입니다. JOIN과 반복 계산을 줄일 수 있지만 데이터 중복과 무결성 관리 부담이 증가하므로 실제 성능 병목이 확인된 부분에 제한적으로 적용해야 합니다.

③ 모든 Primary Key를 제거하기 위해

② JOIN 증가만 발생

③

다음 중 반정규화의 장점으로 가장 적절한 것은?

② JOIN 횟수 감소 가능

②

다음 중 반정규화의 단점으로 가장 적절한 것은?

② 데이터 중복과 무결성 관리 부담이 증가할 수 있다.  
③ Table을 생성할 수 없게 된다.  
④ Primary Key를 사용할 수 없다.

중복 데이터를 여러 곳에서 일관되게 유지해야 하므로 무결성 관리 부담이 커질 수 있습니다.

③ 모든 Foreign Key를 제거한다.  
④ 정규화를 수행하지 않고 바로 적용한다.
