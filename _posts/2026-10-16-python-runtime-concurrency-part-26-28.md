## 26부. 메모리 관리와 객체 수명

### 26.1. 도달 가능성·참조 관계·객체 수명

**도달 가능성**은 현재 유지되는 이름이나 다른 살아 있는 객체를 따라가서 특정 객체에 접근할 수 있는지를 뜻합니다. 이름 하나가 사라져도 다른 경로가 남아 있으면 객체는 계속 사용됩니다.[^datamodel]

```python
# 예제: 26-01
원본 = [10, 20]
보관함 = {"점수": 원본}

del 원본

print(보관함["점수"])  # 출력: [10, 20]
보관함["점수"].append(30)
print(보관함["점수"])  # 출력: [10, 20, 30]
```

이 예제에서는 `보관함`에서 내부 리스트로 가는 참조가 남아 있습니다. `del 원본`은 이름의 연결을 지웠을 뿐입니다.

```text
삭제 전: 원본 ─────────┐
                      ├─ 같은 리스트 객체
        보관함["점수"] ┘

삭제 후: 보관함["점수"] ── 리스트 객체 유지
```

**객체 회수 가능 시점과 실제 회수 시점은 구별합니다.** 파이썬 언어는 도달 불가능해진 모든 객체의 즉시 소멸을 보장하지 않습니다. 파일 같은 외부 자원은 객체 회수에 맡기지 않고 명시적으로 닫습니다.[^datamodel]

### 26.2. CPython의 참조 계수와 순환 참조 수집

일반적인 CPython은 **참조 계수**를 중심으로 객체를 관리하고, 이것만으로 처리하기 어려운 순환 참조를 별도의 수집기로 보완합니다.[^gc]

| 구분 | 판단하는 내용 | 주의점 |
| --- | --- | --- |
| 참조 계수 | 객체를 직접 가리키는 참조 | 서로를 가리키는 고리에서는 계수가 남을 수 있음 |
| 순환 참조 수집 | 외부에서 도달할 수 없는 참조 고리 | 모든 객체가 추적 대상인 것은 아님 |
| 개발자의 자원 관리 | 파일·연결·잠금을 언제 정리할지 | 객체 회수와 별개의 책임 |

```python
# 예제: 26-02
import sys

자료 = []
추가전 = sys.getrefcount(자료)
별칭 = 자료
추가후 = sys.getrefcount(자료)

print(추가후 - 추가전)  # 출력: 1

del 별칭
print(sys.getrefcount(자료) == 추가전)  # 출력: True
```

위 출력은 **이 독립 예제를 일반적인 CPython 3.13에서 실행한 경우**입니다. `getrefcount`에 인자를 전달할 때 생기는 임시 참조도 관측값에 포함됩니다. 디버거·실행 환경·불멸 객체 등의 영향을 받으므로 절대값을 암기하거나 객체의 유일한 소유자를 판정하는 용도로 사용하지 않습니다.[^sys][^immortal]

3.13의 일반 빌드 수집기는 추적 객체를 생존한 수집 횟수에 따라 0·1·2세대로 나누어 다룹니다. 이것은 생성 후 흐른 실제 시간을 세는 것이 아닙니다. 수집기 설정과 관측 함수는 개발·진단용으로 사용하고, 세대 구성을 모든 후속 버전의 규칙으로 일반화하지 않습니다.[^gc]

`gc.disable()`은 자동 순환 참조 수집을 끕니다. **참조 계수에 의한 모든 객체 회수를 끄는 명령은 아닙니다.** `gc.collect()`로 명시적인 수집을 요청할 수도 있습니다.[^gc]

### 26.3. 순환 참조와 수거 가능한 고리

자기 자신이나 서로를 가리키는 객체는 외부 이름을 지워도 내부 참조가 남습니다. 중요한 것은 **고리가 존재한다는 사실이 아니라, 외부에서 그 고리에 도달할 수 있는지**입니다.[^gc][^finalization]

```python
# 예제: 26-03
import gc
import weakref

class 연결:
    pass

자동수집 = gc.isenabled()
gc.disable()
try:
    대상 = 연결()
    대상.다음 = 대상
    관찰 = weakref.ref(대상)
    del 대상

    print(관찰() is None)  # 출력: False
    gc.collect()
    print(관찰() is None)  # 출력: True
finally:
    if 자동수집:
        gc.enable()
```

이 예제는 자동 수집을 잠시 멈춘 뒤 명시적으로 수집하여 차이를 관찰합니다. `gc.collect()`가 반환하는 회수 개수는 다른 임시 객체의 영향을 받을 수 있으므로 고정하지 않았습니다.

| 상황 | 구분 |
| --- | --- |
| 외부 이름에서 계속 접근 가능한 고리 | 아직 살아 있는 자료 구조 |
| 외부 연결이 끊긴 고리 | 순환 참조 수집의 대상이 될 수 있음 |
| 계속 커지는 전역 보관함 | 수집기보다 보관 정책을 먼저 확인 |
| 디버깅 설정으로 따로 보관한 회수 대상 | 설정 때문에 유지되는지 확인 |

**“소멸 메서드가 있는 순환 참조는 무조건 수거되지 않는다”는 설명도 부정확합니다.** 파이썬 3.4의 안전한 최종화 도입 이후 일반적인 파이썬 객체의 상황이 달라졌습니다. 객체의 재생존, 확장 타입, 디버깅 설정 같은 예외를 함께 구분해야 합니다.[^finalization]

### 26.4. 강한 참조·약한 참조·약한 참조 캐시

일반적인 대입과 컨테이너 저장은 객체를 유지하는 **강한 참조**입니다. **약한 참조**는 연결 대상의 수명을 그것만으로 연장하지 않습니다.[^weakref]

```python
# 예제: 26-04
import gc
import weakref

class 자료:
    pass

캐시 = weakref.WeakValueDictionary()
대상 = 자료()
캐시["하나"] = 대상

print("하나" in 캐시)  # 출력: True

del 대상
gc.collect()

print("하나" in 캐시)  # 출력: False
```

| 도구 | 약하게 연결하는 대상 | 활용 |
| --- | --- | --- |
| `weakref.ref` | 개별 객체 | 대상의 생존 여부 관찰 |
| `WeakValueDictionary` | 사전의 값 | 다른 곳에서 사용하는 동안만 자료 재사용 |
| `WeakKeyDictionary` | 사전의 키 | 객체에 부가 정보를 연결 |
| `WeakSet` | 집합 원소 | 객체를 소유하지 않는 등록 목록 |
| `WeakMethod` | 바인딩된 메서드의 대상 관계 | 메서드 콜백 연결 |

약한 참조를 조회한 결과는 `None`일 수 있습니다. **한 번 조회한 결과를 지역 이름에 보관한 뒤 검사**하는 방식이 안전합니다. 검사할 때와 사용할 때 각각 다시 조회하면 그사이에 대상이 사라질 수 있습니다.[^weakref]

일반 리스트와 사전은 직접 약한 참조의 대상이 되지 않습니다. 슬롯을 직접 정의하는 클래스는 필요한 경우 `__weakref__` 슬롯도 고려합니다. 약한 참조는 캐시의 최대 용량이나 보관 시간을 정하는 기능은 아닙니다.[^weakref]

### 26.5. 이름 삭제·최종화·명시적인 자원 정리

**최종화**는 객체 수명이 끝나는 과정에서 수행하는 정리이고, **명시적인 자원 정리**는 개발자가 필요한 시점에 파일·연결 등을 닫는 일입니다. 자원 사용 범위가 정해져 있다면 `with`가 우선입니다.[^datamodel][^contextlib]

```python
# 예제: 26-05
from io import StringIO

with StringIO("자료") as 파일:
    print(파일.read())  # 출력: 자료

print(파일.closed)  # 출력: True
```

이름 `파일`은 블록 뒤에도 존재하지만 내부 자원은 이미 닫혔습니다. **이름의 생존과 자원의 사용 가능 여부가 같지 않다**는 예제입니다.

| 수단 | 핵심 동작 | 한계 |
| --- | --- | --- |
| `del 이름` | 이름의 연결 삭제 | 다른 참조·자원 상태까지 일괄 정리하지 않음 |
| `close()` | 해당 객체가 정한 자원 종료 | 호출 시점과 오류 처리를 직접 관리 |
| `with` | 진입·종료 규약에 따라 정리 | 강제 프로세스 종료까지 복구하지는 못함 |
| `__del__` | 객체 최종화 과정의 메서드 | 실행 시점·종료 환경에 의존 |
| `weakref.finalize` | 최종화 콜백 등록 | 확정적인 자원 수명 관리의 대체재는 아님 |

`__del__`에서 예외가 발생해도 일반 함수 호출처럼 호출자에게 전달되지 않습니다. 최종화 중 객체를 다른 곳에 저장하면 다시 살아나는 경우도 있습니다. 복잡한 업무 처리를 소멸 메서드에 넣지 않습니다.[^datamodel][^finalization]

`weakref.finalize`에 등록하는 콜백이나 인자가 대상 객체를 강하게 붙잡으면 의도한 회수가 방해됩니다. 특히 대상의 바인딩된 메서드를 그대로 넣는 설계는 참조 관계를 확인해야 합니다.[^weakref]

### 26.6. 캐시·클로저·추적 정보가 객체를 붙잡는 경우

필요가 끝났는데도 보관 정책 때문에 참조가 유지될 수 있습니다. **수집기를 호출하기 전에 남아 있는 참조의 소유자를 찾습니다.**[^functools][^traceback]

```python
# 예제: 26-06
import gc
import weakref
from functools import lru_cache

class 상자:
    pass

@lru_cache(maxsize=2)
def 만들기(번호):
    return 상자()

대상 = 만들기(1)
관찰 = weakref.ref(대상)
del 대상
gc.collect()
print(관찰() is None)  # 출력: False

만들기.cache_clear()
gc.collect()
print(관찰() is None)  # 출력: True
```

캐시에 저장된 반환값이 대상을 유지합니다. `lru_cache`는 인자와 결과를 보관하며, 메서드에 적용하면 인자인 `self`도 객체 수명에 영향을 줄 수 있습니다.[^functools]

| 객체를 유지하는 경로 | 점검할 것 |
| --- | --- |
| 전역 리스트·사전 | 삭제 시점과 최대 보관량 |
| 캐시 | 용량·무효화·인자와 반환값 |
| 클로저 | 내부 함수가 참조하는 바깥 이름 |
| 콜백·바인딩된 메서드 | 등록 해제와 대상 인스턴스 |
| 예외·추적 정보 | 추적 정보가 연결하는 프레임과 지역 객체 |
| 미완료 태스크·결과 목록 | 완료·회수·결과 소비 시점 |

위 표는 앞에서 배운 참조 관계를 점검 경로로 정리한 것입니다. 예외 객체 자체를 장기간 쌓는 대신 필요한 정보를 문자열로 남기거나, 지원되는 추적 정보 도구로 프레임 보관을 줄이는 방식을 고려합니다.[^datamodel][^traceback][^tasks]

### 26.7. 객체 크기와 메모리 할당 추적

`sys.getsizeof`는 **해당 객체에 직접 귀속된 크기**를 보여 줍니다. 컨테이너가 가리키는 모든 내부 객체의 크기를 재귀적으로 더하지 않습니다.[^sys]

```python
# 예제: 26-07
import sys

내부자료 = bytearray(100_000)
보관함 = [내부자료]

print(sys.getsizeof(보관함))  # 관찰: 바깥 리스트의 직접 크기
print(sys.getsizeof(내부자료))  # 관찰: 내부 바이트 배열의 직접 크기
```

같은 내부 객체를 여러 곳에서 공유한다면 단순 재귀 합산은 중복 계산할 수도 있습니다. “어느 객체부터 얼마나 포함할 것인가”라는 측정 범위를 먼저 정합니다.

`tracemalloc`은 추적을 시작한 뒤 파이썬 메모리 할당 경로에서 관측한 블록을 추적합니다. 스냅샷을 비교하면 어느 코드 위치에서 보관량이 늘었는지 확인할 수 있습니다.[^tracemalloc]

```python
# 예제: 26-08
import tracemalloc

tracemalloc.start()
try:
    이전 = tracemalloc.take_snapshot()
    자료 = [bytearray(1024) for _ in range(100)]
    이후 = tracemalloc.take_snapshot()
    변화 = 이후.compare_to(이전, "lineno")

    print(any(항목.size_diff > 0 for 항목 in 변화))  # 출력: True
    현재, 최고 = tracemalloc.get_traced_memory()
    print(최고 >= 현재)  # 출력: True
finally:
    tracemalloc.stop()
```

| 측정 대상 | 확인할 수 있는 내용 | 그대로 판단하면 안 되는 것 |
| --- | --- | --- |
| `getsizeof` | 직접 크기 | 공유 자료까지 포함한 전체 크기 |
| `tracemalloc` | 추적된 할당의 위치·변화 | 모든 외부 라이브러리·장치 메모리 |
| 운영체제의 프로세스 메모리 | 프로세스 관점의 사용량 | 개별 파이썬 객체의 소유 관계 |

추적에는 시간·메모리 비용도 있습니다. 외부 확장 코드가 별도로 할당한 메모리는 추적 방식에 따라 누락될 수 있습니다.[^tracemalloc]

또한 객체가 해제되어도 할당기가 메모리를 재사용하려고 보유할 수 있습니다. **운영체제에서 보이는 사용량이 즉시 줄지 않는다는 사실만으로 누수를 확정하지 않습니다.**[^memory]

### 26.8. 객체 재사용·문자열 인터닝·버전과 빌드 차이

동일한 값의 불변 객체가 내부적으로 재사용되는 경우가 있습니다. 이것은 `is`를 값 비교에 써도 된다는 뜻이 아닙니다. 값 비교는 `==`, 객체 동일성은 `is`로 구분합니다.[^datamodel]

```python
# 예제: 26-09
import sys

왼쪽 = sys.intern("".join(["파이썬", "학습"]))
오른쪽 = sys.intern("".join(["파이썬", "학습"]))

print(왼쪽 == 오른쪽)  # 출력: True
print(왼쪽 is 오른쪽)  # 출력: True
```

여기서는 명시적으로 인터닝했고 반환값도 보관했습니다. 일반적인 문자열 생성이나 정수 리터럴 비교에 같은 결과를 무조건 적용하지 않습니다. 소멸한 객체의 식별값이 다른 객체에 재사용될 가능성도 있습니다.[^sys][^datamodel]

**불멸 객체**는 일부 객체의 참조 계수 갱신·회수 방식을 최적화하는 CPython 내부 개념입니다. 모든 사용자 객체가 해제되지 않는다는 뜻은 아닙니다.[^immortal]

자유 스레딩 빌드에서는 참조 계수 처리와 메모리 관리에 별도의 최적화가 들어갑니다. 일반 빌드에서 관찰한 즉시 소멸 시점이나 참조 계수 수치를 그대로 일반화하지 않습니다.[^nogil]

<blockquote class="prompt-warning">
<p>참조 계수는 언어 전체의 규칙이 아니라 구현 방식입니다. 수집기의 세대 수·임계값·세부 알고리즘도 버전과 빌드에 따라 달라질 수 있으므로 특정 수치를 모든 파이썬의 규칙으로 암기하지 않습니다.</p>
</blockquote>

## 27부. 스레드·프로세스·다중 인터프리터

### 27.1. 동시성·병렬성·작업의 병목

**동시성**은 여러 작업이 겹치는 기간에 진행되는 성질이고, **병렬성**은 같은 순간에 여러 계산이 실제로 수행되는 성질입니다. 번갈아 진행하는 동시성도 있고, 여러 실행 자원을 사용하는 병렬성도 있습니다.[^threading][^asyncdesign]

```text
번갈아 진행: 가 일부 → 나 일부 → 가 나머지 → 나 나머지

병렬 실행:  실행 자원 하나에서 가 진행
            실행 자원 둘에서 나 진행
```

| 병목 | 예시 | 먼저 검토할 방향 |
| --- | --- | --- |
| 파이썬 코드의 계산 | 큰 반복문·조합 탐색 | 알고리즘 개선·프로세스·적합한 병렬 실행 환경 |
| 외부 응답 대기 | 네트워크·파일 입출력 | 스레드 또는 비동기 입출력 |
| 외부 확장 코드의 계산 | 전역 잠금을 해제하는 연산 | 해당 라이브러리의 병렬 실행 지원 확인 |
| 공유 자원 경쟁 | 하나의 잠금·연결에 작업 집중 | 공유 범위·작업 분할·용량 제한 개선 |

이 표는 선택을 위한 출발점입니다. 작은 작업은 생성·전달·동기화 비용이 계산 이익보다 클 수 있으므로 실제 병목과 작업 크기를 측정합니다.[^futures][^multiprocessing]

<mark>동시성은 여러 작업의 진행을 조율하고, 병렬성은 같은 순간의 계산을 여러 실행 자원에 나눕니다. 입출력 대기를 겹치는 것은 동시성의 대표적인 활용입니다.</mark>

### 27.2. 스레드와 프로세스의 공유·격리

**스레드**는 한 프로세스 안에서 실행 흐름을 나눕니다. 같은 인터프리터의 스레드는 일반적인 파이썬 객체를 공유할 수 있습니다. **프로세스**는 별도의 주소 공간에서 실행되며, 자료를 주고받으려면 별도 통신 수단을 사용합니다.[^threading][^multiprocessing]

| 기준 | 같은 인터프리터의 스레드 | 별도 프로세스 |
| --- | --- | --- |
| 일반 리스트·사전 | 같은 객체를 공유 가능 | 보통 전달·복원된 별도 객체 |
| 자료 전달 | 참조와 동기화 수단 | 직렬화·파이프·큐·공유 메모리 등 |
| 주요 비용 | 실행 전환·잠금 경쟁 | 생성·직렬화·통신·추가 메모리 |
| 오류 영향 | 같은 프로세스 자원에 영향 | 프로세스별 분리 가능 |
| 상태 설계 | 공유 상태를 명확히 보호 | 전달 자료와 합치는 위치를 명확히 정의 |

분리된 프로세스라고 파일·네트워크·데이터베이스까지 자동 격리되지는 않습니다. 별도 보안 설정 없이 악성 코드를 안전하게 실행하는 장치로 취급하지 않습니다.

```python
# 예제: 27-01
from queue import Queue
from threading import Thread

결과함 = Queue()

def 계산(값):
    결과함.put(값 * 2)

작업들 = [Thread(target=계산, args=(값,)) for 값 in [1, 2, 3]]
for 작업 in 작업들:
    작업.start()
for 작업 in 작업들:
    작업.join()

결과 = sorted(결과함.get() for _ in 작업들)
print(결과)  # 출력: [2, 4, 6]
```

`Queue`는 스레드 사이의 안전한 전달을 위한 도구입니다. 결과가 들어오는 순서를 가정하지 않고 모아서 정렬했습니다.[^queue]

| 호출·설정 | 의미 |
| --- | --- |
| `Thread(target=함수)` | 실행할 함수를 지정하고 스레드 객체 생성 |
| `start()` | 새 실행 흐름을 시작하며 같은 객체에는 한 번만 호출 |
| `run()` 직접 호출 | 현재 스레드에서 일반 메서드처럼 실행 |
| `join()` | 호출한 쪽이 대상의 종료를 기다림 |
| `join(timeout=...)` | 지정 시간까지만 기다리며 종료 여부는 별도 확인 |
| `daemon=True` | 해당 스레드만 남았을 때 프로그램 종료를 막지 않음 |

`join()`은 반환값을 수집하거나 작업의 예외를 호출자에게 다시 발생시키는 기능이 아닙니다. 데몬 스레드는 종료 시 자원 정리가 보장되지 않으므로 중요한 저장 작업의 종료 수단으로 쓰지 않습니다.[^threading]

### 27.3. 전역 인터프리터 잠금과 적용 범위

전역 인터프리터 잠금은 흔히 `GIL`이라고 부릅니다. **전역 잠금을 사용하는 CPython의 같은 인터프리터에서는 한 시점에 한 스레드만 파이썬 바이트코드를 실행합니다.**[^threadstate]

그러나 이것은 “모든 스레드가 아무 일도 병렬로 할 수 없다”는 뜻이 아닙니다. 블로킹 입출력이나 일부 확장 코드의 계산 구간에서는 잠금을 해제하여 다른 실행이 진행될 수 있습니다.[^threadstate]

| 표현 | 판단 | 이유 |
| --- | --- | --- |
| 파이썬 스레드는 만들 수 없다 | 틀림 | 스레드는 만들고 함께 진행할 수 있음 |
| 같은 인터프리터의 순수 파이썬 계산이 코어 수만큼 자동 병렬화된다 | 틀림 | 전역 잠금이 활성화된 경우 제약이 있음 |
| 잠금이 있으면 잔액 확인과 차감도 하나의 원자적 처리다 | 틀림 | 업무 동작 전체를 묶는 사용자 잠금이 필요 |
| 잠금을 해제하는 외부 연산은 별도로 판단해야 한다 | 맞음 | 실제 계산이 수행되는 위치·구현이 다름 |

특정 내장 연산이 어떤 버전에서 안전하게 처리된다는 관찰과, **확인 → 읽기 → 수정 → 쓰기 전체가 하나의 거래처럼 실행된다는 보장**은 다릅니다. 내장 컨테이너가 내부 잠금을 사용해도 업무상 불변 조건을 자동 보장하지 않습니다.[^freethreading][^nogil]

### 27.4. 자유 스레딩 빌드와 현재 잠금 상태

자유 스레딩 빌드는 전역 인터프리터 잠금 없이 여러 스레드가 파이썬 코드를 실행할 수 있도록 구성한 CPython입니다. 3.13에서 실험적으로 도입되었고, 3.14에서 공식 지원 단계로 전환되었습니다. **이것과 모든 기본 설치에서 잠금이 사라졌다는 주장은 다릅니다.**[^nogil][^supported]

```python
# 예제: 27-02
import sys
import sysconfig

print(sys.implementation.name)  # 관찰: 구현체 이름
print(sysconfig.get_config_var("Py_GIL_DISABLED") == 1)  # 관찰: 빌드의 자유 스레딩 지원

확인함수 = getattr(sys, "_is_gil_enabled", None)
print(확인함수() if 확인함수 else "확인 기능 없음")  # 관찰: 현재 잠금 활성 여부
```

위의 밑줄로 시작하는 함수는 CPython 전용 진단 기능입니다. **빌드가 기능을 지원하는지**와 **현재 실행에서 잠금이 켜져 있는지**를 각각 확인합니다.[^freethreading]

| 확인할 조건 | 이유 |
| --- | --- |
| 구현체·버전·빌드 | 같은 파이썬 버전이라도 실행 조건이 다를 수 있음 |
| 시작 옵션과 현재 잠금 상태 | 지원 빌드에서도 잠금을 켜고 실행할 수 있음 |
| 확장 모듈의 지원 여부 | 일부 모듈을 가져오면 잠금이 다시 활성화될 수 있음 |
| 공유 객체의 사용 방식 | 병렬 실행 가능성과 업무 상태의 안전성은 별개 |
| 실제 작업의 속도·메모리 | 모든 작업에서 성능 개선이 보장되지 않음 |

자유 스레딩은 잠금이 필요 없다는 뜻이 아닙니다. 오히려 기존에 실행 순서에 기대던 코드의 공유 상태를 분명히 점검해야 합니다.[^freethreading][^supported]

### 27.5. 경쟁 상태·임계 구역·동기화 도구

**경쟁 상태**는 실행 순서에 따라 결과가 달라지는 문제입니다. 여러 단계가 함께 지켜져야 하는 구간을 **임계 구역**으로 정하고 같은 잠금으로 보호합니다.[^threading]

다음은 두 스레드가 같은 값을 읽은 뒤 쓰도록 일부러 맞춘 학습 예제입니다. 우연히 재현되기를 기다리지 않도록 `Barrier`로 읽기 완료 시점을 동기화했습니다.

```python
# 예제: 27-03
from threading import Barrier, Thread

횟수 = 0
합류점 = Barrier(2)

def 증가():
    global 횟수
    읽은값 = 횟수
    합류점.wait(timeout=5)
    횟수 = 읽은값 + 1

작업들 = [Thread(target=증가) for _ in range(2)]
for 작업 in 작업들:
    작업.start()
for 작업 in 작업들:
    작업.join()

print(횟수)  # 출력: 1
```

| 단계 | 첫 번째 스레드 | 두 번째 스레드 |
| --- | --- | --- |
| 읽기 | 0을 읽음 | 0을 읽음 |
| 합류 | 두 스레드의 읽기 완료까지 대기 | 두 스레드의 읽기 완료까지 대기 |
| 쓰기 | 읽은 0에 1을 더해 저장 | 읽은 0에 1을 더해 저장 |
| 최종 결과 | 두 번 실행했지만 1 | 같은 증가분을 덮어씀 |

이 출력은 앞의 코드가 의도적으로 만든 순서에서 얻는 결과입니다. 실제 업무에서는 아래처럼 **읽기와 쓰기를 포함하는 전체 갱신**을 보호합니다.

```python
# 예제: 27-04
from threading import Lock, Thread

횟수 = 0
잠금 = Lock()

def 증가():
    global 횟수
    for _ in range(1000):
        with 잠금:
            횟수 += 1

작업들 = [Thread(target=증가) for _ in range(2)]
for 작업 in 작업들:
    작업.start()
for 작업 in 작업들:
    작업.join()

print(횟수)  # 출력: 2000
```

이 코드는 모든 수정 경로가 같은 `잠금`을 사용합니다. 다른 코드가 잠금 없이 같은 값을 수정하면 보호가 깨집니다.

| 도구 | 적합한 목적 | 주의점 |
| --- | --- | --- |
| `Lock` | 한 번에 한 실행만 임계 구역 진입 | 같은 스레드의 중복 획득도 막힐 수 있음 |
| `RLock` | 같은 스레드의 재진입 | 획득 횟수에 맞게 해제 필요 |
| `Condition` | 공유 상태가 조건을 만족할 때까지 대기 | 깨어난 뒤 조건을 다시 확인 |
| `Event` | 준비·종료 등의 신호 전달 | 신호 자체가 복합 자료를 보호하지 않음 |
| `Semaphore` | 동시에 사용하는 자원의 개수 제한 | 초당 요청 횟수 제한과는 다름 |
| `BoundedSemaphore` | 초기 허용량을 넘는 잘못된 해제 탐지 | 역시 자원의 소유 관계를 설계해야 함 |
| `Barrier` | 정해진 실행들이 같은 단계에 도달하도록 합류 | 한쪽이 도달하지 않으면 다른 쪽도 진행 불가 |
| `Queue` | 생산자와 소비자 사이 자료 전달 | 처리 완료는 별도로 기록 |

`Condition.wait()`는 관련 잠금을 놓고 기다린 뒤, 돌아오기 전에 다시 획득합니다. `notify()`는 잠금을 즉시 해제하지 않습니다. 단순 신호보다 실제 조건을 확인하는 `wait_for(조건함수)`가 적합한 상황이 있습니다.[^threading]

`Queue.get()`은 항목을 꺼내는 것이고, `task_done()`은 처리가 끝났다는 표시입니다. `Queue.join()`은 모든 처리가 완료될 때까지 기다립니다. `empty()` 확인 후 `get()`을 호출하는 방식은 그사이에 상태가 바뀔 수 있습니다.[^queue]

**교착 상태**는 서로 상대의 진행을 기다려 아무도 끝나지 못하는 상태입니다. 여러 잠금을 같은 순서로 획득하고, 잠금을 잡은 채 다른 작업의 종료를 불필요하게 기다리지 않는 방향으로 설계합니다. 실행기 안에서도 작업끼리 같은 풀의 결과를 기다리면 교착 상태가 생길 수 있습니다.[^futures]

### 27.6. 프로세스 시작 방식·직렬화·진입점 보호

프로세스의 생성 방법에 따라 가져오는 상태와 제약이 달라집니다.[^multiprocessing]

| 시작 방식 | 핵심 동작 | 주의점 |
| --- | --- | --- |
| `spawn` | 새 인터프리터를 시작하여 필요한 자료 전달 | 작업 함수를 가져올 수 있어야 함 |
| `fork` | 현재 프로세스 상태에서 자식 생성 | 여러 스레드·외부 라이브러리 상태 복제 주의 |
| `forkserver` | 별도의 서버에 자식 생성을 요청 | 지원 운영체제·초기화 조건 확인 |

**3.14 기준**으로 윈도와 macOS는 `spawn`, 이를 지원하는 일반적인 리눅스 환경은 `forkserver`가 기본입니다. `fork`는 더 이상 어느 플랫폼에서도 기본 시작 방식이 아닙니다. 설치 버전의 실제 기본값은 `multiprocessing.get_start_method()`로 확인합니다.[^multiprocessing]

아래는 `spawn`을 명시하여 부모와 자식의 일반 리스트가 분리되는 것을 확인하는 예제입니다. **코드 전체를 하나의 파일로 저장해서 실행합니다.**

```python
# 예제: 27-05
import multiprocessing


def 변경(자료, 전달함):
    자료.append(9)
    전달함.put(자료)


if __name__ == "__main__":
    환경 = multiprocessing.get_context("spawn")
    원본 = [1, 2]
    전달함 = 환경.Queue()
    작업 = 환경.Process(target=변경, args=(원본, 전달함))
    작업.start()
    try:
        결과 = 전달함.get(timeout=10)
        작업.join(timeout=10)
        if 작업.is_alive():
            raise TimeoutError("자식 프로세스 종료 대기 초과")
        if 작업.exitcode != 0:
            raise RuntimeError("자식 프로세스 실패")
        print(원본)  # 출력: [1, 2]
        print(결과)  # 출력: [1, 2, 9]
    finally:
        if 작업.is_alive():
            작업.terminate()
            작업.join()
        작업.close()
        전달함.close()
        전달함.join_thread()
```

부모의 리스트는 바뀌지 않았고, 자식이 만든 결과를 큐로 다시 받았습니다. 큐의 자료를 받기 전에 자식 종료부터 기다리면 큰 자료 전달에서 교착 문제가 생길 수 있으므로 **자료 소비와 종료 대기의 순서**도 고려합니다.[^multiprocessing]

`terminate()`는 이 예제에서 비정상 대기 상황의 정리 수단입니다. 정상 업무의 일반적인 취소 수단으로 남용하면 잠금·큐·파일 상태를 손상시킬 수 있습니다.[^multiprocessing]

| 자주 실패하는 구성 | 이유·수정 방향 |
| --- | --- |
| 최상위에서 무조건 자식 생성 | 자식의 모듈 가져오기 때 다시 생성될 수 있으므로 진입점 보호 |
| 작업 함수로 지역 함수·람다 전달 | 기본 직렬화 방식에서 가져올 수 있는 함수가 아닐 수 있음 |
| 부모의 전역 리스트를 결과함으로 사용 | 자식의 수정이 부모에 자동 반영되지 않음 |
| 서로 다른 생성 문맥의 잠금 혼용 | 시작 방식에 따라 호환되지 않을 수 있음 |
| 파일·연결 객체를 무조건 전달 | 직렬화·운영체제 자원 상속 조건을 확인해야 함 |

공유 메모리나 관리자를 사용하면 명시적으로 공유 상태를 구성할 수 있습니다. 다만 **공유 메모리는 자동 동기화가 아니고, 관리자 프록시의 여러 호출도 하나의 원자적 연산으로 묶이지 않습니다.** `fork`로 시작했다고 일반 객체가 계속 실시간 공유되는 것도 아닙니다.[^sharedmemory][^multiprocessing]

### 27.7. 실행기·작업 풀·결과 객체·취소

실행기는 작업을 제출하고 결과를 수집하는 공통 인터페이스입니다. `Future`는 아직 끝나지 않았을 수 있는 작업의 결과·예외·상태를 나타냅니다.[^executorspep]

```python
# 예제: 27-06
from concurrent.futures import ThreadPoolExecutor


def 두배(값):
    return 값 * 2


with ThreadPoolExecutor(max_workers=2) as 실행기:
    결과 = list(실행기.map(두배, [3, 1, 2]))

print(결과)  # 출력: [6, 2, 4]
```

`map`의 결과는 입력 순서를 따릅니다. 먼저 끝난 작업부터 소비하려면 `as_completed`를 검토합니다. **작업 완료 순서와 결과를 꺼내는 순서는 다를 수 있습니다.**[^futures]

프로세스 풀도 같은 형태의 인터페이스를 사용합니다.

```python
# 예제: 27-07
import multiprocessing
from concurrent.futures import ProcessPoolExecutor


def 제곱(값):
    return 값 * 값


if __name__ == "__main__":
    환경 = multiprocessing.get_context("spawn")
    with ProcessPoolExecutor(max_workers=2, mp_context=환경) as 실행기:
        결과 = list(실행기.map(제곱, [1, 2, 3]))
    print(결과)  # 출력: [1, 4, 9]
```

| 기능 | 의미 | 함정 |
| --- | --- | --- |
| `submit` | 한 작업을 제출하고 결과 객체 반환 | 제출 직후 완료되었다고 볼 수 없음 |
| `result()` | 결과를 기다리고 실패 시 예외 전달 | 대기 시간이 길어질 수 있음 |
| `result(timeout=...)` | 결과를 제한 시간 동안 기다림 | 시간 초과만으로 작업이 취소되지는 않음 |
| `exception()` | 저장된 예외 조회 | 아직 미완료라면 대기할 수 있음 |
| `cancel()` | 아직 시작하지 않은 작업의 취소 시도 | 이미 실행 중이면 보통 취소할 수 없음 |
| `shutdown(cancel_futures=True)` | 아직 시작하지 않은 작업 취소 | 실행 중인 작업을 즉시 종료하지 않음 |

다음은 실행 중인 작업과 아직 대기 중인 작업의 취소를 비교합니다.

```python
# 예제: 27-08
from concurrent.futures import ThreadPoolExecutor
from threading import Event

시작신호 = Event()
종료신호 = Event()


def 대기작업():
    시작신호.set()
    if not 종료신호.wait(timeout=10):
        raise TimeoutError("종료 신호 없음")
    return "완료"


with ThreadPoolExecutor(max_workers=1) as 실행기:
    진행중 = 실행기.submit(대기작업)
    try:
        if not 시작신호.wait(timeout=5):
            raise TimeoutError("시작 신호 없음")
        대기중 = 실행기.submit(lambda: "대기 작업")
        print(진행중.cancel())  # 출력: False
        print(대기중.cancel())  # 출력: True
    finally:
        종료신호.set()
    print(진행중.result())  # 출력: 완료
```

이 코드는 **스레드 풀**이므로 람다를 전달할 수 있습니다. 프로세스 풀로 바꿀 때는 함수의 직렬화 가능성도 다시 확인해야 합니다.

실패는 결과를 꺼내는 지점에서 처리합니다.

```python
# 예제: 27-09
from concurrent.futures import ThreadPoolExecutor


def 검사(값):
    if 값 < 0:
        raise ValueError("음수 입력")
    return 값


with ThreadPoolExecutor(max_workers=1) as 실행기:
    작업 = 실행기.submit(검사, -1)
    try:
        작업.result()
    except ValueError as 오류:
        print(오류)  # 출력: 음수 입력
```

실행기의 `with`를 벗어날 때는 일반적으로 남아 있는 작업의 종료를 기다립니다. 따라서 `result(timeout=...)`에서 시간 초과가 발생했더라도 블록을 빠져나오는 과정은 더 오래 걸릴 수 있습니다.[^futures]

큰 입력을 한꺼번에 제출하면 대기 작업과 결과가 메모리를 차지합니다. 3.14의 `Executor.map`에는 미소비 작업 수를 제한하는 `buffersize`가 추가되었습니다. `chunksize`는 프로세스 풀의 묶음 처리와 관련되며 스레드 풀에는 같은 효과가 없습니다.[^futures]

### 27.8. 다중 인터프리터·격리·자료 전달

**다중 인터프리터**는 한 프로세스 안에 파이썬 실행 상태를 여러 개 두는 방식입니다. 모듈·전역 이름 등의 상태를 분리하고, 적절한 구성에서는 인터프리터별 잠금을 이용해 병렬 실행할 수 있습니다.[^perinterpreter][^interpreterspep]

파이썬 3.14에는 `concurrent.interpreters`와 `InterpreterPoolExecutor`가 추가되었습니다. 여러 인터프리터를 생성하는 것만으로 스레드가 자동 생성되거나 병렬로 실행되지는 않습니다.[^interpreters]

**다음 두 예제는 파이썬 3.14 이상이 필요합니다.** 이 글의 CPython 3.13.5 실행 검증에는 포함하지 않았습니다.

```python
# 예제: 27-10
# 실행 조건: 파이썬 3.14 이상
from concurrent import interpreters

값 = 1
다른해석기 = interpreters.create()
try:
    다른해석기.exec("값 = 10; print(값, flush=True)")  # 출력: 10
    print(값, flush=True)  # 출력: 1
finally:
    다른해석기.close()
```

다른 인터프리터에서 `값`을 바꾸어도 현재 인터프리터의 같은 이름은 바뀌지 않습니다. 위의 직접 실행은 현재 운영체제 스레드에서 차례로 수행하는 예제이지, 병렬 실행을 측정하는 예제가 아닙니다.[^interpreters]

```python
# 예제: 27-11
# 실행 조건: 파이썬 3.14 이상
from concurrent.futures import InterpreterPoolExecutor

if __name__ == "__main__":
    with InterpreterPoolExecutor(max_workers=2) as 실행기:
        결과 = list(실행기.map(pow, [2, 3], [3, 2]))
    print(결과)  # 출력: [8, 9]
```

`InterpreterPoolExecutor`는 작업 스레드마다 별도의 인터프리터를 둡니다. 전달할 호출 대상·인자·반환값의 직렬화와 확장 모듈의 호환성을 확인해야 합니다.[^futures][^interpreterspep]

| 방식 | 실행 상태 | 일반적인 변경 가능 객체 |
| --- | --- | --- |
| 같은 인터프리터의 여러 스레드 | 같은 모듈·전역 상태 | 직접 공유 가능 |
| 다중 인터프리터 | 인터프리터별 상태 분리 | 명시적 전달·복사·지원되는 공유 수단 필요 |
| 여러 프로세스 | 주소 공간과 실행 상태 분리 | 프로세스 간 통신·공유 메모리 필요 |

## 28부. 비동기 프로그래밍

### 28.1. 동기·비동기·블로킹·논블로킹

**동기·비동기**는 작업의 완료를 어떤 흐름으로 다루는지에 관한 구분입니다. **블로킹·논블로킹**은 호출 때문에 현재 실행 흐름이 기다리며 멈추는지에 관한 구분입니다. 두 쌍을 완전히 같은 말로 쓰지 않습니다.[^asyncdesign][^asyncdev]

| 구분 | 확인할 질문 | 예시 |
| --- | --- | --- |
| 동기적 호출 | 이 호출의 결과를 얻은 뒤 다음으로 가는가? | 일반 함수의 결과를 즉시 받음 |
| 비동기적 처리 | 작업의 완료를 별도로 기다리거나 전달받는가? | 코루틴·태스크·완료 통지 |
| 블로킹 | 호출이 끝날 때까지 현재 스레드가 묶이는가? | 일반적인 대기 함수·일부 입출력 호출 |
| 논블로킹 | 당장 처리할 수 없으면 기다리지 않고 돌아오는가? | 준비되지 않은 소켓의 즉시 반환 |

`await`는 현재 코루틴이 기다리도록 만들 수 있지만, 이벤트 루프의 스레드를 그대로 재우는 것과는 다릅니다. 기다리는 대상이 아직 준비되지 않았다면 이벤트 루프는 다른 실행 가능한 작업을 진행할 수 있습니다.[^asyncpep][^asyncdesign]

<mark>이 글의 이벤트 루프 기반 비동기는 기다리는 동안 같은 스레드의 다른 작업을 진행하는 방식입니다. 계산량을 자동으로 줄이거나 새 스레드를 자동 생성하는 기능은 아닙니다.</mark>

### 28.2. 코루틴 함수·코루틴 객체·대기

`async def`로 정의하고 `yield`를 포함하지 않는 함수는 코루틴 함수입니다. 호출하면 **본문을 즉시 끝까지 실행하는 대신 코루틴 객체를 반환**합니다.[^asyncpep]

```python
# 예제: 28-01
import asyncio

실행기록 = []

async def 계산():
    실행기록.append("본문 실행")
    return 6

대상 = 계산()
print(asyncio.iscoroutine(대상))  # 출력: True
print(실행기록)  # 출력: []
print(asyncio.run(대상))  # 출력: 6
print(실행기록)  # 출력: ['본문 실행']
```

| 표현 | 얻는 것·하는 일 |
| --- | --- |
| `계산` | 코루틴 함수 객체 |
| `계산()` | 아직 실행되지 않은 코루틴 객체 |
| `await 계산()` | 현재 코루틴에서 해당 실행을 진행하고 결과를 받음 |
| `create_task(계산())` | 이벤트 루프가 관리하는 태스크 생성 |
| `asyncio.run(계산())` | 최상위에서 이벤트 루프를 관리하며 실행 |

코루틴 객체를 생성만 하고 대기하거나 예약하지 않으면 실행되지 않으며 경고가 발생할 수 있습니다. 이미 완료된 **같은 코루틴 객체**를 다시 실행할 수도 없습니다. 같은 함수를 다시 호출하면 새로운 코루틴 객체를 만들 수 있습니다.[^asyncpep][^asyncdev]

`async def` 안에 일반적인 무거운 계산만 넣으면 여전히 현재 실행을 오래 차지합니다. 함수 앞에 `async`를 붙였다는 이유만으로 다른 스레드에서 계산되지 않습니다.[^asyncdev]

### 28.3. 이벤트 루프·태스크·결과 객체

**이벤트 루프**는 실행 가능한 콜백과 태스크를 진행하고, 입출력·시간·완료 신호를 기다립니다. 하나의 이벤트 루프 스레드에서는 한 번에 하나의 태스크나 콜백이 파이썬 실행을 진행합니다.[^asyncdesign]

| 대상 | 역할 | 주의점 |
| --- | --- | --- |
| 코루틴 객체 | 실행을 중단·재개할 수 있는 계산 | 생성만으로 자동 예약되지 않음 |
| `asyncio.Task` | 코루틴 실행·완료·취소 상태 관리 | 운영체제 스레드 자체가 아님 |
| `asyncio.Future` | 나중에 채워질 결과·예외 | 일반 사용자는 대개 직접 생성할 필요가 없음 |
| `concurrent.futures.Future` | 실행기에 제출한 작업의 결과 | 비동기 결과 객체와 호출 방식이 다름 |

`asyncio.Future`는 완료될 때까지 `await`할 수 있습니다. 반면 아직 끝나지 않았을 때 `.result()`를 직접 호출하면 기다리는 대신 `InvalidStateError`가 발생합니다. 실행기의 결과 객체에서 `.result()`가 블로킹하는 동작과 다릅니다.[^asyncfuture][^futures]

```python
# 예제: 28-02
import asyncio

async def 실행():
    루프 = asyncio.get_running_loop()
    결과 = 루프.create_future()
    루프.call_soon(결과.set_result, 7)
    print(await 결과)  # 출력: 7

asyncio.run(실행())
```

이 코드는 콜백이 결과를 채우고 대기 중인 코루틴이 재개되는 구조를 보여 줍니다. 일반 프로그램에서는 직접 결과 객체를 만들기보다 기존 비동기 함수와 태스크를 사용하는 경우가 많습니다.

실행기의 결과를 이벤트 루프에 연결할 때는 `asyncio.wrap_future` 같은 연결 수단을 사용합니다. 이벤트 루프 안에서 실행기 결과의 `.result()`로 오래 기다리면 다른 태스크의 진행도 막을 수 있습니다.[^asyncfuture][^asyncdev]

따로 생성한 태스크는 태스크 그룹이나 보관 집합 등으로 수명을 관리합니다. 이벤트 루프가 태스크를 약하게 참조하므로, 어디에서도 강하게 보관하지 않은 태스크는 완료 전에 회수될 수 있습니다. 반대로 완료된 태스크를 계속 보관하면 결과와 연결된 자료가 남을 수 있으므로 완료 후 정리와 예외 수집도 필요합니다.[^tasks]

완료된 태스크는 결과를 여러 번 대기하여 받을 수 있습니다. 그러나 결과 객체의 오류·취소 상태도 함께 유지되므로 “여러 번 대기 가능”을 “매번 새로 실행”으로 해석하지 않습니다.[^asyncfuture]

### 28.4. 직접 대기·태스크 예약·실행 시작

아래처럼 하나를 대기한 뒤 다음 코루틴을 만들면 순차적으로 실행됩니다. 동시에 진행시키려면 먼저 태스크를 모두 생성하거나 여러 코루틴을 모아서 예약해야 합니다.[^tasks]

```python
# 예제: 28-03
import asyncio

async def 읽기(값):
    await asyncio.sleep(0)
    return 값

async def 실행():
    첫결과 = await 읽기(1)
    둘째결과 = await 읽기(2)
    print([첫결과, 둘째결과])  # 출력: [1, 2]

    첫작업 = asyncio.create_task(읽기(1))
    둘째작업 = asyncio.create_task(읽기(2))
    print([await 첫작업, await 둘째작업])  # 출력: [1, 2]

asyncio.run(실행())
```

두 출력은 같지만 예약 구조는 다릅니다. 아래쪽은 두 작업을 모두 예약한 뒤 결과를 받습니다. 결과를 첫 번째부터 출력한다고 두 번째 작업의 시작까지 늦춰지는 것은 아닙니다.

**모든 `await`가 다른 태스크로의 전환을 보장하지는 않습니다.** 기다리는 대상이 즉시 완료되면 현재 실행이 계속될 수 있습니다.[^tasks][^asyncpep]

```python
# 예제: 28-04
# 실행 조건: CPython 3.13의 기본 태스크 생성 방식
import asyncio

async def 즉시완료():
    return 1

async def 실행():
    기록 = []

    async def 다른작업():
        기록.append("다른 작업")

    작업 = asyncio.create_task(다른작업())
    await 즉시완료()
    기록.append("현재 작업")
    await 작업
    print(기록)  # 출력: ['현재 작업', '다른 작업']

asyncio.run(실행())
```

이 예제는 **기본 태스크 생성 방식**을 전제로 합니다. 즉시 실행 태스크 팩터리를 설정하면 생성 중 코루틴 본문이 실행될 수 있습니다. 3.14의 `create_task`에는 즉시 시작 제어와 관련된 `eager_start` 인자도 있습니다.[^tasks][^tasks314]

`asyncio.sleep(0)`은 다른 실행에 기회를 주는 명시적인 양보입니다. 그러나 반복마다 양보한다고 무거운 계산이 여러 코어로 나뉘는 것은 아닙니다.[^tasks]

### 28.5. `gather`와 `TaskGroup`의 실패 전파

여러 작업을 묶을 때는 성공 결과뿐 아니라 **한 작업이 실패한 뒤 나머지를 어떻게 처리할지**를 선택해야 합니다.[^tasks]

| 기준 | 기본 `gather` | `TaskGroup` |
| --- | --- | --- |
| 결과 접근 | 입력 순서의 결과 목록 | 생성한 태스크에서 결과 조회 |
| 일반 자식 예외 | 첫 예외를 대기자에게 전달 | 나머지 자식의 취소를 요청 |
| 나머지 작업 | 기본적으로 자동 취소하지 않음 | 정리·종료를 기다린 뒤 구간 이탈 |
| 여러 실패 | 옵션에 따라 결과 위치에 예외 포함 가능 | 관련 예외를 예외 그룹으로 전달 |
| 작업 수명 | 호출자가 별도로 관리할 여지가 큼 | 관리 구간에 작업 수명을 묶음 |

아래에서는 한 작업이 실패해도 다른 작업이 취소되지 않았다는 것을 확인합니다.

```python
# 예제: 28-05
import asyncio

async def 남은작업(진행신호):
    await 진행신호.wait()
    return "계속 진행"

async def 실패작업():
    raise ValueError("입력 오류")

async def 실행():
    신호 = asyncio.Event()
    남은태스크 = asyncio.create_task(남은작업(신호))
    try:
        await asyncio.gather(실패작업(), 남은태스크)
    except ValueError:
        print(남은태스크.cancelled())  # 출력: False
    finally:
        신호.set()
        print(await 남은태스크)  # 출력: 계속 진행

asyncio.run(실행())
```

프로그램을 곧바로 끝내면 `asyncio.run`의 종료 정리 때문에 미완료 작업이 취소되는 모습을 볼 수 있습니다. 그것을 `gather`가 나머지 작업을 자동 취소한 것으로 혼동하지 않습니다.[^runner][^tasks]

다음은 태스크 그룹이 다른 작업의 정리까지 기다리는 예제입니다.

```python
# 예제: 28-06
import asyncio

async def 대기작업(시작신호, 기록):
    try:
        시작신호.set()
        await asyncio.Event().wait()
    finally:
        기록.append("자원 정리")

async def 실패작업(시작신호):
    await 시작신호.wait()
    raise ValueError("처리 실패")

async def 실행():
    시작신호 = asyncio.Event()
    기록 = []
    try:
        async with asyncio.TaskGroup() as 묶음:
            묶음.create_task(대기작업(시작신호, 기록))
            묶음.create_task(실패작업(시작신호))
    except* ValueError:
        print("실패 처리")  # 출력: 실패 처리
    print(기록)  # 출력: ['자원 정리']

asyncio.run(실행())
```

여기서는 일반 예외인 `ValueError`가 실패를 일으킵니다. `CancelledError`는 일반 실패와 다르게 다뤄지고, `KeyboardInterrupt`·`SystemExit`도 특별 처리가 있으므로 모든 예외를 똑같이 설명하지 않습니다.[^tasks314]

`gather(return_exceptions=True)`는 예외를 결과 목록에 포함하여 전체 결과를 확인할 수 있게 합니다. 이것은 작업 성공을 뜻하지 않으며, 반환된 각 항목의 실패 여부를 검사해야 합니다.[^tasks]

### 28.6. 취소·시간 제한·정리

태스크의 `cancel()`은 **취소 요청**입니다. 실행 중인 코드를 운영체제 수준에서 즉시 없애는 명령이 아닙니다. 취소가 전달될 기회에 `CancelledError`가 발생하고, 코루틴은 정리를 수행할 수 있습니다.[^asyncexceptions][^tasks314]

```python
# 예제: 28-07
import asyncio

async def 대기작업(시작신호):
    try:
        시작신호.set()
        await asyncio.Event().wait()
    finally:
        print("정리 완료")  # 출력: 정리 완료

async def 실행():
    시작신호 = asyncio.Event()
    작업 = asyncio.create_task(대기작업(시작신호))
    await 시작신호.wait()
    작업.cancel()
    try:
        await 작업
    except asyncio.CancelledError:
        print("취소 확인")  # 출력: 취소 확인

asyncio.run(실행())
```

취소를 요청한 뒤 `await 작업`으로 종료까지 확인했습니다. 완료를 확인하지 않고 참조만 버리면 자원 정리·실패 수집이 끝났다고 보기 어렵습니다.

**`asyncio.CancelledError`는 `BaseException`의 하위 클래스**입니다. 일반적인 `except Exception`으로는 잡히지 않습니다. 직접 잡았다면 필요한 정리 후 대개 다시 발생시켜 취소를 전파합니다.[^asyncexceptions]

| 도구 | 시간 초과·취소 시 동작 | 핵심 주의점 |
| --- | --- | --- |
| `Task.cancel()` | 해당 태스크에 취소 요청 | 즉시 강제 중단이 아님 |
| `asyncio.timeout()` | 관리 구간의 현재 태스크를 취소하고 바깥에 시간 초과 전달 | 바깥에서 `TimeoutError` 처리 |
| `asyncio.wait_for()` | 지정 대상을 기다리다 시간 초과 시 취소 요청 | 취소 정리를 기다려 더 오래 걸릴 수 있음 |
| `asyncio.wait()` | 조건·시간에 따라 완료·미완료 집합 반환 | 시간 초과만으로 미완료를 자동 취소하지 않음 |
| `asyncio.shield()` | 대기자의 취소가 안쪽 작업으로 전파되는 것을 차단 | 대기자는 여전히 취소될 수 있음 |

아래는 시간 예산을 0으로 두어 **다음 대기 기회에서 시간 초과가 전달되는 구조**만 확인합니다. 실제 서비스의 권장 제한 시간을 제시하는 예제가 아닙니다.[^tasks]

```python
# 예제: 28-08
import asyncio

async def 대기():
    try:
        await asyncio.Event().wait()
    finally:
        print("시간 초과 정리")  # 출력: 시간 초과 정리

async def 실행():
    try:
        async with asyncio.timeout(0):
            await 대기()
    except TimeoutError:
        print("시간 초과 처리")  # 출력: 시간 초과 처리

asyncio.run(실행())
```

시간 초과가 발생해도 취소 처리와 자원 정리에 시간이 필요할 수 있습니다. 이벤트 루프 자체가 블로킹되면 시간 제한의 전달도 늦어질 수 있습니다. **시간 제한을 정확한 시각의 강제 종료 장치로 보지 않습니다.**[^tasks314][^asyncdev]

실행 중인 스레드 함수를 `to_thread`로 호출했다면, 바깥 태스크를 취소해도 그 함수가 즉시 멈추지는 않습니다. 중단 가능한 입출력, 종료 신호, 적절한 작업 분리 등 별도의 설계가 필요합니다.[^futures][^tasks]

### 28.7. 비동기 반복·제너레이터·자원 관리

비동기 반복은 다음 값을 구하는 과정에서 대기가 필요한 반복입니다. `async for`는 비동기 반복 규약을 사용하지만, 각 반복 본문을 자동으로 병렬 실행하지는 않습니다.[^asyncpep][^asyncgen]

| 문법·규약 | 역할 |
| --- | --- |
| `__aiter__` | 비동기 반복자 제공 |
| `__anext__` | 다음 값을 얻을 대기 가능한 객체 제공 |
| `StopAsyncIteration` | 비동기 반복 종료 |
| `async def` 안의 `yield` | 비동기 제너레이터 정의 |
| `__aenter__`·`__aexit__` | 진입·종료 과정에서 대기 가능한 자원 관리 |
| `async with` | 비동기 자원 관리 규약 사용 |

비동기 제너레이터를 중간에 그만 읽는다면 정리 시점을 명확히 하는 것이 좋습니다. `aclosing`은 구간을 벗어날 때 비동기 제너레이터를 닫도록 도와줍니다.[^contextlib][^asyncgen]

```python
# 예제: 28-09
import asyncio
from contextlib import aclosing

async def 자료생성():
    try:
        for 값 in range(3):
            await asyncio.sleep(0)
            yield 값
    finally:
        print("생성기 정리")  # 출력: 생성기 정리

async def 실행():
    async with aclosing(자료생성()) as 생성기:
        async for 값 in 생성기:
            print(값)  # 출력: 0
            break
    print("사용 종료")  # 출력: 사용 종료

asyncio.run(실행())
```

실제 출력 순서는 `0 → 생성기 정리 → 사용 종료`입니다. 생성기 본문의 `finally`가 소스에서 앞에 쓰여 있어도 생성기를 닫는 시점에 실행됩니다.

일반 파일 객체의 `read()`를 비동기 함수 안에서 호출한다고 비동기 파일 읽기가 되지는 않습니다. 비동기 인터페이스를 쓰거나 필요한 블로킹 구간을 다른 실행 단위로 옮겨야 합니다.[^asyncdev]

### 28.8. 블로킹 분리·스레드 연계·동시 실행 수·문맥 변수

이벤트 루프 스레드에서 오래 걸리는 일반 함수를 호출하면 다른 태스크도 진행하지 못합니다. 기존 블로킹 함수는 `asyncio.to_thread`로 스레드에 맡기고 결과를 대기하는 방법이 있습니다.[^asyncdev][^tasks]

```python
# 예제: 28-10
import asyncio
import time


def 기존조회():
    time.sleep(0.01)
    return "조회 완료"


async def 실행():
    결과 = await asyncio.to_thread(기존조회)
    print(결과)  # 출력: 조회 완료

asyncio.run(실행())
```

이 예제의 짧은 대기는 기존 블로킹 입출력을 대신한 것입니다. 전역 잠금을 사용하는 일반 CPython에서 순수 파이썬 계산을 스레드로 옮긴다고 다중 코어 계산이 자동으로 빨라지지는 않습니다.[^threadstate]

다른 스레드에서 이벤트 루프에 콜백을 전달할 때는 `call_soon_threadsafe`, 코루틴을 제출할 때는 `run_coroutine_threadsafe`를 사용합니다. 이벤트 루프의 일반 객체를 아무 스레드에서나 직접 수정하지 않습니다.[^asyncdev]

#### 첫째. 비동기 코드도 공유 상태를 보호해야 합니다

하나의 이벤트 루프에서 실행하더라도 **읽기 → 대기 → 쓰기** 사이에 다른 태스크가 같은 상태를 바꿀 수 있습니다. 이런 논리적 경쟁에는 `asyncio.Lock` 같은 비동기 동기화 도구를 검토합니다.[^asyncsync]

`asyncio`의 잠금·이벤트·세마포어는 운영체제 스레드 간 동기화를 위한 도구가 아닙니다. 반대로 코루틴이 스레드용 잠금을 잡은 채 `await`하면 같은 루프의 다른 태스크가 해당 잠금에서 스레드를 막는 구조를 만들 수 있습니다.[^asyncsync][^asyncdev]

`threading.RLock`도 비동기 태스크용 잠금의 대체재는 아닙니다. 같은 스레드의 재진입을 허용하므로, 같은 이벤트 루프 스레드에서 실행하는 서로 다른 태스크를 구분하여 배제하지 못할 수 있습니다.[^threading][^asyncsync]

#### 둘째. 동시에 실행할 개수를 제한합니다

```python
# 예제: 28-11
import asyncio

async def 실행():
    제한 = asyncio.Semaphore(2)
    진행수 = 0
    최대수 = 0

    async def 처리(값):
        nonlocal 진행수, 최대수
        async with 제한:
            진행수 += 1
            최대수 = max(최대수, 진행수)
            try:
                await asyncio.sleep(0)
                return 값 * 2
            finally:
                진행수 -= 1

    결과 = await asyncio.gather(*(처리(값) for 값 in range(4)))
    print(결과)  # 출력: [0, 2, 4, 6]
    print(최대수)  # 출력: 2

asyncio.run(실행())
```

이 예제는 한 이벤트 루프에서 동작하며, 횟수 갱신 도중에는 대기하지 않습니다. 스레드가 직접 같은 상태를 수정하는 경우까지 안전하다는 뜻은 아닙니다.

**세마포어는 실행 중인 구간을 제한하지만, 생성한 태스크의 전체 개수를 제한하지는 않습니다.** 매우 큰 입력을 모두 태스크로 만들면 대기 중인 태스크가 메모리를 차지합니다. 제한된 크기의 큐와 고정된 소비자 수를 함께 사용할 수 있습니다.[^asyncsync][^asyncqueue]

| 제한 방법 | 제한하는 것 | 별도 관리할 것 |
| --- | --- | --- |
| 세마포어 | 보호 구간의 동시 진입 수 | 이미 생성된 태스크 수 |
| 유한 크기의 큐 | 큐에 쌓인 항목 수 | 항목 크기·입력 보관량·결과 보관량 |
| 고정 소비자 수 | 처리 작업의 수 | 외부 연결·재시도·시간 제한 |
| 요청률 제한 | 일정 시간 동안의 요청량 | 순간 동시 실행 수와 별도 조건 |

큐가 가득 찼을 때 생산자가 `await put()`에서 기다리도록 하면 생산 속도가 소비 속도에 맞춰집니다. 큐의 최대 크기는 보통 **항목 수**이지 메모리 바이트 수가 아닙니다.[^asyncqueue]

#### 셋째. 문맥 변수는 작업별 부가 정보를 관리합니다

문맥 변수는 요청 식별값처럼 현재 실행 문맥에 연결된 값을 관리합니다. 기본 태스크 생성에서는 문맥이 복사되어 사용되므로 같은 스레드의 여러 태스크라도 값의 재설정이 분리될 수 있습니다.[^contextvars][^contextpep]

```python
# 예제: 28-12
import asyncio
from contextvars import ContextVar

요청이름 = ContextVar("요청이름", default="기본")

async def 처리(이름):
    복원표 = 요청이름.set(이름)
    try:
        await asyncio.sleep(0)
        return 요청이름.get()
    finally:
        요청이름.reset(복원표)

async def 실행():
    복원표 = 요청이름.set("바깥")
    try:
        결과 = await asyncio.gather(처리("가"), 처리("나"))
        print(결과)  # 출력: ['가', '나']
        print(요청이름.get())  # 출력: 바깥
    finally:
        요청이름.reset(복원표)

asyncio.run(실행())
```

`set`이 반환한 토큰을 `reset`에 넘기면 이전 상태로 되돌립니다. 문맥이 복사되어도 그 안의 변경 가능한 값까지 깊은 복사되는 것은 아닙니다. 공유 리스트를 값으로 넣었다면 내부 변경은 별도로 판단해야 합니다.[^contextvars][^contextpep]

`to_thread`는 호출 코루틴이 실행될 때의 문맥을 작업 스레드로 전달합니다. 스레드 쪽에서 새로 설정한 문맥 값이 호출자에게 자동 역전파되는 것은 아닙니다. 일반적인 전역 변수나 `threading.local`과 같은 개념으로 취급하지 않습니다.[^tasks][^contextpep]

## 잘 놓치는 핵심

### 1. 참조 수집과 업무상 보관 정책은 다릅니다

계속 접근 가능한 캐시는 수집기가 알아서 비워 주지 않습니다. 필요한 수명보다 오래 보관한다면 캐시 크기·등록 해제·결과 소비 시점을 먼저 바꿉니다.[^functools][^gc]

### 2. 전역 잠금과 사용자 잠금은 역할이 다릅니다

인터프리터 내부를 보호하는 장치가 잔액 확인·차감·기록 전체를 하나로 묶어 주지는 않습니다. 자유 스레딩에서도 업무상 동기화는 별도로 필요합니다.[^threadstate][^freethreading]

### 3. 기다리는 호출이 무엇을 막는지 확인합니다

스레드의 `join`, 실행기 결과의 `result`, 비동기 태스크의 `await`는 모두 기다리는 표현이지만 막는 실행 단위가 다릅니다. 이벤트 루프 안에서는 스레드 전체를 막는 호출을 특히 주의합니다.[^threading][^asyncfuture][^asyncdev]

### 4. 시간 초과와 실제 중단은 다릅니다

결과를 기다리다 시간이 초과되어도 작업이 계속 실행될 수 있습니다. 취소 요청 뒤의 정리와 종료 확인까지 설계해야 합니다.[^futures][^tasks314]

### 5. 큐가 비었다고 모든 처리가 끝난 것은 아닙니다

소비자가 항목을 꺼낸 뒤 처리 중일 수 있습니다. 항목 개수, 처리 중인 작업, 완료 표시를 구분합니다.[^queue][^asyncqueue]

### 6. 태스크를 많이 만드는 것과 처리량 증가는 다릅니다

실행 자원·연결 수·외부 제한을 넘기면 대기와 메모리 사용이 늘어납니다. 동시 진입 수뿐 아니라 입력과 결과의 보관량도 제한합니다.[^asyncsync][^asyncqueue][^futures]

### 7. 버전과 구현체가 없으면 답이 달라질 수 있습니다

전역 잠금, 프로세스 시작 방식, 다중 인터프리터, 참조 계수에 관한 질문에는 구현체·버전·빌드·운영체제 조건을 함께 확인합니다.[^datamodel][^freethreading][^multiprocessing][^interpreters]

| 코루틴 함수를 호출하면 바로 실행되는가? | 코루틴 객체를 만들며 실제 대기·예약이 필요합니다. |
| `await`마다 다른 태스크로 넘어가는가? | 대기 대상이 즉시 완료되면 현재 실행이 이어질 수 있습니다. |
| 비동기 태스크는 스레드인가? | 코루틴의 실행 상태를 관리하는 객체입니다. |
| `gather`는 하나가 실패하면 모두 취소하는가? | 기본 동작은 아니며 태스크 그룹과 구별합니다. |
| 취소하면 즉시 멈추는가? | 요청 전달·정리·종료 확인 과정을 거칩니다. |
| 세마포어만으로 메모리를 제한할 수 있는가? | 생성한 태스크·대기 자료·결과의 보관량은 별도입니다. |

표는 본문의 개념을 압축한 복습용입니다. 답변을 확장할 때는 **정의 → 실행 조건 → 반례 또는 짧은 예제** 순서로 설명하면 됩니다.

## 예시로 한 바퀴: 제한된 큐로 점수 처리하기

다음은 **두 소비자가 작은 큐에서 점수를 꺼내 처리하는 학습 예제**입니다. 실제 외부 통신 없이 `sleep(0)`으로 대기 지점만 표현합니다.

목표는 처리 실패를 기록하면서도 큐의 완료 수를 정확히 맞추고, 예상하지 못한 실패에서는 태스크 그룹이 나머지를 정리하도록 하는 것입니다. 유한 큐와 소비자 수를 이용한 구성입니다.[^asyncqueue][^tasks314]

```python
# 예제: 종합-01
import asyncio

    성공결과 = []
    실패결과 = []

            항목 = await 전달함.get()
            try:
                if 항목 is None:
                    return
                이름, 원문 = 항목
                try:

                        await asyncio.sleep(0)
                        점수 = int(원문)
                        if not 0 <= 점수 <= 100:
                            raise ValueError("점수 범위 오류")
                    성공결과.append((이름, 점수))

                    실패결과.append((이름, "점수 검증 실패"))
                except TimeoutError:
                    실패결과.append((이름, "처리 시간 초과"))
            finally:
                전달함.task_done()

    async with asyncio.TaskGroup() as 묶음:
        for _ in range(소비자수):
            묶음.create_task(소비())
        for 항목 in 입력자료:
            await 전달함.put(항목)
        for _ in range(소비자수):
            await 전달함.put(None)
        await 전달함.join()

    성공결과.sort()
    실패결과.sort()
    print(성공결과)  # 출력: [('가', 80), ('나', 90), ('라', 100)]
    print(실패결과)  # 출력: [('다', '점수 검증 실패')]
    print(sum(점수 for _, 점수 in 성공결과))  # 출력: 270


asyncio.run(실행())
```

### 처리 흐름

| 단계 | 코드가 맡는 역할 | 확인할 원리 |
| --- | --- | --- |
| 큐 생성 | 대기 항목을 최대 두 개까지 보관 | 생산자가 소비 속도를 따라 기다림 |
| 소비자 생성 | 두 개의 처리 태스크 유지 | 모든 입력을 별도 태스크로 만들지 않음 |
| 점수 검증 | 문자열을 정수로 변환하고 범위 확인 | 타입 힌트 대신 실제 입력 검사 |
| 예상한 실패 | 실패 결과에 기록 | 한 항목의 실패를 업무상 결과로 취급 |
| 예상하지 못한 실패 | 태스크 그룹으로 전파 | 관련 작업의 취소·정리 |
| `task_done()` | 꺼낸 항목마다 정확히 한 번 호출 | 성공·실패·종료 표시 모두 정산 |
| 종료 표시 | 소비자 수만큼 `None` 전달 | 각 소비자가 빠져나올 경로 확보 |
| `join`과 그룹 종료 | 자료 처리와 태스크 종료 확인 | 큐의 빈 상태만으로 판단하지 않음 |

이 입력에서 실제 자료는 항상 두 원소 튜플이므로 `None`을 종료 표식으로 구분할 수 있습니다. 일반적인 자료에 `None`도 들어갈 수 있다면 별도의 구별 가능한 표식을 설계해야 합니다.

**이 예제가 프로그램 전체의 메모리를 일정하게 만드는 것은 아닙니다.** 입력과 결과를 리스트에 보관하기 때문입니다. 매우 큰 자료에서는 입력을 순차적으로 읽고, 결과도 유한 큐를 거쳐 파일·저장소에 계속 내보내도록 확장합니다.

결과 리스트는 하나의 이벤트 루프 안에서 수정하고, 개별 `append` 구간에는 대기가 없습니다. 같은 리스트를 작업 스레드와 직접 공유하는 설계로 바꾸면 동기화 조건도 다시 검토해야 합니다.
