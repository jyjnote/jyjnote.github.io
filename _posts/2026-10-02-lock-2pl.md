`Lock`은 <mark>여러 Transaction이 같은 데이터에 동시에 접근할 때 충돌을 막기 위해 데이터 접근을 제한하는 방법</mark>입니다.

`2PL`은 Lock을 획득하는 단계와 해제하는 단계를 분리하여 Transaction의 직렬 가능성을 보장하는 대표적인 동시성 제어 방식입니다.

<blockquote class="prompt-info">
<p>한 줄: Lock은 데이터 접근을 잠그고, 2PL은 Lock 획득과 해제 순서를 규칙으로 만든 방식입니다.</p>
</blockquote>

<details markdown="1">
<summary>한 줄로</summary>

공유 Lock은 읽기, 배타 Lock은 쓰기와 연결되고, 2PL은 Lock 획득 단계와 해제 단계를 나눕니다.

</details>

## Lock이 필요한 이유

두 Transaction이 동시에 같은 데이터를 수정한다고 가정합니다.

### 입력 Table · ACCOUNT

| ACCOUNT_ID | BALANCE |
| --- | ---: |
| A | 10000 |

```text
Transaction 1
→ A 계좌 수정

Transaction 2
→ A 계좌 수정
```

두 Transaction이 동시에 같은 값을 읽고 수정하면 갱신 손실 같은 문제가 발생할 수 있습니다.

Lock을 사용하면 한 Transaction이 데이터를 수정하는 동안 다른 Transaction의 접근을 제한할 수 있습니다.

```text
Transaction 1
→ Lock 획득
→ 데이터 수정
→ Lock 해제

Transaction 2
→ Lock이 해제될 때까지 대기
```

## 공유 Lock

`공유 Lock`은 주로 데이터를 읽을 때 사용하는 Lock입니다.

여러 Transaction이 동시에 같은 데이터를 읽는 것은 일반적으로 허용할 수 있습니다.

```text
Transaction 1
→ 공유 Lock
→ 읽기

Transaction 2
→ 공유 Lock
→ 읽기
```

둘 다 데이터를 변경하지 않으므로 동시에 접근할 수 있습니다.

```text
공유 Lock + 공유 Lock
→ 가능
```

## 배타 Lock

`배타 Lock`은 데이터를 수정할 때 사용하는 Lock입니다.

한 Transaction이 배타 Lock을 가지고 있다면 다른 Transaction은 같은 데이터에 공유 Lock이나 배타 Lock을 얻을 수 없습니다.

```text
Transaction 1
→ 배타 Lock
→ 수정
```

다른 Transaction은 기다려야 합니다.

```text
Transaction 2
→ 접근 대기
```

```text
배타 Lock
→ 단독 사용
```

## 공유 Lock과 배타 Lock 비교

| 구분 | 공유 Lock | 배타 Lock |
| --- | --- | --- |
| 주 용도 | 읽기 | 쓰기 |
| 다른 공유 Lock과 동시 사용 | 가능 | 불가 |
| 다른 배타 Lock과 동시 사용 | 불가 | 불가 |
| 데이터 변경 | 일반적으로 불가 | 가능 |

```text
공유 Lock
→ 여러 Transaction이 함께 읽기 가능
```

```text
배타 Lock
→ 하나의 Transaction만 사용
```

## Lock 호환성

시험에서는 Lock끼리 동시에 사용할 수 있는지를 자주 묻습니다.

| 현재 Lock | 요청 Lock | 허용 여부 |
| --- | --- | --- |
| 공유 | 공유 | O |
| 공유 | 배타 | X |
| 배타 | 공유 | X |
| 배타 | 배타 | X |

가장 간단하게 기억하면 됩니다.

```text
공유 + 공유
→ 가능

나머지 조합
→ 불가
```

<blockquote class="prompt-warning">
<p>기본적인 Lock 호환성 문제에서는 공유 Lock끼리만 동시에 허용된다고 기억하면 빠릅니다.</p>
</blockquote>

## Lock의 기본 흐름

Transaction이 데이터를 사용하려면 먼저 필요한 Lock을 획득합니다.

```text
Lock 요청
↓
Lock 획득
↓
데이터 접근
↓
작업 완료
↓
Lock 해제
```

다른 Transaction이 충돌하는 Lock을 요청하면 대기합니다.

```text
Lock 충돌
→ 대기
```

## 2PL

`2PL`은 `Two-Phase Locking`의 약자입니다.

Transaction의 Lock 동작을 두 단계로 나눕니다.

```text
확장 단계
↓
축소 단계
```

핵심은 한 번 Lock을 해제하기 시작하면 새로운 Lock을 다시 획득하지 않는 것입니다.

## 확장 단계

확장 단계에서는 Lock을 획득할 수 있지만 해제하지 않습니다.

```text
Lock 획득
→ 가능

Lock 추가 획득
→ 가능

Lock 해제
→ 하지 않음
```

Transaction이 필요한 Lock을 점점 늘려가는 단계입니다.

```text
Lock 수
→ 증가
```

## 축소 단계

축소 단계에서는 Lock을 해제할 수 있지만 새로운 Lock을 획득할 수 없습니다.

```text
Lock 해제
→ 가능

새로운 Lock 획득
→ 불가
```

한 번 Lock을 해제하기 시작하면 다시 확장 단계로 돌아갈 수 없습니다.

```text
Lock 수
→ 감소
```

## 2PL 흐름

```text
확장 단계
→ Lock 획득
→ Lock 획득
→ Lock 획득

전환점

축소 단계
→ Lock 해제
→ Lock 해제
```

금지되는 흐름은 다음과 같습니다.

```text
Lock 획득
↓
Lock 해제
↓
새로운 Lock 획득
```

Lock을 해제한 뒤 다시 새로운 Lock을 얻으면 2PL 규칙을 위반합니다.

## 예시

Transaction이 A와 B 데이터를 사용한다고 가정합니다.

### 정상적인 2PL

```text
A Lock 획득
↓
B Lock 획득
↓
A Lock 해제
↓
B Lock 해제
```

```text
확장
→ A Lock
→ B Lock

축소
→ A 해제
→ B 해제
```

2PL 규칙을 만족합니다.

### 2PL 위반

```text
A Lock 획득
↓
A Lock 해제
↓
B Lock 획득
```

A Lock을 해제한 순간 축소 단계에 들어갔으므로 이후 B Lock을 새로 획득할 수 없습니다.

## Lock Point

확장 단계에서 마지막 Lock을 획득한 시점을 `Lock Point`라고 합니다.

```text
Lock 획득
↓
Lock 획득
↓
마지막 Lock 획득
→ Lock Point
↓
Lock 해제 시작
```

Lock Point를 기준으로 Transaction의 직렬 순서를 판단할 수 있습니다.

## 2PL과 직렬 가능성

2PL은 충돌 직렬 가능한 Schedule을 만들기 위한 대표적인 방법입니다.

```text
2PL 준수
→ 직렬 가능성 보장
```

즉, 여러 Transaction이 병행 실행되더라도 결과가 어떤 직렬 실행 결과와 동일하도록 만들 수 있습니다.

다만 2PL이 모든 동시성 문제를 해결하는 것은 아닙니다.

## 2PL과 Deadlock

2PL을 사용하면 Deadlock이 발생할 수 있습니다.

### 예시

```text
Transaction 1
→ A Lock 보유
→ B Lock 기다림
```

```text
Transaction 2
→ B Lock 보유
→ A Lock 기다림
```

서로 상대방의 Lock 해제를 기다리게 됩니다.

```text
T1
→ B 기다림

T2
→ A 기다림

→ Deadlock
```

<blockquote class="prompt-warning">
<p>2PL은 직렬 가능성을 보장할 수 있지만 Deadlock 자체를 방지하는 규칙은 아닙니다.</p>
</blockquote>

## Strict 2PL

`Strict 2PL`은 일반 2PL보다 Lock 해제 시점을 더 엄격하게 제한합니다.

보통 쓰기와 관련된 배타 Lock을 Transaction이 COMMIT 또는 ROLLBACK할 때까지 유지합니다.

```text
배타 Lock 획득
↓
데이터 수정
↓
COMMIT 또는 ROLLBACK
↓
배타 Lock 해제
```

이렇게 하면 다른 Transaction이 아직 확정되지 않은 변경 내용을 사용하는 문제를 줄일 수 있습니다.

## 2PL과 Strict 2PL 비교

| 구분 | 2PL | Strict 2PL |
| --- | --- | --- |
| 단계 | 확장·축소 | 확장·축소 기본 원칙 유지 |
| Lock 해제 | 축소 단계에서 가능 | 배타 Lock을 종료 시점까지 유지 |
| 직렬 가능성 | 보장 가능 | 보장 가능 |
| 회복성 | 기본 수준 | 더 강한 회복성 제공 |

시험에서는 일반 2PL의 두 단계와 Strict 2PL의 Lock 유지 차이를 구분하면 됩니다.

## 잘 놓치는 핵심

### 1. 공유 Lock끼리는 함께 가능

```text
공유 + 공유
→ O
```

### 2. 배타 Lock이 끼면 충돌

```text
공유 + 배타
→ X

배타 + 배타
→ X
```

### 3. 2PL은 두 단계다

```text
확장
→ Lock 획득

축소
→ Lock 해제
```

### 4. Lock 해제 후 새 Lock 획득은 2PL 위반

```text
해제
↓
새 Lock 획득
→ X
```

### 5. 2PL은 Deadlock을 막지 못한다

직렬 가능성은 보장할 수 있지만 Transaction끼리 서로 기다리는 Deadlock은 발생할 수 있습니다.

## 시험·면접

### 핵심 암기

```text
공유 Lock
→ 읽기
→ 공유 Lock끼리 가능
```

```text
배타 Lock
→ 쓰기
→ 다른 Lock과 충돌
```

```text
2PL
→ 확장 단계
→ 축소 단계
```

```text
확장
→ Lock 획득

축소
→ Lock 해제
```

### 시험 함정

2PL의 `2단계`는 Transaction을 두 번 실행한다는 뜻이 아닙니다.

Lock을 **획득하는 단계와 해제하는 단계**로 나눈다는 의미입니다.

또한 2PL을 사용한다고 Deadlock이 발생하지 않는 것은 아닙니다.

### 면접 짧은 답변

Lock은 여러 Transaction이 같은 데이터에 동시에 접근할 때 충돌을 제어하는 방법입니다. 공유 Lock은 주로 읽기에 사용되어 여러 Transaction이 함께 가질 수 있고, 배타 Lock은 쓰기에 사용되어 다른 Lock과 충돌합니다. 2PL은 Lock을 획득하는 확장 단계와 해제하는 축소 단계로 나누며, 한 번 Lock을 해제하기 시작하면 새로운 Lock을 획득할 수 없습니다. 이를 통해 직렬 가능성을 보장할 수 있지만 Deadlock은 발생할 수 있습니다.

## 객관식 문제

### 문제 1 · 공유 Lock

공유 Lock에 대한 설명으로 옳은 것은?

① 여러 Transaction이 동시에 가질 수 없다.  
② 주로 읽기 작업과 관련된다.  
③ 반드시 데이터를 수정한다.  
④ 배타 Lock과 항상 함께 사용할 수 있다.

<details markdown="1">
<summary>정답</summary>

②

공유 Lock은 주로 읽기 작업에 사용되며 여러 Transaction이 동시에 공유 Lock을 가질 수 있습니다.

</details>

### 문제 2 · Lock 호환성

동시에 허용되는 Lock 조합은?

① 공유 + 공유  
② 공유 + 배타  
③ 배타 + 공유  
④ 배타 + 배타

<details markdown="1">
<summary>정답</summary>

①

기본 Lock 호환성에서는 공유 Lock끼리만 동시에 허용됩니다.

</details>

### 문제 3 · 2PL

2PL의 두 단계로 옳은 것은?

① 읽기 단계 · 쓰기 단계  
② 확장 단계 · 축소 단계  
③ COMMIT 단계 · ROLLBACK 단계  
④ 시작 단계 · 종료 단계

<details markdown="1">
<summary>정답</summary>

②

2PL은 Lock을 획득하는 확장 단계와 Lock을 해제하는 축소 단계로 나뉩니다.

</details>

### 문제 4 · 2PL 위반

다음 중 2PL을 위반하는 흐름은?

① A Lock 획득 → B Lock 획득 → A Lock 해제  
② A Lock 획득 → B Lock 획득 → B Lock 해제  
③ A Lock 획득 → A Lock 해제 → B Lock 획득  
④ A Lock 획득 → B Lock 획득 → 모두 해제

<details markdown="1">
<summary>정답</summary>

③

한 번 Lock을 해제해 축소 단계에 들어가면 새로운 Lock을 획득할 수 없습니다.

</details>

### 문제 5 · Deadlock

2PL에 대한 설명으로 옳은 것은?

① Deadlock을 완전히 제거한다.  
② 직렬 가능성을 보장할 수 있지만 Deadlock은 발생할 수 있다.  
③ Lock을 사용하지 않는다.  
④ 배타 Lock을 허용하지 않는다.

<details markdown="1">
<summary>정답</summary>

②

2PL은 직렬 가능성을 보장하는 대표적인 방법이지만 Deadlock 자체를 방지하지는 않습니다.

</details>
