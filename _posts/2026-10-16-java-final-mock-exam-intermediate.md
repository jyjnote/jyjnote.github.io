## 응시 기준

기본 기준은 **자바 21 정식 기능**입니다. 특정 기관의 실제 기출문제나 공식 출제 비중이 아니며, 제한 시간도 이 연습을 위해 제안한 값입니다. 새 미리보기 기능이나 구현체의 우연한 동작은 정답 근거로 삼지 않습니다.

각 문제의 정답은 하나입니다. 코드 문제는 서로 독립된 프로그램이고, 별도로 적지 않은 외부 간섭·인터럽트·자원 부족은 없습니다. 문법 자체를 묻는 문제는 먼저 컴파일 가능 여부를 판단합니다. 한글 이름은 변수·클래스·메서드의 식별자로 사용했습니다.

<mark>정답뿐 아니라 틀린 선택지가 왜 틀렸는지 설명할 수 있어야 해당 개념을 이해한 것으로 봅니다.</mark>

## 실전 문제

### 문제 01. 계산 결과와 대입

다음 코드의 출력 결과로 옳은 것은?

```java
class 문제01 {
    public static void main(String[] 인수) {
        byte 작은값 = 120;
        작은값 += 10;
        double 몫 = 7 / 2;
        System.out.println(작은값 + " " + 몫);
    }
}
```

① `130 3.0`

② `-126 3.0`

③ `-126 3.5`

④ 컴파일 오류가 발생한다.

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ②**

`작은값 + 10`의 계산값은 130입니다. 복합 대입에는 다시 `byte`로 바꾸는 변환이 포함되며, 8비트 부호 있는 값으로 남는 결과는 −126입니다.

`double`은 **결과를 받는 변수의 타입**입니다. `7 / 2` 자체는 정수끼리 계산하므로 3이고, 이를 저장하면서 3.0이 됩니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 오답 | `byte`에는 130을 그대로 저장할 수 없습니다. 이 코드에서는 덧셈 후 축소 변환이 일어납니다. |
| ② | 정답 | 복합 대입의 축소 변환으로 첫 값은 −126이 되고, 정수 나눗셈 결과 3을 실수형에 저장하므로 둘째 값은 3.0입니다. |
| ③ | 오답 | 오른쪽의 `7 / 2`는 두 피연산자가 정수이므로 먼저 정수 나눗셈을 합니다. |
| ④ | 오답 | `작은값 += 10`은 `작은값 = 작은값 + 10`과 형 변환 규칙이 다릅니다. 제시된 복합 대입은 컴파일됩니다. |

**핵심:** 계산 타입을 먼저 판단하고, 마지막에 대입 변환을 적용합니다.[^conversion][^expression]

</details>

### 문제 02. 조건식과 증가 연산

다음 코드의 출력 결과로 옳은 것은?

```java
class 문제02 {
    public static void main(String[] 인수) {
        int 값 = 0;
        boolean 첫째 = 값++ > 0 && ++값 > 1;
        boolean 둘째 = 값 == 1 || ++값 > 2;
        System.out.println(값 + " " + 첫째 + " " + 둘째);
    }
}
```

① `1 false true`

② `2 false true`

③ `3 false true`

④ `1 true true`

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ①**

| 단계 | 판단 | `값` |
| --- | --- | --- |
| `값++ > 0` | 비교에는 0을 사용하므로 거짓입니다. 이후 변수는 증가합니다. | 1 |
| `&&`의 오른쪽 | 왼쪽이 거짓이므로 평가하지 않습니다. | 1 |
| `값 == 1` | 참입니다. | 1 |
| `\|\|`의 오른쪽 | 왼쪽이 참이므로 평가하지 않습니다. | 1 |

증가 기호의 개수를 세는 것이 아니라, **그 식이 실제로 평가되는지**부터 확인합니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 정답 | 첫 조건식과 둘째 조건식에서 모두 오른쪽 식이 생략됩니다. 첫 후위 증가만 반영됩니다. |
| ② | 오답 | 첫 조건식 오른쪽의 전위 증가까지 실행했다고 잘못 계산한 결과입니다. |
| ③ | 오답 | 두 조건식의 오른쪽 증가 연산을 모두 실행한다고 가정한 결과입니다. |
| ④ | 오답 | 후위 증가식은 증가 전 값 0으로 비교합니다. 첫 비교는 거짓입니다. |

**핵심:** 단락 평가로 건너뛴 식에서는 증가 연산도 발생하지 않습니다.[^expression]

</details>

### 문제 03. 반복문 안의 분기

다음 코드가 출력하는 합계는?

```java
class 문제03 {
    public static void main(String[] 인수) {
        int 합계 = 0;
        for (int 수 = 1; 수 <= 4; 수++) {
            switch (수) {
                case 1: 합계 += 1;
                case 2: 합계 += 2; break;
                case 3: continue;
                default: 합계 += 4;
            }
            합계 += 10;
        }
        System.out.println(합계);
    }
}
```

① `37`

② `49`

③ `39`

④ `13`

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ③**

| `수` | 분기 안에서 더하는 값 | 분기 뒤의 10 | 누적 합계 |
| --- | --- | --- | --- |
| 1 | 1과 2 | 더합니다. | 13 |
| 2 | 2 | 더합니다. | 25 |
| 3 | 없습니다. | `continue`로 건너뜁니다. | 25 |
| 4 | 4 | 더합니다. | 39 |

레이블 없는 `break`는 가장 안쪽의 분기문을 끝냅니다. 반면 여기서 `continue`는 반복문의 다음 회차로 진행합니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 오답 | `case 1` 다음에 `break`가 없는데도 `case 2`를 건너뛴 것으로 계산한 결과입니다. |
| ② | 오답 | `continue` 뒤에도 `합계 += 10`을 실행한다고 계산한 결과입니다. |
| ③ | 정답 | 반복별 증가량은 13, 12, 0, 14이므로 합계는 39입니다. |
| ④ | 오답 | `switch`의 `break`가 바깥 반복문까지 종료한다고 잘못 판단한 결과입니다. |

**핵심:** `break`와 `continue`가 어느 구문에 작용하는지 구분합니다.[^statement]

</details>

### 문제 04. 메서드 호출 뒤의 상태

다음 코드의 출력 결과로 옳은 것은?

```java
class 문제04 {
    static void 변경(int 수, int[] 배열) {
        수 += 3;
        배열[0] += 3;
        배열 = new int[]{100};
        배열[0] += 1;
    }
    public static void main(String[] 인수) {
        int 원래값 = 4;
        int[] 원래배열 = {4};
        변경(원래값, 원래배열);
        System.out.println(원래값 + " " + 원래배열[0]);
    }
}
```

① `4 7`

② `7 7`

③ `4 101`

④ `4 4`

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ①**

호출 시 정숫값 4와 배열의 **참조값**이 각각 복사됩니다. `수 += 3`은 메서드 안의 변수만 바꿉니다.

`배열[0] += 3`은 호출자도 가리키는 원래 배열을 바꿉니다. 그다음 `배열 = new int[]{100}`은 매개변수만 새 배열을 가리키게 하므로, 마지막의 101은 호출자의 배열과 관계없습니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 정답 | 정수 매개변수의 변경은 호출자에게 반영되지 않지만, 원래 배열의 원소 변경은 공유됩니다. |
| ② | 오답 | 정수 매개변수를 수정하면 호출자의 정수 변수까지 바뀐다고 잘못 판단했습니다. |
| ③ | 오답 | 배열 매개변수에 새 배열을 대입하면 호출자의 참조도 바뀐다고 잘못 판단했습니다. |
| ④ | 오답 | 배열 전체가 깊게 복사되어 전달된다고 잘못 판단했습니다. |

**핵심:** 객체 내부 변경과 참조 변수의 재대입은 다른 동작입니다.[^type][^expression]

</details>

### 문제 05. 클래스와 객체의 초기화

다음 프로그램을 새로 실행했을 때 출력되는 문자열은?

```java
class 문제05 {
    static class 상위 {
        static { System.out.print("1"); }
        { System.out.print("3"); }
        상위() { System.out.print("4"); }
    }
    static class 하위 extends 상위 {
        static { System.out.print("2"); }
        { System.out.print("5"); }
        하위() { System.out.print("6"); }
    }
    public static void main(String[] 인수) {
        new 하위();
        System.out.print("/");
        new 하위();
    }
}
```

① `132456/3456`

② `123456/123456`

③ `123456/3456`

④ `123465/3465`

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ③**

첫 생성에서는 상위 정적 초기화 1, 하위 정적 초기화 2가 먼저 실행됩니다. 이어 상위 인스턴스 초기화 3 → 상위 생성자 4 → 하위 인스턴스 초기화 5 → 하위 생성자 6이 실행됩니다.

두 번째 생성에서는 이미 끝난 정적 초기화를 반복하지 않습니다. 새 객체를 위한 3 → 4 → 5 → 6만 다시 실행합니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 오답 | 하위 클래스의 정적 초기화보다 상위 객체의 초기화가 먼저 실행된다고 잘못 판단했습니다. |
| ② | 오답 | 두 번째 객체 생성 때에도 정적 초기화 블록이 다시 실행된다고 잘못 판단했습니다. |
| ③ | 정답 | 정적 초기화는 처음에 상위·하위 순서로 한 번 진행되고, 객체 초기화는 객체마다 진행됩니다. |
| ④ | 오답 | 하위 생성자 본문이 하위 인스턴스 초기화 블록보다 먼저 실행된다고 잘못 판단했습니다. |

**핵심:** 클래스 초기화와 객체 초기화는 실행 횟수부터 다릅니다.[^execution]

</details>

### 문제 06. 필드와 메서드의 선택

다음 코드의 출력 결과로 옳은 것은?

```java
class 문제06 {
    static class 상위 {
        int 점수 = 10;
        String 읽기() { return "상"; }
    }
    static class 하위 extends 상위 {
        int 점수 = 20;
        @Override String 읽기() { return "하"; }
    }
    static String 선택(상위 값) { return "넓"; }
    static String 선택(하위 값) { return "좁"; }
    public static void main(String[] 인수) {
        상위 값 = new 하위();
        System.out.println(값.점수 + " " + 값.읽기() + " " + 선택(값));
    }
}
```

① `20 하 좁`

② `10 상 넓`

③ `20 하 넓`

④ `10 하 넓`

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ④**

| 식 | 선택 근거 | 결과 |
| --- | --- | --- |
| `값.점수` | 변수의 선언 타입 `상위` | 10 |
| `값.읽기()` | 실제 객체 `하위`의 재정의 | 하 |
| `선택(값)` | 인수 식의 컴파일 시 타입 `상위` | 넓 |

`선택(하위)`라는 더 좁은 매개변수의 메서드가 있어도, 이번 호출의 인수 식은 `상위` 타입입니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 오답 | 모든 선택을 실제 객체의 타입으로 판단한 결과입니다. |
| ② | 오답 | 재정의한 인스턴스 메서드도 선언 타입만 따라 실행된다고 잘못 판단했습니다. |
| ③ | 오답 | 재정의와 중복 정의는 구분했지만 필드까지 동적으로 선택한다고 잘못 판단했습니다. |
| ④ | 정답 | 필드와 중복 정의 선택에는 선언 타입이, 재정의한 인스턴스 메서드 실행에는 실제 객체가 작용합니다. |

**핵심:** 필드 가림·오버로딩·오버라이딩을 각각 따로 판정합니다.[^class][^expression]

</details>

### 문제 07. 다른 패키지에서의 접근

공개 클래스 `부모`는 `기본` 패키지에 있고, `protected int 점수`를 선언했습니다. 공개 클래스 `자식`은 **다른 패키지인 `확장`에서 `부모`를 상속**합니다.

`자식`의 인스턴스 메서드 안에 `부모 부모참조`, `자식 자식참조`라는 매개변수가 있습니다. 아래 접근 중 **컴파일 가능한 것만** 묶은 선택지는?

| 표시 | 접근식 |
| --- | --- |
| 가 | `this.점수` |
| 나 | `자식참조.점수` |
| 다 | `부모참조.점수` |

모듈 접근 제한은 없고, 참조는 모두 유효하다고 가정합니다.

① 가만 가능하다.

② 가, 다

③ 가, 나, 다

④ 가, 나

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ④**

같은 패키지인지부터 확인합니다. 이 문제는 패키지가 다르므로 상속 관계뿐 아니라 **접근에 쓰는 참조의 타입**도 봐야 합니다.

`this`와 `자식참조`는 조건을 만족합니다. `부모참조`가 실제로 `자식` 객체를 가리키더라도, 그 식의 선언 타입만으로는 이 접근이 허용되지 않습니다.

| 선택지 | 판정 | 해설 |

### 문제 22. 두 데이터 변경을 하나로 처리

```java
        });
        Thread 실행 = new Thread(작업);
        실행.start();
        실행.join();
        System.out.print(작업.isDone() + " ");
        try {
            System.out.print(작업.get());
        } catch (ExecutionException 예외) {
            System.out.print(예외.getCause().getClass().getSimpleName());
        }
    }
}
```

① `false IllegalArgumentException`

② `true 0`

③ `join()`에서 작업 내부 예외가 그대로 전달되어 출력하지 못한다.

④ `true IllegalArgumentException`

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ④**

스레드가 끝날 때까지 기다렸으므로 작업은 완료 상태입니다. **완료에는 성공뿐 아니라 예외로 끝난 경우도 포함**됩니다.

`FutureTask`는 작업에서 나온 예외를 기록합니다. `get()`이 `ExecutionException`을 던지고, 그 원인 예외의 단순 이름이 `IllegalArgumentException`입니다. 대기 중 인터럽트는 없다고 봅니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 오답 | 예외로 끝난 작업은 완료 상태가 아니라고 잘못 판단했습니다. |
| ② | 오답 | 실패한 정수 결과 작업은 기본값 0을 반환한다고 잘못 판단했습니다. |
| ③ | 오답 | `join()`은 스레드 종료를 기다립니다. 이 작업의 예외는 미래 결과에 기록됩니다. |
| ④ | 정답 | 작업은 예외로 완료되었으므로 완료 상태는 참이며, `get()`의 실행 예외에서 원래 원인을 확인합니다. |

**핵심:** 완료 여부는 성공 여부가 아닙니다. 실패 원인은 결과를 가져오는 단계에서 확인합니다.[^future][^futuretask]

### 문제 24. 공유 변수의 증가

| ④ | 오답 | 증가 연산 자체는 허용됩니다. 문제는 연산 전체의 원자성이 보장되지 않는다는 점입니다. |

### 문제 29. 의존성 주입과 테스트 범위

② 저장소 필드가 `final`이므로 대역 저장소를 생성자로 전달할 수 없다.

③ 반환값이 맞았으므로 실제 데이터베이스 질의와 트랜잭션까지 정상이라고 입증했다.

<details markdown="1">
<summary>정답과 해설</summary>

`정산`은 구체적인 데이터베이스 구현을 직접 만들지 않고 `저장소` 계약에 의존합니다. 테스트에서는 그 계약을 구현한 간단한 대역을 넣어 `900 + 100`이라는 계산을 검사할 수 있습니다.

실제 저장소 구현이 올바른 질의를 보내는지, 연결 설정이 맞는지, 실패 시 롤백하는지는 실제 구성요소를 연결한 별도 검사에서 확인해야 합니다.

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 오답 | 생성자를 통해 의존 객체를 전달하는 것은 일반 자바 코드만으로도 가능합니다. |
| ② | 오답 | `final`은 생성 후 재대입을 제한할 뿐, 생성자가 어떤 적합한 구현체를 받을지는 별개입니다. |
| ③ | 오답 | 대역으로 대체한 외부 동작은 이 테스트의 검증 범위에 들어 있지 않습니다. |
| ④ | 정답 | 대역은 계산 로직을 외부 환경에서 분리합니다. 이 테스트가 실제 연결까지 수행한 것은 아닙니다. |

**핵심:** 대역을 사용한 검사는 외부 환경과 로직을 분리하지만, 외부 연동을 대신 검증하지는 않습니다.[^injection]

</details>

### 문제 30. 가상 스레드와 외부 자원

한 서비스는 동시에 들어오는 요청이 많고, 요청 처리 시간의 대부분을 데이터베이스 응답 대기에 씁니다. 데이터베이스 연결 풀의 상한은 30개입니다.

이 서비스에 가상 스레드를 도입할 때 적절한 판단은?

① 대기 중심 작업의 동시 처리에는 도움이 될 수 있지만, 데이터베이스 연결 수 등 외부 자원 한도는 별도로 관리한다.

② 계산 중심 작업도 스레드 수만큼 같은 비율로 빨라진다.

③ 가상 스레드는 가벼우므로 연결 풀의 상한을 없애는 것이 항상 안전하다.

④ 가상 스레드에서는 인터럽트와 스레드 지역 변수를 사용할 수 없다.

<details markdown="1">
<summary>정답과 해설</summary>

**정답: ①**

대기하는 작업이 많을수록 작업마다 운영체제 스레드를 계속 점유하는 부담을 줄이는 접근이 의미 있을 수 있습니다. 다만 실제 개선 정도는 작업 특성과 병목에 따라 달라집니다.

연결을 동시에 30개만 사용할 수 있다면 나머지 요청은 연결을 기다리거나, 서비스의 입장 제한 정책에 따라 조절해야 합니다. **대기 작업을 많이 만들 수 있다는 것과 외부 시스템이 그만큼 처리할 수 있다는 것은 다릅니다.**

| 선택지 | 판정 | 해설 |
| --- | --- | --- |
| ① | 정답 | 가상 스레드로 대기 작업을 표현하기 쉬워져도 데이터베이스의 처리 능력이나 연결 수가 무한해지지는 않습니다. |
| ② | 오답 | 가상 스레드가 계산 자체를 더 빠르게 하거나 프로세서 코어 수를 늘려 주는 것은 아닙니다. |
| ③ | 오답 | 스레드 비용과 데이터베이스 연결 비용·처리 한도는 서로 다른 자원 제약입니다. |
| ④ | 오답 | 가상 스레드도 인터럽트와 스레드 지역 변수를 지원합니다. 사용 비용과 수명 관리는 별도로 고려합니다. |

**핵심:** 가상 스레드는 대기 작업의 규모를 다루는 수단이지 모든 자원 한도를 없애는 기능이 아닙니다.[^virtual]

</details>

## 예시로 한 바퀴 — 오답을 고치는 방법

13번을 틀렸다면 “수정 불가라 원본도 고정된다”라는 자신의 잘못된 가정을 먼저 적습니다. 그다음 원본 목록 하나와 그 원본을 바라보는 뷰, 생성 당시 요소를 담은 복사본을 각각 구분합니다.

원본의 첫 원소를 바꾸고 새 원소를 추가한 뒤, 뷰에는 두 변경이 반영되고 복사본에는 반영되지 않는다고 설명합니다. 마지막으로 11번과 연결하여 **목록의 원소 교체와 원소 객체 내부 변경은 별개**라는 문장을 덧붙입니다.[^list][^collections]

같은 방식으로 문제 23~25를 묶어 “종료를 기다렸다”, “변경을 볼 수 있다”, “갱신 전체가 하나로 실행된다”, “같은 잠금을 쓴다”를 각각 따로 점검합니다.[^future][^memory]

## 버전과 검증 범위

출력값이 정해진 **본문 프로그램 18개**를 자바 21에서 컴파일·실행하여 제시한 정답과 대조했습니다. 8번과 20번은 의도한 원인으로 컴파일 오류가 발생하는지 확인했습니다.

7번의 접근식 3개와 9번의 후보 문장 4개는 각각 독립적으로 컴파일했습니다. 27번은 별도의 두 모듈을 구성하여 기본 상태·내보내기 추가·한정 개방 추가의 리플렉션 접근 차이를 확인했습니다.

추가로 8·20번의 수정 예, 24번의 원자적 증가 대안, 25번의 정적 잠금 대안, 29번의 대역 저장소 예를 검사했습니다. 28번은 대상 17 클래스 파일 생성과 이후 버전 표준 기능의 사용 제한을 확인했으며, 별도의 자바 17 실행 환경에서 실행한 검증은 아닙니다.

24번의 원래 코드는 컴파일을 확인하되 특정 실행값을 정답 근거로 사용하지 않았습니다. 데이터베이스의 실제 연동, 가상 스레드의 처리량, 특정 객체의 회수 시점은 실험으로 검증했다고 주장하지 않습니다. 이런 문항은 문제의 전제와 공식 계약을 기준으로 판단합니다.
