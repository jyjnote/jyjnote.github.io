제3정규형(3NF)은 2NF를 만족하면서 일반 Attribute 사이의 이행 함수 종속을 제거한 상태입니다.

이 글에서는 정의만 외우지 않고 실제 Table을 어떻게 보고 판단하는지까지 연결합니다.

<blockquote class="prompt-info">
<p>한 줄: 3NF는 Key가 아닌 Attribute가 다른 일반 Attribute를 결정하는 구조를 분리합니다.</p>
</blockquote>

<details>
<summary>한 줄로</summary>

3NF = 2NF + 이행 함수 종속 제거

</details>

## 2NF 이후 출발점

2NF 분해 후 다음 ORDERS Relation이 남았다고 해봅시다.

```text
ORDERS
ORDER_ID | ORDER_DATE | CUSTOMER_ID | CUSTOMER_NAME
O1       | 9/1        | C1          | 김고객
O2       | 9/2        | C2          | 이고객
```

Primary Key는 `ORDER_ID`입니다.

## 함수 종속

다음 함수 종속이 있습니다.

```text
ORDER_ID → ORDER_DATE
ORDER_ID → CUSTOMER_ID
CUSTOMER_ID → CUSTOMER_NAME
```

따라서 간접적으로

```text
ORDER_ID → CUSTOMER_NAME
```

도 성립합니다.

## 이행 함수 종속

구조를 따라가 보면 다음과 같습니다.

```text
ORDER_ID
↓
CUSTOMER_ID
↓
CUSTOMER_NAME
```

Primary Key인 ORDER_ID가 CUSTOMER_ID를 결정하고, CUSTOMER_ID가 다시 CUSTOMER_NAME을 결정합니다.

이런 간접 종속을 이행 함수 종속이라고 합니다.

## 왜 문제인가

같은 고객이 여러 주문을 하면 CUSTOMER_NAME이 반복됩니다.

```text
O1 | C1 | 김고객
O3 | C1 | 김고객
O8 | C1 | 김고객
```

고객 이름이 바뀌면 여러 주문 Row를 수정해야 합니다.

수정 이상이 발생할 수 있습니다.

## 3NF 분해

고객 정보를 별도 Relation으로 분리합니다.

```text
ORDERS
ORDER_ID | ORDER_DATE | CUSTOMER_ID

CUSTOMER
CUSTOMER_ID | CUSTOMER_NAME
```

이제 주문은 고객 ID만 참조합니다.

## 분해 후 함수 종속

ORDERS에서는

```text
ORDER_ID → ORDER_DATE, CUSTOMER_ID
```

CUSTOMER에서는

```text
CUSTOMER_ID → CUSTOMER_NAME
```

각 사실이 자신을 결정하는 Key와 함께 저장됩니다.

## 실습 DB와 연결

실습 DB도 같은 구조입니다.

```text
CUSTOMER
→ CUSTOMER_ID, NAME, REGION, GRADE

ORDERS
→ ORDER_ID, CUSTOMER_ID, ORDER_DATE, STATUS
```

주문 Row마다 고객 이름을 반복 저장하지 않고 CUSTOMER_ID만 Foreign Key로 저장합니다.

## 2NF와 3NF 비교

2NF는 복합 Key의 일부에 종속되는 문제를 제거합니다.

3NF는 일반 Attribute를 거쳐 발생하는 이행 종속을 제거합니다.

```text
2NF
→ 부분 함수 종속 제거

3NF
→ 이행 함수 종속 제거
```

## 정확한 3NF 조건

조금 더 정확한 정의에서는 모든 비자명한 함수 종속 `X → A`에 대해 다음 중 하나를 만족하면 3NF로 봅니다.

```text
X가 Super Key
또는
A가 Prime Attribute
```

초급 단계에서는 **일반 Attribute 사이의 이행 종속 제거**로 기억하면 충분하지만, BCNF와 비교할 때는 이 정확한 조건이 중요합니다.

## 3NF 판단 순서

다음 순서로 확인합니다.

```text
1. 2NF 확인
2. Candidate Key 확인
3. 일반 Attribute가 다른 일반 Attribute를 결정하는지 확인
4. Key → 일반 → 일반 구조 찾기
5. 이행 종속을 별도 Relation으로 분리
```

특히 `A → B → C` 형태를 찾는 것이 핵심입니다.

## 3NF 이후

3NF는 실무에서 많이 사용하는 정규화 수준입니다.

하지만 모든 결정자가 반드시 Super Key인 것은 아닐 수 있습니다.

이 더 강한 조건을 요구하는 것이 BCNF입니다.

## 다른 개념과 비교

### 비교 1. 2NF

```text
2NF
→ 부분 종속 제거
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 2. 3NF

```text
3NF
→ 이행 종속 제거
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 3. BCNF

```text
BCNF
→ 모든 결정자 Super Key
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 실수 1. Table 이름만 보고 Entity와 Relation을 같은 수준으로 생각한다.

이 실수를 피하려면 다음 순서를 지킵니다.


## 시험·면접

### 핵심 암기

```text
3NF = 2NF + 이행 함수 종속 제거
```

### 시험 접근 순서

```text
1. Entity 또는 Relation 확인
2. Candidate Key 확인
3. 함수 종속 확인
4. 이상 현상 확인
5. 정규형 조건 확인
6. 필요한 분해 확인
```

### 시험 함정

현재 예시 데이터에서 값이 우연히 유일하다고 해서 함수 종속이나 Key가 자동으로 성립하는 것은 아닙니다.

Schema와 업무 규칙을 기준으로 판단해야 합니다.

### 면접에서 짧게 답한다면

제3정규형(3NF)은 2NF를 만족하면서 일반 Attribute 사이의 이행 함수 종속을 제거한 상태입니다.

정규화와 모델링에서는 Key와 함수 종속을 기준으로 중복과 이상 현상을 줄이는 방향으로 구조를 설계합니다.

## 예시로 한 바퀴

`제3정규형 · 3NF` 문제를 만나면 작은 Relation부터 그립니다.

```text
Key
→ 결정되는 Attribute
→ 반복되는 사실
→ 발생 가능한 이상 현상
```

그다음 어떤 Attribute가 어떤 Key에 종속되는지 화살표로 표시합니다.

마지막으로 분해가 필요하다면 **같은 사실을 한 곳에서만 관리할 수 있도록** Relation을 나눕니다.
