`제3정규형`은 <mark>제2정규형을 만족하면서 비주요 Attribute 사이의 이행 함수 종속을 제거한 상태</mark>입니다.

핵심은 **Key가 아닌 Attribute가 다른 일반 Attribute를 거쳐 결정되지 않도록 Table을 분리하는 것**입니다.

<blockquote class="prompt-info">
<p>한 줄: 제3정규형은 Key가 아닌 Attribute 사이의 이행 함수 종속을 제거합니다.</p>
</blockquote>

<details markdown="1">
<summary>한 줄로</summary>

2NF를 만족한 뒤 이행 함수 종속을 제거하면 3NF입니다.

</details>

## 먼저 이행 함수 종속

다음 학생 Table을 보겠습니다.

| 학생번호 | 학생이름 | 학과코드 | 학과명 |
| --- | --- | --- | --- |
| 1001 | 학생1 | D01 | 컴퓨터공학 |
| 1002 | 학생2 | D02 | 통계학 |
| 1003 | 학생3 | D01 | 컴퓨터공학 |

Primary Key가 `학생번호`라고 가정합니다.

함수적 종속은 다음과 같습니다.

```text
학생번호
→ 학생이름
```

```text
학생번호
→ 학과코드
```

```text
학과코드
→ 학과명
```

따라서 다음 관계도 성립합니다.

```text
학생번호
→ 학과코드
→ 학과명
```

학생번호가 학과코드를 거쳐 학과명을 결정합니다.

이런 관계를 `이행 함수 종속`이라고 합니다.

## 이행 함수 종속 구조

기본 형태는 다음과 같습니다.

```text
A → B
B → C
```

그러면 결과적으로

```text
A → C
```

가 성립합니다.

하지만 C가 A에 직접적으로만 종속되는 것이 아니라 B를 거쳐 결정됩니다.

```text
A
→ B
→ C
```

제3정규형에서는 이러한 구조를 제거합니다.

## 왜 문제가 되는가

기존 Table을 다시 보겠습니다.

| 학생번호 | 학생이름 | 학과코드 | 학과명 |
| --- | --- | --- | --- |
| 1001 | 학생1 | D01 | 컴퓨터공학 |
| 1002 | 학생2 | D02 | 통계학 |
| 1003 | 학생3 | D01 | 컴퓨터공학 |

`D01`과 `컴퓨터공학` 정보가 여러 Row에 반복됩니다.

```text
D01
→ 컴퓨터공학
```

학생이 늘어날수록 같은 학과 정보가 계속 중복됩니다.

이 때문에 학과명이 변경되면 여러 Row를 함께 수정해야 할 수 있습니다.

## 수정 이상 예시

D01의 학과명이 `컴퓨터공학과`로 변경되었다고 가정합니다.

한 Row만 수정하면 다음처럼 됩니다.

| 학생번호 | 학과코드 | 학과명 |
| --- | --- | --- |
| 1001 | D01 | 컴퓨터공학과 |
| 1003 | D01 | 컴퓨터공학 |

같은 `D01`인데 학과명이 서로 달라졌습니다.

```text
이행 함수 종속
↓
중복
↓
수정 이상 가능
```

## 제3정규형으로 분해

이행 함수 종속을 만드는 부분을 별도 Table로 분리합니다.

### 학생 Table

| 학생번호 | 학생이름 | 학과코드 |
| --- | --- | --- |
| 1001 | 학생1 | D01 |
| 1002 | 학생2 | D02 |
| 1003 | 학생3 | D01 |

```text
학생번호
→ 학생이름

학생번호
→ 학과코드
```

### 학과 Table

| 학과코드 | 학과명 |
| --- | --- |
| D01 | 컴퓨터공학 |
| D02 | 통계학 |

```text
학과코드
→ 학과명
```

이제 학과명은 학생 Table에 반복 저장되지 않습니다.

```text
이행 함수 종속 제거
↓
중복 감소
↓
제3정규형
```

## 변환 전과 후

### 변환 전

| 학생번호 | 학생이름 | 학과코드 | 학과명 |
| --- | --- | --- | --- |
| 1001 | 학생1 | D01 | 컴퓨터공학 |
| 1002 | 학생2 | D02 | 통계학 |
| 1003 | 학생3 | D01 | 컴퓨터공학 |

```text
학생번호
→ 학과코드
→ 학과명
```

### 변환 후

```text
학생 Table
→ 학생번호, 학생이름, 학과코드

학과 Table
→ 학과코드, 학과명
```

이제 학생 Table 안에서 일반 Attribute가 다른 일반 Attribute를 거쳐 결정되지 않습니다.

## 비주요 Attribute

제3정규형에서는 `비주요 Attribute`라는 표현이 중요합니다.

비주요 Attribute는 후보 Key를 구성하지 않는 일반 Attribute입니다.

예를 들어 다음 Table에서

| 학생번호 | 학생이름 | 학과코드 | 학과명 |
| --- | --- | --- | --- |
| 1001 | 학생1 | D01 | 컴퓨터공학 |
| 1002 | 학생2 | D02 | 통계학 |

학생번호가 유일한 후보 Key라면

```text
학생번호
→ 주요 Attribute
```

```text
학생이름
학과코드
학과명
→ 비주요 Attribute
```

가 됩니다.

비주요 Attribute인 `학과코드`가 또 다른 비주요 Attribute인 `학과명`을 결정하고 있으므로 3NF 위반의 대표적인 형태가 됩니다.

## 2NF와 3NF 차이

| 구분 | 제거 대상 |
| --- | --- |
| 제2정규형 | 부분 함수 종속 |
| 제3정규형 | 이행 함수 종속 |

### 제2정규형

```text
복합 Key 일부
→ 일반 Attribute
```

를 제거합니다.

### 제3정규형

```text
Key
→ 일반 Attribute
→ 또 다른 일반 Attribute
```

구조를 제거합니다.

## 1NF · 2NF · 3NF 흐름

```text
1NF
→ 원자값
```

```text
2NF
→ 부분 함수 종속 제거
```

```text
3NF
→ 이행 함수 종속 제거
```

정규화는 앞 단계를 만족한 상태에서 다음 단계로 진행합니다.

```text
1NF
↓
2NF
↓
3NF
```

## 제3정규형 판단 순서

### 1. 2NF인지 확인

먼저 부분 함수 종속이 제거되어 있어야 합니다.

### 2. 함수적 종속 확인

다음과 같은 관계가 있는지 찾습니다.

```text
Key → A
A → B
```

### 3. A와 B가 비주요 Attribute인지 확인

비주요 Attribute 사이에서 종속 관계가 발생한다면 이행 함수 종속을 의심합니다.

### 4. 별도 Table로 분리

```text
A → B
```

관계를 별도 Table로 분리합니다.

## 잘 놓치는 핵심

### 1. 3NF는 2NF를 먼저 만족해야 한다

```text
2NF
+
이행 함수 종속 제거
=
3NF
```

### 2. 일반 Attribute가 다른 일반 Attribute를 결정하는지 본다

```text
Key
→ A
→ B
```

형태를 찾으면 됩니다.

### 3. Key에서 직접 결정되는 것은 문제의 핵심이 아니다

```text
학생번호
→ 학생이름
```

처럼 Key가 일반 Attribute를 직접 결정하는 것은 자연스럽습니다.

문제는 다음과 같은 구조입니다.

```text
학생번호
→ 학과코드
→ 학과명
```

### 4. 3NF 이후에도 더 강한 정규형이 있다

제3정규형보다 더 엄격한 조건을 가지는 `BCNF`가 있습니다.

<blockquote class="prompt-warning">
<p>시험에서는 2NF의 부분 함수 종속과 3NF의 이행 함수 종속을 혼동하지 않는 것이 중요합니다.</p>
</blockquote>

## 시험·면접

### 핵심 암기

```text
3NF
→ 2NF 만족
→ 이행 함수 종속 제거
```

```text
A → B
B → C
→ A → C
```

```text
Key
→ 일반 Attribute
→ 일반 Attribute
```

### 시험 함정

복합 Key가 없다고 해서 자동으로 제3정규형이 되는 것은 아닙니다.

부분 함수 종속은 없을 수 있지만 이행 함수 종속은 여전히 존재할 수 있습니다.

### 면접 짧은 답변

제3정규형은 제2정규형을 만족하면서 비주요 Attribute 사이의 이행 함수 종속을 제거한 형태입니다. 예를 들어 학생번호가 학과코드를 결정하고 학과코드가 학과명을 결정한다면 학과 정보를 별도 Table로 분리하여 중복과 수정 이상을 줄일 수 있습니다.

## 객관식 문제

### 문제 1 · 핵심

제3정규형의 핵심으로 가장 적절한 것은?

① 원자값 보장  
② 부분 함수 종속 제거  
③ 이행 함수 종속 제거  
④ 모든 Table 통합

<details markdown="1">
<summary>정답</summary>

③

제3정규형은 비주요 Attribute 사이의 이행 함수 종속을 제거하는 단계입니다.

</details>

### 문제 2 · 이행 함수 종속

다음 관계가 있을 때 나타나는 종속은?

```text
학생번호 → 학과코드
학과코드 → 학과명
```

① 부분 함수 종속  
② 이행 함수 종속  
③ 다치 종속  
④ 함수적 종속이 없음

<details markdown="1">
<summary>정답</summary>

②

학생번호가 학과코드를 거쳐 학과명을 결정하므로 이행 함수 종속입니다.

```text
학생번호
→ 학과코드
→ 학과명
```

</details>

### 문제 3 · 분해

다음 Table을 3NF로 분해할 때 가장 적절한 구조는?

| 학생번호 | 학생이름 | 학과코드 | 학과명 |
| --- | --- | --- | --- |

① 학생 Table 하나만 유지  
② 학생 Table과 학과 Table로 분리  
③ 모든 Column 삭제  
④ 학생번호를 제거

<details markdown="1">
<summary>정답</summary>

②

다음처럼 분리할 수 있습니다.

```text
학생
→ 학생번호, 학생이름, 학과코드

학과
→ 학과코드, 학과명
```

</details>

### 문제 4 · 2NF와 3NF

다음 연결로 옳은 것은?

① 2NF → 이행 함수 종속 제거  
② 3NF → 부분 함수 종속만 제거  
③ 2NF → 부분 함수 종속 제거  
④ 1NF → 이행 함수 종속 제거

<details markdown="1">
<summary>정답</summary>

③

제2정규형은 부분 함수 종속을 제거하고, 제3정규형은 이행 함수 종속을 제거합니다.

</details>

### 문제 5 · 복합 Key

다음 설명으로 옳은 것은?

① 복합 Key가 없으면 반드시 3NF이다.  
② 복합 Key가 없어도 이행 함수 종속이 존재할 수 있다.  
③ 3NF는 원자값과 관계없다.  
④ 3NF에서는 Primary Key를 제거한다.

<details markdown="1">
<summary>정답</summary>

②

복합 Key가 없어 부분 함수 종속이 없더라도 비주요 Attribute 사이의 이행 함수 종속은 존재할 수 있습니다.

</details>
