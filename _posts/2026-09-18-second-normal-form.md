제2정규형(2NF)은 1NF를 만족하면서 모든 일반 Attribute가 Candidate Key 전체에 완전 함수 종속되도록 부분 함수 종속을 제거한 상태입니다.

이 글에서는 정의만 외우지 않고 실제 Table을 어떻게 보고 판단하는지까지 연결합니다.

<blockquote class="prompt-info">
<p>한 줄: 2NF는 복합 Key의 일부만으로 결정되는 일반 Attribute를 별도 Relation으로 분리합니다.</p>
</blockquote>

<details>
<summary>한 줄로</summary>

2NF = 1NF + 부분 함수 종속 제거

</details>

## 출발 Table

다음 주문 상세 통합 Table을 봅니다.

```text
주문상세_통합

ORDER_ID | ORDER_DATE | CUSTOMER_ID | CUSTOMER_NAME | PRODUCT_ID | PRODUCT_NAME | PRICE | QTY
O1       | 9/1        | C1          | 김고객        | P1         | 키보드       | 50000 | 1
O1       | 9/1        | C1          | 김고객        | P2         | 마우스       | 30000 | 2
O2       | 9/2        | C2          | 이고객        | P1         | 키보드       | 50000 | 1
```

한 주문에 여러 상품이 있으므로 한 Row를 식별하려면 다음 복합 Key를 생각할 수 있습니다.

```text
(ORDER_ID, PRODUCT_ID)
```

이제 각 일반 Attribute가 이 복합 Key 전체에 의존하는지 확인합니다.

## 함수 종속 정리

다음 함수 종속이 존재한다고 해봅시다.

```text
ORDER_ID → ORDER_DATE, CUSTOMER_ID, CUSTOMER_NAME

PRODUCT_ID → PRODUCT_NAME, PRICE

(ORDER_ID, PRODUCT_ID) → QTY
```

`QTY`는 주문과 상품을 함께 알아야 결정됩니다.

하지만 `ORDER_DATE`는 ORDER_ID만 알아도 결정됩니다.

`PRODUCT_NAME`은 PRODUCT_ID만 알아도 결정됩니다.

## 부분 함수 종속

복합 Key 일부만으로 일반 Attribute가 결정되는 것이 부분 함수 종속입니다.

```text
(ORDER_ID, PRODUCT_ID)
```

중 일부인

```text
ORDER_ID
```

만으로 `ORDER_DATE`, `CUSTOMER_ID`가 결정됩니다.

또 일부인

```text
PRODUCT_ID
```

만으로 `PRODUCT_NAME`, `PRICE`가 결정됩니다.

이 Relation은 2NF를 만족하지 않습니다.

## 완전 함수 종속

`QTY`는 다릅니다.

```text
(ORDER_ID, PRODUCT_ID) → QTY
```

ORDER_ID만으로는 어떤 상품의 수량인지 알 수 없습니다.

PRODUCT_ID만으로도 어떤 주문의 수량인지 알 수 없습니다.

복합 Key 전체가 필요합니다.

이것이 완전 함수 종속입니다.

## 2NF 분해

부분 함수 종속을 분리합니다.

```text
ORDERS
ORDER_ID | ORDER_DATE | CUSTOMER_ID | CUSTOMER_NAME

PRODUCT
PRODUCT_ID | PRODUCT_NAME | PRICE

ORDER_ITEM
ORDER_ID | PRODUCT_ID | QTY
```

이제 ORDER_ITEM의 `QTY`는 복합 Key 전체에 의존합니다.

## 아직 3NF는 아니다

ORDERS를 자세히 보면 다음 관계가 남아 있을 수 있습니다.

```text
ORDER_ID → CUSTOMER_ID
CUSTOMER_ID → CUSTOMER_NAME
```

즉

```text
ORDER_ID → CUSTOMER_NAME
```

이라는 이행 종속이 생깁니다.

2NF는 만족해도 3NF는 아직 위반할 수 있습니다.

## 단일 Key Relation

Candidate Key가 단일 Attribute라면 부분 함수 종속은 발생할 수 없습니다.

부분 함수 종속은 **복합 Candidate Key의 일부**에 대한 종속이기 때문입니다.

따라서 단일 Key Relation이 1NF라면 부분 함수 종속 때문에 2NF를 위반하는 경우는 없습니다.

## 2NF 판단 순서

다음 순서로 풉니다.

```text
1. 1NF인지 확인
2. Candidate Key 찾기
3. Candidate Key가 복합인지 확인
4. 일반 Attribute가 Key 일부에 종속되는지 확인
5. 부분 종속 Attribute를 별도 Relation으로 분리
```

시험에서는 3번과 4번이 핵심입니다.

## 분해 전후 이상 현상

분해 전에는 PRODUCT_NAME이 주문 Row마다 반복됩니다.

상품 이름이 바뀌면 여러 Row를 수정해야 합니다.

분해 후에는 PRODUCT에서 한 번만 수정하면 됩니다.

```text
PRODUCT_ID → PRODUCT_NAME
```

이라는 사실을 PRODUCT Relation 한 곳에 저장하기 때문입니다.

## 2NF와 1NF 비교

| 구분 | 1NF | 2NF |
| --- | --- | --- |
| 핵심 | 원자값 | 부분 함수 종속 제거 |
| Key 분석 | 기본 | 복합 Key 중요 |
| 대표 문제 | 다중값 Cell | Key 일부에 종속 |
| 다음 단계 | 2NF | 3NF |

2NF는 함수 종속 분석이 본격적으로 들어가는 단계입니다.

## 다른 개념과 비교

### 비교 1. 1NF

```text
1NF
→ 원자값
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 2. 2NF

```text
2NF
→ 부분 종속 제거
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

### 비교 3. 3NF

```text
3NF
→ 이행 종속 제거
```

비교할 때는 **무엇을 결정하는가**, **어떤 중복을 줄이는가**, **어떤 성능 비용이 생기는가**를 구분합니다.

## 자주 하는 실수

### 실수 1. Table 이름만 보고 Entity와 Relation을 같은 수준으로 생각한다.

이 실수를 피하려면 다음 순서를 지킵니다.

```text
업무 규칙
→ Key
→ 함수 종속
→ 이상 현상
→ 필요한 분해
```

`제2정규형 · 2NF`에서도 데이터 몇 Row만 보고 판단하지 말고 **Schema의 의미와 업무 규칙**을 기준으로 봅니다.

### 실수 2. Key를 찾기 전에 정규형부터 판단한다.

이 실수를 피하려면 다음 순서를 지킵니다.

```text
업무 규칙
→ Key
→ 함수 종속
→ 이상 현상
```

## 시험·면접

### 핵심 암기

```text
2NF = 1NF + 부분 함수 종속 제거
```

### 시험 접근 순서

```text
1. Entity 또는 Relation 확인
2. Candidate Key 확인
3. 함수 종속 확인
4. 이상 현상 확인
5. 정규형 조건 확인
6. 필요한 분해 확인
```

### 시험 함정

현재 예시 데이터에서 값이 우연히 유일하다고 해서 함수 종속이나 Key가 자동으로 성립하는 것은 아닙니다.

Schema와 업무 규칙을 기준으로 판단해야 합니다.

### 면접에서 짧게 답한다면

제2정규형(2NF)은 1NF를 만족하면서 모든 일반 Attribute가 Candidate Key 전체에 완전 함수 종속되도록 부분 함수 종속을 제거한 상태입니다.

정규화와 모델링에서는 Key와 함수 종속을 기준으로 중복과 이상 현상을 줄이는 방향으로 구조를 설계합니다.

## 예시로 한 바퀴

`제2정규형 · 2NF` 문제를 만나면 작은 Relation부터 그립니다.

```text
Key
→ 결정되는 Attribute
→ 반복되는 사실
→ 발생 가능한 이상 현상
```

그다음 어떤 Attribute가 어떤 Key에 종속되는지 화살표로 표시합니다.

마지막으로 분해가 필요하다면 **같은 사실을 한 곳에서만 관리할 수 있도록** Relation을 나눕니다.
