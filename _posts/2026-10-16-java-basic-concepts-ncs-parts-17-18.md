## 17부. 개발 도구·빌드·테스트·배포·진단

### 137. 기본 개발 도구

**개발 도구는 입력과 결과물을 기준으로 구분합니다.** 소스를 클래스 파일로 바꾸는 도구, 프로그램을 실행하는 도구, 클래스 파일을 조사하는 도구는 서로 다릅니다.[^tools]

#### 137-1. 핵심 도구의 역할

| 도구 | 주된 입력 | 하는 일 | 시험에서 구분할 점 |
| --- | --- | --- | --- |
| `javac` | 자바 소스 | 클래스 파일 생성 | 컴파일러 |
| `java` | 실행할 클래스·아카이브·소스 | 프로그램 실행 | 실행기 |
| `javadoc` | 소스와 문서화 주석 | 설명 문서 생성 | 일반 실행 결과를 만드는 도구가 아님 |
| `jshell` | 짧은 선언·문장·표현식 | 대화형 실행 | 작은 문법 실험에 사용 |
| `javap` | 클래스 파일 | 선언·바이트코드 정보 표시 | 원래 소스를 완벽히 복구하지 않음 |
| `jar` | 클래스·자원 파일 | 아카이브 생성·조회 | 컴파일러가 아님 |

통합 개발 환경의 실행 버튼도 내부적으로 컴파일과 실행 설정을 이용합니다. 버튼 하나로 보인다는 이유로 두 과정이 같아지는 것은 아닙니다.

#### 137-2. 컴파일과 실행을 직접 구분하기

파일 이름은 `Main.java`입니다.

```java
public class Main {
    public static int 더하기(int 첫째, int 둘째) {
        return 첫째 + 둘째;
    }

    public static void main(String[] 인수) {
        System.out.println(더하기(3, 4));
    }
}
```

컴파일과 실행:

```text
javac -encoding UTF-8 --release 21 -d out Main.java
java -cp out Main
```

출력:

```text
7
```

| 부분 | 의미 |
| --- | --- |
| `-encoding UTF-8` | 소스 파일을 읽을 문자 인코딩 |
| `--release 21` | 자바 21의 언어·대상 클래스 형식·지원 표준 기능을 기준으로 컴파일 |
| `-d out` | 클래스 파일을 저장할 위치 |
| `-cp out` | 실행할 클래스를 찾을 경로 |
| `Main` | 실행할 클래스 이름. 일반 클래스 실행에서 `.class`를 붙이지 않음 |

`java Main.java`처럼 소스 파일을 실행하는 방식도 있지만, **소스가 바로 기계어가 된다는 뜻은 아닙니다.** 실행기가 소스 실행 절차를 제공하는 것입니다.[^javac][^java]

#### 137-3. 실행·클래스·모듈·소스 경로를 혼동하지 않기

| 구분 | 찾는 대상 | 예시 |
| --- | --- | --- |
| 운영체제의 실행 경로 | `java`, `javac` 같은 실행 파일 | `PATH` |
| 개발 도구 설치 위치 | 빌드 도구 등이 사용할 개발 도구 | `JAVA_HOME` |
| 클래스 경로 | 클래스 파일·아카이브 | `-cp`, `--class-path` |
| 모듈 경로 | 이름 있는 모듈 | `--module-path` |
| 소스 경로 | 추가로 찾을 자바 소스 | `--source-path` |

`JAVA_HOME`만 바꿨는데 실행되는 `java`가 그대로일 수 있습니다. 운영체제의 실행 경로, 통합 개발 환경 설정, 빌드 도구의 설정을 각각 확인해야 합니다.

아래 명령은 **해당 클래스와 의존성이 실제로 준비되어 있다는 전제**의 경로 작성 예시입니다.

```text
윈도우: java -cp "out;lib/*" Main
리눅스·맥: java -cp "out:lib/*" Main
```

클래스가 `study.Main`이면 클래스 경로는 `study` 폴더 자체가 아니라 그 상위 루트를 가리킵니다. `import`는 이름을 줄여 쓰는 선언이지, 외부 라이브러리를 내려받거나 경로를 자동 등록하는 명령이 아닙니다.

#### 137-4. 경고·디버그 정보·매개변수 이름

| 옵션 | 목적 | 같지 않은 것 |
| --- | --- | --- |
| `-Xlint:all` | 여러 종류의 경고 확인 | 모든 논리 오류 검출 |
| `-Werror` | 경고가 있으면 컴파일 실패 처리 | 경고 자체가 언어상 오류라는 뜻 |
| `-g` | 지역 변수 등을 포함한 디버그 정보 생성 | 프로그램의 원래 소스 전체 저장 |
| `-parameters` | 리플렉션에서 읽을 매개변수 이름 저장 | 지역 변수 디버그 정보 전체 |
| `--release` | 대상 버전의 언어·클래스 형식·표준 기능 제한 | 모든 외부 의존성의 버전 자동 변환 |

`-g`와 `-parameters`는 목적이 다릅니다. 매개변수 이름을 실행 중 조사하는 프레임워크에서는 후자의 설정이 중요할 수 있습니다.[^javac]

#### 137-5. 클래스 조사와 문서 생성

앞에서 만든 클래스를 다음처럼 조사합니다.

```text
javap -classpath out -c Main
```

`-c`는 메서드의 바이트코드를 보여 줍니다. 주석, 원래 들여쓰기, 모든 지역 변수 이름까지 되돌려 주는 것은 아닙니다.

문서화 주석은 `/** ... */` 형식입니다. `@param`, `@return`, `@throws`로 매개변수·반환값·예외를 설명할 수 있습니다. `javadoc`은 이런 정보와 선언을 문서로 만듭니다.[^javadoc]

**핵심 판별:** “소스를 바꾼다”는 컴파일, “실행한다”는 실행기, “이미 만들어진 클래스를 들여다본다”는 클래스 조사입니다.

### 138. 프로젝트 구조와 배포 파일

**프로젝트에는 실행 코드뿐 아니라 테스트 코드, 설정, 이미지, 메시지 같은 자원이 있습니다.** 파일을 어디에 두고 무엇을 결과물에 넣을지 정해야 합니다.[^pom]

#### 138-1. 소스·자원·테스트의 구분

메이븐과 일반적인 자바 빌드에서 사용하는 대표 구조입니다. 자바 언어가 모든 프로젝트에 강제하는 폴더 구조는 아닙니다.

```text
프로젝트/
├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/study/Main.java
│   │   └── resources/app.properties
│   └── test/
│       ├── java/study/MainTest.java
│       └── resources/test-data.txt
└── target/
```

| 위치 | 내용 | 기본적인 처리 |
| --- | --- | --- |
| 실행 소스 | 업무 코드 | 컴파일하여 실행 결과물에 포함 |
| 실행 자원 | 설정·메시지·이미지 | 자원 처리 후 결과물에 포함 |
| 테스트 소스 | 검증 코드 | 별도로 컴파일하여 테스트에 사용 |
| 테스트 자원 | 시험용 입력 | 테스트 실행에 사용 |
| 결과 디렉터리 | 클래스·보고서·아카이브 | 다시 만들 수 있는 산출물 |

테스트 코드가 실행 코드와 같은 폴더에 뒤섞이면 배포 범위와 의존성 관리가 불명확해집니다. 기본 배포 아카이브에 테스트 클래스가 들어가지 않는 것과, 테스트를 실행하지 않는 것은 다른 이야기입니다.

#### 138-2. 자바 아카이브의 정체

`JAR`는 여러 파일을 묶는 압축 기반 형식입니다. 클래스와 자원을 포함할 수 있으며, 만들어졌다는 이유만으로 곧바로 실행 가능한 것은 아닙니다.[^jar-spec]

| 구성 | 의미 |
| --- | --- |
| `.class` | 컴파일된 코드 |
| 설정·이미지·메시지 | 프로그램 자원 |
| `META-INF/MANIFEST.MF` | 아카이브 메타정보 |
| `Main-Class` | 일반 실행형 아카이브의 시작 클래스 |
| `Class-Path` | 매니페스트에서 지정하는 외부 의존성 경로 |
| `module-info.class` | 모듈 설명자 |

137절의 `out`이 준비된 폴더에서 실행합니다.

```text
jar --create --file app.jar --main-class Main -C out .
jar --list --file app.jar
java -jar app.jar
```

마지막 명령의 출력:

```text
7
```

`-C out .`는 `out` 안의 내용을 기준으로 넣는다는 뜻입니다. 아카이브 안에 불필요하게 `out/`을 한 단계 더 포함시키는 것과 다릅니다.[^jar]

#### 138-3. 실행형 아카이브와 의존성 포함

| 방식 | 구성 | 주의 |
| --- | --- | --- |
| 일반 아카이브 | 주로 자기 프로젝트의 클래스·자원 | 외부 라이브러리가 자동으로 합쳐지는 것은 아님 |
| 의존성을 펼쳐 합친 아카이브 | 여러 의존성의 클래스·자원을 병합 | 같은 경로의 자원·서명·서비스 정보 충돌 주의 |
| 중첩 아카이브 | 내부에 다른 아카이브를 보관 | 중첩 구조를 이해하는 별도 실행기 등이 필요 |
| 웹 애플리케이션 아카이브 | 웹 실행 환경용 배포 구조 | 일반 아카이브와 실행 환경·구조가 다름 |

**표준 실행기가 아카이브 안의 모든 중첩 아카이브를 자동 탐색한다고 외우면 안 됩니다.** 스프링 부트의 실행형 아카이브는 전용 실행 구조를 사용합니다.[^boot-jar]

`java -jar` 모드에서는 일반 명령행 클래스 경로 설정이 그대로 결합된다고 가정하지 않습니다. 외부 의존성은 매니페스트나 사용하는 패키징 방식에 맞게 구성합니다.[^java]

#### 138-4. 파일 경로와 클래스 경로 자원

파일 시스템의 `Path`와 클래스 경로 자원은 다릅니다. 아카이브 내부의 설정은 일반 파일 경로가 아닐 수 있습니다.

다음은 별도 연습 폴더의 `Main.java`입니다. `resources/message.txt`를 UTF-8로 만들고 내용은 `학습 자료입니다.`로 저장합니다.

```java
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

public class Main {
    public static void main(String[] 인수) throws Exception {
        try (InputStream 입력 = Main.class.getResourceAsStream("/message.txt")) {
            if (입력 == null) {
                throw new IllegalStateException("메시지 자원이 없습니다.");
            }
            String 내용 = new String(입력.readAllBytes(), StandardCharsets.UTF_8);
            System.out.println(내용.strip());
        }
    }
}
```

컴파일·패키징·실행:

```text
javac -encoding UTF-8 --release 21 -d out Main.java
jar --create --file resource.jar --main-class Main -C out . -C resources .
java -jar resource.jar
```

출력:

```text
학습 자료입니다.
```

| 호출 방식 | 탐색 기준 |
| --- | --- |
| `Main.class.getResourceAsStream("/message.txt")` | 클래스 경로의 루트 기준 |
| `Main.class.getResourceAsStream("message.txt")` | 해당 클래스의 패키지 기준 |
| `ClassLoader.getResourceAsStream("message.txt")` | 로더가 관리하는 자원 이름 기준. 앞에 `/`를 붙이지 않음 |

이 비교는 일반 클래스 경로 예제입니다. 이름 있는 모듈의 자원 접근에는 모듈 캡슐화 조건도 관계됩니다.[^class-resource]

#### 138-5. 다중 버전·서명 — 보충

다중 버전 아카이브는 기본 구현과 버전별 구현을 하나에 담는 방식입니다. 매니페스트의 `Multi-Release: true`와 `META-INF/versions/버전/` 구조를 사용합니다.

실행 환경보다 높은 버전의 구현을 무조건 고르는 것이 아닙니다. 실행 환경에서 사용할 수 있는 버전부터 탐색합니다. 하나의 아카이브에 서로 다른 배포판 파일을 아무렇게나 넣는 기능도 아닙니다.[^jar-spec]

`jarsigner`의 서명 검증은 서명된 내용의 무결성과 서명자 확인을 돕습니다. **암호화, 취약점 부재, 악성 동작 부재를 보장하는 검사는 아닙니다.** 공개된 아카이브에 비밀번호를 넣고 서명해도 비밀번호가 감춰지지 않습니다.[^jarsigner]

### 139. 빌드와 의존성 관리 — 외부 도구

**빌드는 소스를 실행·배포 가능한 결과물로 준비하는 전체 과정입니다.** 컴파일, 자원 처리, 테스트, 패키징 등을 자동화할 수 있습니다. 메이븐과 그레이들은 자바 언어 자체의 키워드나 표준 라이브러리가 아닙니다.[^maven-life][^gradle-java]

#### 139-1. 컴파일·빌드·패키징·배포

| 개념 | 질문 | 예 |
| --- | --- | --- |
| 컴파일 | 소스가 대상 클래스 파일로 바뀌는가? | `javac` |
| 테스트 | 설정한 조건을 만족하는가? | 경곗값·예외 검사 |
| 패키징 | 배포할 파일이 올바르게 묶였는가? | 아카이브 생성 |
| 빌드 | 필요한 준비 단계를 어떻게 실행하는가? | 컴파일·테스트·패키징 연결 |
| 배포 | 결과물을 어디에 제공하거나 실행시키는가? | 저장소 업로드·실행 환경 반영 |

어떤 빌드는 테스트를 생략하도록 설정할 수 있습니다. 따라서 “빌드 성공”이라는 문구만으로 실행된 검사 범위를 판단하지 않습니다.

#### 139-2. 메이븐의 생명주기

일반적인 자바 아카이브 프로젝트에서 중요한 단계입니다. 중간 단계 일부는 이해를 위해 생략했습니다.[^maven-life]

```text
validate → compile → test → package → verify → install → deploy
```

| 단계 | 핵심 역할 |
| --- | --- |
| `validate` | 프로젝트 정보 등 기본 조건 확인 |
| `compile` | 실행 소스 컴파일 |
| `test` | 설정된 단위 테스트 실행 |
| `package` | 아카이브 등 결과물 생성 |
| `verify` | 연결된 추가 검증의 결과 확인 |
| `install` | 로컬 의존성 저장소에 결과물 설치 |
| `deploy` | 설정된 원격 의존성 저장소에 게시 |

한 생명주기의 뒤 단계를 호출하면 그 앞 단계들도 순서에 따라 진행됩니다. 다만 **단계가 존재한다는 사실과 어떤 플러그인 작업이 실제로 연결되어 있는지는 구분**합니다.

`clean`은 별도 생명주기입니다. `mvn package`에 `clean`이 자동 포함된다고 외우지 않습니다. `mvn clean verify`는 결과물 정리와 검증을 명시적으로 요청한 것입니다.

메이븐의 `deploy`는 기본적으로 **결과물을 원격 저장소에 올리는 단계**입니다. 웹 서버에서 서비스를 재시작한다는 뜻과 동일하지 않습니다.

#### 139-3. 단계와 플러그인 작업

| 구분 | 의미 |
| --- | --- |
| 생명주기 단계 | 작업을 연결할 위치 |
| 플러그인 | 구체적인 기능을 제공하는 도구 |
| 플러그인의 목표 | 실제로 수행할 작업 |

예를 들어 테스트 단계에는 테스트 실행 도구의 작업이 연결됩니다. 통합 테스트는 별도 플러그인·단계 설정이 필요할 수 있습니다. **검증 단계에 도달했다고 모든 종류의 통합 테스트가 저절로 생기지는 않습니다.**

#### 139-4. 의존성은 이름·버전·사용 시점으로 관리

메이븐의 대표 식별 정보는 조직, 결과물 이름, 버전입니다. 실제 의존성 식별에는 유형과 분류자 같은 정보도 쓰일 수 있습니다.[^pom-reference]

```text
groupId : artifactId : version
조직 식별자 : 라이브러리 이름 : 버전
```

| 메이븐 범위 | 실행 소스 컴파일 | 실행 시 | 테스트 시 | 직관 |
| --- | --- | --- | --- | --- |
| `compile` | 포함 | 포함 | 포함 | 기본 의존성 |
| `provided` | 포함 | 원칙적으로 제외 | 포함 | 실행 환경이 제공할 것으로 가정 |
| `runtime` | 제외 | 포함 | 포함 | 실행할 때 필요한 구현체 등 |
| `test` | 제외 | 제외 | 포함 | 테스트 전용 |

`provided`라고 적는 행위가 서버에 라이브러리를 설치해 주지는 않습니다. 실제 실행 환경이 제공하지 않으면 실패할 수 있습니다.[^maven-dependency]

`import` 범위는 일반 클래스 가져오기와 다릅니다. 의존성 관리 영역에서 다른 의존성 관리 목록을 가져오는 용도로 사용합니다. `system` 범위는 특정 로컬 파일에 의존하므로 이식성과 재현성을 해치기 쉽습니다.

#### 139-5. 직접·전이 의존성과 충돌

직접 의존성은 내가 선언한 것입니다. 전이 의존성은 그 라이브러리가 다시 요구한 것입니다.

아래는 설명용 의존성 그래프입니다.

```text
내 프로젝트 → 도구가 → 공통 1.0
내 프로젝트 → 도구나 → 도구다 → 공통 2.0
```

**메이븐의 일반적인 중재 규칙은 가까운 경로 우선**입니다. 별도의 관리·재정의 조건이 없다면 위 구조에서는 `공통 1.0`이 선택됩니다. 경로 깊이가 같으면 먼저 선언된 경로가 영향을 줍니다.[^maven-dependency]

“버전 숫자가 큰 것이 항상 선택된다”는 설명은 틀립니다. 그레이들의 기본 버전 충돌 선택과도 동일한 규칙으로 외우면 안 됩니다. 도구별 규칙과 명시한 제약을 확인합니다.[^gradle-conflict]

| 문제 | 확인 방법 |
| --- | --- |
| 예상과 다른 버전 선택 | 의존성 그래프와 중재 결과 확인 |
| 컴파일은 되지만 실행 중 메서드 없음 | 컴파일·실행 의존성 버전 비교 |
| 불필요한 전이 의존성 유입 | 제외 설정과 직접 선언 검토 |
| 관련 라이브러리 버전 불일치 | 검증된 버전 관리 목록 적용 |

`dependencyManagement`는 **버전·범위 등을 관리**하는 영역입니다. 목록에 적힌 모든 의존성을 자동 사용하게 만드는 영역은 아닙니다. 실제 선언이나 전이 관계가 있어야 의존성이 참여합니다.

#### 139-6. 그레이들의 작업과 구성

그레이들은 작업과 작업 간 의존 관계를 중심으로 빌드를 구성합니다. 자바 플러그인을 적용하면 컴파일·자원 처리·테스트·아카이브 작업 등이 연결됩니다.[^gradle-java]

| 그레이들 구성 | 의미 |
| --- | --- |
| `implementation` | 내부 구현에 필요한 의존성 |
| `api` | 라이브러리 사용자의 컴파일에도 드러낼 의존성. 자바 라이브러리 플러그인 등에서 제공 |
| `compileOnly` | 컴파일 시만 필요한 의존성 |
| `runtimeOnly` | 실행 시만 필요한 의존성 |
| `testImplementation` | 테스트 컴파일·실행 의존성 |
| `testRuntimeOnly` | 테스트 실행에만 필요한 의존성 |
| `annotationProcessor` | 컴파일 중 애너테이션 처리기 |

`implementation`은 사용하는 쪽의 컴파일 경로에 내부 의존성을 공개하지 않는 데 의미가 있습니다. **실행에도 필요 없다는 뜻은 아닙니다.** 메이븐의 `provided`와 그레이들의 `compileOnly`를 테스트 경로까지 완전히 같은 개념으로 취급하지 않습니다.[^gradle-config]

자바 플러그인의 `build`는 보통 결과물 생성과 검사 작업에 연결됩니다. `clean`이 반드시 자동 선행하는 것은 아닙니다. 그레이들은 메이븐의 모든 생명주기 단계를 그대로 실행하는 도구도 아닙니다.

#### 139-7. 재현 가능한 빌드와 저장소 — 보충

| 항목 | 이유 |
| --- | --- |
| 빌드 도구 래퍼 | 프로젝트에서 사용할 도구 버전을 맞춤 |
| 자바 도구 체인 | 컴파일·테스트에 쓸 자바 버전을 맞춤 |
| 의존성·플러그인 버전 고정 | 실행 시점에 따라 선택 결과가 바뀌는 일을 줄임 |
| 의존성 잠금 | 실제 해석된 버전을 기록하여 재사용 |
| 저장소·검증 정보 관리 | 내려받는 출처와 파일 변경을 확인 |
| 자원 인코딩·파일 순서·시각 관리 | 결과물의 차이를 줄임 |

래퍼만 사용한다고 자바 버전, 외부 저장소, 환경 변수까지 모두 동일해지는 것은 아닙니다. 개발 중인 스냅샷 버전이나 가변 버전 범위는 같은 이름으로도 다른 결과를 가져올 수 있습니다.[^gradle-lock]

신뢰하지 않는 프로젝트의 빌드 스크립트는 코드를 실행할 수 있습니다. 의존성 확인과 별개로 빌드 스크립트·플러그인도 검토해야 합니다.

**핵심 판별:** 빌드 도구는 작업을 연결하고 의존성을 준비합니다. 실제 언어 규칙의 판정은 컴파일러가 담당합니다.

### 140. 테스트와 정적 분석 — 외부 도구 포함

**테스트는 정해 놓은 입력·상황에서 실제 결과가 기대한 조건을 만족하는지 확인하는 과정입니다.** 실행이 끝났다는 사실과 올바른 결과를 검증했다는 사실은 다릅니다.

#### 140-1. 테스트의 범위

| 종류 | 중심 질문 | 예시 |
| --- | --- | --- |
| 단위 테스트 | 작은 로직이 조건대로 동작하는가? | 합격 기준 판정 |
| 통합 테스트 | 실제 구성요소가 연결되어 동작하는가? | 저장 로직과 시험용 데이터베이스 연결 |
| 계약 테스트 | 외부에 약속한 요청·응답 규약이 맞는가? | 응답 필드·오류 형식 확인 |
| 전체 흐름 테스트 | 사용자 관점의 절차가 이어지는가? | 요청·처리·저장·응답 연결 |
| 회귀 테스트 | 변경 후 기존 동작이 깨지지 않았는가? | 과거 오류 사례 재검사 |
| 성능 테스트 | 처리량·지연·자원 사용이 목표에 맞는가? | 동시 요청 시 응답시간 측정 |

회귀 테스트는 작은 단위부터 전체 흐름까지 여러 범위로 구성할 수 있습니다. **단위·통합은 검사 범위에, 회귀는 검사 목적에 가깝다**는 차이를 기억합니다.

#### 140-2. 정상값보다 경계와 예외도 확인

“점수는 0~100이고 70점 이상이면 합격”이라는 학습용 규칙을 가정합니다.

| 구분 | 입력 | 기대 |
| --- | --- | --- |
| 최솟값 | 0 | 불합격 |
| 경계 바로 아래 | 69 | 불합격 |
| 경계 | 70 | 합격 |
| 최댓값 | 100 | 합격 |
| 범위 아래 | -1 | 잘못된 입력 예외 |
| 범위 위 | 101 | 잘못된 입력 예외 |

파일은 `src/main/java/study/Main.java`입니다.

```java
package study;

public class Main {
    public static boolean 합격(int 점수) {
        if (점수 < 0 || 점수 > 100) {
            throw new IllegalArgumentException("점수 범위 오류");
        }
        return 점수 >= 70;
    }

    public static void main(String[] 인수) {
        System.out.println(합격(69));
        System.out.println(합격(70));
    }
}
```

출력:

```text
false
true
```

한 가지 정상값만 확인하면 `>=`를 `>`로 잘못 적은 오류를 놓칠 수 있습니다. 경곗값 검사는 조건 연산자의 실수를 찾는 데 도움이 됩니다.

#### 140-3. 외부 테스트 도구의 기본 구조

다음은 **JUnit Jupiter 5.11.4의 문법으로 작성한 외부 테스트 예제**입니다. 자바 표준 라이브러리가 아니므로 테스트 의존성과 실행기가 필요합니다.[^junit]

파일은 `src/test/java/study/MainTest.java`입니다. 바로 위의 `study.Main`을 검사합니다.

```java
package study;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.ValueSource;

class MainTest {
    @ParameterizedTest
    @CsvSource({"0, false", "69, false", "70, true", "100, true"})
    void 경계검사(int 점수, boolean 기대) {
        assertEquals(기대, Main.합격(점수));
    }

    @ParameterizedTest
    @ValueSource(ints = {-1, 101})
    void 범위검사(int 점수) {
        assertThrows(IllegalArgumentException.class, () -> Main.합격(점수));
    }
}
```

이 테스트에는 **정상·경계 입력 4개와 잘못된 입력 2개**가 있습니다. 테스트 메서드는 두 개이지만 매개변수별 실행 사례는 여섯 개입니다.

#### 140-5. 테스트 선언과 검증의 차이

| 요소 | 역할 |
| --- | --- |
| `@Test` | 일반 테스트 메서드 선언 |
| `@ParameterizedTest` | 여러 입력에 같은 검증 적용 |
| `@BeforeEach` | 각 테스트 실행 전 준비 |
| `@AfterEach` | 각 테스트 실행 후 정리 |
| `@BeforeAll`, `@AfterAll` | 테스트 클래스 차원의 준비·정리 |
| `assertEquals` | 기대값과 실제값 비교 |
| `assertSame` | 같은 객체 참조인지 검사 |
| `assertArrayEquals` | 배열의 내용 비교 |
| `assertThrows` | 지정한 예외 유형 또는 그 하위 유형 발생 검사 |
| `assertThrowsExactly` | 정확히 지정한 예외 유형 발생 검사 |

기본 수명 설정에서 클래스 차원의 준비·정리 메서드는 보통 정적 메서드로 선언합니다. 인스턴스 수명 설정을 바꾸면 조건이 달라질 수 있습니다.[^junit][^junit-assert]

#### 140-6. 자바의 assert와 테스트 단언

자바 언어의 `assert`는 실행 옵션에 따라 비활성화될 수 있습니다. 테스트 도구의 `assertEquals` 호출과 같은 활성화 규칙을 쓰는 것이 아닙니다.[^java]

```java
public class Main {
    public static void main(String[] 인수) {
        try {
            assert false : "조건 실패";
            System.out.println("검사 건너뜀");
        } catch (AssertionError 오류) {
            System.out.println("단언 실패");
        }
    }
}
```

일반적인 기본 설정으로 실행:

```text
java Main
```

출력:

```text
검사 건너뜀
```

단언을 활성화하여 실행:

```text
java -ea Main
```

출력:

```text
단언 실패
```

이 차이 때문에 사용자 입력 검증을 언어의 `assert`에만 맡기면 안 됩니다. 반드시 검사할 조건은 일반 분기와 적절한 예외로 처리합니다.

#### 140-7. 테스트 대역과 독립성

테스트 대역은 실제 협력 객체를 대신하는 객체입니다. 프레임워크별 용어와 기능은 조금씩 다를 수 있습니다.

| 대역 | 대표 목적 | 직관 |
| --- | --- | --- |
| 더미 | 인수 자리만 채움 | 실제로 쓰지 않는 값 |
| 스텁 | 정해진 답 제공 | 조회하면 항상 준비한 회원 반환 |
| 가짜 구현 | 단순하지만 동작하는 대체 구현 | 메모리 안의 저장소 |
| 모의 객체 | 호출·상호작용 검증 | 저장 메서드가 한 번 호출되었는지 확인 |
| 스파이 | 호출 기록 또는 실제 객체 일부 관찰 | 실제 동작과 관찰을 조합 |

대역으로 저장 호출을 확인한 테스트는 실제 데이터베이스의 제약조건·트랜잭션·질의까지 검증한 것이 아닙니다. 단위 테스트와 실제 연동 테스트가 필요한 이유입니다.[^test-doubles]

시간·난수·외부 통신은 결과를 흔들 수 있습니다. 시계나 외부 서비스의 역할을 인수로 받아 통제하면 재현 가능한 검사가 쉬워집니다.

비동기 테스트에서 `sleep`으로 대충 기다리는 것은 작업 완료를 보장하지 않습니다. 완료 결과를 기다리거나 동기화 도구를 사용하되, 실패 시 끝없이 멈추지 않도록 시간 제한을 둡니다.

#### 140-8. 정적 분석·검사 범위·반복 검증

| 방법 | 살펴보는 것 | 한계 |
| --- | --- | --- |
| 컴파일러 검사 | 타입·문법·확정 할당 등 | 업무 규칙의 정확성은 별개 |
| 정적 분석 | 실행하지 않고 코드·바이트코드의 의심 패턴 탐색 | 잘못된 경고·누락 가능 |
| 테스트 | 실제 입력에 대한 결과 | 선택한 사례 밖은 별도 확인 필요 |
| 실행 범위 측정 | 어떤 문장·분기가 실행되었는지 | 올바른 결과를 단언했는지까지 보장하지 않음 |
| 반복 자동 검사 | 변경할 때 같은 검사 수행 | 검사 자체의 품질과 환경에 의존 |

**실행 범위 100%는 오류 0%가 아닙니다.** 지나간 코드를 세는 것과 모든 입력·상태·결과를 검증하는 것은 다릅니다.

### 141. 디버깅과 실행 상태 관찰

**디버깅은 잘못된 동작의 원인을 좁히는 과정입니다.** 실행 상태 관찰은 그 판단에 필요한 기록·지표·덤프를 확보하는 일입니다.[^tools][^jcmd]

#### 141-1. 질문에 맞는 자료 선택

| 알고 싶은 것 | 우선 볼 자료·도구 | 해석 |
| --- | --- | --- |
| 오류가 어느 호출에서 시작됐는가? | 예외와 호출 스택 | 발생 위치·전파 경로 |
| 스레드가 무엇을 기다리는가? | 스레드 덤프 | 잠금·대기·호출 위치 |
| 어떤 객체가 메모리를 잡고 있는가? | 힙 덤프·참조 경로 | 객체와 도달 관계 |
| 일정 시간 동안 무슨 일이 있었는가? | 실행 기록 | 시간 흐름에 따른 사건 |
| 메모리 회수 빈도·사용량이 변하는가? | 지표·수집기 로그 | 변화 추세 |
| 실행 옵션이 무엇인가? | 가상 머신 설정 조회 | 실제 적용된 실행 조건 |

**스레드 덤프와 힙 덤프를 바꿔 외우지 않습니다.** 전자는 실행 흐름, 후자는 객체 상태와 참조 관계가 중심입니다.

#### 141-2. 호출 스택의 방향

```java
public class Main {
    static void 중간() {
        확인();
    }

    static void 확인() {
        var 이름들 = StackWalker.getInstance().walk(흐름 ->
            흐름.map(프레임 -> 프레임.getMethodName()).toList());
        System.out.println(이름들);
    }

    public static void main(String[] 인수) {
        중간();
    }
}
```

출력:

```text
[확인, 중간, main]
```

현재 호출 지점에서 호출자 방향으로 읽은 결과입니다. 예외 출력에서는 감싸진 원인 예외와 억제된 예외도 함께 구분해야 합니다.[^stackwalker]

중단점은 특정 위치에서 실행을 멈추는 기능입니다. 한 줄 진행, 메서드 안으로 진입, 호출자에게 돌아가기, 조건부 중단 등을 이용합니다. 중단 자체가 실행 순서를 바꾸므로 동시성 문제는 디버깅 중 재현 양상이 달라질 수 있습니다.

도구의 지원 명령·권한·접속 방식은 실행 환경에 따라 확인합니다. 모든 가상 머신 구현체에서 같은 내부 진단 기능을 보장한다고 가정하지 않습니다.[^tools]

#### 141-4. 실행 중 프로세스에 질문하기 — 보충

아래 `12345`는 **설명용 프로세스 번호**입니다. 실제로 내가 관리할 권한이 있는 자바 프로세스 번호로 바꿔 사용합니다.

진단 명령은 같은 장비·사용자 권한 등의 접속 조건을 만족해야 합니다. `help`로 해당 프로세스가 지원하는 명령부터 확인합니다.[^jcmd]

힙 덤프와 상세 조사는 실행 중단·저장 공간·처리 부하에 영향을 줄 수 있습니다. 운영 문제를 조사하면서 다른 장애를 만들지 않도록 비용을 확인합니다.

| 자료 | 보는 방식 | 주의 |

| 실행 기록 | 일정 기간의 사건을 연결 | 설정·표본·기록 시작 시점에 영향 |

실행 기록은 과거에 기록하지 않은 모든 사건을 나중에 복원하는 장치가 아닙니다. 기록 항목과 부하도 설정에 따라 다릅니다.

### 142. 성능 측정과 튜닝

**성능은 같은 조건의 작업을 얼마나 빨리, 얼마나 많이, 어떤 자원 비용으로 처리하는지의 문제입니다.** 코드가 짧다고 빠른 것은 아니고, 한 번 빨랐다고 항상 빠른 것도 아닙니다.

#### 142-1. 성능 지표의 차이

| 지표 | 묻는 것 | 주의 |
| --- | --- | --- |
| 처리량 | 단위 시간에 끝낸 작업 수 | 지연시간과 같은 지표가 아님 |
| 응답 지연 | 요청부터 결과까지 걸린 시간 | 평균만 보면 느린 일부 요청을 놓침 |
| 백분위 지연 | 어느 비율의 요청이 그 시간 이내에 끝나는가? | 평균·최댓값과 구분 |
| 시작 시간 | 실행 시작부터 사용할 준비까지 | 첫 요청 준비 시간과 구분 |
| 메모리 사용 | 얼마나 많은 메모리를 사용하는가? | 힙·프로세스 전체를 구분 |
| 할당률 | 새 객체를 얼마나 빠르게 만드는가? | 살아남는 객체량과 구분 |
| 정지 시간 | 작업이 멈춘 구간이 얼마나 긴가? | 전체 메모리 회수 작업 시간과 구분 |

99백분위 지연이 특정 값이라는 것은 측정 대상 요청의 약 99%가 그 값 이하라는 의미입니다. “모든 요청의 지연 상한”이라는 뜻은 아닙니다. 계산 방식과 측정 대상도 함께 확인합니다.

#### 142-2. 한 번의 시간 측정이 위험한 이유

| 요인 | 결과에 주는 영향 |
| --- | --- |
| 처음 클래스 로딩 | 첫 실행에만 준비 비용 발생 |
| 실행 중 컴파일 | 반복 실행 도중 코드가 최적화됨 |
| 준비 실행 부족 | 안정된 상태와 초기 상태가 섞임 |
| 결과 미사용 | 계산이 불필요한 코드로 제거될 수 있음 |
| 상수 입력만 사용 | 계산이 미리 단순화될 수 있음 |
| 출력·파일 접근 포함 | 계산 대신 다른 비용을 주로 재게 됨 |
| 다른 프로그램의 부하 | 같은 코드도 실행 조건이 달라짐 |

자바의 미세 성능 측정에는 `JMH` 같은 전용 도구가 사용됩니다. 준비 실행, 반복 측정, 별도 프로세스, 결과 소비 등의 장치를 제공합니다.[^jmh-dead][^jmh-constant]

**전용 도구를 쓴다는 사실만으로 측정 설계까지 자동으로 맞아지는 것은 아닙니다.** 실제 입력 크기·분포·실패 비율·경합 정도를 반영해야 합니다.

#### 142-3. 경과 시간과 시계 시각

경과 시간 비교에는 `System.nanoTime()`의 **두 시점 차이**를 사용합니다. 이 값은 달력 시각이 아니며, 숫자 단위가 나노초라고 실제 해상도까지 항상 1나노초인 것은 아닙니다.[^system]

`System.currentTimeMillis()`는 시각 정보와 관련됩니다. 시계 조정의 영향까지 고려해야 하므로 두 메서드를 같은 것으로 취급하지 않습니다.

#### 142-4. 튜닝의 판단 순서

| 순서 | 확인할 질문 |
| --- | --- |
| 1. 목표 | 평균 지연, 느린 꼬리 요청, 처리량 중 무엇을 개선하는가? |
| 2. 재현 | 어느 입력·동시성·자원 조건에서 느린가? |
| 3. 관찰 | 계산, 할당, 잠금, 파일·통신 대기 중 어디에 시간이 드는가? |
| 4. 가설 | 관찰한 병목을 줄일 변경인가? |
| 5. 비교 | 한 번에 바꾼 조건을 통제했는가? |
| 6. 검증 | 정확성·메모리·다른 작업의 지연을 악화시키지 않았는가? |

예를 들어 외부 응답을 기다리는 시간이 대부분이면 작은 산술식을 바꾸는 효과는 제한적입니다. 반대로 계산 자체가 병목이면 스레드 수만 늘려도 빨라진다고 보장할 수 없습니다.

#### 142-5. 힙 크기와 프로세스 메모리

`-Xmx`는 자바 힙의 최대 크기와 관련된 옵션입니다. **프로세스 전체 메모리의 최대치가 아닙니다.** 스레드 스택, 클래스 메타정보, 코드 캐시, 직접 메모리 등도 고려합니다.[^java][^nmt]

| 관찰 | 가능한 해석 |
| --- | --- |
| 힙이 크지만 회수 후 줄어듦 | 일시적인 객체가 많이 생성될 수 있음 |
| 회수 후 살아남는 객체량이 계속 증가 | 캐시·보관 자료·불필요 참조 조사 필요 |
| 힙은 안정적이나 전체 메모리 증가 | 힙 밖 메모리 등도 조사 |
| 메모리 회수 빈도 증가 | 할당률·살아남는 객체·힙 조건 함께 조사 |

캐시가 커진 것인지 누수인지 목적과 보관 정책을 함께 봅니다. “메모리를 많이 쓴다”와 “불필요한 참조가 끊기지 않는다”는 같은 판단이 아닙니다.

#### 142-6. 네이티브 메모리 추적 — 선택 심화

핫스팟의 네이티브 메모리 추적은 가상 머신 내부의 메모리 사용을 범주별로 조사하는 기능입니다. 모든 외부 네이티브 라이브러리의 할당을 완벽히 추적하는 것은 아닙니다.[^nmt]

실행 시작 시 추적을 켜는 설정 예시:

```text
java -XX:NativeMemoryTracking=summary -jar app.jar
```

실제로 실행 중인 프로세스에 대한 조회 예시:

```text
jcmd 12345 VM.native_memory summary
```

추적 자체에도 비용이 있습니다. 추적을 끈 상태로 시작한 프로세스에 대해 나중에 전체 과거 기록이 나타난다고 생각하지 않습니다.

### 143. 시작 최적화와 실행 이미지

**실행 이미지는 프로그램을 실행하는 데 필요한 구성요소를 묶은 결과물입니다.** 클래스 파일, 맞춤형 실행 환경, 운영체제용 설치 패키지, 네이티브 실행 파일을 구분해야 합니다.[^jlink][^jpackage][^native-image]

#### 143-1. 네 가지 결과물 비교

| 결과물 | 주로 담는 것 | 핵심 |
| --- | --- | --- |
| 자바 아카이브 | 클래스·자원 | 실행할 자바 환경이 별도로 필요할 수 있음 |
| 맞춤형 자바 실행 이미지 | 필요한 모듈과 실행 환경 | 가상 머신을 사용하는 실행 구조 |
| 설치·앱 패키지 | 프로그램·실행 환경·실행기 등 | 사용자의 설치·실행 편의 |
| 네이티브 실행 파일 | 특정 환경의 기계어와 필요한 실행 지원 | 바이트코드 아카이브와 다른 산출물 |

이름에 “이미지”가 들어간다고 모두 같은 기술은 아닙니다. 컨테이너 이미지 역시 운영 환경 파일을 배포하는 단위이며 위 결과물을 내부에 포함할 수 있습니다.

#### 143-2. jlink와 jpackage

| 도구 | 목적 | 하지 않는 일 |
| --- | --- | --- |
| `jlink` | 모듈과 의존성을 맞춤형 실행 이미지로 구성 | 애플리케이션 전체를 네이티브 기계어로 변환 |
| `jpackage` | 자바 프로그램의 앱 이미지·설치 패키지 구성 | 모든 운영체제용 패키지를 한 환경에서 자동 생성 |

`jlink`에서 필요한 모듈을 빼면 해당 기능을 사용하는 프로그램은 실패할 수 있습니다. 정적 의존성 분석에 드러나지 않는 서비스 제공자·동적 로딩도 확인해야 합니다.[^jlink][^jdeps]

기본 모듈만 넣는 학습용 예시입니다. 출력 디렉터리는 아직 존재하지 않아야 합니다.

```text
jlink --add-modules java.base --output runtime-image
```

만든 실행 환경으로 137~138절의 단순 아카이브를 실행하는 예시:

```text
리눅스·맥: ./runtime-image/bin/java -jar app.jar
윈도우: .\runtime-image\bin\java.exe -jar app.jar
```

이 프로그램은 기본 모듈만 사용하므로 실행할 수 있습니다. 데이터베이스·화면 기능을 사용하는 프로그램에도 무조건 같은 모듈 목록을 적용하는 예시는 아닙니다.

#### 143-3. 클래스 데이터 공유

클래스 데이터 공유는 준비한 클래스 관련 데이터를 아카이브에서 재사용하여 시작 비용과 메모리 사용을 줄이는 데 도움을 주는 기능입니다. 자바 21에서 다룰 수 있는 시작 최적화 개념입니다.[^cds]

| 혼동 | 실제 구분 |
| --- | --- |
| 프로그램 결과를 저장하는 캐시다 | 클래스 관련 준비 데이터를 재사용하는 기능 |
| 서로 다른 프로세스가 가변 객체를 마음대로 공유한다 | 읽기 전용으로 공유할 수 있는 데이터와 각 실행 상태를 구분 |
| 모든 개발 도구·옵션 조합에서 같은 파일을 쓴다 | 아카이브와 실행 환경의 일치 조건 확인 |

#### 143-4. 자바 24·25의 사전 준비 캐시 — 보충

| 기준 버전 | 중심 개념 |
| --- | --- |
| 자바 24 | 클래스 로딩·연결 등의 사전 준비 데이터를 이용하는 캐시 |
| 자바 25 | 캐시 생성 절차 개선과 메서드 실행 프로파일의 재사용 |

이런 기능은 일반 가상 머신 실행에서 준비 비용을 줄이려는 것입니다. **프로그램을 가상 머신 없이 실행하는 네이티브 파일로 바꾼다는 뜻은 아닙니다.** 실행한 작업이 실제 사용을 대표하는지, 개발 도구와 애플리케이션이 바뀌면 다시 준비해야 하는지 등을 확인합니다.[^aot25]

#### 143-5. 외부 네이티브 이미지 도구 — 선택 심화

그랄 가상 머신의 네이티브 이미지 기능은 도달 가능한 코드와 필요한 실행 지원을 분석해 특정 운영체제·구조에 맞는 실행 파일을 만듭니다.[^native-image]

| 장점이 될 수 있는 것 | 별도 고려할 것 |
| --- | --- |
| 시작 비용 감소 | 빌드 시간과 빌드 환경 |
| 배포 방식 단순화 | 운영체제·하드웨어별 결과물 |
| 사용하지 않는 요소 축소 | 리플렉션·자원·동적 기능의 메타정보 |

별도 자바 설치 없이 실행할 수 있다는 표현은 메모리 관리와 실행 지원이 모두 사라진다는 뜻이 아닙니다. 장시간 처리량도 모든 프로그램에서 일반 실행보다 높다고 단정하지 않습니다.

#### 143-6. 컨테이너·배포에서 볼 것

실행 이미지가 작아도 요청 폭주, 외부 연결 부족, 저장 공간 고갈은 발생할 수 있습니다. 메모리·처리 자원 한도와 종료 절차까지 함께 확인합니다.

특히 힙 최대치를 컨테이너의 전체 메모리 한도와 같게 잡으면 힙 밖에 쓸 여유가 부족할 수 있습니다. 실제 자원 사용을 측정한 뒤 정합니다.[^java][^nmt]

### 144. 업그레이드와 호환성 점검

**호환성은 기존 코드나 결과물을 바꾼 환경에서 계속 사용할 수 있는 성질입니다.** 소스를 다시 컴파일하는 경우와 기존 클래스 파일을 그대로 사용하는 경우부터 구분합니다.[^binary]

#### 144-1. 세 가지 호환성

| 종류 | 질문 | 예 |
| --- | --- | --- |
| 소스 호환성 | 같은 소스가 다시 컴파일되는가? | 새 중복 정의 때문에 호출이 모호해지는지 |
| 바이너리 호환성 | 기존 클래스 파일이 새 라이브러리와 연결되는가? | 호출하던 메서드가 여전히 존재하는지 |
| 동작 호환성 | 실제 의미와 결과가 기대대로 유지되는가? | 정렬·시간대·예외 동작 등의 변화 |

컴파일과 연결이 성공해도 결과가 달라질 수 있습니다. 반대로 새 소스의 컴파일 규칙과 이미 만들어진 바이너리의 연결 규칙은 동일한 질문이 아닙니다.

#### 144-2. 클래스 파일 버전

| 자바 버전 | 클래스 파일의 대표 주 버전 |
| --- | --- |
| 8 | 52 |
| 11 | 55 |
| 17 | 61 |
| 21 | 65 |

숫자 자체보다 **낡은 실행 환경이 더 새로운 클래스 형식을 읽지 못할 수 있다**는 관계가 핵심입니다. 대상 버전을 잘못 맞추면 `UnsupportedClassVersionError` 등이 발생할 수 있습니다.[^classfile]

새 개발 도구로 예전 버전을 대상으로 만들 때는 지원되는 `--release` 값을 사용합니다. 이 옵션이 외부 라이브러리까지 예전 버전으로 다시 만들어 주지는 않습니다.[^javac]

#### 144-3. 비슷해 보이는 오류의 차이

| 오류·예외 | 먼저 의심할 점 |
| --- | --- |
| `UnsupportedClassVersionError` | 실행 환경과 클래스 파일 버전 불일치 |
| `ClassNotFoundException` | 이름으로 요청한 클래스를 로더가 찾지 못함 |
| `NoClassDefFoundError` | 필요한 클래스 정의를 사용할 수 없음. 초기화 실패 후에도 가능 |
| `NoSuchMethodError` | 실행 시 연결된 클래스에 기대한 메서드가 없음 |
| `InaccessibleObjectException` | 리플렉션 접근이 강한 캡슐화 등에 의해 허용되지 않음 |

`NoSuchMethodError`가 나면 소스 오타만 보지 말고 실제 실행에 들어간 의존성 버전을 확인합니다. 이름이 같은 아카이브라도 다른 버전이 선택됐을 수 있습니다.[^linking][^accessible]

#### 144-4. 분석 도구와 한계

| 도구 | 하는 일 | 한계 |
| --- | --- | --- |
| `jdeps` | 클래스·패키지·모듈 의존성 분석 | 문자열 기반 동적 로딩 등을 모두 추론하지 못함 |
| `jdeprscan` | 비권장 표준 기능의 사용 탐색 | 모든 외부 라이브러리의 비권장 기능까지 대신 검사하지 않음 |
| 컴파일 경고 | 바뀐 규칙·비권장 사용 등 확인 | 실제 실행 검증의 대체가 아님 |
| 회귀 테스트 | 중요한 동작의 유지 확인 | 준비한 사례의 범위에 의존 |

기본 조사 명령:

```text
jdeps --print-module-deps app.jar
jdeprscan --release 21 app.jar
```

필요한 의존성을 함께 제공하지 않으면 분석 자체가 불완전하거나 실패할 수 있습니다. 진단 도구도 입력과 경로가 정확해야 합니다.[^jdeps][^jdeprscan]

#### 144-5. 상수 인라이닝 — 보충

다음은 **컴파일타임 상수**를 사용하는 경우의 설명용 흐름입니다.

```text
라이브러리의 공개 상수: 기준 = 70
호출자 컴파일: 70이라는 값이 호출자 클래스에 들어갈 수 있음
라이브러리만 기준 = 80으로 변경해 교체
옛 호출자를 그대로 실행: 여전히 70을 사용할 수 있음
```

`public static final`이라는 모양만으로 모두 컴파일타임 상수인 것은 아닙니다. 기본형·문자열의 상수 변수 조건과 초기화 표현식 등을 함께 봅니다. 상수 변경이 중요하면 호출자 재컴파일 여부도 점검합니다.[^binary]

#### 144-6. 미리보기·비권장·접근 완화

| 개념 | 주의 |
| --- | --- |
| 미리보기 기능 | 컴파일·실행 활성화와 해당 버전 조건을 맞춤 |
| 비권장 기능 | 즉시 제거됐다는 뜻은 아니지만 대체 방향 확인 |
| 제거된 기능 | 의존 코드·배포 구조를 실제로 수정해야 함 |
| 내부 구현 기능 | 공개 표준 기능과 같은 호환성을 기대하지 않음 |
| `--add-opens` 등 | 특정 접근 문제의 임시 대응과 근본적인 의존성 개선을 구분 |

미리보기 기능을 쓴 클래스는 미래 버전에서 자동으로 계속 실행된다고 가정하지 않습니다. 필요한 버전에서 다시 검토·컴파일합니다.[^java][^classfile]

**업그레이드 확인 순서:** 실행 자바 → 컴파일 대상 → 빌드 도구·플러그인 → 외부 의존성 → 접근 제한 → 테스트 → 대표 부하에서 실행입니다.

## 18부. 전문 표준 기능과 자바 생태계 확장

### 145. 데스크톱과 멀티미디어 — 선택 심화

**데스크톱 기능은 창·버튼·이벤트·그래픽처럼 사용자의 화면과 입력 장치를 다루는 기능입니다.** 자바 21의 `java.desktop` 모듈에는 화면 구성뿐 아니라 이미지·인쇄·사운드·자바빈즈 관련 기능도 포함됩니다.[^desktop]

#### 145-1. 화면을 이루는 세 요소

| 요소 | 하는 일 | 예시 |
| --- | --- | --- |
| 컴포넌트 | 화면에 표시하거나 입력받음 | 버튼·레이블·입력칸 |
| 컨테이너·배치 관리자 | 컴포넌트의 포함 관계와 위치를 관리 | 창·패널·격자 배치 |
| 이벤트·리스너 | 발생한 동작과 대응 코드를 연결 | 버튼 클릭 후 처리 |

개념 흐름은 다음과 같습니다.

```text
사용자가 버튼 클릭
→ 클릭 이벤트 발생
→ 등록된 리스너 호출
→ 필요한 계산 또는 작업 요청
→ 화면 갱신
```

`AWT`는 기본 창·이벤트·그래픽 기반을 제공합니다. `Swing`은 그 기반 위에서 다양한 화면 컴포넌트를 제공합니다. 자바에프엑스는 별도 프로젝트로 배포되므로, 자바 21 표준 개발 도구에 항상 포함된 기능으로 외우면 안 됩니다.[^desktop][^javafx]

#### 145-2. 화면 처리는 이벤트 전달 스레드에서

대부분의 스윙 컴포넌트는 별도 문서가 허용한 경우를 제외하면 **이벤트 전달 스레드에서 접근**해야 합니다. 일반적인 `main` 실행 스레드와 화면 이벤트를 처리하는 스레드는 같지 않습니다.[^swing]

다음 예제는 창을 띄우지 않고, 현재 실행 위치만 확인합니다.

```java
import javax.swing.SwingUtilities;

public class Main {
    public static void main(String[] 인수) throws Exception {
        System.out.println(SwingUtilities.isEventDispatchThread());

        SwingUtilities.invokeAndWait(() ->
            System.out.println(SwingUtilities.isEventDispatchThread())
        );
    }
}
```

출력:

```text
false
true
```

첫 출력은 일반 실행 스레드입니다. 둘째 출력은 이벤트 전달 스레드로 작업을 넘긴 뒤 실행됩니다.

| 방법 | 의미 |
| --- | --- |
| `invokeLater` | 이벤트 전달 스레드에 작업을 예약하고 호출자는 계속 진행 |
| `invokeAndWait` | 작업을 넘기고 완료될 때까지 기다림. 이벤트 전달 스레드에서 호출하면 안 됨 |
| `SwingWorker` | 오래 걸리는 작업과 화면 갱신을 나누는 데 사용 |

파일 다운로드나 긴 계산으로 이벤트 전달 스레드를 붙잡으면 화면의 입력 반응이 막힐 수 있습니다. **작업이 오래 걸리는 것과 화면을 오래 점유하는 것을 구분**합니다.[^swing]

#### 145-3. 화면 이외의 데스크톱 기능

| 영역 | 개념 |
| --- | --- |
| 그래픽·이미지 | 도형 그리기, 이미지 읽기·쓰기, 색과 좌표 |
| 글꼴·인쇄 | 문자 표현, 페이지와 인쇄 작업 |
| 접근성 | 보조 기술이 화면 구성요소의 의미를 읽도록 지원 |
| 클립보드·끌어놓기 | 프로그램 사이의 데이터 전달 |
| 사운드 | 샘플 기반 음원·음악 이벤트 처리 |
| 자바빈즈 | 속성·이벤트·메서드 정보를 도구가 알아보도록 하는 구성요소 규약 |

서버의 화면 없는 실행 환경에서는 창·클립보드 등의 기능 사용이 제한될 수 있습니다. 같은 자바 코드라도 실행 환경에 그래픽 장치가 있다고 가정하지 않습니다.[^desktop]

#### 145-4. 자바빈즈와 스프링 빈은 다르다

자바빈즈는 속성 접근 메서드와 이벤트 등, 재사용 가능한 구성요소를 다루는 규약·도구 체계입니다. 스프링 빈은 **스프링 컨테이너가 관리하는 객체**를 뜻합니다. 이름이 비슷하지만 정의가 다릅니다.[^beans][^spring-ioc]

| 표현 | 판단 |
| --- | --- |
| 속성 읽기·쓰기 메서드를 가진 객체 | 자바빈즈의 속성 규약과 연결할 수 있음 |
| 컨테이너가 등록·생성·연결한 객체 | 스프링 빈 |
| 일반 생성자로 직접 만든 객체 | 그것만으로 스프링 빈이 되는 것은 아님 |
| 이름에 빈이 들어가는 모든 객체 | 서로 같은 규칙을 따른다고 단정할 수 없음 |

**시험 포인트:** 화면 이벤트·이벤트 전달 스레드·자바빈즈 정도를 먼저 구분하고, 그래픽 세부 메서드는 후순위로 둡니다.

### 146. 이름 서비스와 원격 호출 — 선택 심화

**이름 서비스는 이름으로 자원을 찾는 기능이고, 원격 호출은 다른 실행 환경에 있는 객체의 작업을 요청하는 기능입니다.** 찾기와 호출을 같은 개념으로 묶지 않습니다.

#### 146-1. 이름·디렉터리 조회

자바의 이름·디렉터리 인터페이스인 `JNDI`는 여러 이름 서비스와 디렉터리 서비스에 접근하는 공통 구조를 제공합니다. 실제 접근 방식은 제공자와 설정에 따라 달라집니다.[^naming]

```text
프로그램이 자원의 논리적 이름을 사용
→ 이름 조회 기능이 제공자에게 요청
→ 제공자가 실제 자원을 찾음
→ 프로그램이 결과를 사용
```

| 개념 | 의미 |
| --- | --- |
| 이름 서비스 | 이름과 객체·자원의 연결을 다룸 |
| 디렉터리 서비스 | 이름뿐 아니라 속성과 검색 조건도 다룸 |
| 문맥 | 이름을 해석하고 조회하는 환경 |
| 제공자 | 특정 서비스와 연결하는 구현 |
| 이름 조회 | 찾는 동작. 해당 자원의 실제 작업 수행과는 별개 |

`LDAP`는 디렉터리 접근 규약이고, `JNDI`는 자바 프로그램이 이름·디렉터리 기능을 이용하는 인터페이스입니다. 하나는 통신 규약, 다른 하나는 프로그램에서 사용하는 추상화라는 차이가 있습니다.[^naming]

예를 들어 애플리케이션이 논리적 이름으로 데이터 소스를 조회하고, 얻은 데이터 소스에서 연결을 요청할 수 있습니다. 다만 그 이름과 자원은 컨테이너나 제공자에 실제로 등록돼 있어야 합니다.

#### 146-2. 원격 메서드 호출

자바 원격 메서드 호출인 `RMI`는 원격 인터페이스를 통해 다른 가상 머신의 객체에 작업을 요청하는 구조입니다. 호출 모양이 지역 메서드와 비슷해도 네트워크·직렬화·원격 실행 실패를 고려해야 합니다.[^rmi]

```text
서버: 원격 객체 준비·내보내기 → 이름 등록
클라이언트: 이름 조회 → 원격 참조 획득
클라이언트: 원격 메서드 호출
→ 요청 전달 → 서버 객체 실행 → 결과 또는 예외 전달
```

| 구성요소 | 역할 |
| --- | --- |
| 원격 인터페이스 | 원격으로 호출할 작업의 계약 |
| 원격 객체 | 서버에서 실제 작업 수행 |
| 스텁 | 클라이언트 쪽에서 원격 요청을 전달하는 대리 객체 |
| 레지스트리 | 이름과 원격 객체 참조를 연결 |
| 원격 예외 | 통신 등 원격 호출 과정의 실패를 표현 |

#### 146-3. 매개변수 전달에서 혼동하지 않기

| 대상 | 기본적인 전달 의미 |
| --- | --- |
| 일반 직렬화 가능 객체 | 직렬화된 값을 받아 상대편에서 객체를 복원 |
| 내보내진 원격 객체 | 실제 원격 객체를 가리키는 원격 참조로 전달 |
| 직렬화할 수 없는 일반 객체 | 그대로 전달할 수 있다고 가정하면 안 됨 |

여기서 원격 참조 전달은 자바 언어 자체가 **참조에 의한 매개변수 전달**을 지원한다는 뜻이 아닙니다. 지역 자바 메서드의 인수 전달은 여전히 값 전달입니다. 원격 호출 계층이 객체를 표현하고 전송하는 방식을 구분해야 합니다.[^rmi]

**사고 예시:** 서버가 작업을 끝낸 뒤 응답 전달에 실패하면, 클라이언트는 실패를 관찰했더라도 서버의 작업 결과가 이미 반영됐을 수 있습니다. 따라서 재시도가 중복 처리를 만들 수 있는지 따져야 합니다.

#### 146-4. 신뢰 경계

외부에서 받은 이름이나 직렬화된 데이터를 무조건 신뢰하지 않습니다. 조회 가능한 대상, 객체 복원 정책, 네트워크 접근 범위, 인증과 권한을 함께 제한하는 방향으로 설계합니다.

**시험 포인트:** 이름을 찾는 기능, 원격 대리 객체, 객체 복사와 원격 참조, 지역 호출과 원격 실패를 구분합니다.

### 147. 나머지 표준 모듈과 제공자 구조

**표준 인터페이스가 있다는 것과 실제 제공자가 설치됐다는 것은 다릅니다.** 또한 표준 모듈 이름과 패키지 이름은 구분해야 합니다.

#### 147-1. 기능·제공자·사용자의 관계

| 위치 | 하는 일 | 예시 |
| --- | --- | --- |
| 사용자 코드 | 정해진 인터페이스를 호출 | 데이터베이스 연결 요청 |
| 공통 인터페이스 | 호출 계약 제공 | 데이터베이스 연결 표준 |
| 제공자 | 특정 시스템에 맞게 구현 | 특정 데이터베이스 드라이버 |

사용자가 호출하는 표면을 응용 프로그래밍 인터페이스라고 하고, 제공자가 연결되는 확장 계약을 서비스 제공자 인터페이스라고 부릅니다. 핵심은 영문 약자를 외우는 것이 아니라 **누가 호출하고 누가 구현하는가**입니다.

#### 147-2. 스크립트 기능과 엔진

`javax.script`는 스크립트 엔진을 찾고 실행하는 표준 인터페이스입니다. `ScriptEngineManager`가 특정 이름의 엔진을 못 찾으면 `null`을 반환할 수 있습니다. 따라서 “표준 스크립트 인터페이스가 있으니 자바스크립트 엔진도 반드시 있다”는 추론은 틀립니다.[^scripting]

```text
엔진 관리자 생성
→ 필요한 언어의 엔진 조회
→ 없으면 설치·설정 문제를 처리
→ 있으면 허용된 입력을 실행
```

엔진의 실제 제공 여부와 이름은 설치·의존성에 따라 달라지므로, 이 부분은 특정 실행 결과를 고정해 외우지 않습니다.

#### 147-3. 자바 21 표준 모듈 지도

다음은 자바 21의 **표준 모듈을 기능별로 묶은 지도**입니다. 모든 개발 도구·내부 구현 모듈을 나열한 표는 아닙니다.[^modules]

| 모듈 | 핵심 기능 |
| --- | --- |
| `java.base` | 객체·문자열·컬렉션·입출력·기본 보안 등 기초 |
| `java.compiler` | 자바 컴파일러·언어 모델·애너테이션 처리 인터페이스 |
| `java.datatransfer` | 데이터 전송·클립보드 관련 계약 |
| `java.desktop` | 화면·그래픽·이미지·인쇄·사운드·자바빈즈 |
| `java.instrument` | 실행 중 코드 계측 |
| `java.logging` | 표준 로깅 |
| `java.management` | 가상 머신·애플리케이션 관리 |
| `java.management.rmi` | 관리 기능의 원격 연결 |
| `java.naming` | 이름·디렉터리 서비스 |
| `java.net.http` | 웹 통신 클라이언트 |
| `java.prefs` | 사용자·시스템 선호 설정 |
| `java.rmi` | 원격 메서드 호출 |
| `java.scripting` | 스크립트 엔진 인터페이스 |
| `java.se` | 표준 플랫폼 모듈들을 묶는 집합 모듈 |
| `java.security.jgss` | 일반 보안 서비스·인증 교환 |
| `java.security.sasl` | 인증·보안 계층 지원 |
| `java.smartcardio` | 스마트카드 통신 |
| `java.sql` | 데이터베이스 연결 표준 |
| `java.sql.rowset` | 행 집합 기능 |
| `java.transaction.xa` | 분산 트랜잭션 자원 협력 인터페이스 |
| `java.xml` | 구조화 문서 파싱·검증·변환 |
| `java.xml.crypto` | 구조화 문서의 암호·서명 관련 기능 |

`java.transaction.xa`가 있다는 사실을 “자바 표준 개발 도구에 완전한 기업용 트랜잭션 서버가 들어 있다”로 확대하면 안 됩니다. 인터페이스의 범위와 실제 관리 구현을 구분합니다.

반대로 개발 도구에는 `jdk.jfr`처럼 `jdk.`로 시작하는 모듈도 있습니다. 개발 도구에 들어 있다는 사실과 표준 플랫폼 명세의 범위는 같은 말이 아닙니다.[^modules]

#### 147-4. 패키지 이름만 보고 분류하지 않기

자카르타의 주요 기업용 인터페이스가 `jakarta.*` 이름을 사용하는 것과 별개로, 자바 표준에는 `javax.swing`, `javax.sql`, `javax.crypto` 등이 존재합니다. **모든 `javax`를 일괄적으로 `jakarta`로 바꾸는 규칙은 없습니다.**[^desktop][^modules][^servlet]

다음 예제는 실제 클래스가 속한 모듈을 확인합니다.

```java
public class Main {
    public static void main(String[] 인수) {
        System.out.println(String.class.getModule().getName());
        System.out.println(java.sql.Connection.class.getModule().getName());
        System.out.println(javax.script.ScriptEngine.class.getModule().getName());
    }
}
```

출력:

```text
java.base
java.sql
java.scripting
```

**시험 포인트:** 패키지와 모듈, 표준 인터페이스와 제공자, 자바 표준과 자카르타를 서로 다른 축으로 분류합니다.

### 148. 설계 원칙과 패턴 — 언어 공통

**설계 원칙은 변경에 견디는 구조를 판단하는 기준이고, 설계 패턴은 반복되는 설계 문제의 해결 형태입니다.** 자바의 예약어나 전용 문법이 아니라 다른 객체지향 언어에도 적용되는 개념입니다.[^patterns]

#### 148-1. 응집도·결합도·합성

| 개념 | 묻는 질문 | 학습 예시 |
| --- | --- | --- |
| 응집도 | 한 구성요소의 책임이 얼마나 한 방향으로 모였는가? | 점수 판정과 무관한 파일 전송까지 한 클래스가 맡는가? |
| 결합도 | 한 부분의 변경이 다른 부분을 얼마나 흔드는가? | 저장 방식 변경 때문에 판정 규칙도 수정하는가? |
| 합성 | 필요한 기능을 가진 객체를 내부에서 협력시키는가? | 판정 서비스가 정책 객체를 사용 |
| 위임 | 실제 작업을 다른 객체에 맡기는가? | 서비스가 정책의 판정 메서드를 호출 |

상속과 합성은 우열만 외우지 않습니다. **진짜 하위 타입 관계인지, 단순한 기능 재사용인지**를 먼저 봅니다. 하위 타입 계약이 맞지 않는데 코드 몇 줄을 재사용하려고 상속하면 사용자가 기대한 동작을 깨뜨릴 수 있습니다.

#### 148-2. 객체지향 설계의 다섯 원칙

| 원칙 | 핵심 뜻 | 오해하기 쉬운 문장 |
| --- | --- | --- |
| 단일 책임 | 같은 변경 이유를 모으고 다른 변경 이유를 분리 | 메서드는 무조건 하나만 있어야 한다는 뜻이 아님 |
| 개방·폐쇄 | 예상한 변화는 확장으로 수용하고 기존의 안정된 부분 변경을 줄임 | 기존 코드는 영원히 수정 금지라는 뜻이 아님 |
| 리스코프 치환 | 하위 타입을 사용해도 상위 타입의 계약을 깨뜨리지 않음 | 상속 문법이 컴파일되면 자동으로 만족하는 것이 아님 |
| 인터페이스 분리 | 사용하지 않는 기능에 의존하도록 강요하지 않음 | 인터페이스를 무조건 잘게 쪼개라는 뜻이 아님 |
| 의존 역전 | 중요한 정책과 세부 구현이 적절한 추상화에 의존하도록 배치 | 생성자 매개변수를 쓰는 것과 완전히 같은 개념이 아님 |

원칙의 목적은 원칙 이름을 많이 적용하는 것이 아니라 **변경 영향을 관리하는 것**입니다. 아주 작은 코드에 불필요한 계층과 인터페이스를 늘리는 것도 비용입니다.[^solid]

#### 148-3. 의존성 주입·제어 역전·의존 역전

| 개념 | 판단 기준 |
| --- | --- |
| 의존성 주입 | 필요한 협력 객체를 사용 객체의 외부에서 전달하는가? |
| 제어 역전 | 실행 흐름·객체 생성 같은 제어의 일부를 프레임워크나 조립자에게 맡겼는가? |
| 의존 역전 원칙 | 중요한 정책이 구체적인 세부 구현에 직접 묶이지 않도록 의존 방향을 설계했는가? |

**의존성 주입은 스프링 없이도 할 수 있습니다.** 아래에서는 생성자에 판정 정책을 전달합니다.[^injection]

```java
import java.util.Objects;

public class Main {
    interface 판정정책 {
        boolean 합격(int 점수);
    }

    static final class 기준정책 implements 판정정책 {
        private final int 기준;

        기준정책(int 기준) {
            if (기준 < 0 || 기준 > 100) {
                throw new IllegalArgumentException("기준 범위 오류");
            }
            this.기준 = 기준;
        }

        @Override
        public boolean 합격(int 점수) {
            return 점수 >= 기준;
        }
    }

    static final class 평가서비스 {
        private final 판정정책 정책;

        평가서비스(판정정책 정책) {
            this.정책 = Objects.requireNonNull(정책);
        }

        String 평가(int 점수) {
            if (점수 < 0 || 점수 > 100) {
                throw new IllegalArgumentException("점수 범위 오류");
            }
            return 정책.합격(점수) ? "합격" : "불합격";
        }
    }

    public static void main(String[] 인수) {
        var 첫째 = new 평가서비스(new 기준정책(70));
        var 둘째 = new 평가서비스(new 기준정책(80));

        System.out.println(첫째.평가(75));
        System.out.println(둘째.평가(75));
    }
}
```

출력:

```text
합격
불합격
```

이 예제에서 **사용 방식은 의존성 주입**, **교체 가능한 판정 방식은 전략 패턴**으로 해석할 수 있습니다. 하나의 구조가 서로 다른 관점에서 여러 개념에 해당할 수 있습니다.

#### 148-4. 생성 패턴 다섯 가지

| 패턴 | 핵심 질문 | 직관 |
| --- | --- | --- |
| 팩터리 메서드 | 생성할 구체 타입의 선택을 하위 구현에 맡길 것인가? | 만드는 과정을 확장점으로 둠 |
| 추상 팩터리 | 서로 어울리는 객체 묶음을 생성할 것인가? | 같은 계열의 부품을 함께 만듦 |
| 빌더 | 복잡한 객체를 단계적으로 구성할 것인가? | 선택 항목을 모아 마지막에 완성 |
| 프로토타입 | 이미 준비된 객체를 복제해 만들 것인가? | 원형을 복사 |
| 싱글턴 | 정해진 범위에서 대표 인스턴스를 하나로 제한할 것인가? | 공유되는 하나의 관리 객체 |

정적 팩터리 메서드는 이름 있는 정적 메서드로 객체를 제공하는 관용 방식입니다. 이름에 팩터리가 있다고 모두 설계 패턴의 **팩터리 메서드 패턴**과 같은 구조인 것은 아닙니다.

#### 148-5. 구조 패턴 일곱 가지

| 패턴 | 목적 | 구분할 말 |
| --- | --- | --- |
| 어댑터 | 맞지 않는 인터페이스를 변환 | 변환 |
| 브리지 | 추상화와 구현의 변화 축을 분리 | 독립적 확장 |
| 컴포지트 | 단일 객체와 묶음을 같은 방식으로 처리 | 부분·전체 |
| 데코레이터 | 기존 인터페이스를 유지하며 기능을 덧붙임 | 기능 추가 |
| 퍼사드 | 복잡한 하위 시스템에 단순한 사용 창구 제공 | 단순화 |
| 플라이웨이트 | 공유 가능한 상태를 나누어 사용 | 상태 공유 |
| 프록시 | 다른 객체의 접근·호출을 대리하거나 제어 | 대리·통제 |

**어댑터는 호환, 데코레이터는 기능 추가, 프록시는 접근·호출 제어**를 중심으로 구분합니다. 실제 구현 코드의 모양이 비슷해도 의도가 다를 수 있습니다.

#### 148-6. 행동 패턴 열한 가지

| 패턴 | 목적 |
| --- | --- |
| 책임 연쇄 | 여러 처리자 중 요청을 처리할 대상을 연결 |
| 커맨드 | 요청을 객체로 만들어 전달·대기·기록 등에 활용 |
| 인터프리터 | 작은 언어의 문법과 해석 규칙 표현 |
| 반복자 | 내부 구조를 노출하지 않고 요소를 순회 |
| 중재자 | 여러 객체의 복잡한 상호작용을 모아 조정 |
| 메멘토 | 내부 상태를 과도하게 노출하지 않고 저장·복원 |
| 관찰자 | 상태 변화에 관심 있는 대상에게 알림 |
| 상태 | 내부 상태에 따라 행동을 바꿈 |
| 전략 | 사용할 알고리즘·정책을 교체 |
| 템플릿 메서드 | 처리 순서를 고정하고 일부 단계를 확장 |
| 방문자 | 객체 구조와 그 구조에 수행할 연산을 분리 |

생성·구조·행동이라는 세 분류는 무엇을 변화시키고 분리하는지에 따른 분류입니다. 처음에는 **전략·템플릿·어댑터·데코레이터·프록시·관찰자·싱글턴**부터 확실히 구분합니다.[^patterns]

#### 148-7. 데코레이터의 짧은 예제

```java
import java.util.Objects;

public class Main {
    interface 알림 {
        String 내용();
    }

    static final class 기본알림 implements 알림 {
        @Override
        public String 내용() {
            return "합격";
        }
    }

    static final class 강조알림 implements 알림 {
        private final 알림 원본;

        강조알림(알림 원본) {
            this.원본 = Objects.requireNonNull(원본);
        }

        @Override
        public String 내용() {
            return "[중요] " + 원본.내용();
        }
    }

    public static void main(String[] 인수) {
        알림 기본 = new 기본알림();
        알림 강조 = new 강조알림(기본);

        System.out.println(기본.내용());
        System.out.println(강조.내용());
    }
}
```

출력:

```text
합격
[중요] 합격
```

원본 객체를 직접 수정하지 않고, 같은 인터페이스를 가진 객체로 감싸 기능을 추가했습니다. 상속 없이도 행동을 확장할 수 있는 예입니다.

#### 148-8. 특히 헷갈리는 네 쌍

| 비교 | 첫째 | 둘째 |
| --- | --- | --- |
| 전략·상태 | 호출자가 선택한 정책을 교체하는 관점 | 객체의 현재 상태에 맞춰 행동이 달라지는 관점 |
| 전략·템플릿 메서드 | 협력 객체로 알고리즘을 교체 | 상속 구조에서 정해진 흐름의 일부를 확장 |
| 관찰자·책임 연쇄 | 변화에 관심 있는 대상을 통지 | 요청을 처리자들의 연결로 전달 |
| 싱글턴·정적 유틸리티 | 대표 객체의 존재를 관리 | 인스턴스 없이 정적 기능을 모음 |

**싱글턴 객체라고 내부 상태까지 자동으로 스레드 안전해지는 것은 아닙니다.** 인스턴스를 안전하게 하나 만드는 문제와, 만들어진 객체의 가변 상태를 안전하게 사용하는 문제는 다릅니다.

### 149. 서버 개발 — 자바 표준 바깥의 확장

**서버 개발은 요청을 받고, 업무 규칙을 실행하고, 데이터를 읽고 저장한 뒤 응답하는 과정입니다.** 자바 언어·표준 라이브러리, 자카르타 명세, 구현 서버, 스프링을 같은 층으로 놓지 않습니다.

#### 149-1. 표준·구현체·프레임워크의 층

| 층 | 의미 | 예시 |
| --- | --- | --- |
| 언어·표준 플랫폼 | 자바 코드와 기본 실행 기능 | 클래스·컬렉션·데이터베이스 연결 표준 |
| 기업용 명세 | 서버 환경에서 사용할 기능의 계약 | 서블릿·자카르타 영속성 |
| 구현체 | 계약을 실제 동작으로 구현 | 서블릿 컨테이너·영속성 제공자 |
| 프레임워크 | 개발 구조와 객체 연결 등을 지원 | 스프링 |
| 개발 편의 구성 | 설정·의존성·실행 구성을 자동화 | 스프링 부트 |

서블릿은 요청·응답과 생명주기를 다루는 명세입니다. 스프링 웹 기능은 서블릿 기반 방식도 제공하지만, 스프링 전체가 서블릿과 같은 말은 아닙니다.[^servlet][^spring-mvc]

#### 149-2. 서블릿의 생명주기와 공유 상태

```text
컨테이너가 서블릿 준비
→ 초기화
→ 여러 요청 처리
→ 종료 시 정리
```

초기화, 요청 처리, 종료 정리는 각각 `init`, `service`, `destroy`와 연결됩니다. 요청마다 반드시 새 서블릿 객체가 생기는 것으로 외우면 안 됩니다. 컨테이너는 같은 서블릿 인스턴스에 대한 요청을 여러 스레드에서 처리할 수 있습니다.[^http-servlet]

| 저장 위치 | 주의 |
| --- | --- |
| 요청 처리 메서드의 지역 변수 | 호출별 변수이지만, 참조 대상까지 전부 독립이라고 단정하지 않음 |
| 서블릿의 가변 인스턴스 필드 | 여러 요청이 공유할 수 있음 |
| 요청 객체의 속성 | 해당 요청 처리 흐름과 연결 |
| 세션 속성 | 같은 세션의 여러 요청이 함께 접근할 수 있음 |

사용자 이름을 서블릿 필드 하나에 저장하면 다른 요청이 그 값을 덮어쓸 수 있습니다. 요청별 데이터를 어디에 두는지와 객체의 공유 범위를 함께 봅니다.

#### 149-3. 필터·서블릿·인터셉터

| 요소 | 주된 관점 |
| --- | --- |
| 서블릿 필터 | 서블릿 컨테이너의 요청·응답 처리 경로에 참여 |
| 서블릿 | 요청을 받아 실제 처리 흐름을 수행 |
| 스프링 웹 인터셉터 | 스프링의 요청 처리 대상과 연결된 전후 처리 |
| 스프링 관점 지향 기능 | 프록시 등을 통해 메서드 호출에 공통 동작 적용 |

모두 “전후에 무언가를 한다”는 모양이 있지만 적용 위치가 다릅니다. 서버의 모든 요청이 모든 스프링 프록시를 자동으로 통과하는 것은 아닙니다.[^servlet][^spring-mvc][^spring-aop]

#### 149-4. 쿠키·세션·요청 전달

| 비교 | 의미 |
| --- | --- |
| 쿠키 | 클라이언트가 보관하고 요청과 함께 보낼 수 있는 데이터 |
| 서버 세션 | 서버 측에서 여러 요청을 연결해 상태를 관리하는 개념 |
| 요청 속성 | 한 요청 처리 과정에서 공유할 데이터 |
| 세션 식별자 | 여러 요청을 같은 세션과 연결하는 단서 |
| 서버 내부 전달 | 서버 안에서 처리를 넘김. 보통 같은 요청 흐름 유지 |
| 리다이렉트 | 클라이언트가 다른 위치로 새 요청을 하도록 응답 |

세션 데이터와 세션 식별자는 같은 것이 아닙니다. 흔히 세션 식별자를 쿠키로 전달하지만, 쿠키 전체가 곧 서버 세션이라는 뜻은 아닙니다.[^http-session]

서버 내부 전달은 `forward`, 리다이렉트는 `sendRedirect`와 연결해 구분합니다. “이동한다”라는 말만 보고 같은 동작으로 처리하지 않습니다.[^dispatcher]

#### 149-5. 요청 처리 구조

아래는 스프링의 서블릿 기반 웹 처리와 업무 계층을 연결한 **학습용 단순화**입니다. 모든 애플리케이션에 고정된 유일한 구조는 아닙니다.

```text
클라이언트 요청
→ 필터
→ 중앙 요청 처리 서블릿
→ 요청을 담당할 컨트롤러 선택
→ 서비스의 업무 규칙 실행
→ 저장소 계층을 통한 데이터 접근
→ 결과를 응답 본문 또는 화면으로 변환
```

`DispatcherServlet`은 스프링 웹에서 요청 처리를 조정하는 중심 역할을 합니다. 컨트롤러는 입력·응답의 연결, 서비스는 업무 규칙, 저장소는 데이터 접근이라는 책임으로 나눠 생각하면 이해하기 쉽습니다.[^spring-mvc]

화면을 만드는 방식에서는 모형·화면·제어의 분리가 사용됩니다. 응답 본문을 직접 만드는 서버에서는 화면 파일이 반드시 필요하지는 않습니다.

#### 149-6. 데이터베이스 접근 기술의 관계

| 개념·기술 | 역할 |
| --- | --- |
| 데이터베이스 연결 표준 | 연결·명령문·결과 집합을 다루는 기본 인터페이스 |
| 객체 관계 매핑 | 객체와 관계형 데이터 구조를 연결하는 접근 방식 |
| 자카르타 영속성 | 객체 영속성·매핑 등을 규정하는 명세 |
| 하이버네이트 | 자카르타 영속성 구현을 제공하는 객체 관계 매핑 도구 |
| 스프링 데이터 자카르타 영속성 지원 | 저장소 추상화로 데이터 접근 코드 구성을 돕는 기능 |

즉, **명세와 구현체와 편의 추상화는 서로 다릅니다.** 스프링 데이터의 저장소를 사용해도 실제 영속성 제공자와 데이터베이스 연결이 필요합니다.[^persistence][^hibernate][^spring-data]

#### 149-7. 영속성 문맥과 객체 상태 — 보충

| 상태 | 의미 |
| --- | --- |
| 새 객체 | 아직 영속성 문맥과 연결되지 않은 새 엔티티 |
| 관리 상태 | 영속성 문맥이 관리하는 엔티티 |
| 분리 상태 | 영속성 식별 정보가 있지만 현재 문맥이 관리하지 않는 엔티티 |
| 삭제 예정 상태 | 삭제가 요청된 관리 엔티티 |

`persist`와 `merge`를 모두 “저장”이라는 한 단어로 외우지 않습니다. 특히 `merge`는 전달한 객체의 상태를 관리 객체에 반영하고 **관리되는 결과 객체를 반환**합니다. 전달한 객체 자체가 반드시 관리 상태가 된다고 가정하면 안 됩니다.[^entitymanager]

관리 중인 객체의 변경은 동기화 과정에서 데이터베이스에 반영될 수 있습니다. 하지만 객체의 필드에 값을 넣은 순간 데이터베이스 커밋까지 완료됐다는 뜻은 아닙니다.[^persistence]

#### 149-8. 플러시·커밋·조회 문제

| 개념 | 의미 |
| --- | --- |
| 플러시 | 영속성 문맥의 변경과 데이터베이스를 동기화 |
| 커밋 | 트랜잭션을 성공으로 완료 |
| 롤백 | 트랜잭션의 변경을 취소 |
| 지연 조회 | 연관 데이터가 필요해지는 시점 등에 추가 조회 |
| 연쇄적인 추가 조회 문제 | 여러 객체의 연관 데이터를 각각 읽으며 조회가 반복되는 상황 |

<mark>플러시와 커밋은 같은 동작이 아닙니다.</mark> 변경 명령이 데이터베이스로 전달됐더라도 트랜잭션이 아직 완료되지 않았을 수 있습니다.[^entitymanager]

객체 목록을 한 번 읽고 각 객체의 연관 데이터를 다시 읽으면 여러 추가 질의가 발생할 수 있습니다. 이를 무조건 “객체 개수만큼 정확히 항상 발생한다”로 외우지 말고, 조회 전략·쿼리·캐시를 확인하는 문제로 이해합니다.[^hibernate-fetch]

#### 149-9. 스프링 컨테이너와 빈

스프링 컨테이너는 등록 정보를 바탕으로 객체를 생성하고, 의존성을 연결하고, 생명주기를 관리합니다. 핵심은 특별한 문법 자체가 아니라 **객체의 조립과 관리 책임을 분리하는 것**입니다.[^spring-ioc][^spring-di]

| 용어 | 뜻 |
| --- | --- |
| 빈 | 컨테이너가 관리하는 객체 |
| 빈 정의 | 어떤 객체를 어떻게 만들고 연결할지에 대한 정보 |
| 생성자 주입 | 생성 시 필요한 의존성을 전달 |
| 컴포넌트 탐색 | 정해진 범위의 선언을 찾아 등록 |
| 설정 클래스·빈 선언 | 등록할 객체와 구성 방법을 명시 |

직접 `new`로 만든 객체도 프로그램에서 정상적으로 사용할 수 있습니다. 다만 컨테이너를 거치지 않았다면 컨테이너 기반의 주입·프록시·생명주기 기능을 자동으로 기대할 수는 없습니다.

#### 149-10. 빈의 범위와 스레드 안전성

| 범위 | 개념 |
| --- | --- |
| 싱글턴 | 기본적으로 해당 컨테이너의 해당 빈 정의에 하나의 인스턴스 |
| 프로토타입 | 해당 빈을 요청할 때마다 새 인스턴스 제공 |
| 요청 | 하나의 웹 요청과 연결 |
| 세션 | 하나의 웹 세션과 연결 |

스프링의 싱글턴을 “프로세스 전체에서 그 클래스의 객체가 절대로 하나”라고 외우지 않습니다. 여러 컨테이너나 여러 빈 정의가 있을 수 있습니다.[^spring-scopes]

또한 싱글턴 빈 내부의 `ArrayList`나 일반 정수 필드가 자동으로 동기화되는 것은 아닙니다. 빈의 수명과 공유 상태의 동시성은 다른 문제입니다.

#### 149-11. 프록시와 관점 지향

관점 지향은 여러 업무에 반복되는 공통 관심사를 분리하는 접근입니다. 스프링의 일반적인 관점 지향 처리는 프록시를 통해 메서드 호출에 부가 동작을 적용합니다.[^spring-aop]

```text
외부 호출자
→ 프록시의 부가 처리
→ 대상 객체의 메서드
→ 프록시의 후속 처리
```

핵심은 **호출이 실제로 프록시를 통과하는가**입니다.

| 호출 | 기본 프록시 방식에서의 판단 |
| --- | --- |
| 프록시 참조로 대상 메서드 호출 | 설정된 부가 처리 적용 가능 |
| 대상 객체 내부의 `this.다른메서드()` | 일반적으로 프록시를 우회 |
| 직접 만든 객체의 메서드 호출 | 스프링이 만든 프록시를 자동으로 거치지 않음 |

따라서 같은 객체 안에서 메서드를 호출했다고 그 메서드의 모든 선언적 기능이 새롭게 적용되는 것은 아닙니다. 별도의 바이트코드 위빙 등 다른 방식의 설정은 구분합니다.[^spring-aop]

#### 149-12. 선언적 트랜잭션

`@Transactional`은 스프링에서 트랜잭션 처리의 속성을 선언하는 방식입니다. 트랜잭션 관리 설정과 실제 호출 경로가 갖춰져야 합니다.[^transactional]

| 속성 | 묻는 질문 |
| --- | --- |
| 전파 | 이미 트랜잭션이 있으면 참여할지, 별도로 시작할지 |
| 격리 수준 | 동시에 실행되는 트랜잭션의 관찰·간섭을 어디까지 허용할지 |
| 읽기 전용 | 읽기 중심이라는 의도를 어떻게 전달할지 |
| 시간 제한 | 트랜잭션 처리에 어떤 제한을 둘지 |
| 롤백 규칙 | 어떤 실패에서 트랜잭션을 취소할지 |

기본적인 롤백 규칙은 `RuntimeException`과 `Error`에 대해 롤백하며, 검사 예외에는 동일한 기본 규칙이 적용되지 않습니다. 다만 메서드별·전역 설정으로 바꿀 수 있으므로 **“검사 예외는 어떤 설정에서도 절대 롤백하지 않는다”도 오답**입니다.[^spring-rollback]

예외를 내부에서 잡아 정상 반환하면 바깥의 트랜잭션 처리가 그 예외를 직접 관찰하지 못할 수 있습니다. 단, 내부 자원이나 다른 처리에서 이미 롤백 전용 상태가 되었는지는 별도로 확인해야 합니다.

#### 149-13. 스프링과 스프링 부트

| 구분 | 중심 역할 |
| --- | --- |
| 스프링 프레임워크 | 객체 관리·의존성 주입·관점 지향·웹·트랜잭션 등의 기반 |
| 스프링 부트 | 의존성·설정·실행 구성을 편리하게 구성 |
| 스타터 | 특정 목적에 맞는 의존성을 묶어 도입을 도움 |
| 자동 설정 | 의존성·빈·설정 등의 조건을 보고 구성을 적용 |
| 실행 아카이브 | 애플리케이션과 필요한 실행 구성을 함께 패키징하는 방식 |

자동 설정은 조건과 사용자의 명시적 설정에 영향을 받습니다. “이름에 자동이 있으니 어떤 설정도 이해할 필요가 없다”는 뜻은 아닙니다.[^boot-auto][^boot-jar]

**시험 포인트:** 빈의 범위, 의존성 주입, 프록시 통과 여부, 트랜잭션의 경계, 명세·구현체의 관계부터 구분합니다.

### 150. 외부 라이브러리와 인접 플랫폼

**자바로 만든 도구가 모두 자바 표준에 포함되는 것은 아닙니다.** 사용 언어, 실행 플랫폼, 라이브러리의 배포 범위를 구분합니다.

#### 150-1. 데이터 교환과 통신

| 구분 | 예시 | 분류 |
| --- | --- | --- |
| 구조화 문서 처리 | `java.xml` | 자바 표준 모듈 |
| 웹 통신 | `java.net.http.HttpClient` | 자바 표준 기능 |
| 데이터베이스 연결 | `java.sql`과 드라이버 | 표준 인터페이스와 실제 드라이버를 구분 |
| JSON 처리·객체 변환 | 잭슨 등 | 외부 라이브러리 |
| 자카르타 JSON 처리 | JSON 처리 명세와 제공자 | 자카르타 영역 |
| 자바에프엑스 | 별도 화면 도구 묶음 | 외부 배포 프로젝트 |

잭슨은 데이터 처리 기능을 제공하는 별도 프로젝트입니다. 자카르타 JSON 처리 또한 자바 표준 플랫폼과 같은 범위로 놓지 않습니다.[^jackson][^jsonp][^javafx]

데이터 표현이 JSON이라는 사실만으로 객체의 타입·검증·보안 정책이 자동으로 정해지지 않습니다. 외부 입력의 허용 필드, 크기, 형식과 변환 실패를 따로 설계해야 합니다.

#### 150-2. 로깅의 표면과 실제 기록 구현

`SLF4J`는 로깅 호출을 위한 공통 표면을 제공하며, 실제 기록은 연결된 로깅 제공자가 담당합니다. 공통 호출 인터페이스와 실제 출력 구현을 구분해야 합니다.[^slf4j]

```text
업무 코드의 로깅 호출
→ 공통 로깅 인터페이스
→ 선택된 제공자
→ 콘솔·파일 등 실제 기록
```

| 개념 | 주의 |
| --- | --- |
| 로깅 인터페이스 | 호출할 메서드를 제공하는 쪽 |
| 로깅 제공자 | 실제 기록을 처리하는 쪽 |
| 로깅 연결 장치 | 다른 로깅 호출을 한 체계로 전달 |
| 여러 제공자 | 의도하지 않은 선택·경고·충돌을 확인 |

로그를 많이 남기는 것과 관찰 가능성이 높은 것은 같은 말이 아닙니다. 필요한 사건·식별자·수준을 정하고, 비밀번호나 인증 토큰 같은 민감한 값이 기록되지 않도록 해야 합니다.

#### 150-3. 같은 가상 머신을 쓰는 다른 언어

코틀린은 자바와 상호 운용할 수 있지만, 널 처리·프로퍼티·함수 표현 등의 규칙이 자바와 완전히 같지는 않습니다. 같은 가상 머신 위에서 실행된다고 같은 언어가 되는 것은 아닙니다.[^kotlin]

| 축 | 질문 |
| --- | --- |
| 소스 언어 | 어떤 문법과 타입 규칙으로 작성했는가? |
| 중간 결과물 | 어떤 클래스 파일·다른 형식으로 변환했는가? |
| 실행 환경 | 어떤 가상 머신·실행기가 처리하는가? |
| 사용 라이브러리 | 어떤 표준·외부 기능에 의존하는가? |

자바와 다른 언어가 같은 라이브러리를 호출하는 것은 가능하지만, 예외 선언이나 널 가능성의 표현까지 자동으로 같은 규칙이 되는 것은 아닙니다.

#### 150-4. 안드로이드와 자바 표준 실행 환경

안드로이드에서는 자바 계열 소스를 사용할 수 있지만, 실행에는 `ART`와 `DEX` 형식 등이 관여합니다. 일반적인 서버의 `HotSpot` 가상 머신과 실행 구조를 동일하게 취급하지 않습니다.[^android]

```text
자바 계열 소스 사용 가능
≠ 모든 자바 표준 기능을 같은 방식으로 사용 가능
≠ 서버용 자바 아카이브가 수정 없이 그대로 실행 가능
```

사용할 수 있는 기능은 안드로이드 버전·개발 도구·라이브러리 처리 범위 등을 확인해야 합니다. 언어 문법 지원과 실행 환경의 라이브러리 지원을 나누어 봅니다.

#### 150-5. 새로운 기술을 분류하는 질문

처음 보는 라이브러리 이름은 아래 질문으로 정리합니다.

| 질문 | 확인할 내용 |
| --- | --- |
| 무엇을 해결하는가? | 데이터 변환·통신·화면·저장·테스트 등의 역할 |
| 어디에 속하는가? | 자바 표준·자카르타·외부 프로젝트 |
| 누가 실제 구현하는가? | 인터페이스·제공자·서버·드라이버 |
| 어느 단계에 필요한가? | 컴파일·테스트·실행·운영 |
| 무엇과 호환되어야 하는가? | 자바 버전·프레임워크·의존성·운영체제 |
| 실패를 어떻게 확인하는가? | 예외·로그·테스트·진단 자료 |

**정리의 기준은 이름 암기보다 역할·경계·호환성입니다.**

<span id="pitfalls"></span>

## 잘 놓치는 핵심

### 1. import는 설치 명령이 아니다

`import`는 이름 해석을 돕습니다. 라이브러리 내려받기는 빌드 도구·저장소가, 클래스 탐색은 컴파일·실행 경로가 담당합니다. 세 역할을 분리합니다.

### 2. 컴파일·빌드·테스트 성공은 같은 말이 아니다

타입이 맞아도 업무 결과는 틀릴 수 있습니다. 테스트를 생략한 빌드도 가능하고, 준비한 테스트가 실제 요구사항을 충분히 다루지 못할 수도 있습니다.

### 3. 아카이브는 자동 실행·자동 의존성 포함을 뜻하지 않는다

시작 클래스, 클래스 경로, 자원 위치, 외부 의존성을 각각 확인합니다. 파일 확장자만으로 실제 실행 구성을 판단하지 않습니다.[^jar-spec]

### 4. 메이븐의 deploy는 서비스 재시작과 다르다

기본 생명주기의 `deploy`는 원격 저장소에 결과물을 게시하는 단계입니다. 서비스를 실행 환경에 반영하는 일반적인 배포 개념과 구분합니다.[^maven-life]

### 5. 의존성 선택은 항상 최신 버전 우선이 아니다

메이븐의 경로 기반 중재, 그레이들의 기본 충돌 해결, 명시적 버전 제약을 구분합니다. “빌드 도구가 알아서 했으니 원하는 버전이다”로 끝내지 않습니다.[^maven-dependency][^gradle-conflict]

### 6. 실행 범위와 검증 품질은 다르다

어떤 줄을 실행했는지와 올바른 결과를 확인했는지는 다릅니다. 정상값·경곗값·예외·상호작용을 함께 검증합니다.

### 7. 언어 단언과 테스트 단언은 다르다

자바의 `assert`는 실행 옵션에 따라 비활성화될 수 있습니다. 테스트 프레임워크의 단언 호출을 같은 방식으로 비활성화된다고 생각하면 안 됩니다.[^java][^junit-assert]

### 8. 스레드 덤프와 힙 덤프는 답하는 질문이 다르다

스레드 덤프는 실행·대기·잠금을, 힙 덤프는 객체·참조·메모리 점유를 조사하는 데 사용합니다. 두 자료를 함께 써야 하는 장애도 있습니다.

### 9. 평균이 좋아져도 일부 요청은 더 느려질 수 있다

처리량·평균 지연·백분위 지연·메모리·정확성을 함께 봅니다. 한 지표 개선을 전체 품질 향상으로 확대하지 않습니다.

### 10. 최대 힙 크기는 전체 프로세스 메모리 한도가 아니다

직접 메모리, 스택, 클래스 메타정보 등의 비용이 남습니다. 컨테이너 한도를 힙과 똑같이 잡으면 힙 밖 사용량을 고려하지 못할 수 있습니다.[^nmt][^java]

### 11. 맞춤형 실행 환경과 네이티브 실행 파일은 다르다

`jlink`는 필요한 모듈을 가진 자바 실행 환경을 만듭니다. 애플리케이션을 통째로 네이티브 기계어로 바꾸는 도구가 아닙니다.[^jlink]

### 12. 표준 인터페이스가 제공자를 보장하지 않는다

데이터베이스 연결 인터페이스가 있어도 특정 드라이버가 필요할 수 있습니다. 스크립트 엔진 인터페이스가 있어도 원하는 언어의 엔진은 없을 수 있습니다.[^scripting]

### 13. 의존성 주입은 프레임워크의 독점 기능이 아니다

필요한 객체를 생성자로 전달하는 수동 조립도 의존성 주입입니다. 프레임워크는 많은 객체의 조립과 생명주기를 관리하는 일을 도와줍니다.[^injection]

### 14. 싱글턴은 동시성 보증서가 아니다

하나로 공유되는 객체일수록 내부 상태에 동시에 접근하는지 확인해야 합니다. 싱글턴의 범위도 클래스 로더·컨테이너·빈 정의 등의 조건을 봅니다.

### 15. 프록시를 거치지 않으면 프록시 기능을 기대하기 어렵다

스프링 기본 프록시 방식에서는 같은 객체 내부의 직접 호출이 프록시를 우회할 수 있습니다. 애너테이션의 존재와 실제 적용 경로를 함께 확인합니다.[^spring-aop]

### 16. 명세·구현체·편의 계층은 다르다

자카르타 영속성, 하이버네이트, 스프링 데이터의 역할을 구분합니다. 서로 관련되어 있다고 서로 대체 가능한 같은 종류의 도구는 아닙니다.[^hibernate][^spring-data]

### 17. 객체 변경·플러시·커밋은 다른 단계다

관리 객체의 필드를 바꾼 것, 데이터베이스와 동기화한 것, 트랜잭션을 완료한 것을 나누어 판단합니다.[^entitymanager]

### 18. 이름·문법·실행 환경을 각각 확인한다

`javax`라는 이름만으로 기업용 구형 기능이라고 단정하지 않습니다. 자바 문법을 쓴다는 이유로 안드로이드와 일반 자바 서버의 실행 구조를 같다고 보지도 않습니다.[^modules][^android]

### 1. 도구 문제를 푸는 다섯 단계

### 3. 질문에 답하는 문장

| 질문 | 핵심 답변 |
| --- | --- |
| 컴파일과 빌드는 어떻게 다른가? | 컴파일은 클래스 파일 생성이고, 빌드는 테스트·자원 처리·패키징 등을 포함하는 준비 과정입니다. |
| 테스트를 통과하면 오류가 없는가? | 준비한 검사 조건을 통과한 것이며, 검사하지 않은 입력과 환경까지 보장하지는 않습니다. |
| 의존성 주입을 왜 사용하는가? | 객체의 사용과 조립을 분리해 협력 객체를 교체하고 시험하기 쉽게 합니다. |
| 스프링 빈은 무조건 하나인가? | 빈 범위에 따라 다르며, 기본 싱글턴도 컨테이너와 빈 정의의 범위를 봅니다. |
| 관점 지향 처리는 언제 적용되는가? | 설정된 대상과 호출 경로가 맞아야 하며, 기본 프록시 방식에서는 실제 프록시 통과 여부가 중요합니다. |
| 플러시와 커밋은 같은가? | 플러시는 변경 동기화이고 커밋은 트랜잭션의 성공 완료입니다. |
| 성능이 좋아졌다는 근거는 무엇인가? | 대표 조건에서 정확성을 유지한 채 목표 지표와 자원 비용을 비교한 결과입니다. |

### 4. 이 편의 우선순위

**첫 회독:** 컴파일·빌드·패키징 → 의존성 범위 → 테스트 → 스레드·힙 덤프 → 설계 패턴 → 의존성 주입·프록시·트랜잭션 순서로 읽습니다.

**두 번째 회독:** 세부 옵션, 재현 가능한 빌드, 모듈 이미지, 클래스 데이터 공유, 데스크톱·원격 호출·표준 모듈 지도를 보충합니다.

## 예시로 한 바퀴

### 1. 목표와 범위

**설정에서 합격 기준을 읽고, 정책을 주입하고, 결과를 저장한 뒤 출력하는 작은 프로그램**을 만듭니다. 별도 프레임워크나 외부 데이터베이스 없이 실행합니다.

| 연결할 개념 | 이 예제에서 하는 일 |
| --- | --- |
| 자원 | `app.properties`에서 합격 기준 읽기 |
| 입력 검증 | 빈 이름·점수 범위·설정 오류 확인 |
| 전략·의존성 주입 | 판정 정책을 서비스에 전달 |
| 인터페이스·대체 구현 | 메모리 저장소를 연결 |
| 불변 결과·수정 불가 목록 | 결과 레코드와 목록 복사본 사용 |
| 자체 검사 | 경계·예외를 실제 조건으로 확인 |
| 패키징 | 클래스와 설정을 함께 아카이브에 포함 |
| 실행 이미지 | 필요한 모듈을 가진 환경에서 실행 |

이것은 **단일 스레드 학습 예제**입니다. 메모리 저장소는 데이터베이스 트랜잭션·다중 요청·영구 보관을 구현하지 않습니다. 자체 검사는 원리를 보여 주는 것이며 테스트 프레임워크 전체를 대신하려는 목적은 아닙니다.

### 2. 파일 구조

140절의 테스트 프로젝트와 다른 새 연습 폴더를 사용합니다.

```text
종합연습/
├── src/
│   └── study/
│       └── Main.java
└── resources/
    └── app.properties
```

`resources/app.properties`의 내용:

```properties
pass.score=70
```

### 3. 전체 코드

파일은 `src/study/Main.java`입니다.

```java
package study;

import java.io.InputStream;
import java.io.InputStreamReader;
import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;
import java.util.Properties;

public class Main {
    record 평가결과(String 이름, int 점수, boolean 합격) {
        평가결과 {
            Objects.requireNonNull(이름, "이름이 없습니다.");
            if (이름.isBlank()) {
                throw new IllegalArgumentException("이름이 비어 있습니다.");
            }
            if (점수 < 0 || 점수 > 100) {
                throw new IllegalArgumentException("점수 범위 오류");
            }
        }
    }

    @FunctionalInterface
    interface 판정정책 {
        boolean 합격(int 점수);
    }

    interface 결과저장소 {
        void 저장(평가결과 결과);
        List<평가결과> 모두();
    }

    static final class 메모리저장소 implements 결과저장소 {
        private final List<평가결과> 자료 = new ArrayList<>();

        @Override
        public void 저장(평가결과 결과) {
            자료.add(Objects.requireNonNull(결과));
        }

        @Override
        public List<평가결과> 모두() {
            return List.copyOf(자료);
        }
    }

    static final class 평가서비스 {
        private final 판정정책 정책;
        private final 결과저장소 저장소;

        평가서비스(판정정책 정책, 결과저장소 저장소) {
            this.정책 = Objects.requireNonNull(정책);
            this.저장소 = Objects.requireNonNull(저장소);
        }

        평가결과 평가(String 이름, int 점수) {
            if (점수 < 0 || 점수 > 100) {
                throw new IllegalArgumentException("점수 범위 오류");
            }
            var 결과 = new 평가결과(이름, 점수, 정책.합격(점수));
            저장소.저장(결과);
            return 결과;
        }
    }

    static int 기준읽기() throws Exception {
        Properties 설정 = new Properties();
        try (InputStream 입력 = Main.class.getResourceAsStream("/app.properties")) {
            if (입력 == null) {
                throw new IllegalStateException("설정 파일이 없습니다.");
            }
            try (var 읽기 = new InputStreamReader(입력, StandardCharsets.UTF_8)) {
                설정.load(읽기);
            }
        }

        String 값 = 설정.getProperty("pass.score");
        if (값 == null) {
            throw new IllegalStateException("합격 기준이 없습니다.");
        }

        final int 기준;
        try {
            기준 = Integer.parseInt(값.strip());
        } catch (NumberFormatException 오류) {
            throw new IllegalStateException("합격 기준은 정수여야 합니다.", 오류);
        }
        if (기준 < 0 || 기준 > 100) {
            throw new IllegalStateException("합격 기준 범위 오류");
        }
        return 기준;
    }

    static void 확인(boolean 조건, String 설명) {
        if (!조건) {
            throw new AssertionError(설명);
        }
    }

    static void 자체검사() {
        var 저장소 = new 메모리저장소();
        var 서비스 = new 평가서비스(점수 -> 점수 >= 70, 저장소);

        확인(!서비스.평가("가", 69).합격(), "69점은 불합격");
        확인(서비스.평가("나", 70).합격(), "70점은 합격");
        확인(서비스.평가("다", 100).합격(), "100점은 합격");

        boolean 범위거절 = false;
        try {
            서비스.평가("라", 101);
        } catch (IllegalArgumentException 오류) {
            범위거절 = true;
        }
        확인(범위거절, "범위를 벗어난 점수 거절");
        확인(저장소.모두().size() == 3, "거절한 결과는 저장하지 않음");

        boolean 수정거절 = false;
        try {
            저장소.모두().clear();
        } catch (UnsupportedOperationException 오류) {
            수정거절 = true;
        }
        확인(수정거절, "외부에서 반환 목록을 수정하지 못함");
    }

    public static void main(String[] 인수) throws Exception {
        자체검사();
        System.out.println("자체 검사 통과");

        int 기준 = 기준읽기();
        var 저장소 = new 메모리저장소();
        var 서비스 = new 평가서비스(점수 -> 점수 >= 기준, 저장소);

        서비스.평가("가", 69);
        서비스.평가("나", 70);
        서비스.평가("다", 85);

        System.out.println("합격 기준: " + 기준);
        for (평가결과 결과 : 저장소.모두()) {
            String 판정 = 결과.합격() ? "합격" : "불합격";
            System.out.println(결과.이름() + ": " + 결과.점수() + "점 " + 판정);
        }
        System.out.println("저장 건수: " + 저장소.모두().size());
    }
}
```

### 5. 아카이브로 묶어서 실행

```text
jar --create --file score-app.jar --main-class study.Main -C out . -C resources .

```

출력은 위와 같습니다. `resources` 폴더 자체가 아니라 그 **내용**을 아카이브 루트에 넣어 `/app.properties`로 찾도록 했습니다.

클래스 파일은 있지만 자원을 넣지 않으면 설정을 찾지 못합니다. 따라서 “클래스가 실행됐다”와 “배포 파일이 올바르다”를 따로 검사해야 합니다.

### 6. 의존성과 맞춤형 실행 환경

```text
jdeps --print-module-deps score-app.jar
```

이 예제의 결과:

```text
java.base
```

다른 연습의 결과와 겹치지 않도록, 아직 존재하지 않는 디렉터리에 실행 환경을 만듭니다.

```text
jlink --add-modules java.base --output score-runtime
```

실행:

```text
리눅스·맥: ./score-runtime/bin/java -jar score-app.jar
윈도우: .\score-runtime\bin\java.exe -jar score-app.jar
```

동일한 출력이 나와야 합니다. 이 연습에서는 자바 기본 모듈만 필요합니다. 이후 데이터베이스·화면·외부 제공자를 추가하면 모듈·자원·의존성을 다시 확인해야 합니다.

| ④ | 틀림 | 열거형에도 필드와 메서드를 선언할 수 있습니다. |

</details>

### 문제 18. 프록시와 트랜잭션

스프링의 기본 프록시 기반 선언적 트랜잭션에 대한 설명으로 옳은 것은?

| 선택지 | 내용 |
| --- | --- |
| ① | 같은 객체 내부에서 `this`로 호출해도 언제나 새 프록시를 통과한다. |
| ② | 직접 `new`로 만든 객체도 애너테이션만 있으면 모든 컨테이너 기능이 자동 적용된다. |
| ③ | 검사 예외는 어떤 명시적 설정을 하더라도 절대 롤백할 수 없다. |
| ④ | 설정된 프록시를 통과하는 호출인지와 롤백 규칙을 함께 확인해야 한다. |

<details markdown="1">
<summary>정답과 모든 선택지 해설</summary>

**정답: ④**

| 선택지 | 판단 | 해설 |
| --- | --- | --- |
| ① | 틀림 | 같은 객체 내부의 직접 호출은 일반적으로 프록시를 우회합니다. |
| ② | 틀림 | 컨테이너가 관리하고 설정한 실행 구조가 필요합니다. |
| ③ | 틀림 | 기본 규칙과 사용자 설정을 구분해야 합니다. 검사 예외도 규칙을 정해 롤백할 수 있습니다. |
| ④ | 옳음 | 적용 경로와 속성이 모두 중요합니다. 애너테이션의 존재만으로 충분하지 않습니다. |

</details>

### 문제 19. 영속성의 역할과 처리 단계

객체 영속성과 트랜잭션에 대한 설명으로 옳은 것은?

| 선택지 | 내용 |
| --- | --- |
| ① | 플러시는 변경 동기화이고, 커밋은 트랜잭션을 성공으로 완료하는 것이므로 구분한다. |
| ② | 객체의 필드에 값을 대입한 순간 반드시 데이터베이스 커밋이 완료된다. |
| ③ | 자카르타 영속성 명세·하이버네이트·스프링 데이터는 모두 완전히 같은 종류의 구현체이다. |
| ④ | `merge`는 반환값과 무관하게 전달한 객체 자체를 언제나 관리 상태로 바꾼다. |

<details markdown="1">
<summary>정답과 모든 선택지 해설</summary>

**정답: ①**

| 선택지 | 판단 | 해설 |
| --- | --- | --- |
| ① | 옳음 | 데이터베이스에 변경을 전달한 것과 트랜잭션의 완료는 다릅니다. |
| ② | 틀림 | 객체 변경과 동기화·트랜잭션 완료의 시점을 구분해야 합니다. |
| ③ | 틀림 | 명세, 영속성 구현체, 저장소 편의 추상화라는 역할 차이가 있습니다. |
| ④ | 틀림 | `merge`는 관리되는 결과 객체를 반환합니다. 인수 객체 자체의 상태와 혼동하지 않습니다. |

</details>

## 코드와 명령의 확인 범위
