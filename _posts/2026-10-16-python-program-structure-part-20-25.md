프로그램 구성은 함수와 클래스를 묶는 일뿐 아니라, 오류를 어디에서 처리하고 자원을 언제 정리하며 어떤 환경에서 실행할지 정하는 일입니다. 이 글에서는 예외·자원·파일·모듈·설치 환경·타입 계약을 하나의 흐름으로 연결합니다.[^errors][^modules][^venv][^typing]

<blockquote class="prompt-info">
<p>한 줄 핵심: 실패는 예외로 전달하고, 자원은 정해진 범위에서 정리하며, 코드는 모듈로 나누고, 실행 환경과 타입 계약을 명시합니다.</p>
</blockquote>

<mark>예외를 잡는 것과 문제를 해결하는 것은 다르고, 타입을 적는 것과 실제 값을 검증하는 것도 다릅니다.</mark>

<details>
<summary>한 줄로</summary>

오류의 전달 → 자원의 정리 → 자료의 입출력 → 코드의 분리 → 환경의 재현 → 타입 계약 순서로 읽습니다.

</details>

## 먼저 보는 전체 지도

| 표현·도구 | 중심 역할 | 하지 않는 일 |
| --- | --- | --- |
| `try`·`except` | 지정한 예외의 처리 경로 선택 | 실패한 문장부터 자동으로 재시도 |
| `finally` | 제어가 해당 구문을 벗어날 때 정리 | 강제 종료된 프로세스의 복구 보장 |

| `json` | 제한된 자료 구조의 텍스트 직렬화 | 임의의 파이썬 객체를 그대로 보존 |
| `import` | 모듈을 찾고 이름 연결 | 매번 새 객체로 깊은 복사 |
| 가상환경 | 파이썬 실행·설치 환경 분리 | 악성 코드의 파일 접근 차단 |

표는 각 도구의 계약을 비교한 것입니다. 특히 자원 정리의 실제 행동은 해당 컨텍스트 관리자가, 타입 오류의 정적 진단은 타입 검사 도구가 담당합니다.[^compound][^json][^import][^venv][^typing]

## 20부. 예외와 오류 처리

### 20.1. 구문 오류·실행 중 예외·논리 오류

**구문 오류**는 소스가 문법에 맞지 않는 경우입니다. **실행 중 예외**는 실행 과정에서 특정 연산을 완료하지 못한 경우입니다. **논리 오류**는 실행은 끝났지만 의도와 다른 결과를 계산하는 경우입니다.[^errors]

| 구분 | 간단한 사례 | 확인 방법 |
| --- | --- | --- |
| 구문 오류 | 조건문 뒤 콜론 누락 | 소스 분석 단계의 오류 위치 확인 |
| 실행 중 예외 | 정수로 바꿀 수 없는 문자열 변환 | 예외 종류와 호출 경로 확인 |
| 논리 오류 | 평균에서 원소 개수가 아닌 고정값으로 나눔 | 테스트와 기대값 비교 |

같은 파일에 문법 오류가 있으면 그 파일의 `try`가 실행되기도 전에 소스 분석이 실패할 수 있습니다. 다만 실행 도중 다른 소스를 컴파일하거나 모듈을 가져오며 발생한 `SyntaxError`는 바깥에서 처리할 수 있습니다.[^errors][^builtins]

```python
try:
    compile("if True print(1)", "<학습용>", "exec")
except SyntaxError:
    print("소스 문법 오류")  # 출력: 소스 문법 오류

try:
    int("아흔")
except ValueError:
    print("값 변환 실패")  # 출력: 값 변환 실패

점수들 = [60, 90]
잘못된평균 = sum(점수들) / 3
print(잘못된평균)  # 출력: 50.0
```

마지막 계산은 예외를 일으키지 않습니다. 그러나 두 점수의 평균은 75이므로, 예외가 없다는 사실만으로 프로그램이 정확하다고 판단할 수 없습니다.

### 20.2. 예외 계층과 주요 내장 예외

예외는 클래스와 인스턴스로 표현합니다. 모든 예외의 공통 기반은 `BaseException`이며, 일반적인 업무 오류는 보통 `Exception`의 하위 클래스로 설계합니다.[^exceptions]

```text
BaseException
├─ Exception
│  ├─ ValueError
│  ├─ TypeError
│  ├─ LookupError
│  │  ├─ IndexError
│  │  └─ KeyError
│  ├─ OSError
│  │  ├─ FileNotFoundError
│  │  └─ PermissionError
│  └─ RuntimeError
├─ KeyboardInterrupt
├─ SystemExit
└─ GeneratorExit
```

일부 주요 클래스만 표시한 계층입니다. `except Exception`은 일반적인 오류를 넓게 잡지만, `KeyboardInterrupt`나 `SystemExit`까지 잡지는 않습니다. 반면 예외 타입을 생략한 `except:`는 이들까지 포착할 수 있습니다.[^exceptions]

| 예외 | 구분 기준 | 사례 |
| --- | --- | --- |
| `TypeError` | 연산에 맞지 않는 타입·호출 방식 | 문자열과 정수의 직접 덧셈 |
| `ValueError` | 타입은 받을 수 있지만 값이 부적절 | `int("사과")` |
| `NameError` | 사용할 이름을 찾지 못함 | 정의하지 않은 이름 조회 |
| `AttributeError` | 속성을 찾지 못함 | 없는 메서드 조회 |
| `IndexError` | 시퀀스 인덱스가 범위를 벗어남 | 빈 리스트의 첫 항목 조회 |
| `KeyError` | 매핑에 요청한 키가 없음 | 없는 사전 키의 대괄호 조회 |
| `OSError`의 하위 예외 | 운영체제·입출력 관련 실패 | 파일 부재·접근 권한 부족 |

<blockquote class="prompt-warning">
<p>사용자의 종료 요청까지 무조건 잡아서 계속 실행하는 코드는 피합니다. 잡을 수 있는 범위보다, 실제로 복구할 수 있는 범위를 먼저 정합니다.</p>
</blockquote>

### 20.3. `try`·`except`·`else`·`finally`의 실행 순서

`try`에서 처리 대상 작업을 실행합니다. 일치하는 예외가 발생하면 `except`로 이동하고, `try`가 끝까지 정상 완료되면 `else`를 실행합니다. `finally`는 이 구문을 벗어나는 과정에서 정리 작업을 수행합니다.[^errors]

```python
def 읽기(문자):
    try:
        수 = int(문자)
    except ValueError:
        print("변환 실패")
    else:
        print("변환 성공", 수)
    finally:
        print("정리")

읽기("12")
# 출력: 변환 성공 12
# 출력: 정리
읽기("사과")
# 출력: 변환 실패
# 출력: 정리
```

| `try`의 종료 상황 | `except` | `else` | `finally` 이후 |
| --- | --- | --- | --- |
| 끝까지 정상 완료 | 건너뜀 | 실행 | 다음 문장 진행 |
| 일치하는 예외 발생 | 해당 처리부 실행 | 건너뜀 | 처리 결과에 따라 진행 |
| 일치하지 않는 예외 발생 | 처리하지 못함 | 건너뜀 | 예외를 바깥으로 전달 |
| `return`·`break`·`continue` | 건너뜀 | 건너뜀 | 원래 제어 이동을 이어감 |

**`else`는 단순히 “예외가 없었다”만으로 판단하지 않습니다.** `try` 안의 `return` 등으로 끝나면 실행하지 않습니다. 또한 `except`나 `else`에서 발생한 새 예외를 같은 `try`의 다른 `except`가 다시 잡는 것도 아닙니다.[^compound]

`finally`가 새 예외를 일으키거나 반환을 덮어쓰지 않는다는 전제에서 표의 흐름이 성립합니다. 프로세스 강제 종료나 운영체제 장애까지 정리 실행을 보장하지는 않습니다.[^simple][^withpep]

### 20.4. 여러 예외·처리 순서·과도한 포착

일반 `except`는 위에서 아래로 검사하고 **처음 일치한 처리부 하나**를 선택합니다. 상위 예외를 먼저 적으면 하위 예외를 위한 뒤쪽 분기가 가려질 수 있습니다.[^errors]

```python
class 자료오류(Exception):
    pass

class 빈자료오류(자료오류):
    pass

try:
    raise 빈자료오류("값이 없습니다.")
except 빈자료오류:
    print("구체적인 오류 처리")  # 출력: 구체적인 오류 처리
except 자료오류:
    print("일반적인 자료 오류 처리")

try:
    int(None)
except (TypeError, ValueError):
    print("형식 또는 값이 부적절함")  # 출력: 형식 또는 값이 부적절함
```

파이썬 3.13에서 여러 예외 타입을 하나의 처리부에 적을 때는 괄호 안에 쉼표로 구분합니다. `except TypeError or ValueError:`처럼 쓰면 두 예외를 모두 지정한 것이 아닙니다.[^compound]

`except Exception: pass`는 오류를 없애는 것이 아니라 **실패 정보를 버리고 계속 가는 것**입니다. 복구·사용자 안내·기록·재발생 중 무엇을 할지 정하고, 보호할 작업만 좁은 `try`에 넣는 편이 읽기 쉽습니다.

### 20.5. 발생·재발생·예외 연결

`raise`는 예외를 발생시킵니다. 처리 중인 예외를 그대로 다시 전달할 때는 인자 없는 `raise`를 사용합니다. 오류의 추상화 수준을 바꿔 전달할 때는 `raise 새예외 from 원인`으로 직접 원인을 연결합니다.[^simple]

```python
def 점수변환(문자):
    try:
        return int(문자)
    except ValueError as 원인:
        raise ValueError("점수는 정수 문자열이어야 합니다.") from 원인

try:
    점수변환("높음")
except ValueError as 오류:
    print(str(오류))  # 출력: 점수는 정수 문자열이어야 합니다.
    print(type(오류.__cause__).__name__)  # 출력: ValueError
```

| 표현 | 의도 | 주의 |
| --- | --- | --- |
| `raise ValueError("설명")` | 새로운 실패 알림 | 구체적인 맥락을 전달 |
| `raise` | 현재 처리 중인 예외 재전달 | 활성 예외 없이 쓰면 오류 |
| `raise 새예외 from 원인` | 명시적 원인 관계 설정 | 바깥 계층의 계약으로 변환할 때 유용 |
| `raise 새예외 from None` | 기본 오류 화면의 문맥 연결 표시 억제 | 내부 문맥 정보 자체를 지우는 것은 아님 |

`__cause__`는 명시적 원인, `__context__`는 다른 예외를 처리하던 중 발생했다는 문맥을 나타냅니다. `from None`은 출력 방식에 영향을 주며, 이미 연결된 문맥 객체가 반드시 사라지는 것은 아닙니다.[^exceptions]

### 20.6. 사용자 정의 예외·추가 정보·추적 정보

사용자 정의 예외에는 호출자가 판단할 수 있는 정보를 넣습니다. 문자열 전체를 분석해서 오류 종류를 추측하기보다, 예외 클래스와 속성을 구분하는 편이 명확합니다.[^errors]

```python
class 점수범위오류(ValueError):
    def __init__(self, 점수):
        self.점수 = 점수
        super().__init__(f"점수 범위를 벗어났습니다: {점수}")

try:
    raise 점수범위오류(120)
except 점수범위오류 as 오류:
    오류.add_note("자료의 두 번째 행을 확인하세요.")
    print(오류.점수)      # 출력: 120
    print(오류.args)      # 출력: ('점수 범위를 벗어났습니다: 120',)
    print(오류.__notes__) # 출력: ['자료의 두 번째 행을 확인하세요.']
```

추적 정보는 예외에 이르기까지의 호출 경로를 보여 줍니다. 마지막 줄에서 예외 종류와 설명을 보고, 자신의 코드가 등장하는 호출 지점과 그 입력을 거슬러 확인합니다. 여러 예외가 연결되어 있으면 마지막 오류뿐 아니라 원인도 읽습니다.[^traceback]

`traceback.print_exc()`는 처리 중인 예외 정보를 출력하고, `traceback.format_exc()`는 문자열로 얻습니다. 운영 기록에는 비밀번호·접속 토큰·민감한 원본 자료가 포함되지 않도록 주의합니다.[^traceback]

**예외 처리부의 이름 수명도 일반 대입과 다릅니다.** `except ... as 오류`로 연결한 이름은 처리부가 끝나면 정리됩니다. 나중에 필요하면 메시지 등 필요한 정보를 다른 이름에 옮깁니다.[^compound]

```python
try:
    int("사과")
except ValueError as 오류:
    종류 = type(오류).__name__

print(종류)  # 출력: ValueError
print("오류" in locals())  # 출력: False
```

### 20.7. 예외 그룹과 `except*`

여러 작업의 실패를 함께 보고해야 할 때 `ExceptionGroup`으로 예외들을 묶을 수 있습니다. `except*`는 그룹 내부에서 해당 타입에 맞는 부분을 나누어 처리합니다. 따라서 일반 `except`와 달리 여러 처리부가 실행될 수 있습니다.[^exceptiongroups]

```python
try:
    raise ExceptionGroup(
        "자료 오류 모음",
        [ValueError("점수 오류"), TypeError("형식 오류"), ValueError("범위 오류")],
    )
except* ValueError as 묶음:
    print("값 오류", len(묶음.exceptions))  # 출력: 값 오류 2
except* TypeError as 묶음:
    print("타입 오류", len(묶음.exceptions))  # 출력: 타입 오류 1
```

| 구분 | 일반 `except` | `except*` |
| --- | --- | --- |
| 판단 대상 | 발생한 예외 객체 자체 | 그룹 내부의 일치하는 예외 부분 |
| 실행될 처리부 | 처음 일치한 하나 | 서로 다른 부분에 대해 여러 개 가능 |
| 처리되지 않은 부분 | 전체 예외 전파 | 남은 예외 부분 전파 |
| 대표 용도 | 단일 작업 실패 | 여러 작업·검증의 실패 묶음 |

`ExceptionGroup`에는 `Exception` 계열 예외를 넣습니다. 더 넓은 `BaseException` 계열을 포함하는 그룹은 `BaseExceptionGroup`으로 구별합니다. 같은 `try`에서 `except`와 `except*`를 혼합할 수 없으며, `except*` 처리부에서 바깥 제어 흐름을 떠나는 `return`·`break`·`continue`는 허용되지 않습니다.[^exceptiongroups]

예외 그룹은 동시성을 직접 실행하는 도구가 아닙니다. 이미 발생한 여러 실패를 묶어서 전달·분리하는 도구입니다.

### 20.8. 사전 검사·예외 중심 처리·`assert`·정리의 함정

사전 검사는 작업 전에 조건을 확인합니다. 예외 중심 처리는 작업을 먼저 시도하고 예상한 실패를 처리합니다. 어느 하나가 항상 우월한 것은 아닙니다. 값 범위 검사는 사전에 하는 것이 자연스럽고, 파일 존재 여부처럼 검사 후에도 바뀔 수 있는 상태는 실제 작업의 실패도 처리해야 합니다.[^glossary]

```python
def 점수검증(점수):
    if type(점수) is not int:
        raise TypeError("정수 점수가 필요합니다.")
    if not 0 <= 점수 <= 100:
        raise ValueError("점수는 0부터 100까지입니다.")
    return 점수

print(점수검증(80))  # 출력: 80
try:
    점수검증(True)
except TypeError as 오류:
    print(str(오류))  # 출력: 정수 점수가 필요합니다.
```

여기서는 불리언을 점수로 받지 않으려고 의도적으로 `type(...) is int`를 사용했습니다. 모든 상황에서 정확히 같은 타입만 허용하라는 뜻은 아닙니다.

`assert`는 개발 중 기대하는 내부 조건을 검사하는 도구입니다. 최적화 옵션으로 제거될 수 있으므로 외부 입력·권한·업무 규칙을 보장하는 유일한 검증으로 사용하지 않습니다.[^simple]

```python
def 위험한반환():
    try:
        return "원래 결과"
    finally:
        return "덮어쓴 결과"

print(위험한반환())  # 출력: 덮어쓴 결과
```

파이썬 3.13에서 위 코드는 실행되지만 권장되는 작성 방식은 아닙니다. `finally`에서 반환하면 원래 반환값을 덮어쓰고, 전달 중인 예외까지 가릴 수 있습니다. 정리부에는 가능한 한 **정리만** 넣습니다.[^simple]

## 21부. 컨텍스트 관리자와 자원 관리

### 21.1. 자원 수명과 `with`

자원은 사용을 끝낸 뒤 정리해야 하는 대상입니다. 파일은 닫고, 잠금은 해제하며, 임시 설정은 복원할 수 있습니다. **컨텍스트 관리자**는 특정 코드 범위의 진입·종료 동작을 정의한 객체입니다.[^withpep]

```python
from io import StringIO

with StringIO("자료") as 파일:
    print(파일.read())    # 출력: 자료
    print(파일.closed)    # 출력: False

print(파일.closed)        # 출력: True
```

`with`를 벗어났다고 `파일`이라는 이름이 사라지는 것은 아닙니다. 이름은 남아 있어도 자원의 상태는 닫힌 상태가 될 수 있습니다. `with`가 새로운 지역 스코프를 만드는 것도 아닙니다.[^compound][^io]

자원 정리를 객체의 쓰레기 수집 시점에 맡기지 않고 **사용 구간의 끝에 연결한다**는 점이 핵심입니다. 단, 해당 종료 동작이 프로세스 강제 종료까지 보장되는 것은 아닙니다.[^withpep]

### 21.2. 진입·종료 규약과 `as`의 의미

`__enter__`는 진입할 때, `__exit__`는 종료할 때 호출됩니다. `as` 뒤 이름에는 관리자 객체 자체가 아니라 **`__enter__`의 반환값**이 연결됩니다.[^withpep]

```python
class 사용구간:
    def __enter__(self):
        print("준비")
        return "사용할 값"

    def __exit__(self, 오류종류, 오류, 추적):
        print("정리", 오류종류 is None)
        return False

with 사용구간() as 값:
    print(값)
# 출력: 준비
# 출력: 사용할 값
# 출력: 정리 True
```

| 항목 | 의미 |
| --- | --- |
| `__enter__()` | 준비 후 본문에 넘길 값을 반환 |
| `__exit__(오류종류, 오류, 추적)` | 본문의 종료 상황을 받아 정리 |
| 정상 완료 | 종료 메서드에 세 개의 `None` 전달 |
| 예외 발생 | 예외 타입·객체·추적 정보 전달 |
| `return`·`break`·`continue` | 예외가 아닌 제어 이동이므로 세 개의 `None` 전달 |

정상 제어 이동 때 `__exit__`가 참을 반환하더라도 원래의 `return`을 취소하는 것은 아닙니다. 종료 메서드의 참·거짓 반환은 **예외 억제 여부**에 관여합니다.[^withpep]

### 21.3. 정상 종료·본문 실패·진입 실패

`__enter__`가 정상적으로 반환한 뒤에는 본문 실행이나 `as` 대상 대입에서 실패해도 종료 메서드를 호출합니다. 반면 **`__enter__` 자체가 실패하면 그 관리자의 `__exit__`는 자동 호출되지 않습니다.**[^compound]

```python
class 진입실패:
    def __enter__(self):
        print("진입 시도")
        raise RuntimeError("준비 실패")

    def __exit__(self, 오류종류, 오류, 추적):
        print("이 종료는 자동 실행되지 않음")

try:
    with 진입실패():
        print("본문")
except RuntimeError:
    print("바깥에서 처리")
# 출력: 진입 시도
# 출력: 바깥에서 처리
```

여러 준비 작업 중 일부만 성공한 뒤 진입이 실패할 수 있다면, 진입 과정 자체에 정리 경로가 필요합니다. 이미 연 파일이나 획득한 자원을 그대로 남기지 않아야 합니다.

`with open(...)`에서 파일 열기가 실패하면 관리자 진입 전 단계의 실패입니다. 아직 열리지 않은 파일을 본문의 정리 경로에서 닫으려는 방식으로 해결하지 않습니다.[^compound]

### 21.4. 종료 메서드의 반환과 예외 억제

본문에서 예외가 발생했을 때 `__exit__`가 참으로 판정되는 값을 반환하면 그 예외를 억제합니다. `False`나 `None`이면 원래 예외를 계속 전달합니다.[^withpep]

```python
class 값오류만무시:
    def __enter__(self):
        return self

    def __exit__(self, 오류종류, 오류, 추적):
        return 오류종류 is not None and issubclass(오류종류, ValueError)

with 값오류만무시():
    int("사과")
    print("실패한 문장 다음에는 돌아오지 않음")

print("구간 바깥에서 계속")  # 출력: 구간 바깥에서 계속
```

억제했다고 실패한 문장을 건너뛰고 **본문의 다음 문장으로 돌아오는 것은 아닙니다.** 이미 본문을 떠났으므로 `with` 다음으로 이동합니다.

좁고 의도적인 무시는 `contextlib.suppress(구체적인예외)`로 표현할 수도 있습니다. 관리자가 모든 예외를 무조건 억제하면 원인을 숨기므로, 무시해도 올바른 상태가 유지되는 경우에만 사용합니다.[^contextlib]

### 21.5. 여러 자원과 역순 정리

한 `with`에서 여러 관리자를 쓰면 왼쪽부터 진입하고 오른쪽부터 종료합니다. 이는 앞 관리자가 바깥, 뒤 관리자가 안쪽인 중첩 구조와 같습니다.[^compound]

```python
from contextlib import contextmanager

@contextmanager
def 사용(이름):
    print(이름, "열기")
    try:
        yield 이름
    finally:
        print(이름, "닫기")

with 사용("첫째") as 첫째, 사용("둘째") as 둘째:
    print("본문")
# 출력: 첫째 열기
# 출력: 둘째 열기
# 출력: 본문
# 출력: 둘째 닫기
# 출력: 첫째 닫기
```

뒤 관리자의 진입이 실패해도 앞에서 성공적으로 진입한 관리자는 종료됩니다. 예외가 발생했을 때 안쪽 관리자가 억제하면 바깥 관리자는 이미 억제된 결과를 전달받습니다.[^compound]

정리 순서는 단순한 외울 거리가 아닙니다. 첫 자원을 이용해 두 번째 자원을 만들었다면, 두 번째를 먼저 정리해야 의존하는 바깥 자원이 아직 살아 있습니다.

### 21.6. `contextmanager`와 한 번의 `yield`

`contextmanager`는 제너레이터 함수로 컨텍스트 관리자를 작성하게 해 줍니다. 진입에 성공하는 경로에서는 **정확히 한 번 값을 내주고**, 본문이 끝난 뒤 그 위치에서 재개되어 종료 처리를 합니다.[^contextlib]

```python
from contextlib import contextmanager

@contextmanager
def 임시목록():
    값들 = []
    try:
        yield 값들
    finally:
        값들.clear()

with 임시목록() as 자료:
    자료.extend([10, 20])
    print(자료)  # 출력: [10, 20]

print(자료)  # 출력: []
```

본문의 예외는 제너레이터가 멈춘 `yield` 지점으로 전달됩니다. 관리자가 그것을 잡고 다시 발생시키지 않으면 억제한 것으로 처리될 수 있습니다. 단순히 기록만 할 목적이라면 예외를 다시 전달해야 합니다.[^contextlib]

`yield` 뒤에 정리 문장을 그냥 적는 것과 `finally` 안에 넣는 것은 다릅니다. 예외 경로에서도 정리하려면 `try`·`finally`로 감쌉니다.

이 방식으로 얻은 관리자 객체 하나를 일반적으로 여러 번 재사용할 수는 없습니다. 매번 `임시목록()`을 호출하여 새로운 관리자를 얻는 방식과 구별합니다.[^contextlib]

### 21.7. `ExitStack`과 동적인 자원 개수

자원 개수가 실행 중 결정되면 중첩 `with`를 미리 작성하기 어렵습니다. `ExitStack`은 진입한 관리자의 종료 작업과 등록한 정리 함수를 모아 역순으로 실행합니다.[^contextlib]

```python
from contextlib import ExitStack
from io import StringIO

with ExitStack() as 정리스택:
    파일들 = [
        정리스택.enter_context(StringIO(내용))
        for 내용 in ["가", "나", "다"]
    ]
    print([파일.read() for 파일 in 파일들])  # 출력: ['가', '나', '다']

print(all(파일.closed for 파일 in 파일들))  # 출력: True
```

| 방법 | 등록하는 것 | 예외 억제 가능 여부 |
| --- | --- | --- |
| `enter_context(관리자)` | 진입 실행 후 종료 메서드 | 해당 종료 규약에 따름 |
| `push(종료함수)` | 종료 규약에 맞는 함수 | 반환값으로 억제 가능 |
| `callback(함수, ...)` | 일반 정리 함수 | 반환값으로 억제하지 못함 |
| `close()` | 등록된 정리 작업을 즉시 실행 | 정상 종료에 해당하는 방식으로 해제 |
| `pop_all()` | 정리 책임을 다른 스택으로 이전 | 호출 즉시 자원을 닫지는 않음 |

스택 자체는 `with`로 사용하거나 명시적으로 닫습니다. 객체가 쓰레기 수집되면 등록한 정리 함수가 자동 실행될 것이라고 가정하지 않습니다.[^contextlib]

### 21.8. 비동기 컨텍스트 관리자

자원의 준비·정리가 대기를 필요로 하면 `async with`를 사용할 수 있습니다. 비동기 관리자는 `__aenter__`·`__aexit__`를 제공하고, 진입과 종료 과정에서 대기할 수 있습니다.[^compound][^asyncpep]

```python
import asyncio
from contextlib import asynccontextmanager

@asynccontextmanager
async def 비동기사용():
    print("준비")
    await asyncio.sleep(0)
    try:
        yield "자원"
    finally:
        await asyncio.sleep(0)
        print("정리")

async def 실행():
    async with 비동기사용() as 값:
        print(값)

asyncio.run(실행())
# 출력: 준비
# 출력: 자원
# 출력: 정리
```

이 예제는 일반 파이썬 파일로 실행합니다. 이미 이벤트 루프가 실행되는 환경에서는 `asyncio.run`을 중첩 호출하는 대신 그 환경의 대기 방식을 사용합니다.[^asynciorunner]

비동기라는 이름이 파일·계산 작업을 자동으로 별도 스레드에 보내는 것은 아닙니다. 어떤 작업이 실제로 대기하고 무엇이 실행 흐름을 막는지는 28부에서 다룹니다.[^asyncpep]

## 22부. 파일·경로·직렬화

### 22.1. 텍스트 파일·바이너리 파일·입출력 계층

파일에 저장되는 것은 바이트입니다. **텍스트 입출력**은 바이트를 인코딩 규칙에 따라 문자열로 변환하며, **바이너리 입출력**은 바이트를 그대로 다룹니다.[^io]

| 구분 | 텍스트 모드 | 바이너리 모드 |
| --- | --- | --- |
| 읽은 값 | `str` | `bytes` |
| 쓰는 값 | `str` | 바이트 계열 자료 |
| 인코딩 변환 | 수행 | 직접 수행하지 않음 |
| 줄바꿈 변환 | 설정에 따라 수행 | 수행하지 않음 |
| 대표 용도 | 문서·텍스트 설정 | 이미지·압축·직렬화 바이트 |

일반적인 텍스트 파일은 바깥의 텍스트 계층, 그 아래 버퍼 계층, 더 아래 운영체제와 연결되는 원시 계층으로 볼 수 있습니다. 모든 스트림이 정확히 같은 구성인 것은 아니며, `StringIO`·`BytesIO`처럼 메모리 안에서 동작하는 스트림도 있습니다.[^io]

```python
from io import StringIO, BytesIO

with StringIO("한글") as 문자파일:
    문자 = 문자파일.read()

with BytesIO("한글".encode("utf-8")) as 바이트파일:
    바이트 = 바이트파일.read()

print(type(문자).__name__, len(문자))      # 출력: str 2
print(type(바이트).__name__, len(바이트))  # 출력: bytes 6
```

### 22.2. 파일 모드·위치·버퍼링

파일 모드는 기존 내용을 보존할지, 읽기·쓰기를 허용할지, 새 파일만 만들지를 정합니다. 특히 `w`는 열기에 성공하면 기존 내용을 잘라 내므로 실습 대상 파일을 구별해야 합니다.[^builtins]

| 모드 | 중심 동작 | 기존 파일 | 파일이 없으면 |
| --- | --- | --- | --- |
| `r` | 읽기 | 보존 | 실패 |
| `w` | 쓰기 | 기존 내용 제거 | 생성 |
| `a` | 끝에 추가 | 보존 | 생성 |
| `x` | 새 파일 생성 | 이미 있으면 실패 | 생성 |
| `r+` | 읽기·쓰기 | 보존 | 실패 |
| `w+` | 읽기·쓰기 | 기존 내용 제거 | 생성 |
| `a+` | 읽기·끝에 추가 | 보존 | 생성 |

`b`는 바이너리 모드, `t`는 텍스트 모드입니다. 예를 들어 `rb`는 바이너리 읽기입니다. `+`가 붙었다고 기존 내용 제거 규칙이 없어지는 것은 아닙니다.[^builtins]

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as 임시폴더:
    경로 = Path(임시폴더) / "기록.txt"
    with 경로.open("w+", encoding="utf-8") as 파일:
        쓴개수 = 파일.write("가나")
        print(쓴개수)       # 출력: 2
        print(파일.read())  # 출력:
        파일.seek(0)
        print(파일.read())  # 출력: 가나
```

쓰기 후 위치가 끝에 있으므로 첫 `read()`는 빈 문자열입니다. `seek(0)`은 시작으로 이동합니다. 텍스트 스트림의 `tell()` 결과는 일반적인 문자 번호가 아니라 복원용 위치 값으로 취급하며, 바이너리 파일처럼 임의의 문자 수만큼 이동할 수 있다고 가정하지 않습니다.[^inputoutput]

`flush()`는 파이썬 쪽 버퍼의 자료를 아래 계층으로 밀어냅니다. 이것만으로 물리 저장장치에 영구 기록되었다고 보장하지 않습니다. 더 강한 저장 요구에는 파일시스템·운영체제의 동기화와 교체 전략까지 고려합니다.[^io][^os]

### 22.3. 파일 반복·대용량 처리·스트리밍

`read()`와 `readlines()`로 전체 내용을 한꺼번에 만들 수도 있지만, 파일을 직접 순회하면 한 줄씩 처리할 수 있습니다. 큰 자료에서는 **입력뿐 아니라 중간·출력 결과도 누적하지 않는지** 함께 확인합니다.[^inputoutput]

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as 임시폴더:
    경로 = Path(임시폴더) / "점수.txt"
    경로.write_text("10\n20\n30\n", encoding="utf-8")
    합계 = 0
    with 경로.open(encoding="utf-8") as 파일:
        for 줄 in 파일:
            합계 += int(줄.strip())
    print(합계)  # 출력: 60
```

바이너리 스트림은 정해진 크기의 블록으로 반복해서 읽을 수 있습니다. `iter(호출가능객체, 종료값)`을 이용하면 빈 바이트가 나올 때까지 반복할 수 있습니다.[^builtins]

```python
from io import BytesIO

with BytesIO(b"1234567") as 파일:
    크기들 = [len(블록) for 블록 in iter(lambda: 파일.read(3), b"")]

print(크기들)  # 출력: [3, 3, 1]
```

파일을 사용하는 제너레이터를 반환할 때는 실제 소비 시점까지 파일이 열려 있는지 확인합니다. `with` 안에서 제너레이터 표현식만 만들고 밖에서 읽으면 이미 파일이 닫혔을 수 있습니다. 지연 실행과 자원 수명은 별개의 문제입니다.

### 22.4. 명시적 인코딩·줄바꿈·오류 처리

텍스트를 읽고 쓸 때는 자료의 실제 인코딩을 확인합니다. 파일마다 인코딩이 다를 수 있으므로, 오류를 없애려고 무조건 무시하기보다 저장 규칙과 일치시키는 것이 먼저입니다. 파이썬 3.13의 기본 인코딩은 환경과 실행 설정에 영향을 받으므로 예제에서는 명시합니다.[^io]

```python
from io import BytesIO, TextIOWrapper

원본 = "가\r\n나\r".encode("utf-8")
with TextIOWrapper(BytesIO(원본), encoding="utf-8", newline=None) as 파일:
    내용 = 파일.read()

print(repr(내용))  # 출력: '가\n나\n'
```

읽기에서 `newline=None`은 서로 다른 일반적인 줄바꿈을 `\n`으로 변환합니다. `newline=""`은 줄바꿈을 인식하되 반환할 때 원래 줄바꿈을 유지합니다. 쉼표 구분 파일은 `csv` 모듈이 줄바꿈을 처리하도록 `newline=""`로 여는 방식이 기본입니다.[^builtins][^csv]

| 오류 처리 | 동작 | 주의 |
| --- | --- | --- |
| `strict` | 변환 불가능한 부분에서 예외 | 잘못된 자료를 드러냄 |
| `ignore` | 문제 부분을 버림 | 조용한 자료 손실 가능 |
| `replace` | 대체 문자로 변경 | 원래 자료를 정확히 복원하기 어려움 |

파일에 바이트 순서 표식이 붙었는지, 생산 시스템이 어떤 인코딩을 쓰는지도 확인합니다. 단순히 글자가 읽혀 보인다는 것과 자료를 정확히 해석했다는 것은 같지 않습니다.[^codecs]

### 22.5. 경로 객체·상대 경로·작업 디렉터리

`Path`는 파일시스템 경로를 객체로 다루는 도구입니다. `/`로 경로를 결합하고, 이름·확장자·부모 경로를 구분합니다.[^pathlib]

```python
from pathlib import PurePosixPath, PureWindowsPath

경로 = PurePosixPath("자료") / "점수.csv"
print(경로.name)    # 출력: 점수.csv
print(경로.stem)    # 출력: 점수
print(경로.suffix)  # 출력: .csv

윈도우경로 = PureWindowsPath("C:/자료") / "점수.csv"
print(윈도우경로.is_absolute())  # 출력: True
```

`PurePosixPath`·`PureWindowsPath`는 실제 파일에 접근하지 않고 경로 문법만 다룹니다. 실제 입출력에는 현재 운영체제에 맞는 `Path`를 사용합니다.[^pathlib]

**상대 경로의 기본 기준은 현재 작업 디렉터리입니다.** 소스 파일이 저장된 폴더와 항상 같지 않습니다. `Path.cwd()`는 작업 디렉터리를, 파일 기반 실행에서 `Path(__file__).resolve().parent`는 그 소스 파일의 폴더를 구하는 데 사용할 수 있습니다. 대화형 환경에는 `__file__`이 없을 수 있습니다.[^pathlib][^modules]

<blockquote class="prompt-warning">
<p>편집기에서는 되는데 터미널에서 파일을 못 찾으면, 파일이 없는지 판단하기 전에 현재 작업 디렉터리와 실제 결합한 경로를 확인합니다.</p>
</blockquote>

### 22.6. 디렉터리 탐색·복사·임시 파일·압축

경로 탐색과 파일 내용 처리는 구별합니다. `iterdir`는 바로 아래 항목을 순회하고, `glob`·`rglob`는 패턴에 맞는 경로를 찾습니다. 검색 결과의 순서에 의존한다면 직접 정렬합니다.[^pathlib]

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from shutil import copy2

with TemporaryDirectory() as 임시폴더:
    폴더 = Path(임시폴더)
    원본 = 폴더 / "원본.txt"
    원본.write_text("안녕", encoding="utf-8")
    copy2(원본, 폴더 / "복사본.txt")
    이름들 = sorted(경로.name for 경로 in 폴더.glob("*.txt"))
    print(이름들)  # 출력: ['복사본.txt', '원본.txt']
```

| 도구 | 용도 | 기억할 점 |
| --- | --- | --- |
| `Path.mkdir` | 폴더 생성 | 부모 생성·기존 폴더 허용 옵션 구분 |
| `shutil.copy`·`copy2` | 파일 복사 | `copy2`도 모든 운영체제 메타데이터 복사를 보장하지 않음 |
| `shutil.copytree` | 디렉터리 트리 복사 | 기존 대상 처리 정책 확인 |
| `TemporaryDirectory` | 임시 작업 폴더 | 사용 범위가 끝나면 정리 |
| `zipfile`·`tarfile` | 압축 묶음 처리 | 외부 자료의 경로·크기·특수 항목 검토 |

임시 파일은 예측 가능한 이름을 직접 만들어 쓰기보다 전용 도구를 사용합니다. 윈도우에서는 열린 파일의 재열기·삭제 조건이 다를 수 있으므로, 예제처럼 사용을 끝내고 닫는 순서를 분명히 합니다.[^tempfile][^shutil]

출처를 모르는 압축 파일을 곧바로 중요한 폴더에 풀지 않습니다. 경로 검증과 자원 제한 등 자세한 안전성 검토는 32부에서 다룹니다.[^security]

### 22.7. 자료 형식 비교: `json`·`csv`·`tomllib`·`pickle`

**직렬화**는 객체의 자료를 저장·전달할 수 있는 표현으로 바꾸는 일입니다. 형식마다 표현 가능한 타입과 공유 구조, 언어 호환성이 다릅니다.[^pickle][^json]

| 도구 | 대표 용도 | 결과·입력 | 핵심 제약 |
| --- | --- | --- | --- |
| `json` | 시스템 간 계층형 자료 교환 | 텍스트 | 기본 지원 타입에 제한 |
| `csv` | 행·열 형태의 표 자료 | 텍스트 | 보통 읽은 필드를 직접 변환해야 함 |
| `tomllib` | 구조화된 설정 읽기 | 파일 또는 문자열 | 표준 모듈 자체는 쓰기 기능 없음 |
| `pickle` | 파이썬 객체 구조 저장 | 바이너리 | 신뢰할 수 없는 자료는 역직렬화 금지 |

`json.dumps`는 문자열을 만들고, `json.dump`는 파일 같은 출력 대상에 씁니다. `loads`는 메모리의 자료를, `load`는 읽기 가능한 입력 대상을 받습니다.[^json]

```python
import json

원본 = {"이름": "가람", "점수": [80, 90]}
문자열 = json.dumps(원본, ensure_ascii=False)
복원 = json.loads(문자열)

print(문자열)  # 출력: {"이름": "가람", "점수": [80, 90]}
print(복원 == 원본)  # 출력: True
```

`ensure_ascii=False`는 문자열 안에서 한글을 이스케이프하지 않고 보이게 합니다. 파일 인코딩을 지정하는 옵션은 아니므로 저장할 때의 `encoding`과 구별합니다.[^json]

```python
import csv
from io import StringIO

with StringIO('이름,점수\n"가람,첫째",90\n', newline="") as 파일:
    행 = next(csv.DictReader(파일))

print(행["이름"])                 # 출력: 가람,첫째
print(type(행["점수"]).__name__)  # 출력: str
print(int(행["점수"]) + 5)        # 출력: 95
```

쉼표가 들어간 필드나 따옴표·줄바꿈은 단순한 `split(",")`로 안전하게 처리하기 어렵습니다. 행 전체를 올바른 구문으로 읽은 뒤 숫자 변환과 값 검증을 수행합니다.[^csv]

```python
import tomllib

설정 = tomllib.loads('[service]\nname = "점수 도구"\nlimit = 100\n')
print(설정["service"]["name"])   # 출력: 점수 도구
print(설정["service"]["limit"])  # 출력: 100
```

`tomllib.load`에 파일을 전달할 때는 바이너리 읽기 모드로 엽니다. `tomllib.loads`에는 문자열을 전달합니다. 이름이 비슷해도 입력 형태를 구별합니다.[^tomllib]

### 22.8. 직렬화와 복사·공유 구조·신뢰 경계

직렬화한 뒤 복원한다고 원본과 같은 타입·공유 관계가 모두 유지되는 것은 아닙니다. 예를 들어 기본적인 JSON 변환은 튜플을 배열로 표현하고, 복원하면 리스트가 됩니다.[^json]

```python
import json

원본 = (1, 2)
복원 = json.loads(json.dumps(원본))
print(복원, type(복원).__name__)  # 출력: [1, 2] list

문자키복원 = json.loads(json.dumps({1: "가"}))
print(문자키복원)  # 출력: {'1': '가'}
```

다음은 **현재 코드 안에서 만든 신뢰 가능한 자료만** `pickle`로 왕복하는 예입니다. 같은 리스트를 두 곳에서 참조한 구조를 복원된 객체 안에서도 보존합니다.[^pickle]

```python
import pickle

공유 = [1, 2]
원본 = [공유, 공유]
바이트 = pickle.dumps(원본)
복원 = pickle.loads(바이트)

print(복원 is 원본)        # 출력: False
print(복원[0] is 복원[1])  # 출력: True
print(복원[0] is 공유)     # 출력: False
```

`pickle`은 적절한 객체에서 순환 참조도 다룰 수 있습니다. 그러나 함수와 클래스는 보통 코드 전체가 아니라 모듈·이름을 바탕으로 복원하므로, 해당 정의를 가져올 수 있는 환경이 필요합니다. 파일 핸들·외부 연결을 저장했다가 그대로 재개하는 도구가 아닙니다.[^pickle]

<blockquote class="prompt-danger">
<p>신뢰할 수 없는 pickle 자료를 열지 않습니다. 역직렬화 과정에서 코드가 실행될 수 있습니다. JSON도 입력 크기·구조·값을 검증해야 하지만, 일반적인 JSON 읽기와 pickle 역직렬화는 위험의 성격이 다릅니다.</p>
</blockquote>

이 경고는 확장자만 보고 판단하라는 뜻이 아닙니다. 누가 생성했고 전달 중 바뀌지 않았는지까지 포함한 신뢰 경계를 확인합니다.[^pickle][^json]

## 23부. 모듈·패키지·가져오기 구조

### 23.1. 모듈·패키지·배포 프로젝트

**모듈**은 독립된 이름 공간을 가진 코드 단위입니다. `.py` 파일이 대표적이지만, 내장 모듈이나 확장 모듈도 있으므로 “모듈은 무조건 파이썬 파일 하나”라고 한정하지 않습니다. **가져오기 패키지**는 하위 모듈을 포함할 수 있는 특별한 모듈입니다.[^modules][^import]

| 개념 | 판단 기준 | 예시 |
| --- | --- | --- |
| 모듈 | 독립된 이름 공간 | `math`, 직접 작성한 `계산.py` |
| 가져오기 패키지 | 하위 모듈을 포함하는 모듈 구조 | `도구상자.계산`의 `도구상자` |
| 배포 프로젝트 | 설치·버전·배포 메타데이터의 단위 | 설치 도구가 설치 대상으로 다루는 프로젝트 |
| 라이브러리 | 재사용 기능을 묶어 부르는 일반적 표현 | 하나 이상의 모듈·패키지 |

설치할 때 쓰는 이름과 `import`에 쓰는 이름은 같을 수도, 다를 수도 있습니다. 하나의 배포 프로젝트가 여러 가져오기 패키지를 제공할 수도 있습니다.[^distribution]

따라서 설치 오류는 설치 이름·실행 환경을, 가져오기 오류는 모듈 이름·탐색 경로·초기화 과정을 따로 확인해야 합니다.

### 23.2. `import`와 `from ... import ...`의 바인딩

`import 상태`는 현재 이름 공간의 `상태`를 모듈 객체에 연결합니다. `from 상태 import 기준`은 그 시점에 모듈의 `기준`이 가리키는 객체를 현재 이름 공간의 `기준`에 연결합니다. 어느 쪽도 객체를 깊은 복사하지 않습니다.[^simple][^modules]

아래 두 파일을 **같은 폴더**에 저장하고 `가져오기실험.py`를 실행합니다.

```python
# 파일: 상태.py
print("상태 초기화")
기준 = 10
기록 = []
```

```python
# 파일: 가져오기실험.py
import 상태
from 상태 import 기준, 기록

상태.기준 = 20
상태.기록.append("추가")
print(상태.기준, 기준)
print(기록)

상태.기록 = ["새목록"]
print(기록, 상태.기록)
# 출력: 상태 초기화
# 출력: 20 10
# 출력: ['추가']
# 출력: ['추가'] ['새목록']
```

첫 번째 재대입은 모듈의 이름만 새 정수에 연결합니다. 이미 가져온 `기준`을 자동 갱신하지 않습니다. 반면 `append`는 공유하는 리스트 자체를 바꾸므로 `기록`에서도 보입니다. 나중에 모듈이 새 리스트를 대입하면 다시 서로 다른 객체를 가리키게 됩니다.

<mark>가져오기는 새로운 문법처럼 보여도, 핵심은 이전 편에서 배운 이름 바인딩과 객체 공유입니다.</mark>

### 23.3. 일반 패키지·초기화 파일·이름 공간 패키지

일반 패키지는 보통 `__init__.py`를 포함합니다. 패키지를 초기화할 때 이 파일을 실행하며, 빈 파일로 두거나 제한된 공개 기능을 연결할 수 있습니다.[^modules]

```text
학습폴더/
└─ 도구상자/
   ├─ __init__.py
   ├─ 계산.py
   └─ __main__.py
```

**이름 공간 패키지**는 `__init__.py` 없이도 구성될 수 있습니다. 여러 위치에 나뉜 하위 모듈을 하나의 패키지 이름 아래에 모으는 데 사용합니다. 따라서 초기화 파일이 없는 폴더를 무조건 패키지가 아니라고 판단하지 않습니다.[^namespace]

| 구분 | 일반 패키지 | 이름 공간 패키지 |
| --- | --- | --- |
| 초기화 코드 | 보통 `__init__.py` | 같은 방식의 초기화 파일 없음 |
| 위치 | 일반적으로 한 패키지 위치 | 여러 경로의 부분을 묶을 수 있음 |
| 대표 목적 | 일반적인 코드 묶음 | 여러 배포 단위가 공통 이름 아래 확장 |

패키지 초기화 파일에 대용량 자료 읽기나 네트워크 연결을 넣으면 단순한 가져오기도 무거운 작업이 됩니다. 가져오기만 해도 발생하는 부작용을 작게 유지하는 방향으로 설계합니다.

### 23.4. 절대 가져오기·상대 가져오기·패키지 문맥

절대 가져오기는 최상위 패키지 이름부터 적습니다. 상대 가져오기는 현재 패키지 문맥을 기준으로 점을 사용합니다. **상대 가져오기는 현재 작업 디렉터리를 기준으로 파일 경로를 계산하는 문법이 아닙니다.**[^import]

23.3의 구조에서 다음 파일들을 저장합니다. 이 예제의 `도구상자`는 일반 패키지입니다.

```python
# 파일: 도구상자/__init__.py
from .계산 import 평균

__all__ = ["평균"]
```

```python
# 파일: 도구상자/계산.py
def 평균(값들):
    if not 값들:
        raise ValueError("빈 자료의 평균은 계산하지 않습니다.")
    return sum(값들) / len(값들)
```

```python
# 파일: 도구상자/__main__.py
from .계산 import 평균

print(평균([80, 100]))  # 출력: 90.0
```

`학습폴더`에서 다음과 같이 실행합니다.

```text
python -m 도구상자
```

`python -m 도구상자`는 패키지의 `__main__.py`를 실행합니다. 반면 `python 도구상자/__main__.py`처럼 파일 경로로 직접 실행하면 기대한 패키지 문맥이 없어 상대 가져오기가 실패할 수 있습니다.[^main]

| 표기 | 기준 |
| --- | --- |
| `from 도구상자.계산 import 평균` | 최상위 패키지 이름부터 탐색 |
| `from .계산 import 평균` | 현재 패키지 |
| `from ..계산 import 평균` | 한 단계 위 패키지 |

점의 개수가 올라갈 수 있는 실제 패키지 깊이를 넘으면 오류입니다. 가져오기 문제를 해결하려고 무조건 점을 추가하지 않습니다.[^import]

### 23.5. 모듈 탐색 경로·이름 충돌

모듈을 가져올 때는 먼저 같은 이름으로 이미 적재된 모듈이 있는지 확인합니다. 없으면 등록된 탐색 도구가 모듈을 찾습니다. 기본 경로 기반 탐색은 `sys.path` 등을 이용하지만, 모든 모듈을 단순한 폴더 검색만으로 찾는 것은 아닙니다.[^import]

| 확인할 것 | 의미 |
| --- | --- |
| `sys.executable` | 지금 실행 중인 파이썬 실행기 |
| `sys.path` | 모듈 검색에 사용하는 경로 목록 |
| `모듈.__file__` | 파일 기반 모듈의 원본 위치 확인에 도움 |
| `모듈.__spec__` | 모듈 이름·로더·원본 등 적재 정보 |

파일 경로로 스크립트를 실행할 때는 보통 스크립트 폴더가, `-m`이나 대화형 실행에서는 보통 현재 작업 디렉터리가 초기 검색 경로에 포함됩니다. 환경변수·가상환경·실행 옵션에 따라 달라질 수 있습니다.[^syspath]

```python
import json
import sys

print(json.__name__)                   # 출력: json
print(sys.modules["json"] is json)    # 출력: True
print(json.__spec__.name)              # 출력: json
```

자신의 파일을 `json.py`, `typing.py`, `csv.py`처럼 표준 모듈과 같은 이름으로 지으면 의도하지 않은 파일을 가져올 수 있습니다. 오류가 나면 모듈을 설치하기 전에 **실제로 어느 모듈을 가져왔는지** 확인합니다.[^modules][^syspath]

### 23.6. 모듈 초기화·캐시·최상위 코드 실행

일반적인 가져오기에서는 모듈을 만들고 초기화 코드를 실행한 결과를 `sys.modules`에 보관합니다. 이후 같은 이름의 가져오기는 보통 캐시된 모듈을 재사용합니다.[^import]

23.2의 `상태.py`와 같은 폴더에 다음 파일을 추가합니다. **새 프로세스에서** 실행하는 예제입니다.

```python
# 파일: 반복가져오기.py
import 상태
import 상태 as 다른이름

print(상태 is 다른이름)
# 출력: 상태 초기화
# 출력: True
```

최상위 코드가 다시 실행되지 않으므로 초기화 출력은 한 번입니다. 그러나 “어떤 상황에서도 영원히 한 번만 실행된다”는 뜻은 아닙니다. 별도 프로세스, 캐시 변경, 명시적 재적재, 다른 이름으로의 실행 등은 구별해야 합니다.[^import][^importlib]

함수 정의문·클래스 정의문도 모듈 최상위에 있으면 초기화 과정에서 실행됩니다. 함수의 본문을 호출하지 않아도 기본 인자 평가나 데코레이터 적용 등 정의 단계의 동작은 일어날 수 있습니다.[^modules]

### 23.7. 순환 가져오기·부분 초기화·다시 로드하기

모듈은 초기화가 완전히 끝나기 전에 캐시에 등록됩니다. 그래서 서로를 가져오는 모듈이 이미 존재하는 모듈 객체를 만날 수 있지만, **아직 필요한 이름이 정의되지 않은 상태**일 수도 있습니다.[^import]

```text
첫째 모듈 초기화 시작
→ 둘째 모듈 가져오기
→ 둘째가 첫째의 아직 없는 이름을 요구
→ 부분 초기화 상태 때문에 실패 가능
```

순환 가져오기가 문법적으로 항상 금지되는 것은 아닙니다. 필요한 이름에 접근하는 시점 때문에 실패합니다. 공통 기능을 제삼의 모듈로 옮기거나, 의존 방향을 한쪽으로 정리하는 방식으로 해결할 수 있습니다.[^import]

`importlib.reload`는 이미 가져온 모듈을 다시 실행합니다. 그러나 다른 모듈에서 가져온 이름·이미 생성한 인스턴스·바깥의 참조를 모두 자동으로 새 버전으로 바꾸지는 않습니다.[^importlib]

23.2의 `상태.py`를 유지하고 다음 파일을 새 프로세스에서 실행합니다.

```python
# 파일: 다시적재실험.py
import importlib
import 상태
from 상태 import 기록

기록.append("이전 기록")
importlib.reload(상태)
print(기록)
print(상태.기록)
print(기록 is 상태.기록)
# 출력: 상태 초기화
# 출력: 상태 초기화
# 출력: ['이전 기록']
# 출력: []
# 출력: False
```

또한 재적재는 모듈 사전을 유지하므로 새 소스에서 사라진 옛 이름이 남을 수 있습니다. 개발 중 상태가 복잡하게 얽혔다면 실행기를 새로 시작하는 것이 가장 명확한 비교 기준이 됩니다.[^importlib]

### 23.8. 실행 진입점·공개 이름·동적 가져오기

파일을 프로그램의 시작점으로 실행하면 그 최상위 환경의 이름은 보통 `__main__`입니다. `if __name__ == "__main__":`은 직접 실행할 동작과 가져왔을 때 제공할 정의를 분리합니다.[^main]

```python
# 파일: 진입실험.py
print("모듈 본문")

def 실행():
    print("프로그램 실행")

if __name__ == "__main__":
    실행()
# 직접 파일 실행 시 출력: 모듈 본문
# 직접 파일 실행 시 출력: 프로그램 실행
```

이 파일을 다른 코드에서 가져오면 `모듈 본문`은 출력되지만 보호된 `실행()` 호출은 건너뜁니다. 보호 구문이 모듈 전체의 실행을 차단하는 것은 아닙니다.[^main]

`__all__`은 주로 `from 모듈 import *`에서 가져올 이름을 지정합니다. 접근 권한을 강제하는 보안 장치가 아니며, 목록 밖의 이름을 명시적으로 가져오는 것까지 막지 않습니다.[^modules]

```python
import importlib

모듈 = importlib.import_module("math")
print(모듈.isqrt(81))  # 출력: 9
```

동적 가져오기도 일반적인 가져오기 체계에 참여합니다. 사용자 입력을 검증 없이 모듈 이름으로 사용하면 허용하지 않은 코드까지 실행할 수 있으므로, 확장 기능이 필요하면 허용할 대상을 명시적으로 제한합니다.[^importlib][^security]

## 24부. 가상환경·의존성·배포

### 24.1. 시스템 설치·프로젝트 환경·인터프리터 경로

파이썬 실행기와 패키지 설치 위치는 연결되어 있습니다. 한 컴퓨터에 여러 실행기가 있으면, 한쪽에 설치한 패키지를 다른 실행기에서는 가져오지 못할 수 있습니다.[^venv][^pip]

| 구분 | 확인할 질문 |
| --- | --- |
| 실행기 | 지금 실행하는 파이썬은 어디에 있는가? |
| 설치 도구 | 지금 사용하는 `pip`는 어느 실행기에 연결되는가? |
| 프로젝트 | 이 코드가 기대하는 파이썬·패키지 버전은 무엇인가? |
| 편집기·노트북 | 선택한 실행기·커널이 터미널과 같은가? |

터미널에서 다음 명령으로 현재 실행기와 설치 도구를 함께 확인합니다. 출력되는 경로와 버전은 환경마다 다릅니다.[^pip]

```text
python -c "import sys; print(sys.executable); print(sys.version)"
python -m pip --version
```

“분명 설치했는데 없다”면 재설치부터 반복하지 않습니다. 먼저 오류가 난 프로그램과 설치 명령이 **같은 실행기**를 사용하는지 확인합니다.

### 24.2. 가상환경 생성·활성화·격리 범위

`venv`는 기반 파이썬 설치를 이용해 프로젝트별 환경을 만듭니다. 일반적으로 프로젝트별 패키지를 분리하지만, 운영체제의 파일·네트워크 접근을 막는 보안 격리 장치는 아닙니다.[^venv]

아래는 **윈도우 PowerShell** 예입니다. 먼저 `python --version`이 의도한 파이썬을 가리키는지 확인합니다.

```text
python --version
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip --version
```

활성화는 주로 터미널의 실행 경로를 바꿔 가상환경의 실행기를 먼저 찾도록 합니다. **활성화하지 않아도 실행기 경로를 직접 지정할 수 있습니다.**[^venv]

```text
.\.venv\Scripts\python.exe -m pip --version
.\.venv\Scripts\python.exe -c "import sys; print(sys.prefix != sys.base_prefix)"
```

마지막 명령은 일반적인 가상환경에서 `True`를 출력합니다. 조직 정책으로 활성화 스크립트가 차단되어 있다면 보안 정책을 무조건 해제하기보다 직접 실행기 경로를 사용하는 방법을 고려합니다.[^venv]

리눅스·맥의 일반적인 셸에서는 실행기 경로와 활성화 명령이 다릅니다.

```text
python3 -m venv .venv
source .venv/bin/activate
python -m pip --version
```

가상환경 폴더를 다른 컴퓨터에 그대로 복사하는 것보다, 의존성 정보를 기록하고 대상 환경에서 다시 만드는 편이 적절합니다. 실행기 위치나 스크립트 경로가 환경에 의존하기 때문입니다.[^venv]

### 24.3. 설치 도구와 실행 환경 일치

`python -m pip`는 앞에 지정한 파이썬으로 설치 도구를 실행합니다. 따라서 터미널이 찾은 별도 `pip` 명령과 실행기가 엇갈리는 일을 줄일 수 있습니다.[^pip]

```text
python -m pip list
python -m pip show pip
python -m pip check
```

| 명령 | 확인 목적 |
| --- | --- |
| `list` | 설치된 배포 프로젝트 목록 |
| `show 이름` | 특정 프로젝트의 버전·위치·메타데이터 |
| `check` | 설치된 배포 메타데이터 기준의 의존성 불일치 |
| `install -r requirements.txt` | 요구 사항 파일에 따라 설치 |
| `install .` | 현재 폴더의 프로젝트를 일반 설치 |

`pip check`가 성공해도 프로그램의 논리·보안·모든 실행 경로가 검증된 것은 아닙니다. 또한 `import`에 등장한 이름을 그대로 설치 명령에 넣기 전에, 실제 배포 프로젝트 이름인지 공식 문서를 확인합니다.[^pipcheck][^distribution]

### 24.4. 직접 의존성·전이 의존성·버전 범위

직접 의존성은 프로젝트가 직접 요구하는 패키지입니다. 전이 의존성은 그 패키지가 다시 요구하는 패키지입니다. 설치 도구는 서로의 요구 범위를 만족하는 조합을 찾습니다.[^resolution]

```text
내 프로그램
├─ 첫째 라이브러리 → 공통 라이브러리 1 이상, 2 미만
└─ 둘째 라이브러리 → 공통 라이브러리 2 이상
```

이 조건은 같은 환경에서 동일한 공통 라이브러리 버전 하나로 만족시킬 수 없습니다. 단순히 설치 순서를 바꾸는 문제가 아니라, **버전 조건의 교집합이 없는 문제**입니다.

| 표기 | 범위 해석 |
| --- | --- |
| `==1.4.2` | 해당 버전 지정 |
| `>=1.4,<2` | 1.4 이상, 2 미만 |
| `!=1.4.3` | 특정 버전 제외 |
| `~=1.4` | 1.4 이상이며 2 미만에 해당하는 호환 범위 |
| `~=1.4.2` | 1.4.2 이상이며 1.5 미만에 해당하는 호환 범위 |

세부적인 사전 출시·후속 출시·로컬 버전 처리 등은 버전 지정 명세를 따릅니다. 표의 예제는 일반적인 정식 숫자 버전을 설명합니다.[^versions]

응용 프로그램은 검증한 실행 조합을 재현하는 일이 중요하고, 재사용 라이브러리는 다른 프로젝트와 함께 설치될 수 있는 허용 범위를 설계하는 일이 중요합니다. 모든 프로젝트에 무조건 같은 버전 고정 전략을 적용하지 않습니다.[^repeatable][^pyproject]

### 24.5. 요구 사항 파일·설치 목록·잠금 파일

`requirements.txt`는 설치할 요구 사항을 적는 파일입니다. 정확한 버전 목록일 수도 있고, 범위 조건일 수도 있습니다. `pip freeze`는 현재 설치된 환경을 요구 사항 형태로 출력하지만, **그 자체가 의존성 해결 결과를 보증하는 잠금 기능은 아닙니다.**[^freeze]

윈도우 PowerShell에서는 다음처럼 인코딩을 명시하여 목록을 저장할 수 있습니다.

```text
python -m pip freeze | Set-Content -Encoding utf8 requirements.txt
python -m pip install -r requirements.txt
```

| 자료 | 무엇을 기록하는가? | 한계 |
| --- | --- | --- |
| 프로젝트 의존성 선언 | 필요한 직접 의존성과 허용 범위 | 실제 설치 조합은 달라질 수 있음 |
| 설치 목록 | 현재 환경에 무엇이 설치되었는지 | 개발 중 우연히 설치한 도구도 섞일 수 있음 |
| 잠금 파일 | 해결한 버전·출처·조건 등을 고정 | 지원 형식·플랫폼 범위는 도구별로 확인 |
| 해시·배포 파일 보관 | 설치할 파일의 동일성 확인 | 운영체제·외부 시스템까지 자동 재현하지는 않음 |

현재 표준 잠금 형식으로 `pylock.toml` 명세가 있지만, 생성·소비 도구의 지원 범위는 별도 확인해야 합니다. 특정 잠금 파일을 다른 도구가 무조건 읽을 수 있다고 가정하지 않습니다.[^pylock]

재현성을 높이려면 패키지 버전뿐 아니라 파이썬 버전, 운영체제·아키텍처, 설치 파일, 환경 설정, 외부 서비스까지 구분해서 기록합니다. 설치 조합을 바꾸면 테스트를 다시 수행합니다.[^repeatable]

### 24.6. `pyproject.toml`·메타데이터·빌드 역할

`pyproject.toml`은 프로젝트 메타데이터, 빌드 방식, 도구 설정을 담는 표준 파일입니다. 빌드 실행 도구는 작업을 지휘하고, 빌드 백엔드는 실제 소스 배포나 휠을 만듭니다.[^pyproject]

아래는 **학습용 로컬 프로젝트** 예제입니다. `score-notes-local-demo`는 이 글에서 정한 예시 이름이며, 외부 저장소에서 설치할 프로젝트를 추천하는 것이 아닙니다.

```text
배포학습/
├─ pyproject.toml
├─ README.md
└─ src/
   └─ score_notes/
      ├─ __init__.py
      ├─ __main__.py
      └─ 실행.py
```

`pyproject.toml`에 다음 내용을 저장합니다.

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "score-notes-local-demo"
version = "0.1.0"
description = "파이썬 프로그램 구성 학습 예제"
readme = "README.md"
requires-python = ">=3.13"
dependencies = []

[project.scripts]
score-note = "score_notes.실행:실행"

[tool.setuptools.packages.find]
where = ["src"]
```

`README.md`에는 프로젝트 설명을 적습니다. `src/score_notes/__init__.py`는 이 예제에서는 빈 파일로 만듭니다. 나머지 두 파일은 다음과 같습니다.

```python
# 파일: src/score_notes/실행.py
def 실행():
    print("점수 도구 준비 완료")
    return 0
```

```python
# 파일: src/score_notes/__main__.py
from .실행 import 실행

raise SystemExit(실행())
# 패키지 실행 시 출력: 점수 도구 준비 완료
```

| 설정 | 역할 | 혼동하기 쉬운 대상 |
| --- | --- | --- |
| `[build-system].requires` | 프로젝트를 빌드하는 데 필요한 도구 | 프로그램 실행 시 의존성과 다름 |
| `[project].dependencies` | 설치한 프로그램의 실행 의존성 | 개발 환경에 설치된 전체 목록과 다름 |
| `requires-python` | 사용할 수 있다고 선언한 파이썬 범위 | 그 버전을 자동 설치하는 명령이 아님 |
| `[project.scripts]` | 설치 시 만들 명령과 호출 대상 | 소스 파일 경로를 직접 적는 것이 아님 |
| `[tool...]` | 특정 도구에 전달하는 설정 | 모든 도구가 공통 해석하는 설정은 아님 |

여기서 `setuptools>=68`은 예제 구성에 필요한 빌드 도구의 범위이지 최신 버전 주장이나 고정된 재현 환경이 아닙니다. 일반적인 격리 빌드는 빌드 의존성을 별도 환경에 준비할 수 있으므로 다운로드가 발생할 수 있습니다.[^pyproject][^buildinterface]

### 24.7. 소스 배포·휠·바이너리 호환성

소스 배포는 빌드에 필요한 소스를 중심으로 묶습니다. 휠은 설치 가능한 형태로 준비된 배포 파일입니다. 휠이라고 해서 모두 기계어만 들어 있는 것은 아닙니다. 순수 파이썬 코드도 휠로 배포할 수 있습니다.[^formats]

| 구분 | 소스 배포 | 휠 |
| --- | --- | --- |
| 대표 확장자 | `.tar.gz` | `.whl` |
| 중심 내용 | 빌드 가능한 소스·메타데이터 | 설치 가능한 파일·메타데이터 |
| 설치 전 빌드 | 보통 빌드 절차가 필요 | 이미 준비된 파일을 설치 |
| 환경 의존성 | 빌드 도구·외부 라이브러리 등에 영향 | 휠의 호환 태그와 내용에 영향 |

확장 모듈을 포함한 휠은 파이썬 구현체·버전·바이너리 인터페이스·운영체제·아키텍처 등의 조건이 맞아야 합니다. 파일명에 붙은 호환 태그는 이런 대상을 표현합니다.[^wheeltags]

순수 파이썬 휠에 넓은 호환 태그가 붙었더라도 `requires-python`이나 실제 사용 문법까지 확인해야 합니다. 휠의 형태만 보고 모든 파이썬 버전에서 실행된다고 판단하지 않습니다.[^formats][^pyproject]

### 24.8. 소스 배치·개발용 설치·진입점·공개

`src` 배치는 프로젝트 루트와 가져올 패키지의 위치를 분리합니다. 현재 폴더의 미설치 소스가 우연히 가져와져 설치 누락을 숨기는 문제를 줄이는 데 도움이 됩니다.[^layout]

24.6의 파일을 모두 구성한 뒤 **`배포학습` 폴더에서, 학습용 가상환경의 실행기**로 진행합니다.

```text
python -m pip install -e .
python -m score_notes
score-note
```

개발용 설치는 소스를 수정하면서 작업하는 데 사용합니다. 파이썬 소스 수정은 보통 바로 반영되지만, 프로젝트 메타데이터·진입점·컴파일된 확장 변경 등은 재설치나 재빌드가 필요할 수 있습니다.[^editable]

`score-note`는 설치 도구가 만든 명령입니다. 현재 터미널에서 그 명령을 찾으려면 가상환경 실행 경로가 반영되어 있어야 합니다. 활성화하지 않은 경우에는 가상환경의 명령 파일을 직접 실행합니다.[^entrypoints][^venv]

배포 파일을 만드는 기본 흐름은 다음과 같습니다. 설치·빌드 명령은 네트워크 접근이나 로컬 빌드 도구 준비가 필요할 수 있습니다.

```text
python -m pip install build
python -m build
```

빌드 결과는 보통 `dist` 폴더에 만들어집니다. 공개하기 전에는 **깨끗한 환경에 실제 배포 파일을 설치해 검사**하고, 설명·라이선스·의존성·포함 파일·비밀정보를 확인합니다. 개발용 설치에서 된다는 사실만으로 배포물도 정상이라고 단정하지 않습니다.[^packaging][^editable]

이 글에서는 로컬 프로젝트 구성과 배포 흐름을 설명하며, 외부 저장소에 올리는 업로드 명령은 실행하지 않습니다. 실제 공개는 별도의 이름·권한·배포 정책 확인이 필요한 작업입니다.

## 25부. 타입 힌트와 점진적 타입 검사

### 25.1. 동적 타입·정적 검사·실행 중 검증

타입 힌트는 이름과 함수가 기대하는 타입을 표현합니다. 파이썬 실행기는 일반적인 타입 주석만으로 인자·반환값을 자동 검사하지 않습니다. 정적 타입 검사 도구는 실행 전 코드의 타입 관계를 분석합니다.[^typing]

```python
def 두배(값: int) -> int:
    return 값 * 2

print(두배(3))      # 출력: 6
print(두배("가"))  # 출력: 가가
```

두 번째 호출은 선언한 계약과 맞지 않아 정적 검사에서 지적할 대상입니다. 그러나 실제 연산인 문자열 반복은 가능하므로 실행 결과는 `가가`입니다. 주석이 문자열을 정수로 변환해 주지도 않습니다.

| 구분 | 언제·무엇을 확인하는가? | 한계 |
| --- | --- | --- |
| 타입 힌트 | 기대하는 입력·출력 관계를 표현 | 혼자서는 검사하지 않음 |
| 정적 검사 | 실행 전 코드의 타입 관계 분석 | 모든 실제 값·외부 상태를 알지 못함 |
| 실행 중 검증 | 실제 입력의 타입·범위·구조 확인 | 검증 코드를 실행해야 함 |
| 테스트 | 선택한 입력의 실제 결과 확인 | 검사하지 않은 모든 경우를 보장하지 않음 |

**점진적 타입 검사**는 기존 코드에 타입 정보를 단계적으로 추가하는 접근입니다. 주석 없는 부분·`Any`·외부 라이브러리의 타입 정보·검사 설정에 따라 검사 강도가 달라집니다.[^specialtypes]

이 글에서 “정적 오류”는 타입 체계상 계약 위반을 뜻합니다. 아래 실행 예제의 성공 여부와 특정 타입 검사기의 실제 진단 결과는 별도로 구별합니다.

### 25.2. 변수·함수·컨테이너·호출 가능 객체의 표기

변수에는 콜론, 함수 반환에는 화살표를 사용합니다. 파이썬 3.13에서는 `list[int]`, `dict[str, int]`처럼 내장 컨테이너를 직접 매개변수화할 수 있습니다.[^annotations]

```python
from collections.abc import Iterable

기록: list[int] = [80, 90]
이름별점수: dict[str, int] = {"가람": 80}

def 합계(점수들: Iterable[int]) -> int:
    return sum(점수들)

print(합계(기록))          # 출력: 170
print(합계((10, 20, 30)))  # 출력: 60
```

이 함수는 순회만 필요하므로 입력을 꼭 리스트로 한정하지 않았습니다. 실제로 요구하는 동작이 무엇인지에 맞춰 `Iterable`, `Sequence`, `Mapping` 등을 선택합니다.[^annotations]

| 표기 | 의미 |
| --- | --- |
| `list[int]` | 정수 원소를 가진 리스트 |
| `dict[str, int]` | 문자열 키·정수 값의 사전 |
| `tuple[int, str]` | 첫 값은 정수, 둘째는 문자열인 고정 길이 튜플 |
| `tuple[int, ...]` | 정수가 반복되는 가변 길이 튜플 |
| `Callable[[int, int], int]` | 정수 둘을 받아 정수를 반환하는 호출 대상 |
| `Iterator[str]` | 문자열을 차례로 내는 반복자 |
| `Generator[int, None, None]` | 정수를 내고, 별도 전송값·반환값을 쓰지 않는 제너레이터 |
| `-> None` | 유의미한 결과를 반환하지 않는 함수의 계약 |

`Callable`·`Iterator`·`Generator`는 `collections.abc`에서 가져와 사용할 수 있습니다. 제너레이터의 세 타입 인자는 내주는 값·받는 값·최종 반환값 순서입니다.[^callables][^generics]

`isinstance(자료, list[int])`는 모든 원소가 정수인지 검사하는 방법이 아닙니다. 매개변수가 붙은 일반 제네릭을 그 방식으로 검사할 수 없으며, 컨테이너 종류와 원소 조건은 따로 검사해야 합니다.[^typing]

### 25.3. 합집합·값의 부재·`Any`·`object`·반환하지 않는 타입

`int | str`은 정수 또는 문자열이라는 뜻입니다. `int | None`은 정수 또는 값의 부재를 허용합니다. **`None`을 허용하는 것과 인자를 생략할 수 있는 것은 별개입니다.**[^annotations]

```python
def 필수인자(값: int | None) -> int:
    return 0 if 값 is None else 값

def 생략가능(값: int | None = None) -> int:
    return 0 if 값 is None else 값

print(필수인자(None))  # 출력: 0
print(생략가능())     # 출력: 0
try:
    필수인자()
except TypeError:
    print("인자는 생략할 수 없음")  # 출력: 인자는 생략할 수 없음
```

| 타입 | 뜻 | 기억할 점 |
| --- | --- | --- |
| `Any` | 동적 타입 영역으로 취급 | 검사기가 다양한 연산·대입을 허용하게 됨 |
| `object` | 어떤 객체든 받을 수 있는 상위 타입 | 특정 동작 전에는 타입을 좁혀야 함 |
| `None` | 반환값이나 입력값으로서의 값의 부재 | 함수가 정상적으로 끝날 수 있음 |
| `Never`·`NoReturn` | 정상적으로 반환하지 않는 경로 표현 | `None`을 반환한다는 뜻이 아님 |

`Any`와 `object`는 모두 넓어 보이지만 역할이 다릅니다. `object`에는 모든 객체가 가진다고 보장되지 않는 메서드를 바로 호출하지 않습니다. `Any`는 그 검사를 느슨하게 하므로 타입 오류가 숨어 전달될 수 있습니다.[^specialtypes]

```python
from typing import NoReturn

def 중단(설명: str) -> NoReturn:
    raise ValueError(설명)

try:
    중단("처리를 중단합니다.")
except ValueError as 오류:
    print(str(오류))  # 출력: 처리를 중단합니다.
```

항상 예외를 발생시키는 함수는 정상 반환값이 없다는 계약을 표현할 수 있습니다. 단순히 `return` 문을 쓰지 않아 자동으로 `None`을 반환하는 함수와 다릅니다.[^specialtypes]

### 25.4. 타입 별칭·타입 매개변수·제네릭

타입 별칭은 복잡한 타입에 이름을 붙입니다. 파이썬 3.12부터는 `type` 문으로 명시적인 별칭을 정의하고, 함수·클래스 이름 뒤 대괄호에서 타입 매개변수를 선언할 수 있습니다.[^typeparams]

```python
from collections.abc import Sequence

type 점수목록 = list[int]

def 첫값[항목](값들: Sequence[항목]) -> 항목:
    if not 값들:
        raise ValueError("빈 자료입니다.")
    return 값들[0]

점수: 점수목록 = [80, 90]
print(첫값(점수))             # 출력: 80
print(첫값(("가람", "나래")))  # 출력: 가람
```

제네릭은 “아무 타입이나 받아도 된다”에서 끝나지 않습니다. 위 함수는 **입력 원소의 타입과 반환 타입이 같은 관계**를 표현합니다. 입력과 반환을 각각 `Any`로 적으면 이 관계가 약해집니다.[^generics]

```python
class 상자[항목]:
    def __init__(self, 값: 항목):
        self.값 = 값

    def 꺼내기(self) -> 항목:
        return self.값

정수상자 = 상자[int](7)
print(정수상자.꺼내기())  # 출력: 7
```

기존 코드에서는 `TypeVar`와 `Generic`을 사용하는 표기도 자주 만납니다. 새로운 표기와 기존 표기의 지원 버전·스코프를 구별합니다. 3.13은 타입 매개변수의 기본값도 지원하지만, 그것이 실제 함수 인자의 기본값을 지정하는 것은 아닙니다.[^typeparams][^typing]

타입 별칭은 새로운 런타임 클래스를 만드는 것과도 다릅니다. 정적 검사에서 회원 번호와 주문 번호를 구별하는 별도 타입이 필요하면 `NewType` 같은 도구를 검토할 수 있습니다. 이 경우에도 자동 값 검증을 제공하는 것은 아닙니다.[^typing]

### 25.5. 타입 변수의 상한·제약·변성

**상한**은 어떤 타입을 기반으로 허용할지를, **제약**은 미리 정한 타입 선택지 중 무엇으로 관계를 맞출지를 나타냅니다. 정적 추론에서 하위 타입을 유지하는 방식도 다릅니다.[^generics]

```python
class 이름문자열(str):
    pass

def 그대로[문자형: str](값: 문자형) -> 문자형:
    return 값

def 이어붙이기[문자형: (str, bytes)](첫째: 문자형, 둘째: 문자형) -> 문자형:
    return 첫째 + 둘째

print(type(그대로(이름문자열("가람"))).__name__)  # 출력: 이름문자열
print(이어붙이기("가", "나"))                   # 출력: 가나
```

상한이 있는 타입 변수는 입력의 더 구체적인 하위 타입 관계를 보존할 수 있습니다. 제약된 타입 변수는 지정한 선택지 중 하나로 맞춥니다. 같은 호출에서 문자열과 바이트를 섞는 것이 허용된다는 뜻은 아닙니다.[^generics]

**변성**은 원소 타입의 상하 관계가 컨테이너·함수 전체의 관계로 어떻게 이어지는지 설명합니다. 아래 표는 정적 타입 관계를 설명하며, 런타임 객체를 변환한다는 뜻이 아닙니다.[^generics][^callables]

| 구분 | 직관 | 대표적인 경우 |
| --- | --- | --- |
| 공변 | 더 구체적인 값을 내주는 대상을 넓은 타입 자리에서 사용 | 읽기 전용 `Sequence`의 원소 타입 |
| 반공변 | 더 넓은 입력을 처리하는 함수를 좁은 입력 자리에서 사용 | 호출 가능 객체의 매개변수 타입 |
| 불변 | 원소 타입의 상하 관계를 그대로 대입 관계로 확대하지 않음 | 읽기·쓰기가 모두 가능한 `list` |

예를 들어 `list[str]`를 `list[object]`가 필요한 곳에 자유롭게 넘겨도 된다면, 그 함수가 리스트에 정수를 추가할 수 있습니다. 그러면 원래의 “문자열만 있는 리스트” 계약이 깨집니다. 이 쓰기 가능성 때문에 `list`는 불변으로 다룹니다.

여기서 **타입의 불변성**은 “객체를 수정할 수 없다”는 의미의 불변 객체와 다른 용어입니다. 이름이 같다고 같은 개념으로 암기하지 않습니다.

### 25.6. 구조적 규약·사전 구조·값 제한·메타데이터

#### 구조적 규약: `Protocol`

`Protocol`은 요구하는 메서드·속성을 만족하는지를 표현합니다. 반드시 그 규약 클래스를 직접 상속하지 않아도 정적 계약을 만족할 수 있습니다.[^protocol]

```python
from typing import Protocol

class 읽기규약(Protocol):
    def 읽기(self) -> str:
        ...

class 메모:
    def 읽기(self) -> str:
        return "메모 내용"

def 내용보기(대상: 읽기규약) -> str:
    return 대상.읽기()

print(내용보기(메모()))  # 출력: 메모 내용
```

실행 중 `isinstance` 검사를 허용하려면 `runtime_checkable`을 사용할 수 있지만, 이 검사는 일반적으로 필요한 속성의 존재를 확인하는 수준입니다. 매개변수 타입·반환 타입·업무 의미까지 검증하는 것은 아닙니다.[^protocol]

#### 사전의 키·값 구조: `TypedDict`

`TypedDict`는 특정 문자열 키를 가진 사전의 구조를 표현합니다. 실행 중 결과는 일반 사전이며, 키와 값의 계약을 자동 검사하지 않습니다.[^typeddict]

```python
from typing import TypedDict, NotRequired

class 회원자료(TypedDict):
    이름: str
    나이: int | None
    별명: NotRequired[str]

자료: 회원자료 = {"이름": "가람", "나이": None}
print(type(자료).__name__)  # 출력: dict
print("나이" in 자료)      # 출력: True
print("별명" in 자료)      # 출력: False
```

`나이`는 키 자체가 필수이지만 값으로 `None`을 허용합니다. `별명`은 키가 없어도 됩니다. `Required`, `NotRequired`, `total=False`는 키의 존재 조건을 표현하며, 값의 선택적 타입과는 별개입니다.[^typeddict]

#### 나머지 주요 표현

| 도구 | 표현하는 계약 | 자동으로 하지 않는 일 |
| --- | --- | --- |
| `Literal["대기", "완료"]` | 허용할 특정 값의 타입 | 외부 입력을 직접 차단 |
| `Annotated[int, "0부터 100"]` | 타입에 부가 메타데이터 연결 | 점수 범위 자동 검사 |
| `ClassVar[int]` | 클래스 수준의 변수라는 정적 의도 | 인스턴스 대입의 물리적 금지 |
| `Final[int]` | 재대입하지 않겠다는 정적 계약 | 가리키는 객체의 깊은 동결 |
| `ReadOnly[str]` | 사전 항목의 읽기 전용 정적 계약 | 실제 사전의 변경 차단 |

`ReadOnly`는 3.13의 `TypedDict` 항목에 사용할 수 있습니다. 메타데이터를 해석하는 별도 라이브러리가 있다면 추가 동작이 가능하지만, 그것은 기본 타입 주석 자체의 강제가 아닙니다.[^typeddict][^typing]

### 25.7. 타입 좁히기·검증 함수·자기 타입·오버로드·형 변환 주장

타입 좁히기는 조건에 따라 가능한 타입을 더 구체적으로 판단하는 일입니다. `isinstance`, `is None`, 명시적 분기 등을 통해 검사기가 이후 코드의 타입을 좁힐 수 있습니다.[^narrowing]

```python
def 표시(값: int | str | None) -> str:
    if 값 is None:
        return "값 없음"
    if isinstance(값, int):
        return str(값 + 1)
    return 값.strip()

print(표시(None))     # 출력: 값 없음
print(표시(9))        # 출력: 10
print(표시(" 가람 "))  # 출력: 가람
```

사용자 정의 검사 함수의 의미를 전달할 때는 `TypeGuard`나 `TypeIs`를 사용할 수 있습니다.[^typeis][^narrowing]

| 구분 | `TypeGuard` | `TypeIs` |
| --- | --- | --- |
| 참 분기 | 지정한 타입으로 좁힘 | 기존 타입과 지정 타입의 공통 범위로 좁힘 |
| 거짓 분기 | 그 반환 정보만으로 반대 타입을 제거하지 않음 | 지정 타입을 제외하는 방향으로 좁힘 |
| 입력 타입과의 관계 | 일부 호환되지 않는 좁히기도 허용 | 좁힐 타입이 입력 타입과 호환되어야 함 |
| 책임 | 검사 함수가 참을 반환하는 조건을 올바르게 작성 | 해당 타입인지 양쪽 방향의 의미를 올바르게 작성 |

```python
from typing import TypeIs

def 문자열인가(값: object) -> TypeIs[str]:
    return isinstance(값, str)

def 길이또는증가(값: str | int) -> int:
    if 문자열인가(값):
        return len(값)
    return 값 + 1

print(길이또는증가("가람"))  # 출력: 2
print(길이또는증가(9))       # 출력: 10
```

`TypeIs[str]`라고 적고 “길이가 3 이상인 문자열만 참”으로 검사하면 올바른 문자열도 거짓 분기로 보내므로 계약을 어깁니다. 타입 검사기는 검사 함수의 실제 논리가 항상 올바르다고 증명해 주지 않습니다.[^typeis]

`Self`는 메서드가 호출된 구체적인 자기 타입을 표현합니다. 메서드 체이닝이나 하위 클래스도 유지하는 생성 메서드를 설명할 때 유용합니다.[^self]

```python
from typing import Self

class 기록기:
    def __init__(self):
        self.내용 = []

    def 추가(self, 문장: str) -> Self:
        self.내용.append(문장)
        return self

class 상세기록기(기록기):
    pass

대상 = 상세기록기().추가("시작").추가("완료")
print(type(대상).__name__)  # 출력: 상세기록기
print(대상.내용)           # 출력: ['시작', '완료']
```

`overload`는 정적 검사에 여러 호출 계약을 제시합니다. 실행 시 사용할 구현은 뒤에 따로 작성하며, 주석이 자동으로 서로 다른 함수 본문을 골라 실행하는 것은 아닙니다.[^overload]

```python
from typing import overload

@overload
def 두배(값: int) -> int:
    ...

@overload
def 두배(값: str) -> str:
    ...

def 두배(값: int | str) -> int | str:
    return 값 * 2

print(두배(4))      # 출력: 8
print(두배("가"))  # 출력: 가가
```

`cast`는 타입 검사기에 특정 타입으로 취급하라고 알리는 도구입니다. 실제 값을 변환하거나 검증하지 않습니다.[^typing]

```python
from typing import cast

값 = cast(int, "10")
print(값)                   # 출력: 10
print(type(값).__name__)     # 출력: str
print(type(int(값)).__name__) # 출력: int
```

외부 입력을 `cast`로 감싸는 것만으로 안전해지지 않습니다. 잘못된 타입 주장을 넣으면 정적 검사기가 오히려 잘못된 전제를 믿고 지나갈 수 있습니다.[^typing]

### 25.8. 매개변수 묶음·가변 타입·전방 참조·주석 평가

#### 함수 서명을 보존하는 `ParamSpec`

데코레이터는 인자를 받아 다른 함수로 전달합니다. 모든 인자를 `Any`로 적기보다 `ParamSpec`을 사용하면 위치·키워드 인자의 타입 관계를 보존할 수 있습니다.[^paramspec]

```python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar

매개 = ParamSpec("매개")
반환 = TypeVar("반환")

def 기록하기(함수: Callable[매개, 반환]) -> Callable[매개, 반환]:
    @wraps(함수)
    def 감싸기(*인자: 매개.args, **키워드: 매개.kwargs) -> 반환:
        print("호출", 함수.__name__)
        return 함수(*인자, **키워드)
    return 감싸기

@기록하기
def 더하기(첫째: int, 둘째: int = 1) -> int:
    return 첫째 + 둘째

print(더하기(3, 둘째=4))
# 출력: 호출 더하기
# 출력: 7
```

함수 앞에 추가 매개변수를 붙이는 관계는 `Concatenate`와 함께 표현할 수 있습니다. 단순한 `Callable[..., 반환]`은 같은 수준으로 구체적인 인자 서명을 보존하지 않습니다.[^paramspec]

#### 타입의 가변 묶음: `TypeVarTuple`

`TypeVarTuple`은 원소 타입 여러 개의 묶음을 표현합니다. 함수 인자의 구조를 나타내는 `ParamSpec`과 달리, 튜플이나 가변 제네릭의 타입 목록을 다룹니다.[^typevartuple]

```python
from typing import TypeVarTuple

종류들 = TypeVarTuple("종류들")

def 보존(값: tuple[*종류들]) -> tuple[*종류들]:
    return 값

print(보존((1, "가람", True)))  # 출력: (1, '가람', True)
```

이 함수는 세 값의 타입을 모두 하나로 합치는 것이 아니라, 정수·문자열·불리언이라는 위치별 관계를 표현할 수 있습니다. 타입을 풀어 쓰는 표기의 별표는 실제 호출에서 값을 풀어 쓰는 동작과 구별합니다.[^typevartuple]

`Unpack`은 타입 묶음을 풀어 표현하는 도구이며, `TypedDict`와 함께 키워드 인자의 구조를 명시하는 데도 사용합니다.[^typing]

#### 전방 참조와 3.13의 평가 규칙

아직 정의되지 않은 클래스를 타입 주석에서 참조해야 할 수 있습니다. 파이썬 3.13에서는 일반적인 함수 주석이 정의 시점에 평가되므로, 문자열 주석이나 `from __future__ import annotations`를 이용해 즉시 이름을 찾지 않게 할 수 있습니다.[^annotationhowto]

```python
from __future__ import annotations
from typing import get_type_hints

class 노드:
    def 다음설정(self, 다음: 노드 | None) -> None:
        self.다음 = 다음

주석 = 노드.다음설정.__annotations__
print(type(주석["다음"]).__name__)  # 출력: str

해석 = get_type_hints(노드.다음설정)
print(해석["다음"] == (노드 | None))  # 출력: True
```

`from __future__ import annotations`는 파일 앞쪽에 둡니다. `get_type_hints`는 주석을 해석하여 타입 정보를 얻는 도구이며, 함수의 실제 인자를 검사하거나 객체를 검증하는 도구가 아닙니다.[^annotationhowto][^typing]

| 상황 | 확인할 것 |
| --- | --- |
| 아직 없는 타입 이름 | 문자열 참조·주석 저장 방식 |
| 실행 중 타입 힌트 조회 | 해석 시점에 필요한 이름이 존재하는지 |
| `TYPE_CHECKING` 안에서만 가져온 이름 | 실행 때는 그 가져오기가 수행되지 않는다는 점 |
| 외부에서 받은 주석 평가 | 해석 과정에 코드 실행 위험이 있는지 |
| 다른 파이썬 버전 | 해당 버전의 주석 평가 규칙 |

`TYPE_CHECKING`은 정적 검사기가 참으로 취급하지만 실제 실행에서는 거짓입니다. 그 안에서만 가져온 이름을 실행 중에 무조건 조회할 수 있다고 생각하지 않습니다.[^typing]

또한 `type` 문으로 만든 별칭의 값, 타입 매개변수의 상한 등에는 별도의 지연 평가 규칙이 있습니다. 이 때문에 “파이썬 3.13의 모든 타입 관련 표현은 즉시 평가된다”라고 확장하면 틀립니다.[^typeparams]

## 잘 놓치는 핵심

### 1. 예외를 잡아도 실패한 위치로 되돌아가지 않습니다

예외는 해당 작업의 남은 실행을 중단하고 처리 경로로 이동시킵니다. 재시도가 필요하면 반복·재시도 횟수·중복 처리 방지 정책을 별도로 설계해야 합니다.[^errors]

### 2. `else`는 `try`가 끝까지 정상 완료되어야 실행합니다

`return`·`break`·`continue`로 `try`를 떠났다면, 예외가 없었더라도 `else`는 실행하지 않습니다. `finally`는 원래 제어 이동을 이어가기 전에 실행됩니다.[^compound]

### 3. `with`는 항상 파일을 닫는 문법이 아닙니다

`with`는 관리자별 진입·종료 규약을 실행합니다. 파일이면 닫을 수 있고, 잠금이면 해제할 수 있습니다. 실제 자원 소유권과 종료 동작을 해당 도구의 계약에서 확인합니다.[^withpep]

### 4. 진입 실패와 본문 실패는 다릅니다

진입에 성공한 뒤의 실패는 종료 규약으로 전달됩니다. 진입 자체가 실패한 관리자의 종료 메서드는 자동 호출되지 않으므로, 부분적으로 획득한 자원을 진입 과정에서 정리해야 합니다.[^compound]

### 5. 파일 모드는 읽기·쓰기 권한뿐 아니라 기존 내용 처리도 정합니다

`w+`는 읽기도 가능하지만 기존 내용을 보존한다는 뜻이 아닙니다. `a+`는 읽기도 가능하지만 쓰기는 끝에 추가하는 동작입니다.[^builtins]

### 6. 직렬화 후 같아 보이는 값도 타입·공유 관계는 달라질 수 있습니다

JSON의 튜플 복원·정수 키 변환과 `pickle`의 공유 참조 보존은 서로 다른 계약입니다. 범용적인 복사 대용으로 형식을 무작정 바꾸지 않습니다.[^json][^pickle]

### 7. `from`으로 가져온 이름은 자동으로 갱신되는 연결이 아닙니다

모듈이 그 이름에 새 객체를 대입해도, 이미 가져온 다른 이름이 함께 바뀌지는 않습니다. 공유한 객체 자체의 변경만 양쪽에서 관찰할 수 있습니다.[^simple]

### 8. 가져오기 캐시와 배포 환경은 별개입니다

한 실행기 안의 모듈 캐시가 다른 프로세스·다른 가상환경에도 그대로 공유되는 것은 아닙니다. 이미 가져온 코드를 다시 실행하는 일과 패키지를 다시 설치하는 일도 구별합니다.[^import][^venv]

### 9. 설치 목록만으로 모든 재현 조건이 고정되지는 않습니다

버전 외에 설치 파일·파이썬·운영체제·외부 환경이 달라질 수 있습니다. `pip freeze` 출력과 잠금 파일·배포 파일 검증을 같은 것으로 보지 않습니다.[^freeze][^repeatable]

### 10. 타입이 맞아도 업무 조건은 틀릴 수 있습니다

`int`로 적힌 점수에 10000이 들어오는 것은 타입만으로 걸러지지 않습니다. 불리언을 정수 점수로 받을지, 빈 이름을 허용할지, 중복을 허용할지는 별도의 값 검증 문제입니다.

### 11. 타입 검사 도구가 신뢰하는 전제를 잘못 적을 수도 있습니다

잘못된 `cast`나 거짓된 `TypeIs` 구현은 검사기를 속이는 전제가 됩니다. 타입 힌트는 의도만 적으면 끝나는 것이 아니라 실제 구현과 일치해야 합니다.[^typing][^typeis]

### 12. 입력 소유권과 정리 책임을 함께 정합니다

함수 안에서 연 자원인지, 호출자로부터 빌린 자원인지에 따라 누가 닫는지 명확히 합니다. 자원 관리 문법이 있다는 사실만으로 소유권 설계가 자동 해결되지는 않습니다.

## 예시로 한 바퀴: 점수 파일을 검증하고 요약 저장하기

다음은 이 글을 위해 구성한 종합 예제입니다. 임시 폴더 안에 학습 자료를 만들고, 읽기 → 문법 해석 → 구조 검증 → 값 검증 → 계산 → 저장 순서로 처리합니다.

**타입 힌트와 실제 검증을 함께 사용**하며, 자료 형식 오류와 파일 접근 오류를 무조건 같은 오류로 감추지 않습니다. `OSError` 계열의 입출력 실패는 호출자가 별도로 대응할 수 있게 전파합니다.

```python
import json
from collections.abc import Sequence
from dataclasses import dataclass
from pathlib import Path
from tempfile import TemporaryDirectory
from typing import TypedDict

class 자료오류(ValueError):
    pass

@dataclass(frozen=True)
class 성적:
    이름: str
    점수: int

class 요약자료(TypedDict):
    인원: int
    합계: int
    평균: float

def 성적변환(값: object, 순번: int) -> 성적:
    if not isinstance(값, dict):
        raise 자료오류(f"{순번}번째 자료는 사전이어야 합니다.")
    이름 = 값.get("이름")
    점수 = 값.get("점수")
    if not isinstance(이름, str) or not 이름.strip():
        raise 자료오류(f"{순번}번째 이름이 비어 있거나 문자열이 아닙니다.")
    if type(점수) is not int:
        raise 자료오류(f"{순번}번째 점수는 불리언이 아닌 정수여야 합니다.")
    if not 0 <= 점수 <= 100:
        raise 자료오류(f"{순번}번째 점수가 범위를 벗어났습니다.")
    return 성적(이름.strip(), 점수)

def 읽기(경로: Path) -> list[성적]:
    try:
        with 경로.open(encoding="utf-8") as 파일:
            원본: object = json.load(파일)
    except (json.JSONDecodeError, UnicodeError) as 원인:
        raise 자료오류("파일의 문자 인코딩 또는 자료 문법이 올바르지 않습니다.") from 원인
    if not isinstance(원본, list):
        raise 자료오류("최상위 자료는 목록이어야 합니다.")
    return [성적변환(값, 순번) for 순번, 값 in enumerate(원본, start=1)]

def 요약(자료: Sequence[성적]) -> 요약자료:
    if not 자료:
        raise 자료오류("빈 성적 자료는 요약하지 않습니다.")
    합계 = sum(행.점수 for 행 in 자료)
    return {"인원": len(자료), "합계": 합계, "평균": 합계 / len(자료)}

def 실행(입력경로: Path, 출력경로: Path) -> 요약자료:
    결과 = 요약(읽기(입력경로))
    with 출력경로.open("w", encoding="utf-8") as 파일:
        json.dump(결과, 파일, ensure_ascii=False, indent=2)
    return 결과

with TemporaryDirectory() as 임시폴더:
    폴더 = Path(임시폴더)
    입력경로 = 폴더 / "입력.json"
    출력경로 = 폴더 / "요약.json"
    예시자료 = [{"이름": " 가람 ", "점수": 80}, {"이름": "나래", "점수": 100}]
    입력경로.write_text(json.dumps(예시자료, ensure_ascii=False), encoding="utf-8")

    결과 = 실행(입력경로, 출력경로)
    print(결과)  # 출력: {'인원': 2, '합계': 180, '평균': 90.0}
    저장내용 = json.loads(출력경로.read_text(encoding="utf-8"))
    print(저장내용 == 결과)  # 출력: True

    잘못된자료 = [{"이름": "가람", "점수": True}]
    입력경로.write_text(json.dumps(잘못된자료, ensure_ascii=False), encoding="utf-8")
    try:
        실행(입력경로, 출력경로)
    except 자료오류 as 오류:
        print(str(오류))
        # 출력: 1번째 점수는 불리언이 아닌 정수여야 합니다.
```

또한 저장은 학습을 위한 직접 쓰기 방식입니다. 실제 운영에서 기존 결과의 손상 방지가 중요하면 임시 파일에 완성한 뒤 교체하는 전략, 동시 접근, 저장 실패를 별도로 설계합니다. `with`는 파일을 닫는 책임을 도울 뿐 **원자적 저장이나 트랜잭션을 자동 제공하지 않습니다**.[^io][^os]
